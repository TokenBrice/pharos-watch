# Live Reserve Sync

Dedicated documentation for the live reserve-composition subsystem that powers `GET /api/stablecoin-reserves/:id`, the stablecoin-detail reserve card, and `/status` reserve-sync health.

## Overview

- **Cron:** `sync-live-reserves` (`worker/src/cron/sync-live-reserves.ts`)
- **Schedule:** `11 */4 * * *` (every 4 hours at :11 UTC)
- **Shared 4-hourly lane:** after live reserve sync, the same slot runs redemption backstop sync, Kinesis supply sync, and the named `reserve-post-sync-watchdog` child for collateral-drift cache updates and stale-source alerts (`worker/src/handlers/scheduled/hourly-live-reserves.ts`)
- **Current coverage:** derived from `liveReservesConfig` in stablecoin metadata and the adapter declarations. Use those sources and the generated coverage reports for the current enabled, configured, bound, and unbound sets.
- **Storage:** `reserve_composition`, `reserve_composition_history`, `reserve_sync_state`, `reserve_sync_attempt_history`
- **API:** `GET /api/stablecoin-reserves/:id`
- **Frontend consumers:** `useStablecoinReserves()`, stablecoin detail view model, `/status` reserve-sync health
- **Operational telemetry:** `sync-live-reserves` emits per-coin progress into `cron_run_progress`, including the current coin, adapter, breaker key, and running synced / failed / skipped counters

This pipeline is intentionally separate from curated reserve metadata in `StablecoinMeta.reserves`. Historically, Safety v5.8 through v8.17 used score-grade snapshots for `collateralFromLive`, collateral-quality, and Dependency Risk inputs. Current V9 instead compiles accepted fresh, clean, independent live slices into Backing reserve exposures and reconciles tracked `coinId` slices into effective dependency edges; unmapped share remains self-backed/non-stablecoin exposure. A configured adapter is not enough by itself. When no accepted live rows are captured, V9 falls back to reviewed static/curated reserve rows rather than treating a degraded live attempt as score evidence. Adapter validation and stored-row decoding reject unknown or self-referential `coinId` links and `depType` without `coinId`; subject-aware adapters keep self-held reserve slices visible without turning them into dependency edges. Cyclic or invalid live dependency evidence falls back or fails closed according to the V9 fact-set contract while the reserve snapshot remains available for reserve/status surfaces.

Score-grade adapters may emit a namespace-qualified stable `sourceKey` for each source-owned reserve category. V9 joins a keyed live slice to reviewed metadata only when that key is unique on both sides; an explicit mismatch or collision fails closed. Within the 365-day classification window, `classification-only` reviews may supply keyed asset class, obligor, and risk metadata without certifying whole-book composition, liability attribution, or dependency weights; reviewed non-link dispositions remain binding and measured unknown exposure is unchanged. Historical rows without keys retain a unique normalized-name compatibility join only under `full-composition` reviews. Every adapter output must pass the complete `ReserveSliceSchema` before replacing a persisted snapshot, including the source-key namespace syntax and 160-character limit; invalid output records a failed attempt and preserves the last good snapshot. Daily percentages are never part of slice identity: the live percentage remains the scoring and dependency weight, while the reviewed percentage is evidence about the reviewed composition rather than a join threshold.

Stable keys use source asset codes, token/feed addresses, or fixed source bucket identifiers, never display labels. The live producer and reviewed sidecar must be updated together. Aggregate NAV buckets for `tbill-openeden` and `wtgxx-wisdomtree` intentionally remain unkeyed: their reviewed compositions describe multiple underlying holdings, not the aggregate fund-share observation. Assigning the aggregate key to one constituent (or every constituent) would create a false or ambiguous classification join.

Assurance reports also retain source-native category keys when the reviewed sidecar is at a different level of detail: AUSD's combined cash review does not match separate fund/company cash observations, USDG's individual fund look-through rows do not match the aggregate government-MMF category, AUDD's aggregate deposits do not match individual bank accounts, and BRLV's bond/ETF aggregates do not match separate primary/secondary report rows. Newly disclosed PYUSD Treasury bills have no historical reviewed slice. These categories retain their source classifications without forcing a reviewed join; a composition review, rather than an identity migration, is required to reconcile the different scopes.

Adapters that can emit mapped dependency targets are enrolled in the reviewed mapping registry in `shared/data/coverage-dispositions/dependency-target-dispositions.ts`. Each adapter-level record identifies the implementation source files that were reviewed and records the reviewer, date, rationale, and source-file provenance. The dependency coverage gate rejects missing, stale, duplicate, or source-free adapter reviews when a report-card dependency set reports `live-reserve` as its base source. The registry attests to the adapter mapping rule; canonical target identities remain owned by the adapter and its per-coin configuration, so the registry does not invent per-target fingerprints or duplicate provenance onto every emitted live slice.

Adapters must emit `depType` wherever they emit `coinId`; native reviewed reserve holdings use their explicit collateral kind rather than relying on a default. Authored linked slices are rejected without a type. Runtime schemas still read legacy persisted rows, but dependency derivation withholds unresolved untyped links row by row with `coinId-without-depType`; a unique authored kind for the same coin id may resolve a legacy row until the adapter resyncs.

The Mento adapter preserves native and represented assets as separate keyed rows, including `mento:reserve:axlusdc`, `mento:reserve:axleuroc`, and `mento:reserve:usdt0`. Their canonical parents remain USDC, EURC, and USDT, with bridge representation metadata naming the held token, chain, contract, verification flag, and source. A represented token on an unreviewed chain remains an unlinked measured row with `unverified-mento-representation`. Verification establishes representation identity and documented lineage, not independently audited bridge escrow solvency. When native and represented contributions aggregate into one parent edge, its intermediary remains absent (null in publication) rather than falsely describing the whole holding as bridged; slice-level metadata retains the split.

`avant-reserves-api` emits one unkeyed “Unresolved whole-token reserve composition” row at 100% high risk, with `unknownExposurePct = 100`, matching the reviewed static boundary. Under D24, gross positive longs cannot become full backing weights without a reconciled holder-level denominator and exact held-claim joins. Gross longs, financing debts, perpetual shorts, source-labelled entries, categories and NAV remain separately labelled contextual metadata (`details.contextualObservationsOnly = true`); missing location observations remain null. `gross-leverage-disclosed` explains that these observations are not whole-token composition. Neither source denominations nor source labels establish tracked reserve dependencies. The adapter remains a weak live probe and publishes no collateralization ratio from leverage coverage. savUSD retains its separate ERC-4626 avUSD wrapper identity; the parent's unresolved book is not duplicated as direct savUSD reserves.

`sodax-sonic` is implemented but staged for the distinct Sonic SODAX bnUSD liability; it is not current backing for tracked legacy ICON bnUSD(old), whose binding is suspended. Its pinned borrower scaled-debt census must exactly reconcile to variable-debt supply and cover the live reserve registry. Reviewed oracle code/source clocks govern valuation, and unknown positive reserves remain measured. It is `weak-live-probe`, emits no canonical collateralization ratio, and withholds v2 global-supply completeness pending reviewed identity/perimeter reconciliation.

Legacy bnUSD's curated fallback is now a 100% unclassified residual (`classification-only`, manual review, 100% known unknown), not the withdrawn Sonic v2 composition or custody profile. It carries no new financial observation date, SODAX source keys or upstream dependency links. SODAX's mapping review is retained as `retainedBinding: { status: "staged", reason }`: staged/suspended retention requires a nonempty reason, at least one authored binding and every binding suspended. This preserves provenance only; it neither adds active coverage/legacy links nor relaxes active mapping-review requirements.

SODAX is permanent scoped on-chain context, not a shadow awaiting automatic class promotion. Current omitted supply diagnostics include **ICON, Archway, Havah and Injective**; the historical v1 roster is not a verified global v2 issuance book. The 650-call bound is per page, not a whole-run census cap. Existing borrower/reserve/page/timestamp/code-hash bounds, unknown measured rows and source warnings remain unchanged. Global supply review alone would still not establish an independently reconciled whole reserve book.

## Metadata Contract

Every provenance field below is an evidence claim about the current run, not a feed-family label — rule R6 (ADR-33 in [architecture.md](./architecture.md#architectural-decision-records)), enforced for route attribution by `buildRedemptionSnapshotMetadata` in `worker/src/cron/reserve-adapters/redemption.ts`.

Live reserve support is declared per coin in `StablecoinMeta.liveReservesConfig` (`shared/types/live-reserves.ts`, authored under `shared/data/stablecoins/coins/*.json` and validated by `shared/lib/stablecoins/schema.ts`). Producer, recovery, adapter lookups, and snapshot-store reads/writes use `shared/lib/stablecoins/worker-runtime-registry.ts`: configured feeds retain lossless `liveReservesConfig`, `flags`, `reserves`, and `reserveReview` inputs, while unconfigured entries keep only bounded classification/structural slices. `ReserveAdapterCoin` in `shared/types/core.ts` defines the adapter's metadata contract.

The `worker/src/lib/live-reserves/store.ts` barrel contains only producer-safe storage and overview functions. Public `resolveReserveResult` callers import `store-views.ts` directly; only that presentation layer keeps the full registry and curated-reserve fallback templates. This prevents a producer storage import from initializing the full evidence-heavy catalog.

### Native-share admission and staged bootstrap

JLTXX remains quarantined; no automatic activation is approved. Its class gate runs even with a positive CoinGecko price/market cap. `fetchPinnedNativeShares` reads positive raw Ethereum `totalSupply()` and actual two-decimal encoding at one EIP-1898 canonical finalized block hash, checks that the closing header agrees, and retains original block time. Supply never comes from class assets or from dividing market cap by price. Shares × issuer NAV must match exact CUSIP 46655R119 / class 4397 assets within **0.5% inclusive** before separate observed-market valuation. Unsafe raw-number precision, identity/decimal drift, unavailable pins, future/stale observations, missing reviewed legal/native class perimeter or NAV/block skew provenance, and excess skew withhold admission.

`POST /api/bootstrap-jltxx-reserves` is operator-only, authenticated and idempotent; it requires `Idempotency-Key`, an empty body and no query overrides. Its fixed quarantined-ID allowlist uses the existing runner/core atomic writer under the ordinary `sync-live-reserves` lease and finite linked cancellation/deadline/fetch budget. It captures NAV/native evidence, requires matched current state/composition source, attempt, fingerprint and success clocks on readback, and never expands the active roster or seals a scoring generation. `evidenceCaptured` is not catalog approval or runtime price/market-cap PASS. The existing October 10 review deadline remains; source-reviewed perimeter/skew, current runtime packet and explicit operator decision are still required.

All six raw `chainlink-por` bindings use v3: BC3M/BIB01/GLDY/KAG formerly v1, KAU/TUSD formerly v2. Backed ratios require a paired source-reviewed probe skew bound and provenance; there is no borrowed TUSD/default allowance and no failed-probe gross-supply fallback. Missing review emits `reserve-supply-temporal-policy-unreviewed`, excess original feed-to-every-supply-clock skew emits `reserve-supply-time-skew`, and a complete zero liability denominator emits `zero-liability-denominator`, with no ratio. Scope classification checks both catalog-to-scope and scope-to-catalog directions, including duplicates, unsupported readers and lock/mint references. The detail card preserves typed reasons, scope and original reserve/minimum/maximum supply clocks. TUSD's reviewed 172800-second bound and independent USD1 guard behavior are unchanged.

**BC3M temporal policy (reviewed October 8, 2026):** `issuerCirculationProbe.maxReserveSupplySkewSec` is **86,400 seconds inclusive**, one BC3M reserve-feed heartbeat. [Chainlink's Polygon reference directory](https://reference-data-directory.vercel.app/feeds-matic-mainnet.json), entry `bc3m-por` for proxy `0x648E0fF6A36D58F6FCE5927cB77601b73cAdc2Af`, specifies an 86,400-second heartbeat and 10% deviation threshold. [Backed's PoR methodology](https://backed.fi/news-updates/chainlink-proof-of-reserve-is-now-active) independently states that Chainlink publishes daily or when reserves change by more than 10%, while The Network Firm refreshes its underlying reserve API every 10 minutes. That 10-minute reserve cadence does not establish a supply-reporting cadence or extend the feed-to-supply allowance. The consumed [Backed GraphQL circulation response](https://api.backed.fi/graphql) has no observation timestamp, and this review found no published GraphQL supply-refresh guarantee; it remains corroboration only. Publication still requires exact same-run on-chain gross supply and inventory-adjusted circulation reconciliation across all eight documented deployments, then compares the original Chainlink `updatedAt` against **every** pinned supply-block timestamp. At 86,400 seconds the ratio may publish; beyond it, the reserve slice remains available but the ratio is withheld with `reserve-supply-time-skew`. This policy permits a bounded comparison of different instants, not a simultaneous reserve/liability attestation or a source-age override. BIB01 remains quarantined and receives no policy or activation change.

Operational feed reviews live separately in `worker/src/lib/reserve-feed-reviews.ts`, schema-derived from `ReserveFeedReviewSchema`: configured independent **or** static-validated identity, adapter, failure category, exact warning codes/error prefix, owner/reason, HTTPS sources with valid evidence dates, review and expiry. Reviews must be nonfuture and expire within 14 days; at `now >= expiresAt` the gate re-arms. Unknown/new failures do not inherit acknowledgement. Circuit-open inherits only the latest non-skipped attempt; unreadable/missing history fails closed.

The API's acknowledgement is assembled from the same loaded sync state and assessment clock as its presentation/freshness verdict; matching never refetches a newer state to acknowledge an older response.

Matched in-use reviews emit the admin-only info cause `reserve_feed_reviews_expiring` in their final 48 hours (inclusive, `STATUS_REVIEW_EXPIRY_REMINDER_WINDOW_SEC` in `shared/lib/status-thresholds.ts`); [review renewal](./runbooks/review-renewal.md) requires fresh evidence and never changes snapshot freshness, quarantine, or the automatic gate re-arming at expiry.

`LiveReservesConfig` fields:

| Field              | Meaning                                                                               |
| ------------------ | ------------------------------------------------------------------------------------- |
| `adapter`          | Registered adapter key from `shared/lib/live-reserve-adapters.ts`                     |
| `version`          | Increment when adapter semantics or parsing change materially                         |
| `semantics`        | One of `collateral-mix`, `protocol-reserve`, `attestation-mix`, `single-asset`        |
| `breakerScope`     | Optional circuit-breaker grouping override; defaults to adapter key                   |

| `suspended`        | Optional operator kill switch (`reason`, `since`, optional `reviewBy`, ISO dates)     |
| `bootstrapForSupplyAdmission` | Optional explicitly reviewed reserve-only prerequisite authorization for a quarantined coin; `reviewBy` expires at UTC start of that date, without admitting listing or expanding the active producer census |

A `suspended` marker is for dead or semantically unusable upstream feeds (for example keyed access without a key, or a reachable feed whose measurement basis cannot represent the configured composition). `shared/lib/stablecoins/registry.ts` strips it at load, so sync, Backing, presentation and breakers use no live feed and retain the curated fallback. Authored config remains for reviewed recovery, but a due `reviewBy` date never reopens it. M0's seven bindings were suspended August 19, 2026 and restored only after `M0_API_KEY` and surviving-schema support were supplied. USDXL remains suspended because pool cash omits gross borrower collateral and the USDT0 PSM; repair complete accounting before removing suspension.

Coverage audits distinguish authored config from executable collection: one disjoint partition by lifecycle/kill switch (`configured-active`, `configured-suspended`, `configured-non-active`), lifecycle first so inactive+suspended counts once. Only active unsuspended configs enter normal producer/recovery collection. Reports emit IDs/lifecycle/reasons and separately list non-active assets missing curated reserves/review; these are research inventory, not suspension or V9-live gaps. Preserve historical rows and curated artifacts. Current RS4 held-source evidence and reactivation actions live in [Dated source age caps](./runbooks/dated-source-age-caps.md#suspended-source-and-stale-publisher-recovery); neither overdue review nor reachable source removes a suspension.

`generate-reserve-coverage-audit.ts` emits `configCensus`, `activeWithoutCuratedReserves` and its effective-unconfigured subset `unconfiguredWithoutCuratedReserves` as separate inventories. Missing curated slices do not prove a missing live binding; effective-unconfigured does not prove suspension. Empty/absent curation stays a research gap rather than a fabricated unknown slice, and unavailable supply/market cap stays null. Production coverage observations require supplied report-card/reserve-state inputs, not authored-config counts.

All configured source URLs must be absolute URLs. The schema enforces this for HTTP/indexer inputs, `display.url`, and adapter-specific URL params such as RPC endpoints, dashboard APIs, and liquidity endpoints. Adapter definitions also declare their supported `semantics` values and config `version` set, so metadata changes cannot silently pair an adapter with unsupported reserve semantics.

### Registry-Defined Adapter Classes

`shared/types/live-reserve-adapter-declarations.ts` is the single authoring surface: it owns each adapter key, its Zod params schema (referenced directly by the declaration entry, not through a string identifier or a separate schema module), accepted primary input kinds, config validation policy, public source definition, provenance status, and display badge metadata. Shared `validation` tiers are named constants in `shared/types/live-reserve-adapter-policy.ts` so adapters on the same policy share one definition. `shared/lib/live-reserve-adapter-descriptors.ts` enriches the declarations and publishes `LIVE_RESERVE_ADAPTER_DEFINITIONS` as the single map for config, provenance, display, and adapter consumers; the Worker's `ReserveAdapterDefinition` is a `Pick<>` of the declaration type rather than a hand-copied structural type. `LIVE_RESERVE_ADAPTER_KEYS` and `LiveReserveAdapterKey` remain declaration-derived key views. Five important definition properties are not user-configured per coin:

Equivalent complete descriptors may select explicit named profiles; shared telemetry objects are immutable exact capacity/fee combinations, not inferred capabilities. Per-adapter origin and no-capacity rationale remain explicit, and params-gated telemetry stays at its declaration so a generic profile cannot grant it accidentally. These authoring aids introduce no second schema surface or policy/fingerprint change.

| Property              | Meaning                                                                                                      |
| --------------------- | ------------------------------------------------------------------------------------------------------------ |
| `sourceModel`         | Distinguishes `dynamic-mix`, `validated-static`, and `single-bucket` reserve shapes                          |
| `evidenceClass`       | Distinguishes scoring-eligible `independent` feeds from `static-validated` and `weak-live-probe` feeds       |
| `sourceOriginClass`   | Records who produced the evidence without changing its admission, liveness, or scoring strength             |
| `sharedSourceMode`    | Distinguishes per-coin fetches (`none`) from explicitly source-invariant result sharing (`source-invariant`) |
| `redemptionTelemetry` | Declares whether the adapter can emit direct/proxy redemption capacity and current-fee telemetry             |

- `dynamic-mix`: independently measured reserve compositions. These can be `independent` evidence for scoring when the retained snapshot passes admission.
- `validated-static`: live validation/probe adapters over curated/static slices. These remain authoritative for the reserve detail API, but they are tagged `static-validated` and do not count as independent live collateral inputs for report-card scoring.
- `single-bucket`: one-slice live proofs/attestations. Some are true independent evidence (`anzen-usdz`, `astherus-earn-wrapper`, `blast-usdb-yield-manager`, `btcfi`, `chainlink-nav`, `chainlink-por`, `chronicle-nav`, `erc4626-single-asset`, `escrow-balance`, `hive-hbd-protocol`, `initia-wrapper-vault`, `liquity-native-active-pool`, `liquity-v1`, `m0`, `m0-wrapper-underlying`, `sgforge-coinvertible`, `spiko-api`, `superstate-liquidity`, `united-por`, `usd1-bundle-oracle`, `usdai-hub`, `yamato`), while weak liveness-only or proof-class summary feeds such as `single-asset`, `solstice-attestation`, and `river-protocol-info` are tagged `weak-live-probe`. wiTRY (`witry-brix`) binds `erc4626-single-asset` over its Ethereum ERC-4626 staking wrapper.
- `independent`: scoring-eligible live evidence when the retained snapshot is fresh, authoritative, config-matched, and has no unexcused snapshot degradation; a later failed attempt does not revoke it.
- `static-validated`, `weak-live-probe`: detail/status-visible evidence classes that never override curated collateral scoring. Nested same-run redemption telemetry (`live-direct`, `live-direct-bounded`, `live-queue`, `live-proxy-validated`, or `documented-bound` with `same-run-onchain`, `same-run-api`, or `verified-source-timestamp`) may still bound the holder-facing exit route independently of either non-scoring composition class; legacy `immediateRedeemableUsd` on those classes stays rejected.
- `sourceOriginClass` is orthogonal to `evidenceClass`. It records `issuer-attested`, `onchain-observation`, `independent-assurance`, `reviewed-curation`, or `unknown` for diagnostic provenance. Unreviewed adapters resolve explicitly to `unknown`; the registry never guesses origin from an adapter name or input kind. Origin does not change reserve admission, standalone reserve facts, V9 facts, scores, or public API fields. The private V9 evidence-journal schema can carry the resolved value when journal writers are enabled.
- `source-invariant`: opt-in within-run result sharing for coin-invariant payloads. The result key canonicalizes adapter/version/semantics/inputs/params and omits coin ID; coin-dependent results must declare `none`. Reservoir runs per coin: srUSD reads the SavingModule leg/fee, while wsrUSD uses the deployed direct-rUSD branch. HTTP request sharing and block/resource-keyed PSM inventory deduplicate physical reads without summing shared cash across routes.

For instrument identity, measurement limits, report validation, and retained weak-evidence tiers, read [adapter-specific evidence boundaries](#adapter-specific-evidence-boundaries). The class definitions above remain the shared admission vocabulary.

### Adapter-Specific Evidence Boundaries

`jpmorgan-nav` is the issuer-attested, static-validated, single-bucket source for JLTXX Token Class shares. It reads J.P. Morgan Asset Management's official CUSIP 46655R119/class 4397 markdown publisher, pins the fund name, class name and ticker, and requires positive transaction NAV and class assets with a matching valid dealing date. The source timestamp is the conservative UTC start of that dealing date, never the generated-page or fetch clock. Its five-day source-age budget uses the shared business-day NAV policy. The keyed slice `jpmorgan-nav:class:4397` identifies direct fund shares, not a fabricated underlying Treasury/repo/cash allocation. `details.classAssetsUsd` is an issuer-reported diagnostic and is never treated as circulating supply or unconditional redemption capacity. This adapter does not establish independent reserve assurance and emits no redemption-capacity or fee telemetry.

For JLTXX supplemental on-chain supply admission, `reserve-nav-price.ts` retains positive `details.classAssetsUsd` only from verified CUSIP 46655R119/class 4397/JLTXX evidence whose dealing date matches the NAV source clock. The existing 48-hour successful-fetch and five-day issuer-source freshness gates apply independently. The class total serves as a fail-closed scope constraint: native shares valued at issuer NAV must reconcile within **≤0.5%** of class assets, a reviewed allowance for rounded assets and modest cross-observation drift. Missing or stale class evidence and larger divergence withhold admission with the machine-readable `reserve-nav-supply-withheld` R4 reason; they never become an Ethereum-only completeness claim or an issuer-assets supply substitution. This scope constraint does not change reserve composition, market-price telemetry, or redemption-capacity eligibility.

The reserve NAV decoder accepts the composition store's nullable or omitted metadata boundary and explicitly returns unavailable for either form before parsing. Bootstrap readback and pricing consumers share this fail-closed decoder; absent metadata never becomes a NAV quote or an admission claim.

A curated-validated token-supply probe must bind to the same holder instrument as the curated reserve evidence. Figure YLDS's former Solana configuration was removed with the Hastra wYLDS identity correction; it no longer produces a misleading wYLDS-liveness/FCC-Treasury-reserves pairing. Native FCC curated reserves and independent report metadata remain available, but no replacement live on-chain reserve probe is claimed for the retained Provenance/Stellar identities.

`single-asset` version 2 is permanent `weak-live-probe` issuer-quantity or ERC-20 liveness telemetry. A configured 100% bucket is a label, not measured portfolio composition or independent custody evidence. Neither HTTP nor on-chain liveness branches emit redemption metadata. Whole-source freshness remains `unverified`; configured timestamps are chain-supply diagnostics, not bank-reserve clocks. Invalid quantities or configured clocks fail the latest attempt without freshening last-good evidence. tGBP retains reviewed GBP units while suspended for Worker-egress HTTP 403; version 2 does not resume it. A new independently supported source requires separate review, never a family-wide class flip.

### Fallback Inputs

`inputs.fallbacks` is implemented by `createReserveAdapterRunner()` in `worker/src/cron/reserve-adapter-runner.ts`, shared by the regular producer and targeted configuration recovery.

- The cron tries `inputs.primary` first.
- If the adapter throws, the orchestrator retries the same adapter against each fallback by temporarily swapping that fallback into `inputs.primary`. A fatal adapter warning (for example `source-rows-exceed-total`) returns normally rather than throwing, so it records a `fatal-warning` attempt without trying the fallbacks.
- A successful fallback carries the `primary-fallback-used` info warning. Before persisting it, `syncReserveCoin()` (`worker/src/cron/sync-live-reserves-core.ts`) judges the fallback snapshot with `evaluateLiveReserveAdmission()`. If it would not be admissible for scoring (for example an `unverified`-freshness API read standing in for an on-chain read) while the stored snapshot still is (fresh, consistent, independent, not degraded, on the same clock), the fallback read is withheld: no composition or composition-history row is written, the stored snapshot and its `last_success_at` / `last_success_attempt_id` linkage stay authoritative, and the attempt is finalized `degraded` with the `fallback-withheld-score-grade-retained` warning (effect `degraded`), `metadata.reason` of the same code, `metadata.withheldFallback` (the fallback's admission rejection codes plus the retained snapshot's attempt ID and fetch time), and `last_error` naming the primary failure. Once the stored snapshot stops being admissible (the 48-hour bound, a source-age cap, or a config change) the fallback is written normally. A fallback that is itself admissible replaces the stored snapshot as usual, and primary successes are unaffected. Before 2026-09-25 an admissible stored snapshot was always displaced: crvUSD's two on-chain inputs timed out during a slow run, the Curve prices API fallback wrote an `unverified` snapshot over a four-hour-old score-grade on-chain one, and crvUSD fell from B 72 to C+ 60 with scrvUSD capped behind it.
- If every fallback fails, the attempt history records the primary and fallback failure chain, and the cron-run metadata includes per-coin `attemptFailureSummaries` for automated triage.
- Shared reserve HTTP helpers redact credential query parameters and known provider-key paths before placing URLs in failure errors or I/O limiter labels, including the primary error carried by a successful fallback warning.

### Snapshot Metadata and Warning Effects

Successful adapters can attach structured snapshot metadata that is stored on the authoritative snapshot row (`reserve_composition.metadata`), not on the mutable latest-attempt state.

V10 adapters may retain a typed `metadata.reserveObservation` (`shared/types/safety-score-v9-reserve-scope.ts`). It is a bounded technical/portfolio envelope, never an independent financial-assurance grade: it carries the source generation/digest, actual access/review and observation clocks, exact deployed subjects, included/omitted/unresolved obligations and explicit expiry. On-chain envelopes retain every finalized/safe header and raw getter quantity; a missing getter or changed hash fails the producer rather than becoming zero. Admission uses the earliest actual block time, the policy cross-chain skew bound, zero future skew and the stricter producer/score budget.

`xdai-bridge` emits its pinned Ethereum USDS/sUSDS and Gnosis bridge-minted-minus-burnt comparison as **partial technical accounting**. Pending mints/burns, non-bridge native issuance, fees and interest remain explicitly unresolved; the subset ratio is not whole-economic solvency, liability reconciliation, a financial audit or assurance seasoning. Native xDAI is not a WXDAI root liability. The accepted snapshot's envelope travels beside its own `slices`, `source` and `fetchedAt` through `loadFreshIndependentLiveReserveMap`, fixed-input normalization/base digest and capture/replay. A newer failed attempt cannot replace that provenance; legacy snapshots without an envelope stay absent.

Malformed captured observation envelopes retain a typed `reserveObservationFailure` marker and source digest in provenance. Compilation quarantines only that asset as producer-failed; valid unrelated assets are still evaluated, and malformed observations never become reserve or financial-assurance evidence.

`ReserveSlice.boundedFacts` optionally carries independently scoped contractual maxima, dated observed maturity, enforceable eligibility, current native-asset availability, applicability, or stressed realization facts. Producer observations must match metadata/provenance `boundedFactsGeneration` (`sourceGenerationId`, `observedAtSec`, `maxAgeSec`); consumers retain independent status and the stricter fact/run freshness budget. Origin attaches same-block idle USDC / total vault USDC to its existing source key; redemption capacity remains idle-only. The uncalled cross-chain API observer, exclusive schema and tests were retired on October 8, 2026. Its removal does not change the registered pinned OUSD vault producer or admit cross-chain liquidity; research citations and histories remain.

The bounded-fact builder resolves authored and live revisions by canonical `factKey` before extension validation. A fresh, admissible live observation wins over the same authored identity; otherwise a current admissible authored observation wins. Expired observations are omitted, while a rejected non-expired observation remains diagnostic only if neither source is admissible. Same-source duplicate keys and incompatible cross-source identities still fail closed. This is revision selection, not quantity aggregation: Origin's older reviewed idle balance and newer same-block observation measure the same vault at different times, so the selected numerator/denominator and the complete reserve weights remain unchanged.

A null live-source `maxAgeSec` means no additional source-wide cap, not unlimited freshness: policy, producer-fact and matching retained-generation budgets still apply. A missing or mismatched retained generation remains rejected, and null source caps cannot revive an expired observation.

A live quantity is an unclassified residual only with an explicit producer marker and a unique exact-source-key review confirming insufficient evidence. Unmarked classification-only slices retain their exposure treatment. Marked unknown quantities keep original weights, receive the policy residual charge once and stay bounded even when the whole book is unknown.

DOLA separates attributable Frontier bad debt from unknown non-FiRM issuance using same-denominator live attribution. USDh's September 30 scoped custody report and STRCx credit exposure replace unsupported March synthetic metrics; cNGN's December 2025 allocation remains historical evidence, never a refreshed composition.

**Reserve methodology — `collateralizationRatio` basis.** The field is a measured assets-backing-liabilities ratio, and only two bases may populate it: `gross` (reserve total ÷ supply, both sides from the same feed snapshot and recomputable from the published `totalReserveUsd`/`supplyUsd`) and `net-of-protocol-owned` (the same quotient after removing the issuer's own inventory and protocol-owned liquidity from both sides, which the feed's own scalars must reconcile). Every other basis publishes the issuer's number as `reportedCollateralizationRatio` and no canonical ratio at all, and the coverage/undercollateralization warnings are built only from a canonical ratio: an `unreconciled` headline (matches no derivable denominator) keeps its degraded `collateralization-unreconciled` warning instead of a coverage claim, and an `underived` one (the feed publishes no `total_supply`) publishes no coverage warning because nothing reproducible backs it. Adapters whose published totals are not assets-backing-liabilities — Avant's gross longs over gross financing debt is the reviewed example — publish those numbers under explicit detail keys (`details.grossLongUsd`, `details.grossFinancingDebtUsd`, `details.grossLeverageCoverageRatio`) and no ratio field.

`details.freshnessSource = "same-run-render-clock"` marks a verified snapshot whose timestamp is the source's own render or response clock — the instant the payload was rendered or served — rather than an independently dated as-of time for the reserve state (Mento's dashboard SSR fetch time, Flying Tulip's `lastUpdated`, DOLA FiRM's response timestamp). Such clocks are accepted as `verified` per the settled freshness policy, and the basis is named explicitly so consumers can distinguish a render clock from a dated disclosure.

Redemption telemetry is validated before persistence. Negative capacity or constraint values, capacity ratios outside `0..1`, negative fees, malformed redemption source URLs, invalid redemption freshness/capacity/holder-eligibility enum values, invalid `routeStatusReviewedAt` dates, capacity emitted by adapters that do not declare redemption-capacity support, fee telemetry emitted by adapters that do not declare fee support, and direct/proxy/queue capacity evidence emitted by an incompatible adapter capability fail the adapter output validation. Queue capacity that omits queue depth, settlement delay, or daily-limit semantics is stored only with a degraded warning. Legacy flat capacity/fee fields (`immediateRedeemableUsd`, `immediateRedeemableRatio`, `redemptionFeeBps`) are no longer written: the store-row decoder still reads them from historical rows (30-day retention) and maps them into the nested `redemption` shape at decode time, but every other consumer and all producers use the nested contract.

The shared wire schema owns known producer fields and distinguishes absent, invalid-present and valid nested redemption telemetry; opaque protocol diagnostics and specialized route-attempt extensions remain separate. Stored invalid nested claims are quarantined as an empty object with an in-memory malformed marker: capacity, fees, limits and specialized extensions are never partially salvaged. Present nested evidence takes precedence over historical flat fields even when invalid. Sealing checks the invalid disposition before hashing/serialization and retains that member as `snapshot: null`; serialization cannot erase the marker while preserving a favorable claim. Raw selected-snapshot diagnostics and warnings are validated independently of unrelated later-attempt metadata, so a clean retained success survives a later corrupt error attempt.

An omitted nested `redemption` field or `{ redemption: undefined }` is absent; `null`, scalar and array claims remain invalid. At the historical flat-field migration boundary, null/undefined amounts or fees are unavailable and omitted, while measured zero survives and malformed non-null values still quarantine the whole claim. `buildRedemptionSnapshotMetadata` canonicalizes and deduplicates only wholly valid `sourceUrls` arrays before persistence; malformed arrays are left intact for rejection. The shared wire schema and stored-row decoder validate URLs without rewriting retained evidence arrays.

Same-run adapters populate `routeStatusSource: "onchain"` or `"protocol-api"` only when that run evaluates a route-specific executable predicate such as a pause, halt, shutdown, redeemability, cap, collateral-health, or allowlist gate. Capacity, balances, collateral, TVL, backing, and static configuration are not route-openness evidence by themselves; those paths publish `unknown` / `static-config` or omit the source. The shared metadata builder requires an explicit non-persisted `routeObserved: true` proof before it preserves live route-source attribution.

An unreadable route predicate is absence of evidence, never an optimistic verdict. A failed or malformed required probe publishes `unknown` without live route-source attribution; a readable open predicate supports `open`, while an observed closure preserves `paused` or `degraded` with its on-chain source. Balance-only paths including wrapped M0, collateral-position, Superstate, f(x), and Astherus Earn do not claim live openness. Falcon exposes redemption timing but no unsupported route status. HoneyFactory status uses the same-run pause and cap guards, Sky LitePSM uses the halt-fee sentinels, and Reserve DTF requires both a sound fully collateralized basket and positive throttle capacity.

sBOLD requires both readable collateral-health words (`calcFragments().collInBold` and `maxCollInBold()`) and an open gate before publishing an open route. An unreadable health word emits `sbold-collateral-health-unavailable`, keeps measured withdrawable BOLD as documented-bound context, and publishes `unknown` without live source attribution. An observed pause or collateral-health restriction remains `paused` or `degraded` with its on-chain source.

`freshnessMode = "not-applicable"` is the expected scoring-eligible path for intrinsically current reads such as `evm-branch-balances`, `liquity-v1`, `liquity-v2-branches`, `liquity-native-active-pool`, `m0-wrapper-underlying`, `escrow-balance`, `btcfi`, `xdai-bridge`, `hive-hbd-protocol`, `usdai-hub`, and `collateral-positions-api`, where reserve composition comes from latest-state contract/API state rather than a separately timestamped disclosure. The snapshot still cannot enter collateral scoring. Its broader stable-bucket liquidity is retained as diagnostic context; specific strategy labels such as Agua take precedence over their USDC denomination. Normalized redemption capacity is bound exclusively to same-run reads of the pinned USDC PSM's underlying identity, balance and pause state, not to the balance-sheet USDC bucket.

GBPm additionally requires pinned whole-system ActivePool/DefaultPool accounting and uses the earlier block/dashboard clock. The registry caps that probe at 21,600 seconds (6 hours, three missed 2-hour snapshotter writes) instead of the generic three-day dashboard cap, and the rate cross-check tolerance tightens from 5e-4 to 6e-5 — the ±5e-5 rounding envelope plus a sliver of sub-cadence drift — so multi-day accumulator drift now fails the probe into unverified freshness.

Positive measured holdings remain present; presentation rounding does not define dependency weights. Source-total and unknown-exposure guards remain separate from precision.

USDT's `tether-transparency` composition uses a reviewed raw-dollar packet from the [BDO-attested June 30, 2026 report](https://assets.ctfassets.net/vyse88cgwfbl/2kYf7r64h3tzwiu6F0CbUB/2997abd2f11ecea74a21528048b50707/Opinion___Report_-_Tether_International_Financial_Figure_30-06-2026.pdf), report page 4 (PDF page 9). `params.reviewedComposition` binds that exact URL, date and $187,751,426,411 signed-report denominator to all eleven category `sourceKey` identities and their exact signed-report integer `dollars`. Missing dollars, duplicate or missing identities, partial sums, balanced redistribution between categories, and changed source/date/denominator fail admission. Observed bad states (E4/P3), including reserve shortfalls, genuinely reported non-positive liabilities, and paused routes, publish available slices and ratios with `degraded` warnings rather than adapter errors; only unreadable, malformed, or unverifiable evidence fails closed, and undefined ratios are omitted rather than fabricated.

## Cron Behavior

`runFourHourlyReserveSyncSlot()` in `worker/src/handlers/scheduled/hourly-live-reserves.ts` runs the reserve cron on its own 4-hourly trigger so reserve-adapter fetches do not compete with the 30-minute scoring lane or the daily 08:00 jobs.

`syncLiveReserves()`:

1. Filters `WORKER_ACTIVE_STABLECOINS` to the coins that declare `liveReservesConfig`.
   Configured readable inactive coins are not queued; `sync.collectionEligibility` distinguishes policy exclusion from a persisted attempt. The separately authorized JLTXX reserve-only prerequisite opportunity below does not expand this active full-cohort queue.
2. Orders the queue by adapter evidence class (`independent`, then `static-validated`, then `weak-live-probe`) and packs coins sharing a `source-invariant` adapter contiguously, so run-budget truncation defers weak probes before score-grade feeds and shared fetches are reused immediately. The durable scheduler checkpoint stores the one next-item resume pointer; a resumed run processes only that deferred suffix and does not wrap back to the queue head.
3. Resolves an adapter from `worker/src/cron/reserve-adapters/index.ts`.
4. Builds a breaker key as `live-reserves:${breakerScope ?? adapter}`.
5. Checks the per-source circuit breaker before each coin fetch.
   Each primary or fallback adapter attempt receives its own start time as `nowSec`, so time spent earlier in the queue cannot make current chain heads appear to be in the future.
6. Persists either a fresh snapshot (`reserve_composition`) plus sync-state row, or an error/degraded/skipped sync-state row.
7. After awaited finalization, an exhausted checkpoint-owned `ok` or `degraded` producer seals the accepted metadata generation before its lease releases. Errors and incomplete cohorts never seal.

Redemption remains on its own lease in this four-hour slot and runs after the producer settles, consuming the latest sealed acceptance even after an incomplete, failed or locked head. Recovery completing producer work forces redemption to consume the newly accepted view; consumer-only replay remains idempotent. The sentinel still requires successful exhaustion of this slot's queue. Producer-priority/co-tenancy admission and controlled deadlines are unchanged.

The `reserve-recovery` lane retains its five-minute trigger and always sweeps stale slots, including in `off` mode. In `recover` mode it fences abandoned in-flight attempts, claims a compatible ready pointer, and replays the suffix after active leases permit takeover. It retires up to 25 incompatible historical checkpoints per tick, prioritizing `ready`/`recovering` debt, then `running` debt, before abandoned history. Retirement requires a newer current-hash checkpoint that completed the full configured queue in a real `finished` slot with a terminal clock; a degraded/error aggregate slot result does not invalidate that completed cohort. The newest qualifying slot/highest attempt is selected deterministically and its exact schedule/slot/job/attempt/generation/invocation identity is revalidated in the atomic retirement/pending-attempt fence. The retired checkpoint is `failed` with `checkpoint-superseded-by-newer-full-cohort`; nullable `superseded_by_json` records that identity plus `queueHash`, also copied as `supersededBy` into a matching pending attempt's metadata. Active reserve-child/recovery leases and fresh slot heartbeats prevent retirement; leases are never deleted and an operator-only cohort without a real slot cannot qualify.

A successful idle poll is `ok` even when historical incompatible debt remains. `statusCause = "reserve-recovery-zero-eligible-incompatible"`, inspection and `retiredCheckpoints` remain debt telemetry, not this run's execution failure or `metadata.quality`. Genuine non-ok work names its primary `metadata.reason` in this precedence: `reserve-replay-child-error`, `reserve-replay-child-degraded`, `reserve-replay-deferred`, `reserve-config-recovery-failed`, `reserve-config-recovery-missing-fetcher`, `reserve-config-recovery-deferred`. All applicable codes remain in `metadata.reasons`; failed IDs and child summaries are preserved. Disabled mode, unchanged consumed fingerprints and config-only lease contention are `ok`. The checkpoint pointer remains the sole run-level resume mechanism.

Recovery/config/replay admission protects the natural producer's current due slot until it has a real finished row and clock, and the next slot from 24 minutes before its due time (nine-minute run budget plus the maximum family claim/lease TTL). Missing due delivery remains protected; finished degraded/error slots release priority. Recovery also defers while any slot in `RESERVE_RECOVERY_HEAVY_SLOT_KEYS` (`shared/lib/scheduled-runner-registry.ts`) is running within its controlled 14-minute deadline. These deferrals are `skipped_neutral` with `producer-slot-priority` or `heavy-slot-co-tenancy`, protected identity/condition/time/budget metadata and no config attempts. Admission is checked before lazy imports and fenced again at claim and lease mutations using database time; it proves no publication. No trigger expression or capacity changes.

Both post-claim priority guards await `releaseUnstartedLiveReserveRecoveryClaim()` before deferring. Only the exact owned, unchanged, nonterminal replay with no started item/child can CAS `recovering → ready`; only recovery ownership/lease and row update time change. The queue suffix, historical domain attempt, progress, children and generation remain intact, making replay immediately reclaimable without claim expiry. Started/lost/mutated claims refuse release and publish actual `released`, `already-started` or `not-owned` disposition. The hourly guard additionally requires its invocation to own the claim.

Only a genuine four-hourly `scheduled-job` reserve head waits for an existing family writer, abortably in 15-second polls with one requester owner and one final cron row. The fixed deadline is the minimum of four minutes, observed blocker lease/claim expiry (including the strict-expiry next second), remaining logged head budget and controlled-slot budget after reserving the normal nine-minute producer plus 35 seconds for finalization/logging. A fresh 12-minute head therefore has approximately 145 seconds of admission headroom; renewal cannot extend the captured wait deadline. Recovery never waits. `blockedBy` reports the actual holder separately from requester `leaseOwner`; versioned reserve-family owner envelopes name holder job, path, invocation and slot. Legacy UUIDs acquire holder fields only from exact-owner-matched progress; otherwise those fields are null. Successful acquisition still runs the normal producer → redemption → sentinel sequence.
**Adapter output validation:** After each adapter returns, `validateAdapterOutput()` checks
that all slice `risk` values are valid enum members, all `pct` values are finite and strictly positive,
the slice list is non-empty, and the sum is within 2 points of 100%. Invalid output is treated as
an error. Sum deviation above 0.5 points produces a `degraded` warning, while deviation above 2 points
hard-fails the adapter output with a `fatal` warning.

Source freshness validation also rejects source timestamps that are more than 10 minutes in the future, including nested redemption telemetry timestamps and the newest contributing timestamp (`newestSourceTimestamp`) in Re Metrics, so upstream clock mistakes or millisecond/second parsing errors cannot be treated as fresh snapshots. Multi-row reserve feeds should use the oldest material contributor timestamp as `sourceTimestamp` for verified freshness and can persist `latest*Timestamp` / `sourceTimestampSpreadSec` metadata for diagnostics.

Adapters can also declare shared validation policy in the registry:

- `maxSourceAgeSec`: if adapter metadata includes `sourceTimestamp` and the upstream disclosure is older than the policy allows, the sync is marked `degraded`
- `maxUnknownExposurePct`: if adapter metadata includes `unknownExposurePct` and unmapped reserve exposure is material, the sync is marked `degraded`
- `allowedFreshnessModes`: explicit per-adapter freshness contract enforced by output validation
- when `maxSourceAgeSec` exists but the adapter can only attest freshness heuristically, `freshnessMode = "unverified"` produces an informational `freshness-unverified` warning instead of forcing a degraded status on the sync itself; the snapshot still cannot enter collateral scoring
- late monthly disclosures that routinely publish after the next calendar month starts use `LATE_MONTHLY_DISCLOSURE_SOURCE_MAX_AGE_SEC = 4000000` rather than ad hoc per-coin caps
- month-end disclosures whose successor is published weeks into the following month use `NEXT_MONTH_DISCLOSURE_SOURCE_MAX_AGE_SEC = 70 days`, calibrated to the measured period-end-to-publication lag of each publisher rather than to the month boundary
- timestamp-less dashboard/API feeds should also populate `details.freshnessSource` / `details.freshnessReason` so the lack of verified recency is explicit in stored metadata
- `preferredFreshnessMode` records the honest target (`verified` or `not-applicable`) separately from tolerated `unverified` fallback. Adapters with no usable upstream reserve timestamp instead declare `freshnessLimitation`; they are not missing-probe promotion candidates. The coverage audit separates latest-known tolerated-not-preferred observations ("probe not built") from these upstream limitations. Supply `--reserve-states <file>` with an array (or `{reserves: [...]}`) of `/api/stablecoin-reserves/<id>` responses; without those snapshots it reports observations as unavailable, not inferred from configuration.

|---|---:|---|
| `DASHBOARD_SOURCE_MAX_AGE_SEC` | 3 days | Timestamped reserve dashboards; faster publishers may declare a tighter bound |

Per-coin `scoring.maxSourceAgeSec` may only tighten a declared adapter cap; the shared config schema rejects widening. Omit redundant equal values and inherit the publisher policy. Where an adapter has no age cap, a coin may supply one (for example, reviewed Chainlink NAV windows); latest-state `not-applicable` freshness still bypasses source-age checks. The September 2026 review removed obsolete 4,000,000-second dashboard overrides and duplicated assurance caps rather than widening publishers to clear alerts. EUROP now expires after 100 days instead of its former 10,000,000-second allowance, so an overdue report can lose score-grade eligibility until a newer examined period is published.

For on-chain branch-balance adapters, branches marked with `depType: "wrapper"` are not treated as plain USD-pegged wrappers for the depeg guard. This avoids false degraded states for yield-bearing wrappers such as sUSDe whose market price can intentionally rise above one dollar while the reserve slice still links dependency risk to the underlying asset.

Unknown exposure now follows one repo-wide policy:

- quantify it and persist `unknownExposurePct` when the adapter can do so honestly
- emit an explicit unknown slice when the reserve mix would otherwise hide that exposure
- use threshold-driven warning effects so immaterial unknowns stay informational and material unknowns degrade the sync
- fail closed when the adapter cannot quantify the missing exposure without inventing precision

These policy warnings preserve last-known live detail/status data but exclude the affected snapshot from V9 Backing/dependency compilation. Admission judges the snapshot's own warnings, not the latest attempt's status.

**Circuit breaker recording:** Breaker outcomes are deferred until the entire sync loop
completes, recording the worst outcome per breaker key (failure trumps success). This
prevents first-coin-wins bias where a successful early coin would mask failures of later
coins sharing the same breaker key. Finalization records failure outcomes first and
skips success heartbeats for breakers that are already closed with no failure debt;
those closed-success skips avoid rewriting hundreds of live-reserve circuit rows at
the end of every healthy run. Only upstream HTTP/network failures contribute negative source-health outcomes. Configuration, output validation, corroboration disagreement, schema-shape, D1/storage, and run-budget failures are neutral: they remain coin failures without opening a shared source breaker. A successfully fetched result rejected solely for stale nested redemption evidence records a successful transport outcome, healing old breaker debt, while the attempt remains `degraded` with `metadata.reason = "source-stale"`. Overview counts that attempt as stale even before its first snapshot. No successful snapshot, fetch clock, or success clock is written; stale evidence remains rejected for reserve scoring and redemption. Other fatal warnings still follow the normal validation-failure path. Failure metadata distinguishes `storage-write` (including `D1_ERROR`), `corroboration-mismatch`, `schema-shape`, and `run-budget-exhausted`.

Cron result statuses:

| Status     | When                                                                                                                                                                                                                  |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ok`       | At least one configured coin synced, no coin was budget-deferred (`deferredCoins === 0`), and `failed + skipped <= ceil(total * 0.1)`                                                                                 |
| `degraded` | At least one configured coin synced and either `deferredCoins > 0` or `failed + skipped > ceil(total * 0.1)`; OR no coin synced but every skip was a circuit-breaker hold (no real failures, no budget-deferred tail) |
| `error`    | No configured coin synced and at least one coin truly failed or was budget-deferred (`failed > 0` or `deferredSkipped > 0`)                                                                                           |

Per-coin warnings still matter operationally, but they affect `reserve_sync_state.last_status` for that coin (`degraded`) and the cron metadata warning list, not the run-level `CronResult.status`.

JSON parse failures include the HTTP status, content type, and final response URL when a redirect changed it, with provider credentials redacted. This distinguishes an issuer API schema change from an upstream redirect to a marketing or challenge page. A locally successful request does not prove that Worker egress reaches the same response; inspect the next production attempt before changing the configured source.

The cron loop remains sequential with at most two adapter HTTP/RPC operations in flight, preserving the six-connection trigger budget. The leased wrapper grants 12 minutes; the internal run budget is 9 minutes. Admission reserves one 20-second attempt, 30-second D1 finalization window, and 5-second margin. Every admitted coin shares the absolute run deadline minus that margin across checkpoint, begin, breaker read, fallback chain, and terminal writes. Primary and fallback attempts each receive at most 20 seconds and cannot extend the shared adapter-chain deadline (which reserves finalization time). Checkpoint/begin/failure writes are bounded by the lifecycle deadline; SQL deadline/ownership fences prevent late D1 work from gaining authority. A timed-out or ownership-rejected begin stops the run with its checkpoint retained, never advances an ambiguous pointer. Success still uses authoritative readback on ambiguous acknowledgement.

Run metadata exports in-memory `phaseTimingsMs.stages` for checkpoint starts, breaker reads, begin writes, failure writes, authoritative writes, and progress reporting alongside aggregate setup/queue/adapter/D1/finalization timings. Adapter telemetry uses `ioActivityBurstCount` for zero-active-to-active I/O transitions, not concurrency “waves”. Status snapshot compaction preserves the producer-bounded latency groups (128 groups / 36 KiB) and histogram samples rather than silently truncating them to 40; producer overflow remains explicitly counted. Per-attempt `durationMs` lives under composition `metadata.diag`, excluded from the payload digest and public responses.

The cron reports `setup`, `syncing`, and `finalizing` progress. Budget exhaustion defers untouched tail rows as skipped with `failureCategory = "run-budget-exhausted"`; these are capacity pressure, not source failures, and are excluded from persistent-stale independent alerts. Deferred rows clear attempt/pending IDs and checkpoint ownership retains the resume pointer. Metadata exports `runBudgetTruncated`, `deferredCoins`, `nextCursorStablecoinId`, and resolved budgets. Exhausted finalization-tail budgets skip remaining breaker writes, artifact cleanup, and history pruning explicitly. Success composition/state and both authoritative-gated histories now commit atomically; there is no post-success history-gap warning or resume-repair hook. Source-invariant adapters alone reuse complete config-keyed source results. Cleanup removes sync-state and breaker artifacts for removed live sources.

Artifact cleanup remains best-effort, but the cron metadata now records `artifactCleanup` delete counts, `artifactCleanupWarningCount`, and structured `artifactCleanupWarnings` when cleanup fails. `/status` and the admin status dashboard summarize non-zero cleanup deletes and cleanup warning counts so ghost-artifact cleanup regressions do not require log scraping.

This preserves matched readback and referenced-attempt history across ordinary four-hour finalization without adding staged coins to the active queue, breaker cohort, or scoring generation. Other non-active/unconfigured rows, including retired STBT, Solomon legacy, and USDH adapters, are still deleted; removing the staged binding also removes its retention exception. Retention does not refresh evidence clocks or bypass current-fingerprint re-verification.

### Deploy-time configuration recovery

In `WORKER_RESERVE_RECOVERY_MODE=recover`, the five-minute lane compares compact prior bindings against deployed semantic fingerprints before replaying suffixes. Snapshot and positive-timestamp attempts are separate: `snapshotFingerprint ?? attemptedFingerprint` establishes mismatch, and a current attempted fingerprint consumes that opportunity even if an older snapshot survives. A matching snapshot is never repaired merely because latest attempt differs; old mismatched evidence remains rejected. New/never-attempted ordinary active feeds belong to the producer. The sole separate inactive path is explicitly authorized quarantined NAV `bootstrapForSupplyAdmission`: registered reserve-NAV fetcher, safe config, absent current snapshot/attempt, and unexpired UTC-start review deadline. This reserve-only prerequisite shares the six-target/two-minute limiter; null/legacy bindings alone establish neither mismatch nor authorization.

Expired authored bootstrap fields fail `check:stablecoin-data` and require removal or explicit source re-authorization; expiry never grants a retry or resets a consumed fingerprint. Recovery publishes `supplyAdmissionBootstrapExpired` IDs in checked/partial results and even when producer priority or a held lease defers execution, so an inert prerequisite lane is not hidden behind a zero bootstrap count.

`worker/src/cron/reserve-recovery-config.ts` caps this phase at six coins and two minutes, admitting another coin only with the normal 20-second adapter window, 30-second D1 finalization reserve, and five-second margin available. Coins are serialized; shared transport helpers consume/cancel response bodies inside the same two-operation adapter I/O limiter. The lane retains its declared `2/6` connection peak and `reserve-recovery-chain` group. Per-coin request/result caches are discarded before the next coin, and the fleet scan reads fingerprints rather than composition payloads.

Consumed fingerprints and suspended opportunities are eliminated before importing adapters or execution machinery, keeping unchanged polls heap-light. Registry lookups initialize no adapter implementation; each typed fetcher imports its implementation only when fetched. Targeted recovery uses the standalone adapter runner rather than the fleet producer/finalizer graph. Import or fetch errors still flow through existing per-coin attempt and fallback handling.
During checkpoint replay in this five-minute lane, Kinesis runs after the reserve head rather than beside it, preserving the declared `2/6` peak. Normal four-hourly invocations retain the independent parallel Kinesis chain and their `3/6` budget; failures of the head still do not suppress Kinesis recovery.

The scheduled recovery fence and lease remain in place. The targeted phase additionally takes the existing `sync-live-reserves` lease with heartbeat renewal and parent cancellation, guarded independently by producer/heavy-slot admission before any attempt. Priority deferral returns `config-recovery-priority` and consumes no fingerprint; lease contention records `config-recovery-skipped` / `sync-live-reserves-lease-held` and the actual `blockedBy` holder without changing snapshot authority. Success/failure writes retain attempt-ID and absolute-deadline fences. Cancellation after fetch is checked before authoritative finalization.

A successful matching snapshot removes itself from the next scan. An admitted attempt start persists the deployed `reserve_sync_state.config_fingerprint` before adapter/breaker work and consumes this fingerprint's single targeted opportunity, including transport failure, semantic-stale rejection or interruption. Subsequent polls never targeted-retry that fingerprint, even after ten minutes, four hours or an isolate restart; the ordinary four-hourly producer still retries it. A genuinely changed fingerprint receives one new opportunity. Budget/lease/priority deferral before attempt start consumes none. No additional marker, reserve-state migration or success clock is created. Oldest-attempt-first ordering and existing source breakers remain binding. `configRecovery` preserves attempted/healed/failed IDs, one `priorBindingSources` count per mismatch, disjoint suspended/missing-fetcher/`skippedSameFingerprintCount`/due counts, and `skippedSameFingerprint` IDs; due work splits into attempted/deferred counts. There is no elapsed-time backoff.

A missing registered fetcher quarantines only that asset: its old snapshot stays rejected, a structured `config-recovery-missing-fetcher` warning identifies it, and the lane returns `config-recovery-partial` with the warning in `configRecovery.warnings`. Covered assets continue to refresh. Missing fetchers and failed/deferred targeted work degrade the recovery result without preventing checkpoint replay. The read-only operator CLI still fails on missing fetchers so release coverage gaps are visible before deployment.

The offline release visibility CLI requires an explicit deployed release ref or PR merge base, lists changed active config fingerprints in the working-tree diff, and fails if a required recovery fetcher is missing. Its pure `selectConfigRecoveryTargets` selector compares the same semantic config fingerprints; persisted opportunity consumption is a runtime-only concern. `worker/src/cron/__tests__/reserve-recovery-release.test.ts` tests the release selector with isolated fixtures (changed/unchanged semantics, new/removed/legacy rows and missing fetchers); tests never inspect git history.

The adapters retain their existing `validated-static` / `static-validated` / `issuer-attested` admission and freshness rules; a config epoch does not itself establish a successful read or refresh the report's examined date.

Six healthy, timely changed feeds can heal in one recovery run; a deferred tail is checked on the next tick. ## Storage Model

`cache['live-reserves:accepted-generation:v2']` stores one producer-only schema-v2 metadata envelope. Its root is `(fourHourlyReserveSync, slotStartedAt, queueHash)`, with sealing attempt/generation/invocation, immutable completion time, canonical SHA-256 content digest, and the complete configured-member census. Invalid or unavailable member evidence stays in the census as `snapshot: null`; every non-null snapshot has a valid matching 64-lowercase-hex fingerprint. One joined SELECT projects metadata, warnings, classifications, fingerprint, slice count, successful attempt/fetch identity and latest-attempt outcome without loading slice payloads. Exact active-checkpoint identity, queue hash/count and exhausted frontier fence atomic producer-child completion/cache publication. Each root seals once; only a newer source slot replaces acceptance. Whole-checkpoint completion remains after consumers.

Monotonic/idempotent retention applies only to prior envelopes that pass the full schema and canonical content-digest validation. A lease/checkpoint-fenced producer can repair malformed JSON, invalid root/schema or digest-corrupt acceptance using exact prior-value compare-and-swap; a concurrent older root is superseded, while same-root and newer valid seals remain retained. Consumers still reject invalid acceptance until a valid producer seal replaces it.

Accepted envelopes and consumed `reserveViewSchemaVersion` advance together to 2. The old v1 cache key is neither read nor deleted, v1 under the new key is invalid, and immutable historical rows are not backfilled. Consumed freshness preserves the original explicit mode and `sourceFreshnessInvalid` diagnosis; a null timestamp never reconstructs `not-applicable`. Mode-less v1 bound input remains unavailable to capture until fresh v2 reserve/redemption runs, while genuine static/no-reserve semantics remain separate.

**Rollout acceptance:** observe the first successful post-deploy four-hourly full-cohort v2 seal, then a redemption run carrying v2 consumed metadata. Check the exact v2 key/schema, complete census including null snapshots, valid fingerprints on non-null members, original freshness mode/diagnosis and resulting consumer health. A green deploy, old accepted envelope or repaired historical row is not runtime acceptance; before the new seal the input is unavailable, not zero.

### Snapshot admission gates

The shared result is `{ eligible, reasons: LiveReserveAdmissionRejectionCode[], freshness }`, where `freshness` is the `assessReserveSnapshotFreshness()` result that decided the `stale` gate (`null` without a snapshot or coin). All gates must pass for independent reserve scoring:

| Gate | Rejection code | Rule |
| --- | --- | --- |
| Current configuration | `unconfigured`, `suspended` | The coin must have an unsuspended live configuration. |
| Snapshot authority and integrity | `missing-snapshot`, `inconsistent-snapshot` | Strict slices and warnings (including count parity); matching positive success/fetch timestamps and nonempty attempt IDs when stamped. Warning corruption yields `invalid-warnings` at decoding and quarantines that asset. |
| Semantic configuration identity | `config-mismatch` | Stored fingerprint must be 64 lowercase hex and equal SHA-256 of canonical `{adapter, version, semantics, inputs, params}` (`params` defaults to `{}`). Display/scoring edits do not change it. Missing, malformed or mismatched bindings are not current live detail or redemption evidence; nullable historical decoding is not admission. |
| Evidence class | `non-independent` | Only `independent` reserve evidence qualifies. |
| Fetch and source age | `stale` | Fetch age is at most 48 hours; verified source age uses the tighter coin/adapter cap, falling back to 48 hours. A future Worker fetch is stale with `invalid-fetch-clock`, preserves its negative age, and also rejects admission as `invalid-freshness`; no source-skew allowance applies to fetch clocks. |
| Explicit freshness | `invalid-freshness` | Require `verified` plus a finite positive timestamp no more than ten minutes ahead, or explicit `not-applicable`. Absent/malformed modes or timestamps cannot become verified through decoding. |
| Snapshot warnings | `degraded-snapshot` | Apply the current per-coin warning policy to the retained snapshot, not the newest attempt. |
| Slice count | `insufficient-slices` | At least the requested count (one by default). |

## API Contract

`handleStablecoinReserves()` in `worker/src/api/stablecoin-reserves.ts` requires a readable tracked ID with an effective unsuspended `liveReservesConfig`. Presentation, feed acknowledgement and freshness use the same loaded sync state and assessment clock; the endpoint performs no second sync-state SELECT.

404 behavior:

- Unknown stablecoin ID
- Tracked coin without live reserve support
- Pre-launch or effectively suspended coin

Known live-enabled IDs with no usable snapshot or curated/template fallback return HTTP `200` with `mode: "unavailable"`, empty `reserves`, and live `sync` state. This distinguishes supported coins awaiting usable data from unknown or unsupported IDs.

When a review matches current attempt evidence, `sync.acknowledgedFeed` publishes the complete dated review. It does not change response mode, cache admission, reserves, provenance, or freshness; absence means no currently valid matching acknowledgement.

Successful responses return `StablecoinReservesResponse` with one of these modes:

| Mode                | Meaning                                                                                    |
| ------------------- | ------------------------------------------------------------------------------------------ |
| `live`              | Fresh live snapshot from `reserve_composition`                                             |
| `live-stale`        | Stored fetch is older than 48 hours, or verified source evidence exceeds its configured/adapter reporting allowance (48-hour fallback only when neither declares one) |
| `curated-fallback`  | Live snapshot unavailable; falling back to curated `StablecoinMeta.reserves`               |
| `template-fallback` | Live snapshot unavailable; falling back to reserve templates from `getReserves()`          |
| `unavailable`       | Coin is live-enabled, but neither live data nor fallback reserve presentation is available |

`live` / `live-stale` only apply when the stored snapshot matches the latest successful sync state by `fetched_at` / `attempt_id` and passes strict integrity validation. Staleness independently checks the stored fetch time against 48 hours and verified upstream source age against the source-specific allowance. The detail response, overview freshness counts, and scoring snapshot loader share this decision; refreshing an old document never resets its source age. Orphaned partial writes or corrupt stored snapshots fail closed to the fallback modes.

Per ADR-30 the response publishes the policy values behind that verdict, not only the verdict. `sync.freshness` is the evaluator's own output, copied unchanged: the served snapshot reuses admission's assessment, while fallback and unavailable responses judge the newest consistent generation (else `sync.lastSuccessAt`) by fetch age alone. `fetchBudgetSec` is the budget the serving route actually passed (`LIVE_RESERVE_FRESHNESS_SEC` for `GET /api/stablecoin-reserves/:id`). A client can recompute the verdict: `stale` is `fetchAgeSec > fetchBudgetSec`, or `sourceAgeSec > sourceAgeBudgetSec` when the source fields are non-null. Both ages are measured at `assessedAt`.

`StablecoinReservesResponseSchema` in `shared/types/live-reserves.ts` is the runtime contract for successful `200` responses, including `unavailable`, and is used by the frontend reserve API client. Adapter-specific `metadata`, `metadata.details`, and nested redemption telemetry remain passthrough. Internal instrumentation lives in declared `metadata.diag`, which `resolveReserveResult()` removes before public serialization.

| Response mode                               | Cache-Control                        |
| ------------------------------------------- | ------------------------------------ |
| `live` (sync `ok`, no uncertain write)      | `public, s-maxage=3600, max-age=300` |

| `live-stale`                                | `public, s-maxage=1800, max-age=120` |

| ----------------- | ------------------------------------------------------------------------------------- |

| Field   | Meaning                                                                                      |
| ------- | -------------------------------------------------------------------------------------------- |

`displayBadge` is intentionally separate from `mode` and `provenance`:

- `mode` answers whether an authoritative snapshot exists and whether it is stale
- `provenance` answers scoring/evidence semantics
- `displayBadge` answers the honest user-facing reserve label

The optional `displayUrl` and `evidenceUrls` fields are also intentionally separate:

- `displayUrl` is the curated reserve-card destination configured in `liveReservesConfig.display.url`
- `evidenceUrls` are adapter-emitted URLs tied to the authoritative live snapshot metadata
- the detail page can show both when a coin has a curated overview page plus narrower evidence links for the exact live snapshot

The optional `metadata` object is also present only for authoritative `live` / `live-stale` snapshots. It exposes the adapter snapshot metadata already stored with the reserve snapshot row so the UI can surface feed-specific context without re-querying D1. For example, `crvusd` now exposes `yieldBasisCollateralPct` when Yield Basis positions account for part of the live reserve mix.

The optional `sync` object exposes the last operational state:

| Field             | Meaning                                                                                                                             |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `enabled`         | Effective live configuration exists; this does not mean the coin is scheduled                                                        |
| `collectionEligibility` | Current `{ scheduled, reason }` policy; successful responses permit only `active`, `quarantined`, `frozen`, `delisted`, with `scheduled: true` only for active |
| `status`          | Last sync status (`ok`, `degraded`, `error`, `skipped`)                                                                             |
| `stale`           | Fetch/source age exceeds its budget, or the Worker fetch clock is invalid (including a future fetch; negative age is retained)       |
| `bootstrap`       | No successful live snapshot has been recorded yet                                                                                   |
| `lastAttemptedAt` | Latest attempt timestamp, when present                                                                                              |
| `lastSuccessAt`   | Latest success timestamp, when present                                                                                              |
| `warnings[]`      | Warning messages surfaced by the latest attempt and, when relevant, storage-integrity warnings injected by the fail-closed resolver |
| `lastError`       | Most recent adapter error message (truncated to 200 chars), when present                                                            |
| `failureCategory` | Machine-readable failure class from attempt metadata, when present                                                                  |
| `uncertainWrite`  | `true` when the latest attempt hit the D1 write-timeout / finalize-rejection path and authoritative state could not be proven       |
| `freshness`       | The budgets, clock, and generation behind `stale` (table below)                                                                     |

For an active newly configured feed, `status: "skipped"`, `bootstrap: true` with no attempt/failure evidence is awaiting its first scheduled sync and receives the neutral **Live reserve sync pending** notice. A readable inactive configuration may expose the same synthetic bootstrap without any attempt clock; `collectionEligibility.scheduled: false` explains lifecycle exclusion, not circuit/budget deferral or a persisted skipped attempt. Historical snapshots keep their original clocks and admission verdicts; collection diagnostics neither refresh nor re-admit them. Attempt or failure evidence keeps its separate degraded/error presentation.

Suspended, unconfigured and pre-launch assets return `404` from the reserve endpoint rather than inventing successful-response eligibility reasons.

`sync.freshness` fields (added 2026-09-27; additive and optional in `StablecoinReservesResponseSchema`, so older payloads still parse):

| Field                | Meaning |
| -------------------- | ------- |
| `stale`              | Same verdict as `sync.stale` |
| `staleReasons[]`     | `fetch-age`, `source-age`, or `invalid-fetch-clock`; empty when fresh |
| `assessedAt`         | Unix seconds: the evaluation clock for both ages |
| `fetchedAt`          | Worker fetch time of the judged generation; `null` when no successful fetch is known |
| `attemptId`          | Sync attempt of the judged generation; `null` for legacy rows written before attempt IDs |
| `fetchAgeSec`        | `assessedAt - fetchedAt`, or `null` |
| `fetchBudgetSec`     | Fetch-age budget the serving route used |
| `sourceTimestamp`    | Upstream disclosure time judged. `null` when source age was not part of the verdict: non-`verified` freshness, no finite timestamp, or a fallback response |
| `sourceAgeSec`       | `assessedAt - sourceTimestamp`, or `null` |
| `sourceAgeBudgetSec` | Effective source-age budget: `min(scoring.maxSourceAgeSec, adapter validation.maxSourceAgeSec)`, else the fetch budget; `null` when source age was not judged |
| `sourceAgeBudgetCap` | Which cap won: `scoring` (per-coin cap, including ties), `adapter`, or `fetch-budget`; `null` when source age was not judged |

Uncertain write attempts are intentionally exposed as `sync.uncertainWrite = true` instead of being collapsed into generic stale/error narration. The API may still serve the last consistent snapshot or fallback presentation, but operators can tell that the latest attempted write is ambiguous until a clean follow-up run resolves it. Detail-page polling uses the normal 4-hour reserve cadence only for clean live responses; live responses with `sync.status !== "ok"` or `sync.uncertainWrite = true` use recovery polling and render the active status, failure category, and last error above the reserve card footer.

### Edge Cache Implications for Monitoring

A `live` response with a healthy sync (`sync.status === "ok"` and no uncertain write) is edge-cached for 1 hour (`s-maxage=3600`). When the latest sync is not `ok` or has an `uncertainWrite`, the same `live` response uses the fallback edge cache (`s-maxage=300`, 5 minutes) so the frontend's 2-minute recovery polling can observe the failure and its recovery instead of being served a stale healthy `sync` block for up to an hour.

**For real-time monitoring**, use the Access-gated admin surface (`/admin/`, backed by admin-only `GET /api/status`), which is never edge-cached and always reflects current D1 state.

Fallback, template-fallback, and unavailable responses use a shorter edge cache (`s-maxage=300`, 5 minutes). `live-stale` responses use an intermediate cache (`s-maxage=1800`, 30 minutes); healthy live responses use `s-maxage=3600` (1 hour).

### Collateral positions and credit vaults

`collateral-positions-api` can now optionally attach direct redemption-capacity telemetry alongside the collateral mix when a reviewed bridge-backed stable exit exists. `zchf-frankencoin` uses this path to publish the current CHFAU StablecoinBridge inventory as `redemption.capacityUsd` for redemption-backstop modeling without changing the reserve-slice composition itself. Until Frankencoin's price API publishes CHFAU directly, this route values the CHFAU bridge balance through the existing VCHF CHF-price proxy. `deuro-deuro` uses the same adapter's nine-bridge basket path: each configured StablecoinBridge must pass its underlying-token, decimals, dEURO, and `isMinter` identity checks before its idle inventory is summed, and the summed EUR face is converted to USD at the same-run EUR/USD reference read from the dEURO price payload. That reference is the basket output's peg *expectation*, never its observed value: `redemption.outputValuation` is published only when every weighted output token carries its own price in the same payload, with the observed unit value being the weighted member USD prices, the expected unit value the EUR/USD reference, and `capacityUsd` the measured inventory's market value. When any member is unpriced the valuation is withheld with `outputValuationUnavailableReason: "output-tokens-unpriced"` and capacity stays the nominal FX conversion of the measured face amount, so an unpriced member can never be scored at par (R1).

The `collateral-positions-api` assets-to-liabilities ratio requires a parseable outstanding debt and validated debt-token decimals for every open, non-denied position; collateral decimals are never a debt-unit fallback. Frankencoin rows supply `minted` in `zchfDecimals` priced through `zchf`; dEURO rows supply `principal` plus `interest` (the API's live `Position.principal()` and `getInterest()` reads, together `getDebt()`) in `deuroDecimals` priced through `deuro`. The field family is chosen per row, and a row carrying both or neither family emits `unparseable-minted-balance`. Explicit zero debt needs no price observation, while positive debt requires its identified token's finite positive USD quote. Incomplete liabilities emit `liability-coverage-incomplete` and withhold both total USD liabilities and the ratio, preserving independently valid reserve slices. Debt price clocks qualify the ratio separately from the composition clock: missing clocks, quotes older than the existing two-day `LIVE_RESERVE_FRESHNESS_SEC` budget, or clocks beyond `MAX_FUTURE_SOURCE_TIMESTAMP_SKEW_SEC` (ten minutes) emit `liability-price-freshness` and withhold the ratio and liability valuation without replacing the collateral basket's own freshness timestamp.

`cap-vault` reads Cap cUSD's Ethereum vault state directly. Reserve slices are based on each supported asset's total supplied balance, while redemption-capacity telemetry uses unpaused available balances after borrows so the route does not treat borrowed or paused collateral as immediate exit capacity. The adapter emits nested `metadata.redemption` with `capacityKind = "live-direct-bounded"`, `freshnessKind = "same-run-onchain"`, `routeStatusSource = "onchain"` from per-asset pause checks, and zero-second settlement-delay telemetry. For the current USDC + WTGXX proportional basket, the same producer also reads WTGXX's tracked Chainlink NAV feed, fails the snapshot closed when that required NAV is missing, invalid, future-dated, or stale, and pins the complete value weights plus reserve-value-per-cUSD output unit. This source-bound output valuation is carried with its oracle address and timestamp; it is not inferred from the WTGXX symbol or the configured route output list.

`3jane-usd3` reads USD3's Ethereum strategy, MorphoCredit market, waUSDC conversion, and idle USDC accounting directly. It splits the strategy NAV between the pro-rata liquid waUSDC/USDC buffer and deployed private-credit exposure, then uses `availableWithdrawLimit(address(0))` as direct bounded USDC redemption capacity. The same-run telemetry also carries shutdown state and the documented zero withdrawal fee. The September 25, 2026 USD3 proxy upgrade (block 26057337) deleted the deposit-commitment feature — `minCommitmentTime()` no longer exists and no withdrawal or transfer path reads the ProtocolConfig commitment knob — so the commitment observation and the `cohort-limited` route it fed were removed in the September 26, 2026 implementation review, which verified that `nav()`, `balanceOfWaUSDC()`, `suppliedWaUSDC()`, `getMarketLiquidity()`, and `availableWithdrawLimit(address)` (now also net of ring-fence/redemption floors) keep their reviewed semantics at the new implementation.

`idle-cdo-epoch-variant` reads an Idle/Pareto credit vault's own epoch accounting. These vaults are deliberately not ERC-4626 — `asset()` and `totalAssets()` revert, and deposited underlying is forwarded straight to the whitelisted borrower's wallet — so the adapter uses the CDO's `getContractValue()`, `lastNAVAA()` / `lastNAVBB()`, `epochDuration()`, `epochEndDate()`, `defaulted()`, and `isEpochRunning()`, plus the tranche's `totalSupply()` and `minter()`, in one multicall round. `getContractValue()` is by construction the unlent underlying balance plus the valued receivable, so `getContractValue() - underlying.balanceOf(cdo)` is exactly the borrower receivable with no double counting. The receivable is published as a `private-credit` slice **with no `coinId`** — it is not a claim on the deposit token, and linking it would present a single-obligor loan book as that token's reserves; the cash-equivalent slice is emitted only when the vault actually holds an unlent balance, never assumed. The vault's `token()`, `AATranche()` / `BBTranche()`, and the tranche's `minter()` are all verified against config before any composition is published. The credit slice's liquidity horizon comes from the structural `epochDuration`, not the time remaining in the current cycle, and drops to `unknown` once `defaulted()` is true. A senior tranche with no live junior NAV beneath it degrades with `idle-cdo-no-junior-subordination` rather than being re-rated upward for its seniority label. When the config declares `expectJuniorTranche: false` for a reviewed single-tranche vault — as `aa-falconx-mev-capital` does — the missing junior is recorded as an `info` structural risk fact instead of a `degraded` warning, leaving the first-loss reality on the slice's `risk`/`riskFactors`. NAV reconciliation compares the tranche NAV sum against `getContractValue()` net of `unclaimedFees()`, so accrued protocol fees alone no longer manufacture a reconciliation degrade. The adapter declares no redemption telemetry: the monthly epoch exit's stressed depth is not observable on-chain, and publishing capacity from NAV would fabricate it. `aa-falconx-mev-capital` binds this adapter; it keeps `variantOf: usdc-circle` and its serial USDC dependency edge while its backing is scored from the honest composition instead of inherited from Circle.

Idle's canonical coverage is whole-vault holder backing (`getContractValue() - unclaimedFees()`) divided by the combined AA/BB NAV liabilities. These exact amounts are published as `totalReserveUsd` and `supplyUsd`, so the ratio is reproducible and protocol-owned fees cannot raise holder coverage. Gross contract value and fees remain diagnostics; composition is explicitly `gross-vault-assets`, not an attributed tranche-loss allocation.

`origin-vault-balances`, `blast-usdb-yield-manager`, and `nest-vault-positions` cover additional strategy-vault reserve sources without widening generic adapters. Origin reads OUSD Vault `checkBalance(asset)` plus `totalValue()` so only mapped assets are credited, and it separately reads idle ERC-20 `balanceOf(vault)` as direct bounded redemption capacity while excluding deployed strategy balances. The vault contract publishes no ERC-20 `decimals()` of its own, so `totalValue()` is scaled by `decimals()` read from the tracked coin's own deployment at the same pinned block, required to equal that deployment's reviewed decimals (otherwise the attempt fails closed) and published as `details.totalValueDecimals`; an assumed scale would misplace the `Unmapped Origin vault exposure` remainder by twelve orders of magnitude. Blast reads Ethereum USDYieldManager `totalValue()` and reconciles it against Blast USDB supply. Nest consumes the Nest Alpha Vault positions, NAV, and last-price-update APIs, preserving the latest verified update timestamp, classifying tokenized JTRSY/USTB fund shares at the existing `low` tokenized-layer tier, and grouping private/structured vault exposure as high risk. nOPAL and nBASIS additionally reconcile explicitly reported pending deposits using strict pending-transaction validation; pending subscriptions remain a separate high-risk unknown slice and are never counted as settled fund shares. Positive pending withdrawals remain fail-closed except reviewed receivables (nBASIS Superstate USCC redemptions; nOPAL redemptions against any vault position, admitted 2026-09-25 after a 2026-08-28..31 liquid-stone redemption stayed in flight across 19 consecutive snapshots): the issuer sibling `/calculated-price` endpoint must corroborate settled positions plus all pending movements against gross NAV, and gross NAV less nonnegative claimable fees against net NAV, each within $0.01, with no upstream errors. The corroborated net NAV must also match the vault's own `/price.nav`, the second valuation of the same vault, within a documented cross-source tolerance (1e-4 relative with a $1 absolute floor; live reads differ by ~$0.13 on a $184k NAV): a divergence fails the attempt closed naming both values as `corroboration-mismatch` rather than suppressing the published-NAV residual and reporting reconciled coverage over a contradiction. Admitted receivables remain a separate high-risk unknown slice; total reserves use corroborated gross NAV while calculated net NAV and fees remain separate metadata. Missing, malformed, or mismatched corroboration fails closed. Other Nest vaults retain settled-only accounting. Any Nest vault whose mapped positions (plus admitted pending deposits) cover less than its reported NAV now publishes an explicit high-risk `Nest NAV reconciliation residual` slice and `unknownExposurePct`, rather than silently dropping the unexplained share (previously gated to nOPAL).

Nest retains positive measured holdings through valuation and aggregation with the slice-math `decimals` argument set to `null` (`slicesFromValues(values, null)`). Normalization still validates totals and grouping identity, but does not round dust to zero or repair source drift by changing the largest slice.

Nest recognizes liquid `USDG` as `nest-vault-positions:usdg` with `coinId: usdg-paxos`, allowing an exact join to its reviewed reserve metadata. Unrecognized liquid symbols retain `nest-vault-positions:unknown` without inheriting USDG's identity or classification.

`escrow-balance` covers coins whose exit route is paid out of one pinned escrow or reserve contract, where redemption capacity is a single token-denominated view read. The contract, 4-byte selector, pre-encoded 32-byte argument words, and escrowed-asset decimals are all config-owned, so the adapter never resolves the escrow from the tracked coin's own deployments — necessary because the escrow usually sits on a different chain from the circulating token. ### Adapter helper contracts

Adapter helpers now live in a small helper family, with `worker/src/cron/reserve-adapters/helpers.ts` kept as the shared import surface:

- HTTP JSON / HTML / binary fetch wrappers (`fetchJsonWithRetry`, `fetchTextWithRetry`, `fetchBinaryWithRetry`); response bodies are consumed inside the per-attempt timeout, and every failed body (oversized, aborted, HTTP error) is cancelled so connections return to the six-request budget
- Request-cache identity uses the effective case-insensitive merged `Headers` sent on the wire, plus timeout/retry/body-cap and JSON redirect policy (`follow` by default). `follow`, `error`, and `manual` do not share results. JSON GET/POST requests with `onResponse` bypass both retained results and pending-request coalescing so each observer receives its own actual responses, including retries; the same two-operation I/O limiter, body deadline/cancellation, and intake accounting still apply. Cache retention remains 16 MiB total and 4 MiB per entry.
- Decimal issuer amounts (`strict-amount.ts`) accept finite numbers or trimmed signed decimal text, including `.5`, `1.`, and scientific notation. Radix text, empty text, non-scalars and nonfinite conversions are rejected. `allowGrouped` instead requires correctly sized comma groups or an integer with optional nonempty fractional digits, without exponents or `.5`/`1.` forms. `parseFiniteNumber` throws with the caller's label and optional inclusive minimum; `parsePositiveNumericLike` returns null for invalid or nonpositive values. Genuine zero remains an observation when the caller permits it. ABI hexadecimal quantities and bigint digit strings have separate readers.
- Source clocks (`freshness.ts`) validate Gregorian calendar and clock/offset components before conversion; impossible dates cannot roll into another month. Calendar parsing uses known millisecond units, independently of numeric epoch heuristics. Date-only values use UTC midnight; zoneless datetimes require an explicit source-reviewed `assumed-utc` policy (Sky only), not the host timezone or a claim that the publisher asserted UTC. Accountable's `YYYY.MM.DD HH:mm:ss UTC` remains supported; ambiguous slash dates require a caller-owned format policy. Optional-alternative summaries return null when no clock parses. Material-coverage summaries retain valid/missing counts with nullable extrema/spread even for empty or all-bad input; any missing material clock withholds verified freshness.

### Adding a New Adapter

Research intake uses `npm run audit:coverage -- --domain=reserve-coverage`. It is a permanent advisory report, not an adapter admission evaluator, and rejects unsupported `--check`. `--prod` reads report-card and stablecoin catalog snapshots only. Supply `--reserve-states <file>` separately for reserve-sync observations and retain the supplied state generation; without that file, runtime state is unknown rather than inferred from configuration or a successful catalog fetch.

To register a new adapter for a coin's `liveReservesConfig.adapter`, edit these surfaces in order: **5 files, 6 edit sites** (4 files / 5 sites when the adapter takes no per-coin params). The shared schema and Worker registry tests fail if definition or fetcher coverage drifts.

1. **Params schema + descriptor declaration** — both live in `shared/types/live-reserve-adapter-declarations.ts`. Define the Zod params schema as a const above the table (or reuse `noParamsSchema` / an existing schema), then add one entry to `LIVE_RESERVE_ADAPTER_DESCRIPTOR_DECLARATIONS` whose `paramsSchema` **references that schema object directly** — there is no separate schema module and no string identifier to register. Declare accepted primary input kinds, source/evidence class, source-sharing policy, supported semantics/versions, redemption telemetry, validation policy, and only non-default provenance or display metadata. Prefer a named validation tier from `shared/types/live-reserve-adapter-policy.ts` (`LATEST_STATE_VALIDATION`, `DASHBOARD_VALIDATION`, `DASHBOARD_WITH_UNKNOWN_CAP_VALIDATION`, `MONTHLY_VERIFIED_VALIDATION`, `LATE_MONTHLY_VERIFIED_VALIDATION`, `DISCLOSURE_VALIDATION`, …); an inline `validation` block should carry a comment explaining why the adapter is an exception. EVM addresses use `EvmAddressSchema`, never a bare `z.string()`. The key union, `LIVE_RESERVE_ADAPTER_KEYS`, and the enriched `LIVE_RESERVE_ADAPTER_DEFINITIONS` map all derive from this entry.
2. **Adapter fetch function** — add `worker/src/cron/reserve-adapters/<key>.ts` exporting `async function fetch<Name>Reserves(coin, config, signal, ctx?): Promise<AdapterResult>`. Adapter contract lives in `worker/src/cron/reserve-adapters/types.ts` (`AdapterFn`, `AdapterContext`, `ReserveAdapterDefinition` — the last is a `Pick<>` of the shared declaration, so declaration fields reach the Worker without being re-declared). Use helpers from `./helpers` rather than rebuilding fetch/parse/freshness primitives.
3. **Worker fetcher wiring** — add a `lazyAdapter(() => import("./<key>").then((mod) => mod.fetch<Name>Reserves))` entry to `LIVE_RESERVE_ADAPTER_FETCHERS` in `worker/src/cron/reserve-adapters/index.ts`. This stays a hand-written map because Worker implementations cannot enter the runtime-neutral shared registry and several keys deliberately share one fetcher; its `Record<LiveReserveAdapterKey, AdapterFn>` annotation makes a missing key or invalid named export a compile error, and `registry.test.ts` fails on the same coverage gap. Keep implementation imports inside these factories so inspecting the registry does not initialize the entire adapter graph.
4. **Coin config** — bind the coin's `liveReservesConfig` in `shared/data/stablecoins/coins/<id>.json`. A `params` block is required whenever the adapter's schema rejects `{}`.
5. **Adapter test and fixture** — add `worker/src/cron/reserve-adapters/__tests__/<key>.test.ts` and capture an HTTP-html fixture when applicable. HTML, JSON, and txt fixtures are all age-gated by `scripts/ci/check-html-fixture-age.ts` under the same `captured-at` stamp rule; a JSON or txt fixture that cannot carry the HTML-comment header is exempted in that script with a documented reason.

Changed reserve capture files select `npm run check:html-fixture-metadata` in the PR static guard plan. It validates canonical UTC second-precision stamps (`YYYY-MM-DDTHH:MM:SSZ`), real calendar dates, recorded provenance or explicit legacy exemptions, and refresh-inventory integrity without consulting calendar age. The weekly `check:html-fixture-age` retains the 90-day expiry and future-clock checks. The HTML capture writer truncates milliseconds rather than rounding; JSON captures can record the same comment in a `_capture` field without changing the captured payload's own clocks.

Docs are not a per-adapter step: the Adapter Registry notes above are for non-obvious semantics only, and the roster/counts are derived from the declaration table rather than copied.

For report-backed issuers, reuse `fetchIndependentAssuranceAdapter` in `independent-assurance.ts` when the existing generic engine owns the transport/parser contract. Agora, Anchorage, AUDD, CADD, FDUSD, RLUSD and SBC keep discovery/date/classification data in `*-independent-assurance-profile.ts` modules; they do not add forwarding fetchers. `IndependentAssuranceProfile` is defined in `types.ts`. Gemini, Paxos, FIDD and BRLA retain specialized orchestration. New material-clock consumers must submit every material contributor to the coverage summary and name any reviewed zoneless policy; do not drop all-bad coverage or manufacture a verified clock.

Minimal scaffold (HTTP-json single-asset shape):

```ts
import type { StablecoinMeta } from "@shared/types/core";
import type { LiveReservesConfig } from "@shared/types/live-reserves";
import { parseLiveReserveAdapterParams } from "@shared/lib/live-reserve-adapters";
import type { AdapterContext, AdapterResult } from "./types";
import {
  fetchJsonWithRetry,
  freshnessMetadataFromTimestamp,
  parseTimestampLikeToUnixSeconds,
  requireJsonInput,
} from "./helpers";

interface MyAdapterPayload {
  totalReserves: number;
  updatedAt?: string;
}

export async function fetchMyAdapterReserves(
  _coin: StablecoinMeta,
  config: LiveReservesConfig,
  signal: AbortSignal,
  ctx?: AdapterContext,
): Promise<AdapterResult> {
  const input = requireJsonInput(config.inputs.primary, "my-adapter");
  const params = parseLiveReserveAdapterParams("my-adapter", config.params);
  const payload = await fetchJsonWithRetry<MyAdapterPayload>(input.url, signal, 12_000, ctx);
  const sourceTimestamp = parseTimestampLikeToUnixSeconds(payload.updatedAt);

  return {
    slices: [{ name: params.assetLabel, pct: 100, risk: params.assetRisk }],
    metadata: {
      ...freshnessMetadataFromTimestamp(sourceTimestamp, "issuer-api", "payload has no source timestamp"),
    },
  };
}
```

## Scope Boundaries

- Live reserve sync is detail-page and status-surface infrastructure, not a replacement for curated reserve metadata everywhere else.
- [Safety Score V9](./report-cards.md) uses fresh authoritative independent live reserve slices as Backing reserve exposures when available. `dynamic-mix` adapters can qualify when the retained snapshot passes the shared admission gates, regardless of a later failed attempt; only a subset of `single-bucket` adapters carry `evidenceClass = independent`, while `validated-static` / `weak-live-probe` feeds remain detail/status data only. The compiler reconciles accepted tracked slices to effective dependency edges, and falls back to reviewed static/curated rows only when no accepted live rows were captured.
- Reviewed metadata joins to live reserve rows by unique adapter-owned `sourceKey` when present, with unique normalized-name matching retained only for unkeyed compatibility captures. Percentages never define the join, and classification plus dependency compilation share the same matched identities.
- Blacklist attribution no longer treats live reserves as invisible just because most adapters lack `coinId` links. The report-card resolver enriches both live and curated reserve names with the same blacklist clue pipeline, then resolves inherited exposure to a fixed point across the tracked set so cyclic upstream graphs do not depend on traversal order. The collateral drift alert only compares comparable live reserve mixes: snapshots must still resolve to at least two live slices after normalization, so single-bucket proofs and collapsed one-slice snapshots do not generate noisy curated-vs-live drift alerts.
- [Dependency Map](./dependency-map.md) remains authoritative for graph behavior; dependency edges come from the effective V9 dependency fact set, including accepted live reserve links when present and reviewed static/curated reserve metadata plus manual dependencies on the defined fallback path.
