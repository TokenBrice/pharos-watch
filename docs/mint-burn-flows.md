# Mint/Burn Flow Tracker

> **Agent navigation** — Read the needed contract: Publication admission · Registry ownership · Open USD coverage review · Raw Token Conservation · Daily operator invariant · Sync Algorithm · Scoring · Valuation Completeness · Retention · API Endpoints · Valuation Completeness Rendering · Circuit Breaker Separation. The registry owns the changing source roster; source and operator references use absolute URLs so this public page remains navigable.

On-chain mint and burn event tracker for stablecoins on their **configured issuance chains** via JSON-RPC. EVM scans use admitted full-log Dwellir before Alchemy; USDT Tron uses the admitted native Dwellir reader with TronGrid JSON-RPC fallback. Detects Transfer events (and USDT-specific Issue/Redeem events), aggregates them into hourly flow buckets, exposes per-coin raw `Net Flow` plus baseline-relative `Pressure Shift vs 30D`, computes a market-cap-weighted Bank Run Gauge, and flags flight-to-quality signals. Live ingestion runs in two lanes: a critical 30-minute lane for major coverage and an offset extended hourly lane (`:18`) for long-tail backlog drain.

Product scope note: the public `/flows` page surfaces the admitted issuance scope plus per-coin `coverage` metadata so partial history, lagging sync, or unknown current chain-head states are visible to users instead of implied as complete market-wide coverage. Pending and disabled legs are named separately in `publication.legs`. Configured scope includes Ethereum for most tracked assets, USDT on Tron, USDai on native Arbitrum and Base Dollar on native Base. A configured chain joins published scope only after admission.

Configured contracts, exact start blocks, decoder/bridge bindings and dust thresholds are owned by `MINT_BURN_CONFIG_SPECS` in `worker/src/lib/mint-burn-contracts-data.ts`, not a release roster here. A configured start is not observed history: scheduled catch-up must establish durable coverage and a fresh frontier before publication admission. Other native deployments are not implicitly included. Fund-share mints can represent dividend reinvestment as well as subscriptions; token creation is not necessarily new investor cash.

The `/flows` page leads with the Bank Run Gauge hero (see [Page](#page)); its printed, shredded and net 24h facts and the folded 7-day receipt (weekly totals, top 7-day minter and burner, coverage) use the existing 24-hour coin rows and 7-day hourly buckets. Their labels deliberately describe observed configured-chain events; they do not claim complete market-wide supply creation or redemption.

Operational freshness configuration is shared via `worker/src/lib/mint-burn-health-config.ts`:
- major-symbol baseline (`USDT`, `USDC`, `DAI`, `USDS`, `GHO`, `FRXUSD`, `BOLD`, `reUSD`)
- warning threshold (`6h`)
- critical threshold (`24h`)

Scheduled/http handlers apply env overrides on top of these defaults (`worker/src/handlers/scheduled.ts`, `worker/src/handlers/http/request-dispatch.ts`). Public `/api/health` now keys mint/burn freshness to the critical-lane sync timestamp / run status (the same semantics exposed by `/api/mint-burn-flows`) so quiet majors do not falsely mark the health surface stale just because no new events occurred.

Public `/api/mint-burn-flows` freshness assesses the confirmed critical-lane flow-generation clock using the shared availability ratios, not the latest attempt or cache write. The effective budgets are returned in `_meta.freshBudgetSec` / `degradedBudgetSec` (currently 8h / 12h); these endpoint availability bands are separate from lane escalation and the tighter Safety Score consumer budget used only by flight-to-quality.

Fresh and cached flow responses without a sync timestamp retain their body sync warnings and return `Cache-Control: no-store`, `X-Data-Age: unavailable`, and HTTP `Warning: 199`. Neither response-generation time nor cache-write time substitutes for the missing sync clock.

The detail flow card preserves that producer generation through successful refetches and failed refreshes with saved totals. Its local health notice shares the endpoint budgets and warning floors, ages without another fetch, and leaves an explicit unknown clock unavailable. Like the detail page health strip, it excludes only the typed flight-to-quality dependency and its matching advisory because the card renders coin totals, not the market-wide classification.

Mint and burn events measure token creation and destruction, not investor intent. USDai is the reviewed counterexample: a burn can release PYUSD from the hub for sUSDai loan deployment without an equivalent fall in protocol assets. Since methodology v6.21, individually reviewed events of this kind are tagged `flow_type='protocol_internal'` and leave counted flow; see [Reviewed protocol-internal events](#reviewed-protocol-internal-events). The public FAQ and USDai's curated chart annotation keep the measured burn visible without calling it a redemption or investor outflow.

## Cron Schedule

The critical lane runs every 30 minutes at :04/:34; the extended lane runs hourly at :18. The critical job retains `sync-mint-burn` for freshness and escalation; `sync-mint-burn-extended` has its own rotation/run-state key and warning-only backlog semantics. USDT Tron shares the critical tier with USDT Ethereum. Enabled, admitted Dwellir runs before the chain's incumbent fallback ([provider order](#circuit-breaker-separation)).

Extended-lane health is a **full-pass verdict**, not a per-config age clock. `updateMintBurnAttemptState()` (`worker/src/cron/mint-burn/run-state.ts`) records the current pass start and the last completed pass in `mint-burn:attempt-state:sync-mint-burn-extended`; a pass completes only when every enabled config was actually attempted (or proven up to date) since that start; a provider deferral or an absent attempt record is evidence, not coverage, and cannot complete a pass (ADR-29). `completeMintBurnRun()` degrades the lane when the running pass exceeds `MINT_BURN_EXTENDED_COVERAGE_WINDOW_SEC` — 4 × the extended lane interval (240 min) — or a genuine failure exists (`apiErrors > 1`, a conservation mismatch, or a failed state/cache write). Rotation inside the window never degrades. Metadata publishes `coverageCycle.status` (`cycle-in-progress` while no pass has completed — neutral, never healthy-by-default; `complete` once a pass has finished and the running one is still inside the window; `stalled`), `coverageCycleSec` (duration of the last completed pass) and `expectedWindowSec`. The check runs at each lane start, so `stalled` appears on the first run whose pass age is strictly greater than the window. The critical lane keeps its coverage-ratio rules and publishes no cycle block. Losing the cache restarts the pass, so a cold lane reports `cycle-in-progress` rather than latching a stale age.

Extended placement precedes the `:22/:52` Safety Score fence to avoid overlapping its publication chain. Each physical alias is hourly: combining aliases into one sub-hourly expression would reduce Cloudflare's CPU class to 30 seconds, the exhaustion mode recorded as `platform-abandoned`. The [schedule and dispatch owner](https://github.com/TokenBrice/pharos-watch/blob/main/docs/worker-infrastructure.md#cron-scheduling) owns expressions; [per-job timeouts](https://github.com/TokenBrice/pharos-watch/blob/main/docs/worker-and-api-limits.md#per-job-cron-timeouts) own runtime ceilings.

`syncMintBurn()` returns actual inserted rows as `itemCount`, plus status and bounded lane/config coverage diagnostics. When a targeted sync warning exists, the UI suppresses a duplicate generic stale banner. Cached fallback preserves freshness-derived headers, not an extra transient-query warning while the dataset is fresh.

## Constants & Thresholds

The contract registry owns per-config dust thresholds, start blocks and lane selection. Dust is measured in token-native units; configured overrides are necessary where unit economics differ. Established coverage becomes lagging when a config's block progress trails its own lane's cadence translated to chain blocks: the public freshness cadence (1 hour) for critical configs, the extended lane's `MINT_BURN_EXTENDED_COVERAGE_WINDOW_SEC` full-pass window (4 hours) for extended configs (v6.36). Lag is measured against the newest finalized head from either lane; an extended-lane head counts only within that window.

The [Scoring](#scoring) section owns pressure/activity/flight-to-quality parameters. The [operational budget table](https://github.com/TokenBrice/pharos-watch/blob/main/docs/worker-and-api-limits.md#mint-burn-and-producer-metadata-budgets) owns global/per-config request caps, scan limits and self-deadline; they are not additive per-contract allowances. [Sync Algorithm](#sync-algorithm) owns finalized scan admission.

### Publication admission

`worker/src/lib/mint-burn-publication.ts` owns publication membership, separately from ingestion eligibility. A new leg is `pending-admission` until durable, current-fingerprint scan proof continuously covers the required 90-day window through the incumbent publication watermark and its own frontier is fresh within `MINT_BURN_WATERMARK_MAX_AGE_SEC`. Ninety days is required by `netFlow90dUsd`, even though pressure uses a 30-day baseline. Gaps, dirty materialization and earlier fingerprints cannot establish that proof. Before admitting a proof-qualified candidate, the flow service applies the existing hourly valuation-completeness rule across that baseline: incomplete or unknown valuation keeps it pending with `valuation-incomplete`, so a newly admitted leg cannot null an incumbent coin's historical USD net. Since v6.38, unresolved or unknown baseline classification also keeps the candidate pending with `classification-incomplete`. A proven zero-event baseline needs no invented prices and can qualify. This admission-only check does not re-gate grandfathered or previously admitted legs. Admission is stored in `mint_burn_admission` by config key, retaining the fingerprint of its original admission evidence. Editing an admitted key does not repeat the 90-day gate or remove it from scanning; current-fingerprint coverage checks still apply to every published window. Isolation requires a durable admission row or accepted native scan-ledger evidence for that key; grandfathered membership, bootstrap absence and legacy cursors alone cannot authorize it. Earlier-fingerprint ledger rows establish prior scanning only and never certify current coverage. A previously admitted active-roster leg with no accepted current proof or a frontier beyond `MINT_BURN_WATERMARK_MAX_AGE_SEC` is an isolation candidate. Candidates expand to every existing sibling sharing the stablecoin/chain bucket before testing survivors. Only a complete active-roster evaluation may persist isolation pauses; partial readers cannot authorize them. Quarantine requires a nonempty incumbent roster proving a fresh common complete closed hour; fresh individual tails alone do not suffice. Otherwise no new pause is persisted and the whole-roster unavailable or stale watermark verdict remains. Once isolated, `publication` reports the leg `pending-admission` / `reactivation-pending`, its key joins `paused_keys`, and every paused sibling must prove the incumbent hour before the bucket re-enters through reactivation catch-up without repeating 90-day admission. A config edit lacking current-fingerprint proof removes its bucket when survivors qualify, until the new fingerprint catches up. Event history keeps serving a quarantined leg's stored rows. Operator conservation diagnostics retain enabled previously admitted or grandfathered members through automatic pauses, alongside current admissions; explicit and shared-bucket disables remain excluded. A valid historical mismatch stays critical until a covering verified pass replaces it; invalid identity or fingerprint evidence remains unavailable. Ordinary window, valuation and freshness rules remain in force for the remaining admitted legs.

Fully isolated coins are absent from `coins` and disclosed in `publication.legs` with their status and reason. Supported pending legs keep scanning and persisting outside publication. The common watermark, per-coin totals and baselines, largest events, gauge weights and consumers of published flows use the admitted scope; a coin continues publishing its admitted legs while another chain catches up. Pending observations are not published as zero, nor included as gross subtotals in an otherwise admitted aggregate. Public `publication` retains its evaluation clock, `requiredBaselineSec` and `freshnessBudgetSec`, with exact `legCount`, `admittedCount`, `pendingAdmissionCount` and `disabledCount`. `legsScope: "non-admitted"` marks `legs` as the complete non-admitted diagnostic subset: config fingerprint, status/reason, admission clock, baseline bounds, covered seconds and frontier age. Missing proof/progress remains null with a reason. Deduplicated `admittedPairs` tuples (`[stablecoinId, chainId]`) preserve exact downstream scope without repeating admitted per-config diagnostics. Readers still accept legacy full-leg payloads without the optional compact fields. Cron metadata bounds its non-admitted samples to 200 legs and 8 KiB with explicit shown/omitted counts.

When a previously admitted or grandfathered active-roster leg is isolated or paused while the coin retains admitted legs (v6.35), the coin keeps the admitted-leg USD net, gross and count subtotals. Its `coverage.isPartial` is true, status is `partial-history`, every `coverage.windows` entry has `complete: false` / `unavailableReason: "scan-coverage-incomplete"`, and the corresponding `has*Window` flags are false. This reuses the existing coverage vocabulary; USD valuation still describes the admitted observations separately. Missing admitted scan evidence and partial valuation retain their existing null-net gates. Never-admitted additions and operator- or registry-disabled legs do not qualify the incumbent coin as partial; only chains that lost an established leg carry incomplete aggregate chain coverage. Fully isolated coins remain absent from `coins`.

Since v6.42, DAI and USDD use reviewed range supply proof and bounded retained repair. Each reader window still withholds its exact net and derived signals while it contains unresolved events or legacy hours with unknown classification. Complete repaired recent windows can recover before longer windows; pruned old hours remain unknown until separately audited historical replay or until they leave that window. Gross counted volumes and event ledgers remain observed subtotals throughout. Admission and the watermark retain their independent evidence requirements.

A partial coin has no full-coin direction or pressure. Its observed admitted-chain `gaugeWeightUsd` remains visible and contributes to `trackedMcapUsd`, but does not enter the gauge score or `scoredMcapUsd`. With the minimum baseline history and admitted 24h scan proof, its withheld weight joins `partialValuationInputs` / `partialValuationMcapUsd`, including when missing-leg activity is unknown; the gauge re-weights over scored coins and retains its existing withheld-weight bounds. The partial coin remains in its Safety-classified FTQ cohort as an unbounded net, including cached reclassification, rather than disappearing or becoming zero. Only the existing proven-inactive range test can retain a verdict; otherwise FTQ is unavailable with `flow-window-unavailable`. Per-coin detail retains admitted-leg totals with partial scan coverage; hourly signed nets and affected aggregate chain nets are unavailable, with gross/count subtotals retained. Admitted chain-level detail remains complete when its own proof is complete. `FlowTable` reuses its Partial history badge and observed-subtotal rendering, `FlowGaugeHero` its Partial coverage chip, and `FlowSummaryCard` its inline partial window labels. Their net cells explicitly opt into admitted subtotals through `resolveCoinNetFlow(..., true)`; aggregate, comparison, export and leader readers retain the default incomplete-window null gate. No captions or new reader copy are added.

The 137 pre-gate keys pinned in the immutable `mint-burn-pipeline/grandfathered-config-keys.json` roster are explicitly grandfathered for membership only (`legacy-grandfathered`), including after source-field edits. The real-config regression check proves those keys preserve the pre-gate publication scope; new keys qualify through ordinary admission rather than extending that roster. The separate legacy-cutover fingerprint list still governs historical assurance. This exception creates no synthetic scan proof and does not extend the separate bounded legacy historical-assurance window. Do not add new keys to that roster to bypass admission.

Storage currently combines contracts sharing a coin and chain into one hourly bucket. Existing siblings therefore form an indivisible publication leg: disabling one removes that shared bucket with `shared-bucket-disabled`, and automatic isolation pauses the whole existing bucket. A new same-coin/same-chain sibling remains `pending-admission` with `unsupported-shared-bucket` and is excluded before scanning, because its rows cannot yet be separated from an admitted sibling's history. Per-contract event/hourly attribution is required before admitting such additions; independent new-chain legs use normal catch-up.

Never-admitted catch-up runs after admitted configs and uses only remaining request/runtime capacity. In the extended lane, returning `reactivation-pending` legs receive a turn after the first half of the rotated admitted roster, before its remaining tail, so reactivation can advance before that tail exhausts capacity. Critical admitted work remains first. Pending head preparation, scans, retries and coverage repairs stop six minutes after run start, capped by any earlier phase deadline; a new pending config requires at least 60 seconds left. An expired pending turn does not stop the admitted tail's later deadline. This leaves roughly four minutes of the ten-minute task timeout for materialization, retention and cache publication, without guaranteeing their latency. Its larger bounded range is reduced to fit the existing per-config cap; global and per-config request ceilings, retry bounds and connection peak do not increase. Event density, timestamps/receipts, provider retries and admitted work can reduce progress.

`MINT_BURN_DISABLED_IDS` accepts stablecoin IDs or exact config keys; the existing `MINT_BURN_DISABLED_SYMBOLS` switch and `enabled=false` also disable publication as well as scanning. A symbol shared by more than one tracked coin cannot name one coin: it disables nothing and logs `mint_burn_disabled_symbol_ignored`, but prior durable disabled keys for that ticker are retained so the rollout cannot silently re-enable a quarantined leg; use the exact ID/config key to change that scope. Each scheduled run persists the effective policy in `mint_burn_publication_policy` before scanning. A policy change atomically invalidates flow caches; later writes must still match that policy. Readers and downstream consumers share the persisted scope, including when the critical lane republishes its gauge. The policy also retains `paused_keys` for explicitly disabled keys, for admitted or grandfathered keys that left the active roster, and for an active admitted leg quarantined by the post-admission frontier gate. Such a pause gates that key's re-admission; an inactive key's pause never withholds its retained per-coin detail, while a stalled active leg is withheld until catch-up. Re-enabling or catching up preserves key membership but keeps a stale leg `pending-admission` with `reactivation-pending` until its current-fingerprint frontier is fresh and proves the incumbent closed hour. This does not repeat the 90-day baseline gate. Shared existing buckets wait together, so an absent sibling cannot become a silently complete chain subtotal. See the [operator rollback procedure](https://github.com/TokenBrice/pharos-watch/blob/main/docs/runbooks/mint-burn-integrity.md#publication-admission-and-operator-disable).

### Registry ownership

Current scope, decimals, contract identity, ingestion tier, start block, and event-decoder configuration are owned by
the complete `MINT_BURN_CONFIGS` registry in `worker/src/lib/mint-burn-contracts.ts`. Do not copy that changing roster
into this document. The registry distinguishes `critical` and `extended` ingestion tiers; those tiers are operational
scheduling choices, not safe/risky classifications. USDT tracks only the contract's Issue/Redeem events (adapter
kind `custom-events`). Ethereum's issuance paths emit no zero-address `Transfer` logs; Tron's matching zero-address
Transfers duplicate its custom events and must not be counted again. Other special decoding and bridge rules remain source-owned.

DEWS defaults configured coins to Ethereum and keeps non-Ethereum canonical-chain overrides in
`worker/src/lib/mint-burn-canonical-chain.ts`; current overrides route USDai to Arbitrum and Base Dollar to Base. A
registry-iterating test requires every coin configured only outside Ethereum to have an override or a documented
exception, while coins with an Ethereum contract retain the Ethereum default. This keeps the hot path lightweight
without letting the side map drift silently from `MINT_BURN_CONFIG_SPECS`.

USDT Tron enters as `pending-admission` and catches up in scheduled critical runs. Its reviewed start block is a coverage floor, not contract genesis; it must precede the 90-day admission baseline with margin. The config fingerprint binds that block, its provenance and the Issue/Redeem event definitions. No pre-activation bootstrap is required. Pending Tron leaves the incumbent watermark, published USDT totals and gauge weights unchanged; it cannot make `netFlow90dUsd` unavailable by joining with a shorter history. Admission requires the full 90-day proof and complete baseline valuation, including any historical price repair needed for eventful hours.

Once admitted, Tron's counted Issue/Redeem events join USDT's published hourly totals, 24h/7d/30d/90d nets and pressure baseline; USDT's preferred gauge weight includes its observed Ethereum and Tron circulating supply. The daily digest re-bins that published Bank Run Gauge and uses its coin nets for flight-to-quality, so it inherits the admitted Tron impact rather than recomputing Ethereum-only flow. DDR's mint-surge input sums all admitted published chains over its event-relative window and therefore includes Tron when that window has coverage and valuation. DEWS's separate canonical USDT chain remains Ethereum. Formulae and each consumer's existing freshness, coverage and valuation gates remain unchanged.

Public `/api/mint-burn-flows` and the daily digest collector use the same canonical V9 flight-to-quality classification. `B-` or better is `safe`; `C+`, `C`, and `C-` are neutral; grades below `C-` are `risky`. Classification requires a complete current `safety-score-v9-publication` identity and becomes unavailable when the accepted publication is missing, held, stale, malformed, or identity-mismatched instead of falling back to a hardcoded safe-haven list.

Aggregate FTQ carries one classification source and machine-readable `gauge.classificationReason`. When classification is unavailable, `flightToQuality` and `flightIntensity` are both `null`, never an inactive/zero observation. Its independent `_meta.dependencies.flightToQuality` entry names the accepted Safety Score publication's `generationId`, original `updatedAt`, assessed age, status/reason and `freshBudgetSec`. That consumer budget is two publication refresh intervals (currently 2h / 7,200 seconds), sourced from `SAFETY_SCORE_V9_CONSUMER_MAX_AGE_SEC`; a fresh flow generation does not renew it.

Fresh materializations, cached reads and fallback reads expose the same FTQ state, dependency evidence, `sync.classificationWarning` and HTTP advisory. Every aggregate cache read re-admits the small canonical index, including previously unavailable entries. A newly admitted identity reclassifies the stored 24h coin nets under the existing valuation gates, removes the old classification warning, and never changes the flow observation or sync clock. Missing/held/stale/index-read-failed sources remain explicitly unavailable. Per-coin responses do not load Safety Scores or carry this market-wide dependency.

Per-config adapter provenance is now surfaced through coin `coverage` metadata:
- `adapterKinds` — active decoding families for the coin (`transfer-zero-address`, `custom-events`, `mixed`)
- `startBlockSource` — whether the earliest tracked block is a reviewed contract-specific bound or a blanket default coverage floor
- `startBlockConfidence` — qualitative confidence on historical completeness (`high`, `medium`, `low`)
- `status` — `full`, `partial-history`, `lagging`, `bootstrapping`, `unknown`, or `disabled`; `unknown` means either no admitted continuous history reaches the selected window end or the chain head needed to measure current lag is unavailable. `bootstrapping` means some history reaches that end but the full 24-hour window is not admitted.

Windows use a common closed-hour watermark across the admitted active roster: the minimum accepted current-fingerprint scan end, rounded down to a UTC hour. `window.watermark` exposes its timestamp, assessed age, effective public freshness budget and machine-readable failure reason. This uses the same effective fresh budget as the endpoint's `_meta.freshBudgetSec`, not the base producer cadence. Missing or over-budget frontiers fail closed; an admitted active-roster leg over that budget is quarantined from the watermark and paused for reactivation catch-up, so the remaining coins keep publishing while that leg's outputs stay unavailable. Aggregate and per-coin totals, largest events, net windows and complete-day baselines all use the selected end rather than silently pretending the rotating extended lane reached the latest hour.

Historical admission has two explicit assurance regimes. At and after `MINT_BURN_LEGACY_CUTOVER` (2026-10-20 12:00 UTC), exact current-fingerprint v2 proof is required. Earlier hours may use the bounded pre-T1 cursor/event rule: retained hourly evidence plus a scanned cursor span anchored to an observed pre-cutover scan timestamp, with the frozen cutover source identity. It never anchors history to the request clock or treats an old fingerprint as v2 proof. The coverage/window provenance is `legacy-pre-cutover` whenever this weaker historical assurance is used; otherwise it is `durable-v2`. All admitted contracts must qualify, dirty-hour debt vetoes both regimes, and existing valuation gates remain unchanged. Missing raw history is not rebuilt from pruned events.

The cutover is the last complete UTC-hour boundary before the 12:03 deployment and first T1 producer at 12:05:04; its boundary hour belongs entirely to v2. The historical-assurance transition expires when the longest 90-day window no longer overlaps it: remove that coverage branch after 2027-01-18 12:00 UTC plus the effective watermark freshness budget. Retain the frozen identity roster for the separate v6.31 publication-grandfathering contract until an explicit durable replacement preserves those admissions. The historical transition itself requires no D1 migration or synthetic proof write.

Current rule: the March 24 long-tail transfer wave that inherited the blanket `21_900_000` Ethereum floor is labeled `startBlockSource = default-coverage-floor-2026-03-24` and `startBlockConfidence = low`, so the public API no longer implies contract-specific historical certainty where none exists.

Events are also classified by `flow_type` (`standard`, `bridge_transfer`, `atomic_roundtrip`, or `protocol_internal`) so non-economic bridge transfers, same-tx roundtrip noise, and reviewed issuer-internal movements stay out of aggregate flow metrics.

### Open USD coverage review (2026-09-30)

Open USD (`ousd-open-standard`, issued by Bridge) is distinct from Origin Dollar (`ousd-origin-protocol`). The [issuer's reserve page](https://reserves.bridge.xyz/ousd) binds its Ethereum, Base, Tempo and Solana deployments. The extended lane indexes Ethereum and Base with six decimals, canonical zero-address `Transfer` events and a 10,000-token dust threshold ($10,000 at peg). Both use explicit primary-contract configs and reviewed code-deployment bounds, rather than the default Ethereum coverage floor. Small test mints/burns remain accounting observations; the threshold hides them only from event presentation.

Reviewed deployment bounds are config-specific, not the default Ethereum coverage floor; their provenance belongs with the registry and [reviewed conservation sidecar](https://github.com/TokenBrice/pharos-watch/blob/main/worker/src/lib/mint-burn-conservation-reviewed.json). The decoder counts exactly one canonical zero-address `Transfer` per mint/burn, not duplicate custom issuer events.

**Intentional chain gaps:** Tempo is the dominant issuance chain. Although `chain-registry.ts` declares Tempo Dwellir archive state/full log history, mint/burn also requires a supported Alchemy URL (`ALCHEMY_CHAINS` excludes Tempo), and registry support alone does not admit a chain. Revisit Tempo routing only after reviewing TIP-20 event semantics and deployment history for admission. Solana is also excluded: the lane has no Solana supply-event decoder or RPC ingestion path. Its trigger is a supported Solana mint/burn adapter. No bridge-detection hints were added without verified CCIP, CCTP or LayerZero attribution.

Ethereum remains the configured canonical chain for DEWS. The override map could select Tempo even with an Ethereum config, but doing so before Tempo ingestion would exclude all observed OUSD pairs from canonical metrics. Switch the override to Tempo when that config is live. The digest instead consumes the admitted multi-chain gauge publication. Ethereum and Base together are a minority of issuer supply because Tempo dominates. These flows do not represent whole-coin issuance.

The public flows table describes configured issuance chains, and the per-coin API returns `scope.chainIds`. The detail-page `flow-summary-card.tsx` instead consumes the aggregate `useMintBurnFlows()` response; its coin `coverage` metadata has no chain IDs, so that card does not name the coin's configured chains. Coverage status measures scanned-history maturity/freshness, not the fraction of global supply indexed. This is an existing cross-coin disclosure limitation.

**Conservation decision:** Ethereum is admitted under the exact `transfer-supply` law. The [verified StablecoinTemplateV3 implementation](https://eth.blockscout.com/api/v2/smart-contracts/0x264048239dd1b5939599fae8e6000df40248d524) routes mint, wrap, burn, unwrap and blocked-address burns through stored-sum supply updates with exactly one matching zero-address `Transfer`; ordinary transfers reject zero endpoints. Two hash-pinned archive windows, boundary blocks 26,077,249-26,084,420 and 26,084,420-26,091,591, each returned an exact zero residual. Implementation-slot and six-decimal reads matched at all three boundaries, with no in-range `Upgraded` logs. Base is explicitly unsupported with `unverified-implementation-source`: the [B20 specification](https://docs.base.org/specifications/b20) explains the native token surface, but its canonical Solidity interfaces do not verify the deployed native implementation or every supply-storage writer. Base's two archive windows also passed; that observation alone does not close the source gap. Both decisions are recorded in the reviewed sidecar. Revisit Ethereum on implementation changes and Base when version-pinned native source or a justified source exception permits a complete supply-path and zero-address pairing review. Origin Dollar's vault-yield law does not apply to Open USD.

### Reviewed protocol-internal events

`shared/lib/reviewed-protocol-internal-flows.ts` holds individually reviewed events that moved tokens inside an issuer's own balance sheet, each with its block timestamp. `persistMintBurnRows()` applies it through `applyReviewedProtocolInternalFlows()` (`worker/src/lib/mint-burn-pipeline/reviewed-protocol-flows.ts`) before atomic-roundtrip reconciliation, in both the cron and `npx tsx worker/scripts/one-shot-backfill.ts backfill-mint-burn --execute --allow-atomic-import` paths, so a replay over the event's block rewrites the stored row and recalculates its hourly bucket. Matching requires the exact event id (chain, transaction hash, log index), stablecoin, chain, direction, and the reviewed token amount; a row whose amount drifts keeps its normal classification unless it independently matches the supply-exclusion rule below. The homepage Biggest Supply Moves card reads the same registry and leaves a coin out of its week-over-week ranking while a reviewed event sits inside the comparison (see [Homepage](https://pharos.watch/)).

The narrow address-level exception is inventory already curated as non-circulating in `CURATED_ONCHAIN_SUPPLY_EXCLUSIONS` (`worker/src/lib/onchain-supply-exclusions.ts`). At the same persistence stage, `applySupplyExcludedProtocolInternalFlows()` tags mints to and burns from those holder addresses as `protocol_internal`, matching the coin and chain exactly and the counterparty address case-insensitively. These inventory movements cannot change circulating supply. Burn classification is preserved; the rows remain visible in the event ledger but leave all counted hourly totals, nets, pressure, baselines, Bank Run Gauge, DEWS flow and digest inputs. The existing classification UPDATE rewrites duplicate stored IDs after INSERT OR IGNORE, including non-standard mints, and replay rebuilds their affected hours; a WHERE guard skips rows whose stored classification already equals the classifier output, so re-observed window rows no longer produce identical D1 writes (`rowsUpdated` counts only rows that actually changed). Historical rows require replay; changing the rule alone does not repair stored aggregates.

Everything else still requires per-event review: the USDai vault-to-loan deployment used a contract path that can also redeem. The reviewed registry owns exact event identity, evidence and original timestamps. `reviewedProtocolInternal` counts only exact reviewed-event matches; address-tagged rows contribute to the existing non-standard `flowTypeChanges` count. Frontend supply surfaces already use circulating balances with these inventory exclusions, so they need no additional event-based suppression for address-tagged rows.

### Event Detection

**Standard mint/burn:** ERC-20 `Transfer(address,address,uint256)` events filtered by zero address.

- **Mint:** `topics[1]` (from) = zero address
- **Burn:** `topics[2]` (to) = zero address

**A burn-shaped event is not always supply destruction.** The reviewed conservation sidecar is the sole identity authority for the `zero-address-transfer-without-supply-change:` finding. For those exact chain/token/address/decimal identities, a zero-recipient Transfer first remains a non-counted `review_required` observation. Agora `Burned`, BoringVault `Exit`, and Maple `Withdraw` receipts can prove internal/batch burn paths: the token emitter, indexed owner, native share amount and complete receipt tuple multiplicities must match, not just a transaction-wide topic. Collateral amounts never substitute for share amounts.

For reviewed Transfer-only receipt paths, admission requires a successful transaction addressed directly to the token, its complete source-reviewed calldata, matching owner/amount and a unique token burn in the same block-bound receipt. A burn selector on a router is not evidence of an internal call. Reviewed conditional range proof can also prove internal burns as described below. Without either proof, missing or malformed context is `supply-proof-context-unavailable`, not an effective burn or a dropped observation. Other conservation exclusions, such as rebasing supply or unverified source, do not trigger this filter.

Each config scan reconciles at most twenty retained legacy burn rows after current ingestion, within its existing request budget and deadline. Candidates start at the first whole hour at or after the canonical raw-retention cutoff; an older surviving event cannot prove that its already-pruned siblings are available for rebuilding. Every reviewed classification update atomically records its affected hour in the durable maintenance debt; the existing independent drainer rebuilds the canonical hourly bucket. Unavailable context remains retryable. Raw events remain retained, and no exact correction is claimed for hours whose raw evidence has expired.

The per-config `mint-burn-supply-proof-cursor:v1:` key advances by `(timestamp,id)` only after attempted classifications and their debt persist. Unavailable receipts keep `supply-proof-context-unavailable` and remain retryable; a short/exhausted page wraps the next sweep instead of letting twenty unavailable oldest receipts starve later rows.

**USDT Ethereum special handling:** Public flows track custom `Issue(uint256)` and `Redeem(uint256)` treasury events (adapter kind `custom-events`); neither issuance path emits the canonical zero-address `Transfer` pair. Transfers to zero can occur without changing USDT supply and must not be treated as burns. `DestroyedBlackFunds` is conservation-only evidence, not a public flow event.

**USDT Tron special handling:** Public flows likewise track only `Issue(uint256)` and `Redeem(uint256)`, decoded as six-decimal amounts from the first data word. Issuance and redemption transactions also emit same-amount zero-address `Transfer` events, so counting both families would duplicate supply flow. `DestroyedBlackFunds` remains a freeze-tracker event and is not added to public mint/burn flow coverage. Event links use Tronscan.

| Event | Topic Hash | Amount Encoding |
|-------|-----------|-----------------|
| `Transfer(address,address,uint256)` | `0xddf252ad...` | `transfer-value` (data field) |
| `Issue(uint256)` | `0xcb8241ad...` | `first-data-uint256` |
| `Redeem(uint256)` | `0x702d5967...` | `first-data-uint256` |

**reUSD special handling:** Re Protocol reUSD is tracked from the reUSD token's canonical zero-address `Transfer` events. Earlier vault-event parsing used `Deposited(address,address,uint256)`, but that event reports deposited collateral units; USDC/USDT deposits therefore decode as 6-decimal collateral amounts instead of 18-decimal reUSD shares and can fall below the dust threshold. The token `Transfer(from=0x0)` / `Transfer(to=0x0)` logs are the canonical mint/burn amount source, and they also avoid double-counting instant redemptions that emit both a token burn and a route-level redemption event.

**Custom counterparty encoding.** For events whose relevant address is not in a standard topic slot, `MintBurnEventDef` now exposes an optional `counterpartyEncoding` override:

- `{ source: "topic", index }` — read `log.topics[index]` (must be ≥1).
- `{ source: "data", slot }` — read a 32-byte word from `log.data` at `slot * 32` and take the low-20 bytes as the address. Implemented via the new `readDataWord` helper in `worker/src/lib/evm-logs.ts`.

When omitted, the default is the Transfer convention: mint → `topics[2]` (recipient), burn → `topics[1]` (sender).

## Raw Token Conservation

The mint/burn producer performs a bounded integrity audit for reviewed contract identities using the raw logs already fetched by the normal config scan. This is separate from public economic-flow aggregation: small, atomic and bridge events stay in the raw conservation channel even when excluded from public standard flow. Conditional supply proofs also use this raw channel and the additive evidence ledger described below. Neither path introduces a new cron, provider or public supply override.

Tron's reviewed conservation status is `unsupported`, with reason `tron-historical-state-unavailable`. Numeric historical `eth_call` pins are unsupported and object-form pins can return latest state, so neither proves boundary supply. The producer performs no historical conservation calls for Tron and never turns complete log coverage into a conservation pass. Its independent solidified scan proof still governs flow coverage.

For a complete successful range `[fromBlock, toBlock]`, the audit reads boundary headers and pins supply calls (`totalSupply()` by default, `totalShares()` for USDO) and law-specific guard views to their canonical hashes using [EIP-1898](https://eips.ethereum.org/EIPS/eip-1898). It rechecks the boundary identities before accepting the result. Missing archive support, partial ranges, invalid RPC results, changed hashes, exhausted budget, elapsed deadline or a decode-quarantined raw log produce unverified evidence; there is no fallback to latest-state reads. Contract/topic/range identities, non-removed logs, fixed-width amounts and duplicate consistency are validated before exact native integer summation. Every positive config event, including amounts below the display cutoff, must also correspond to parsed row identities, directions and exact raw amounts before persistence. A passing verdict is published only after successful writes and a bounded readback confirms every eligible row’s identity, direction, native amount, block and timestamp, including rows retained by `INSERT OR IGNORE`. Missing or conflicting stored rows fence advancement.

Before scanning configs, a serialized boundary pre-pass pools eligible ranges by chain/ordered endpoint list: distinct boundary headers, hash-pinned supply calls, then header rechecks. Admitted, enabled Dwellir is first for supported operations, then the existing Alchemy endpoint. Arbitrary historical supply/guard state requires Dwellir archive capability separately from log/header eligibility; recent-only BSC cannot supply old conservation state. Each phase is chunked at 100 calls per POST and charged to the global budget, not per-config budgets. Each POST has a 15-second timeout capped by the remaining 45-second pre-pass allowance or lane deadline. Failures affect dependent configs only. Raw logs are reused rather than scanned again; configs fence and persist individually, but cursors commit only after successful hourly recalc. Interior log block identities remain provider evidence; boundary checks do not retrieve every interior header. Exact conservation detects unmatched omitted events, not omitted offsetting mint/burn pairs.

Boundary-header responses must validate the requested block number, nonzero 32-byte hash and timestamp before an endpoint's JSON-RPC success is accepted. Null or malformed initial/recheck headers retry only the unresolved calls on the next admitted endpoint, within the existing global request budget and pre-pass deadline. If no endpoint supplies a valid header, the audit remains `unavailable` with `invalid-boundary-header`; it is not a positive conservation claim or evidence of a reorg. Only a changed identity between two validated reads of the same block is `boundary-reorg`; that remains an immediate write/cursor fence and run degradation, without retrying away the discrepancy. Diagnostic header-read unavailability alone does not degrade a completed critical or extended ingestion run; its unavailable count and reason remain visible separately. These rules do not change the scan head, confirmation policy or public flow methodology.

The committed evidence sidecar `worker/src/lib/mint-burn-conservation-reviewed.json` is the only list of admitted and explicitly unsupported identities: one entry per config identity (chain, stablecoin id, lowercase EVM or case-preserved Tron address, decimals) carrying the reviewer's identity evidence (explorer-verified source, external address match, on-chain decimals) and supply-path review, with admitted entries carrying audited windows proving the reviewed law exactly. A config with no entry falls back to `unreviewed-contract-or-event-semantics`. Admission requires the exact reviewed identity and compatible event adapter: ordinary zero-address `Transfer` semantics with `transfer-zero-address`, or reviewed `config-events` semantics with `custom-events`. An `unsupported` entry carries a reason from the fixed vocabulary in `worker/src/lib/mint-burn-conservation.ts`: literals `rebasing-supply-without-events`, `total-supply-override`, `deprecated-upgrade-forwarding`, `unverified-implementation-source`, `tron-historical-state-unavailable`, or a reason beginning with `unpaired-supply-path:` or `zero-address-transfer-without-supply-change:`. `m-m0` is explicitly unsupported with `rebasing-supply-without-events` because its index accrues over time. `npm run audit:mint-burn-conservation-admission` produces, replays and merges this evidence. The Worker runtime never parses the evidence file: eligibility resolves from the generated lookup `worker/src/lib/mint-burn-conservation-runtime.generated.json` (identity, disposition, reason and runtime params projected from the sidecar by a registered generator; `npm run check:generated-artifacts -- --only=mint-burn-conservation-runtime` guards drift), keeping the evidence out of the isolate bundle.

Supply-burn admission uses the same sidecar's source-reviewed `supplyBurnProof` projection without changing raw-law admission. A proven individual economic burn does not make a generally false Transfer conservation law valid, and an unsupported raw law is not a verified conservation mismatch. Economic `flow_type` exclusions (bridge, atomic roundtrip and issuer-internal activity) remain independent of proven supply destruction.

### Conditional range supply proof (v6.42)

The reviewed `supplyBurnProof.range` capability uses law `paired-supply-zero-transfers-v1` for exact identities already carrying `zero-address-transfer-without-supply-change:`. Their unsupported reasons and receipt proofs remain intact. `source-only` means reviewed source excludes positive counterfeit mint-shaped Transfers; `require-empty` additionally requires no positive mint-shaped Transfers in the complete range. USYC uses `require-empty` because its administrator can emit both counterfeit zero-side directions without changing supply. A fake mint/burn cycle cannot pass that guard. Rebasing, computed-supply and unrelated unsupported laws remain ineligible.

EURS pins its reviewed slot-12 delegate and excludes in-range `Delegation` events; USYC pins its reviewed EIP-1967 implementation and excludes in-range `Upgraded` events. Agora AUSD remains range-ineligible with `agora-packed-implementation-dispatch-guard-not-reviewed`: its packed implementation/dispatch guard needs a separate review. Its existing `Burned` receipt proof remains available. A range proof does not bypass SwanUSD's pending publication admission.

For the exact inclusive fetched range `[a,b]`, the proof sums every raw mint `M` and zero-recipient Transfer `Z` as integers, including sub-dust, bridge and atomic legs, and compares them with hash-pinned supply at `a−1` and `b`: `R = M − Z − (S_b − S_(a−1))`. Only exact zero residual, complete log evidence, the reviewed mint condition and all source-era guards authorize corresponding exact event IDs. Proxy/delegate identities require matching reviewed state at both boundaries and a complete in-range change-event check, including change-and-back. Missing guards leave the identity ineligible; matching endpoints alone are insufficient. No latest-state fallback, floating arithmetic, tolerance or proportional residual allocation is permitted.

A negative residual under `source-only` records `residual`, leaves ambiguous rows unresolved and allows ingestion progress; existing independent receipt proofs can still recover burns within the remaining budget. A positive residual, positive 0→0 Transfer, reorg or inconsistent event evidence keeps the hard write/cursor fence. Missing archive, logs, guard, deadline or request capacity records a named `unavailable` result and leaves unresolved rows. The proof runs before supply receipt reads: a proven non-bridge range needs no per-burn transaction/receipt contexts. Independent bridge classification still runs, and proof never converts an excluded economic flow into standard flow. Retries with shortened bounds require fresh matching boundary evidence and cannot inherit promotion from a failed parent range.

A `require-empty` range containing positive raw mints remains unresolved, including sub-threshold events now stored as accounting rows. Unresolved mint and burn rows preserve classification uncertainty through hourly materialization; clearing ordinary repair debt cannot convert those events into proven quiet activity. Ordinary scan proof remains a distinct requirement.

Migration `0301_mint_burn_supply_proofs.sql` stores immutable proven, nonempty range witnesses in `mint_burn_supply_proofs`, including config fingerprint, law revision, token/decimals, range, boundary identities, opening/closing supply, raw `M/Z/Δ/R` decimal strings, event-set digest, mode, status/reason and check clock. Its separate lifecycle distinguishes pending, accepted and invalidated evidence. Nullable event `supply_proof_id` binds exact members to that evidence; the proof verifies the parser-recorded `amount_raw` supplied by migration 0300 instead of assigning it. Proof/member classification changes and dirty-hour keys commit atomically; persisted readback checks proof correspondence before hourly totals can authorize burns. Pending or failed materialization remains behind debt. Pending proof-backed effective burns stay out of public event lists and Tape claims until acceptance, and cannot neutralize a mint in roundtrip reconciliation; invalidated events remain review-required. Receipt-only replay preserves a valid range proof while its evidence is retained. Unproven outcomes leave real event rows unresolved; successful empty ranges carry no event authority and create no proof row.

Config/law fingerprint changes withdraw the config's scan coverage directly using durable configuration fingerprints and the scan ledger, independently of surviving proof records or raw event references. Detected canonical conflicts also retire overlapping scan-coverage fingerprints while preserving ledger rows as replay anchors. Merged spans can conservatively remain unavailable beyond the invalidated range until fresh complete replay. Only complete raw-retained hours are reclassified, dirtied and rebuilt; pruned hours remain unavailable and are never reconstructed from surviving subsets.

Retained range repair uses its own progress cursor, never the live `last_block`. It starts at a complete raw-retained hour, re-fetches complete logs and matching archive boundaries, updates only exact proven members and rebuilds whole coin/chain hours through the shared writer. An old survivor cannot authorize rebuilding an hour whose siblings were pruned. Pruned-hour historical replay is a separate operator task.

### Unconditional conservation diagnostics

The permanent admission CLI (`npm run audit:mint-burn-conservation-admission`) records a redacted RPC journal and can replay it offline. Audit-only operation and `--emit-sidecar-draft` do not alter the reviewed sidecar. Reviewer semantic files describe source/control/supply-law evidence; they do not substitute for complete passing audited windows. Only explicit `--merge-into-sidecar` mutates admission authority and regenerates its runtime lookup. Retain journals and restore the sidecar/lookup pair together; never bypass the conservation fence to undo a review.

The BRSRV, CHFSAFO and GLDon Ethereum flow additions have explicit conservation reviews. CHFSAFO and GLDon are admitted under the stored-supply `transfer-supply` law; BRSRV is explicitly unsupported with `total-supply-override`: its verified `StandardToken.totalSupply()` converts stored shares through an external rebasing-provider service instead of returning a stored token sum. Audited-window counts, boundary blocks and sampled arithmetic are owned by the reviewed sidecar. This exclusion does not remove configured `Transfer` flow ingestion or waive its separate bootstrap/backfill requirement.

Reviewed alternative laws are exact, without tolerance: USDT's `config-events` sums Issue mints minus Redeem and conservation-only DestroyedBlackFunds burns, guarded by `deprecated()` being false at both boundaries. Origin Dollar's (`ousd-origin-protocol`) `transfer-plus-vault-yield` adds vault `YieldDistribution` yield minus fee to the zero-address Transfer net; it requires each distribution to pair with a later `TotalSupplyUpdatedHighres` in the same transaction, rejects legacy checkpoints and saturated rebases, pins mutual token/vault identity at both boundaries, and rejects in-range proxy upgrades. USDO's `usdo-bonus-multiplier-shares` replays `BonusMultiplier` in block/log order from the opening view, folds each Transfer amount `A` into `floor(A * 1e18 / multiplier)` shares, and requires net shares to equal the `totalShares` delta. Its replay must match the closing multiplier view, `totalSupply = floor(totalShares * multiplier / 1e18)` must hold at both boundaries, and pinned implementation identity plus the upgrade guard must hold; its record arithmetic units are `raw-shares`.

Conservation-only events are fetched in the same scan, using each definition's emitter when supplied, but never become public flow rows or enter config-event row correspondence checks. Their fetch failures or partial coverage make the audit incomplete without independently counting as ingestion API errors or blocking otherwise valid config-event cursor progress. Public Mint/Burn Flow methodology is unchanged.

Unconditional audit diagnostics use existing `cache` rows at `mint-burn:conservation:<configKey>`, with monotonic writes and a fingerprint covering the audited configuration. These diagnostic caches retain one compact latest record per audited contract; they cannot substitute for the immutable conditional supply-proof ledger. Unresolved verified mismatches survive unavailable follow-up attempts and clear only after a verified passing audit covers the entire failing range for the same identity. Changing a config invalidates old proof. Cache write failures surface through the producer rather than pretending evidence was published.

A verified native mismatch fences cursor advancement and immediately degrades the affected run so the same range can be retried. A passing audit whose guarded write is rejected because it does not cover the stored mismatch is not a published pass: the run keeps `conservationStatus: "mismatch"` with reason `unresolved-stored-mismatch` and fences the cursor for a full-range retry. The fence is also a write barrier: a conservation-fenced attempt (verified mismatch, unreliable raw-log/boundary evidence, or parser correspondence failure) persists no rows into `mint_burn_events`, so rows whose event set was never conservation-verified cannot outlive the fence — a later clean retry that covers the range writes only the rows it re-observed, and its persisted-row readback verifies exactly those. Invalid raw identity or parser/stored-row correspondence evidence is likewise not allowed to advance as a clean scan. Pure audit capability/budget unavailability does not independently stall otherwise valid ingestion or count as an ingestion API error; separate conservation counters expose audit failures and unavailable attempts. The operator verdict stays unverified, and existing partial-coverage, timestamp, bridge-context and persistence rules continue to govern progress.

The operator view reads cached evidence only, displays each latest audited range separately, and never treats the old timestamp-less circulating-supply delta as a critical ingestion verdict. The [public status dashboard](https://pharos.watch/status/) presents these diagnostics; conservation does not change event cutoffs, classifications, counts, valuation or flow formulas.

## Daily operator invariant

`worker/src/lib/mint-burn-supply-reconciliation.ts` independently compares the classified ledger with hash-pinned on-chain supply for complete UTC days. This operator diagnostic does not change flow numbers, circulating-supply publication, scoring, or reader warnings. The existing critical mint/burn run hosts a serialized, bounded, resumable pass; no trigger is added. Receipts start with the first complete UTC day after monitor activation, never treating pre-v6.41 history without dust rows as a complete event population.

For each supported admitted contract, the monitor partitions every positive retained raw event into **counted**, **review by reason**, **bridge**, **atomic**, or **protocol_internal**. It sums exact decimal-string `amount_raw` values using `BigInt`, with independent mint/burn totals and counts per class. Dust is already present in these classes since v6.41 and is not subtracted again. Fully scanned empty days have observed zeros; missing raw amounts, incomplete current-fingerprint scan coverage or pending dirty hours have unavailable arithmetic.

The equation is `closingSupplyRaw − openingSupplyRaw = Σ(classMintRaw − classBurnRaw) + reviewedLawTermRaw`. Stored-supply Transfer laws use a zero law term and exact equality: even one raw unit left over is `unexplained-residual`, with no percentage tolerance. Eligibility comes from the reviewed conservation registry. Identities with the reviewed range-supply law are reconciled too: their one alternate term is a zero-recipient Transfer that destroys nothing, which stays an unresolved burn, so a positive remainder no larger than the day's unresolved burn total is recorded as the law term and any other remainder is still `unexplained-residual`. Rebasing, computed, forwarded and unverified supply, Tron archive limitations, and alternate laws whose required terms are not in the persisted ledger remain `unsupported-law` with a machine-readable reason. Shared coin/chain buckets without contract attribution cannot establish a per-contract pass.

Each compact daily receipt binds the config fingerprint and law, UTC day, check clock, opening/closing block numbers and canonical hashes, raw supply, class sums, review reasons and verdict. Boundaries are the last blocks strictly before UTC midnight, with the following headers proving the brackets. A prior day's closing checkpoint supplies the next opening; only the new closing supply is read in the steady state. Chained 1/7/30/90-day windows sum contiguous compatible daily receipts without new archive calls. A missing day or broken checkpoint chain makes the window unavailable. Unavailable attempts may retry while every raw row is retained; completed receipts are not rebuilt from a pruned subset. The existing `prune-cron-history` job retains receipts for the 95-day hourly horizon.

The shared threshold authority is `shared/lib/mint-burn-reconciliation-policy.ts`: the larger of unresolved mint and burn totals is material strictly above $10M **or** 2% of the leg's closing supply. A supported exact reconciliation with material unresolved review activity raises **`review-suppression`** separately; it cannot pass merely because review rows explain the gap. Current-price USD materiality is a diagnostic, distinct from historical event-time USD flow valuation. Missing price evidence never invents a par price: review materiality remains unavailable unless the native 2% rule already establishes suppression. Chained windows also assess their accumulated review totals. The raw residual itself has no materiality tolerance. USG's excluded treasury inventory remains a circulating-versus-total scope distinction: this invariant compares total supply with all ledger classes, not circulating-supply changes with counted flow.

`cron-sentinel`'s daily `supply-reconciliation` source reads stored receipts only and publishes distinct `mint-burn-unexplained-residual` / `mint-burn-review-suppression` operator findings. It sends changed findings through the existing operator Telegram channel and acknowledges the transition only after successful delivery. Unavailable/unsupported legs stay visible but do not alert on their own. Later unavailable or passing days cannot clear a retained finding for a different day. Per-leg classes, boundaries, reasons and chained windows appear in **Pipeline → Mint/Burn Integrity** on [status](https://pharos.watch/status/); investigation steps are in the [integrity runbook](https://github.com/TokenBrice/pharos-watch/blob/main/docs/runbooks/mint-burn-integrity.md#daily-supply-reconciliation).

## Sync Algorithm

`syncMintBurn()` in `worker/src/cron/sync-mint-burn.ts` composes one invocation-local `MintBurnRun` from `worker/src/cron/mint-burn/run.ts`. The aggregate coordinates run-state/rotation, config scanning, hourly materialization, staged cursor commits and completion, owning the shared `lastBlocksAfterRun`, `pendingCursorUpdates` and `affectedHours` maps. `run-state.ts`, `run-configs.ts` and `run-completion.ts` remain its focused state, scan and terminal-materialization collaborators. Recalc still runs in `finally`, committing admitted hours and their cursor/proof updates before independently materializing each pending coin/chain bucket. A pending failure retains its cursor and replay inputs without holding admitted commits; `pendingMaterialization` names failures and sample bounds. Shared buckets remain behind a common materialization fence. Retention and lane-specific cache invalidation remain unchanged.

Tron uses the existing `worker/src/lib/tron-jsonrpc.ts` reader and its validated solidified head rather than the EVM `finalized` tag. A head older than ten minutes is rejected with `tron-rpc-stale-solid-head`; stale or failed reads retain their machine-readable reason and cannot certify `up-to-date` coverage at a frozen frontier. Filtered log pages stay within the reader's 10,000-block bound, with budgeted adaptive splits and provider fallback. The reader retains its 2 MiB full-block context cap and head-bracketed timestamp lookup. Ordinary mint/burn scans reuse header evidence and do not need blacklist transaction-local event-index hydration.

Active progress keeps stage/budget observability live. |

Aggregate sidecar completion uses HTTP publication success and the canonical `X-Data-Freshness` flow verdict, not the presence of an HTTP `Warning`: optional Safety Score/flight-to-quality dependency advisories remain in per-window sidecar metadata without turning a completed fresh scan/publication into incomplete required work. Missing or non-fresh flow freshness still degrades the run (`mint-burn-aggregate-freshness-unavailable`); failed publication names `mint-burn-aggregate-publication-failed`. A primary scan failure retains its own reason.

Finality coverage is derived from enabled `MINT_BURN_CONFIGS` and the runtime-admitted endpoints returned by `mintBurnRpcEndpoints()`. CHAIN's `finalizedTagUnsupported` capability excludes that endpoint from finality reads, independently of historical log/state support. A finalized header older than the chain's finality budget (`mintBurnFinalizedHeadMaxAgeSec()`: 30 minutes on Ethereum, 2 hours elsewhere because rollup `finalized` tags wait for L1 batch finality) is rejected as a cached or lagging provider head, so a frozen chain cannot certify `up-to-date` coverage. Missing, refused, malformed or stale finalized headers produce per-config/event coverage reason `finality-head-unavailable`, `finality.unavailableChains` in cron metadata, and immediate degraded status (including the extended lane); unaffected chains continue. No tip fallback or successful quiet-zero claim is synthesized for the unavailable chain. A validated conservation `boundary-reorg` remains a write fence and immediate degradation, not a diagnostic finality-read failure.

Timestamp batches admit one complete `{number, hash, timestamp}` header per requested block: the number must match, the hash must be 32-byte hex, and the timestamp must be positive and safe-integer. Duplicate IDs invalidate that member, out-of-range IDs are ignored, and unresolved members retry within the existing budget. Timestamp and hash are never taken from different responses; expected event hashes still gate cache writes. Legacy unpinned readers require the same complete header without acquiring a new freshness policy.

Prospective `mint_burn_scan_coverage` segments bind config identity and a versioned source/decoder fingerprint to inclusive block ranges, validated first/last block timestamps and `finalized` authority. Every configured public event topic must be exhausted, required row context resolved, and no decode quarantine present before staging proof, including quiet scans. Boundary headers use the existing serialized request budget; missing/invalid boundaries or incomplete scans leave that interval unproved without relabelling legacy cursor progress. Only same-fingerprint adjacent/overlapping block intervals merge; elapsed time cannot bridge a failed/unscanned block, old-writer interval or registry/source revision. All older fingerprints and segments remain retained, including evidence needed by the longest 90-day window. Closed UTC 24h/7d/30d/90d coverage requires admitted continuous block/time evidence spanning both exact boundaries for every required config/chain; no events is not evidence of coverage.

**Counterparty resolution (default):** mints read `topics[2]` (recipient), burns read `topics[1]` (sender); a config's `counterpartyEncoding` override changes the slot (see Event Detection).

**Event ID format:** `"{chainId}-{txHash}-{logIndex}"` — deterministic, prevents duplicates via `INSERT OR IGNORE`.

## Shared Ingestion Pipeline Boundaries

EVM cron and admin backfill share `worker/src/lib/mint-burn-pipeline/` finalized-head admission, identity-validated log fetching, parsing, classification, event-time price resolution, persistence, hourly materialization and decode retries. Neither entrypoint imports the other. Both use monotonic-max sync-state commits; a partial replay cannot regress or overadvance a cursor. Explicit historical backfills retain complete-range advancement when the requested range is below the validated finalized ceiling; near-head requests are capped to that ceiling, never to an assumed 75-block margin. The [operator path](#operator-cli-backfill-mint-burn) additionally aborts an incomplete chunk instead of committing its resolved subset. This cutover does not remove previously stored orphan rows: any historical repair needs retained canonical evidence and audited row replacement/materialization, not a cursor rewind alone.

Since v6.40, every EVM fetch validates removal state, the requested emitter and topic filters (including mint/burn direction), block range, block-hash consistency and duplicate transaction/log-index identity before parsing, regardless of conservation-law support. Corrupt responses return incomplete coverage with a machine-readable reason, no accepted logs and no proven frontier for that response; the existing retry fence withholds scan proof and cursor advancement. Identical duplicates are deduplicated. Conservation shares the identity validator while retaining its additional reviewed ABI/amount checks; Tron retains its own boundary. Operator backfill rejects an incomplete chunk before ingestion writes.

`flow_type` is orthogonal to burn classification: bridge, atomic-roundtrip and individually reviewed protocol-internal events stay outside economic aggregates. Raw conservation still sees them. Tape excludes bridge/protocol-internal rows, but a previously projected reviewed burn remains a true historical event; reclassification is not evidence that it never happened.

Cron metadata includes `atomicRoundtripsDetected`, an observability counter for how many rows were tagged during the run.

Recent price healing, historical price repair and the cross-run roundtrip sweep use `materialization-debt.ts`: each bounded maintenance transaction commits its source mutation with all affected stablecoin/chain/hour keys in `mint_burn_dirty_hours` (migration `0280`). Rebuilding reads current raw events in SQL, then finalizes applicable priced `pending_aggregate` repairs and deletes that hour's debt in the same atomic batch. A mutation committed before rebuilding is included; a later mutation re-enqueues the hour. Classification alone never recovers an unpriced event. Failed rebuilds retain durable debt and raw rows. Completion independently seeds and drains bounded debt after the candidate maintenance stages, even if those stages find nothing or fail; it does not rewind ingestion cursors.

Every bucket delete, raw-row rebuild and priced-repair finalization requires the matching durable debt key to exist **inside the same atomic batch**, with debt deleted last. A stale second drainer is a no-op once another drainer has settled that key, even if retention has since removed some or all raw siblings; retained hourly history is not reconstructed from a pruned source. The primitive returns only hours actually rebuilt, so historical repair neither verifies stale no-ops against pruned raw rows nor reports them as its own rebuilds.

The ledger is prospective: neither event age, cursor state nor cron metadata backfills v2 proof. The scheduled scanner stages proof through `scan-coverage.ts`; generic/operator cursor commits without accepted proof remain unproved. The bounded pre-cutover reader transition above is separately labelled weaker assurance, never a ledger mutation. Worker rollback keeps the additive table and prior segments.

Cursor advances require proof ending at that block. An unproven live range gets at most four attempts/config/run within existing request budgets. A known timestamp/decode failure or partial-topic frontier selects the retry endpoint immediately before the failure; otherwise the range halves from the same start. Every prefix is re-scanned with fresh conservation boundaries, never certified from a candidate frontier alone. Live admission funds paged logs, a cold provider-head read when needed, event timestamps and proof headers; retry reservations also fund the three conservation-boundary batches. The extended roster's log-query reservation is a soft target: configurations that cannot afford a complete scan/proof are capacity-deferred and rotated, not attempted with a doomed log-only budget. First-block failure remains `scan-coverage-unproven`, never skipped (`scanAttempts`, `scanAttemptRanges`). Separately, each lane replays up to four coverage gaps/run (10,000 blocks/config, 40 reserved requests, 60 seconds), prioritizing current-fingerprint internal/tail holes within whole raw-retained hours (eight days). An isolated local persisted-event readback deadline, transaction-context shortfall without RPC evidence failure, or D1 resource-window exhaustion halves the next repair span for that config down to one block; the span survives runs beside the independent supply-proof repair cursor and grows by 25% (rounded down to whole blocks) after a successful scan, up to the same 10,000-block cap. Context chunks skipped by local deadline or request exhaustion retain the existing request-not-started diagnostic rather than imply an RPC failure. Each shortened attempt fetches fresh boundary evidence. Admitted gaps precede pending-admission gaps within the shared repair allowance, retaining rotation within each group. Repairs idle after live mutations and between replays using the shared D1 idle convention, bounded by the existing deadlines. After exhaustion, saving a smaller span waits out a full resource window within the lane deadline; a still-overloaded scheduling write is best-effort. Scheduling reads or writes that exhaust capacity stop further repairs with `repair-runtime-exhausted`; discovery and post-materialization repair commits also retain failures without aborting healthy collection. Capacity-only failures remain degraded as `mint-burn-source-coverage-degraded`, without a conservation finding. Proofs follow event persistence and hourly materialization, with monotonic-max cursor commits and `coverageRepairs` reasons. No synthetic proof or rebuilding older hourly-only history from pruned raw rows.

Before the conservation prepass, an initial range whose paged scan/proof cost exceeds its per-config request cap is repeatedly shortened from the same start until it fits. The prepass and scanner use that identical planned range; subsequent runs continue from its certified end. Oversized ranges therefore cannot remain permanently deferred merely because the global budget is larger than the per-config cap.

### Bridge Classifier

Dispatch lives in `worker/src/lib/mint-burn-bridge-classifier.ts`; receipt decoders and canonical Keccak-derived signatures live in `worker/src/lib/mint-burn-bridge-classifier-protocols.ts`. Deployment/token identities live in the resolved contract config. A top-level selector, an unpaired topic, or a shared endpoint appearing anywhere in a transaction cannot exclude a movement.

- **Per-movement evidence.** Each proof consumes one zero-address token `Transfer`, matching exact token, direction, raw integer amount and account, then tags only that parsed transaction/log-index row as `flow_type='bridge_transfer'` (burns also become `burn_type='bridge_burn'`). Unrelated same-transaction rows keep their classification. Raw local amounts never use a tolerance, USD price or shared-decimal conversion.
- **CCTP versions and directions.** Both reviewed Ethereum v1 and v2 messenger/minter/transmitter deployments have their own canonical send/receive ABI. A source `DepositForBurn` must name the token and depositor, with matching depositor-to-minter funding, minter burn/zero Transfer and that version's `MessageSent`. A destination `MintAndWithdraw` must name the token and recipient, with that version's `MessageReceived` and matching token `Mint(minter,recipient,amount)`/zero Transfer pairs. V2 principal and fee mints are matched in their execution order, including equal account/amount pairs; a fee recipient is derived from its own minter-authorized token event. Replacement deposits cannot reuse a consumed burn. Sources: [Circle v1 identities](https://developers.circle.com/cctp/v1/evm-smart-contracts), [v2 identities](https://developers.circle.com/cctp/references/contract-addresses) and [Circle source](https://github.com/circlefin/evm-cctp-contracts/tree/master/src). Official messenger `localMinter()` reads corroborate the minters.
- **CCIP pool versions.** Reviewed token-bound pool actions authenticate both legacy and modern sends and destination OffRamp mints without depending on a changing global ramp-address list. Standard pools require exact `Burned`/`Minted` plus the corresponding token Transfer. The hybrid external-minter route requires `LockedOrBurned`/`ReleasedOrMinted`, the named token and both pool-to-minter/burn or mint/minter-to-recipient transfers; lock/release alone is never a supply event. The USDO pool's custom `Minted` reports a rebasing balance delta, so its source-reviewed multiplier formula reconstructs the exact token mint request with checked integer arithmetic; the balance delta never substitutes for that request. Sources: [Chainlink legacy pools](https://github.com/smartcontractkit/ccip/tree/ccip-develop/contracts/src/v0.8/ccip/pools), [modern pools](https://github.com/smartcontractkit/chainlink-ccip/tree/main/chains/evm/contracts/pools), verified-source mirrors for the [USDO pool](https://www.codeslaw.app/contracts/ethereum/0x500d4882938020e939a5666c1b4200873da7efd3) and [USD1 pool](https://www.codeslaw.app/contracts/ethereum/0x36a72ed0096b414521c45e3ddc9ed657d1d9c141). RPC token/router/version/minter reads and real receipts corroborate these custom deployments; the mirror source was not independently recompiled.
- **LayerZero OFT send/receive.** A paired `OFTSent`/`OFTReceived` must come from the configured token-specific OFT and match the zero Transfer account and local raw debit/credit. Source `PacketSent` must come from the reviewed endpoint and bind the configured OApp, local/destination endpoint IDs and recomputed GUID. GLDon's shared messaging OApp is distinct from its token OFT; its reviewed zero-recipient credit maps to `0xdead`. An Executor address or compose selector is never a token-route proof. This closes the former shared-endpoint false-positive rule. Sources: [LayerZero IOFT](https://github.com/LayerZero-Labs/LayerZero-v2/blob/main/packages/layerzero-v2/evm/oapp/contracts/oft/interfaces/IOFT.sol), [packet codec](https://github.com/LayerZero-Labs/LayerZero-v2/blob/main/packages/layerzero-v2/evm/protocol/contracts/messagelib/libs/PacketV1Codec.sol), [USDai deployments/source](https://github.com/usdai-foundation/usdai-contracts), and [GLDon verified deployment](https://eth.blockscout.com/api/v2/smart-contracts/0x6d119ebada730583ef8dc7b8506fa317a374796a).
- **Unresolved attribution.** A resolved known-pool burn with no recognized proof stays `review_required / known-bridge-pool-without-bridge-signal`. A mint to a known pool, from a receipt-identified Circle minter, or an exact OFT movement missing endpoint proof is unresolved in the same way: it is stored as standard flow with `burn_type='review_required'` and the same reason, so the hourly writer counts it as an unresolved mint (v6.38) instead of issuance. Legacy-hour gating is unchanged: pre-v6.38 hours could only hide unresolved events for supply-proof and CCTP/CCIP configs, and every later hour records its own counts. Transfer-only mints without identifiable minter evidence cannot establish an unknown bridge route without additional reviewed evidence; no trace requests or guessed minter attribution are introduced.
- **Context and validation.** Configurable identities and versions fail closed at module load; event hashes derive from canonical source signatures. Bridge configs reuse the existing transaction+receipt requests, with no added RPC, fan-out or trigger. Missing or malformed required receipt context defers that transaction and holds the safe frontier; valid peers continue. Byte-valid unrelated EVM logs need not be ABI-word aligned. Existing shortfall/deferred-row diagnostics remain authoritative.

The owning classifier suite replays trimmed real RPC receipts for CCTP v1/v2 direct/wrapped sends/receives and fees, legacy/modern CCIP and all configured CCIP pool variants, both OFT routes and a mixed economic/bridge transaction. Synthetic controls cover wrong emitters, tokens, amounts, accounts and log identities. EURC positive coverage and GLDon outbound coverage are explicitly synthetic: bounded EURC queries found no event, and GLDon's deployment-to-capture census contained only a receive. Forward classification does not repair stored history. Changing a bridge config's decoder evidence changes its scan fingerprint, so scan proof recorded under the earlier rules no longer certifies those hours: every window that reaches back before activation is scan-incomplete and publishes no net until it lies entirely after activation (24h after one day, 90d after ninety). After activation the affected legs have no current-fingerprint frontier, so stalled-leg quarantine isolates them until their first complete closed hour under the new fingerprint, then reactivation resumes them. The independent atomic-roundtrip policy also needs to preserve these per-row bridge exclusions.

### Dust in accounting

Since v6.41, every positive decodable event is a real accounting row, including amounts below the config's native-token `dustThreshold`. Migration `0300` adds `below_display_threshold` (0 or 1, default 0 for legacy rows). The flag is computed from exact raw units; an event exactly at the threshold remains visible. Zero-value events remain omitted.

The flag never changes pricing, bridge or supply-proof classification, roundtrip reconciliation, hourly aggregation, or valuation/classification completeness. Counted dust adds native amounts, USD volumes and event counts normally. A dust bridge mint remains excluded; an unproven dust burn adds unresolved classification debt and withholds the hour. Thus mint 15,000 once and burn 5,000 three times conserves zero, rather than dropping all three burns.

Only presentation uses the flag: `/api/mint-burn-events` excludes flagged rows in every scope (and therefore in its UI feed), Tape eligibility excludes them, and largest-event ranking excludes them. Those surfaces are subsets of the accounting ledger. A USD `minAmount` filter does not override the native display cutoff.

**Historical boundary:** dust-inclusive accounting begins with hours fully scanned by the v6.41 writer after its actual activation; the first whole UTC hour starting after activation is the conservative cutover for fresh ingestion. Already-materialized hours keep their original observations: no dust backfill, synthetic aggregate repair or inference from absent old rows occurs. Windows spanning the cutover mix the earlier truncated accounting with the new inclusive accounting; their volume and count step must not be read as an activity anomaly.

The pre-implementation public-RPC census over **2026-11-08 00:00–24:00 UTC**, all 135 configured contracts, used 585 serial throttled requests including boundary checks/retries: 3,700 existing rows/day plus **8,254 added rows/day**. USDC (4,642), USDS (1,549) and DAI (1,125) dominate additions. USDT Issue/Redeem were checked separately because Transfer counts alone do not describe their writer. Extra context demand is 4,208 transactions/day; timestamp demand adds at most 4,522 per-config block identities/day before cross-config cache reuse. Contexts batch 20 transactions (transaction plus receipt); timestamps batch 50 blocks. These are provider-work counts, not one budget unit per RPC member.

Coarse cold-header cadence estimates put USDC at 16 request batches/half-hour against 150, DAI at 7 against 60, and the busiest extended config at 5/four-hour coverage cycle against 25. The sum of per-config maxima is 39 for critical and 321 for extended (spread across four hourly invocations, 800 global units); these are sizing estimates from block-position bins, excluding prepass, retries and failures, not production timing proof. No cap, cadence or connection peak increases. Cold catch-up can exceed one config's cap: the existing bounded certified-prefix retry, context cache and cursor rotation handle smaller ranges; unavailable context never licenses skipped rows or a cursor jump. A single observed block needs at most one 20-transaction context batch.

The 8-day nominal projection is 95,632 total rows, including 66,032 extra dust rows. A local latest-schema SQLite replay with all rows priced/standard and every event index (including the new transaction lookup) used about 92 MiB, of which about 64 MiB is apportioned to added rows. This is a model, not a production D1 receipt; unresolved/price/dirty/frontier protection can retain hours beyond eight days. Index maintenance adds write amplification; measure D1 metadata on activation. The absolute 2.3M-row watchdog remains unchanged. Activity flags include counted dust; the collapse watchdog compares seven days of exactly zero activity with a 30-event baseline, not count growth, so the step does not itself trigger an anomaly.

### Atomic Roundtrip Detection

Only resolved standard-flow rows can establish an atomic roundtrip within one transaction, stablecoin and chain. Standard mints must not be review-required; standard burns must be proven effective burns. Bridge and protocol-internal legs are excluded from the candidate group before comparison.

- Mint and burn sums must be **exactly equal in raw integer token units**, compared with BigInt. There is no percentage tolerance and no partial-principal splitting: mint 100 / burn 100.4 stays standard and contributes a signed native residual of −0.4.
- Migration `0300` adds nullable decimal-string `amount_raw`. Every newly parsed row carries its exact decoded amount. Legacy rows retain NULL; neither the sweep nor the operator infers exactness from stored REAL amounts, newly tags those groups, or changes their existing atomic tags.
- Ingestion, the recent sweep and the operator use the same candidate rule over the complete persisted transaction population, including configs sharing a stablecoin/chain bucket. Each configured sibling must have scanned through the transaction block; a complete current ingestion scan can establish its own progress before cursor commit. Distinct share classes with different decimal scales are not combined.
- An input batch containing only one side cannot by itself revoke a complete stored group. Reconciliation reads every stored peer; it can reverse known-raw unequal groups or remove ineligible old tags only from the group-wide evidence. Source-population and classification guards fence concurrent changes, and changed hours are enqueued atomically.
- The post-run sweep scans at most 200 groups over seven days, advancing a durable keyset past unchanged groups and wrapping after exhaustion. It rebuilds changed hours before checkpointing. The operator uses an explicit continuation cursor for its larger bounded scan.

Historical hourly buckets remain unchanged until complete raw evidence supports a separate repair. The new rule does not recover residuals from pruned or raw-amount-unknown history.

## Scoring

**File:** `worker/src/lib/mint-burn-scoring.ts`

Only standard mints and supply-proven standard effective burns enter counted flow, hourly totals and downstream pressure/flight-to-quality signals. Review-required burn-shaped observations remain in the event ledger but contribute neither counted burn volume nor counted burn events. This admission correction changes inputs, not the pressure formula.

### Pressure Shift vs 30D (Flow Intensity Formula)

The underlying scoring formula is unchanged, but the product now exposes it as the baseline-relative `Pressure Shift vs 30D` signal. Runs server-side in the `/api/mint-burn-flows` aggregate handler.

```
denominator = max(baselineDailyAbs * 0.3, $1M)
z = (currentDailyNet - baselineDailyNet) / denominator
pressureShift = clamp(-100, 100, z * 50)
```

**Activity gate:** If the coin's 24h absolute flow (mint volume + burn volume) is below `MIN_ACTIVITY_USD` ($50,000), pressure shift returns `null` (NR). This prevents misleading scores for dormant or low-activity coins.

- **Input:** 24h net flow, 24h absolute flow (`|mint| + |burn|`), trailing 30 fully closed daily average net flow, trailing 30 fully closed daily average absolute flow, data age in days.

- **Output:** -100 to +100 score, or `null` (NR) if fewer than 7 days of history, if 24h absolute flow is below $50,000, or if the coin has no 24h mint/burn activity.
- Score of 0 = current flow matches baseline. Negative values = pressure is worse than baseline. Positive values = pressure is improving versus baseline.

### Two-Signal Interpretation Model

Per-coin UI and API now answer two different questions explicitly:

1. **Net Flow 24h** — current direction and magnitude from raw mint-minus-burn totals
   - `minting`: `netFlow24hUsd > 0`
   - `burning`: `netFlow24hUsd < 0`
   - `flat`: `netFlow24hUsd = 0` with activity
   - `inactive`: no 24h activity
2. **Pressure Shift vs 30D** — how unusual current pressure is versus the coin's own baseline
   - `improving`: score `> 10` (strictly greater; score of exactly 10 is stable)
   - `stable`: score between `-10` and `+10` (inclusive on both boundaries)
   - `worsening`: score `< -10` (strictly less; score of exactly -10 is stable)
   - `nr`: insufficient history or no current activity

Invariant: minting vs burning semantics now always come from raw net flow, never from score sign.

### Shared Signal Helper

`shared/lib/mint-burn-signals.ts` centralizes interpretation logic used by worker responses and frontend fallbacks:

- `getNetFlowDirection24h()`
- `getPressureShiftState()`
- `getLiteralMintingPressureReading()`: the literal 24h mint-vs-burn balance, published only when both sides are `complete`; otherwise NR with `valuation-partial`, `valuation-unknown` or `no-24h-volume`, because a balance of lower-bound volumes bounds nothing (v6.27)
- `resolvePublishedGaugeBand()` and `formatBankRunGaugeScore()`: the published band as a typed band, and the gauge figure with one rounding and an explicit sign, shared by the page hero and the share card

### Bank Run Gauge (Composite)

Market-cap-weighted average of individual pressure-shift scores:

```
gauge_score = Σ(intensity_i * mcap_i) / Σ(mcap_i)
```

- Skips coins with `null` intensity (insufficient data or NR no-activity window).
- Each aggregate coin row publishes its weight as optional `gaugeWeightUsd` (v6.27): the observed tracked-chain supply applied to that coin, `null` when unavailable (excluded and counted in `mcapUnavailableCoins`, never zero). A coin moves the score only when its `pressureShiftScore` is non-null; scored weights sum to `scoredMcapUsd`.
- The per-coin `clamp(-100, 100, z × 50)` is a methodology bound on each input's intensity, not a display clamp (ADR-34/R7): the gauge is the weighted mean of those bounded intensities, published after normalization to the same `[-100, 100]` domain so floating-point dust cannot leave the documented bands, and no surface clamps the gauge itself.
- Returns `null` when the total market-cap weight of coins with non-null intensity is zero, including when all scores or weights are unavailable.

**One producer.** `refreshAggregateMintBurnFlowCache()` publishes the gauge over admitted active tracked pairs and their tracked-chain supply weights under `mint-burn-flows:v8:aggregate:24`. Other consumers read it through `worker/src/lib/mint-burn-published-gauge.ts`, never recomputing the composite over another universe. The critical lane refreshes every 30 minutes; ordinary extended-lane purges preserve it, while a changed disable policy invalidates it. As before T1, only admitted non-null pressure inputs with observed positive weights enter the weighted mean; there is no roster-percentage quorum. `gauge.scoreScope = admitted-coins` and `gauge.scanCoverage` disclose complete versus incomplete membership, admitted/excluded coin counts and excluded observed market cap (null when any excluded weight is unavailable). The composite is null when no scored weight remains; an excluded coin is never a zero input.

**Mcap weighting — tracked-chain scope.** Each published coin's preferred weight sums circulating supply across its admitted tracked chains, not just its DEWS canonical chain. Pending and disabled chains are excluded. When an admitted coin has no tracked-chain supply entry, the fallback policy below uses observed global circulating supply.

**Aggregate read path.** `fetchAggregateData()` (`worker/src/api/mint-burn-flows/aggregate.ts`) uses row-value tracked-pair membership over `json_each(?)`, pinned to `idx_mbh_chain_coin_hour` for hourly windows and `idx_mbe_coin_chain_ts` for largest events. Keep this index-driven pattern: a correlated `EXISTS` re-scans the pair array for each index row.

Implementation (`worker/src/lib/mint-burn-mcap-weighting.ts`):

- `getMintBurnTrackedChains(stablecoinId, configs)` derives the `chainId` set from the caller's admitted publication snapshot.
- `sumMcapForTrackedChains(stablecoinId, chainCirculating, circulating, configs)` sums `chainCirculating[chainId].current` over those tracked chains, after `canonicalizeChainCirculating(...)` normalizes DefiLlama's capitalized keys (e.g. `Ethereum`) to canonical chain IDs.
- A publication that withholds any configured chain cannot use global supply as a fallback weight: without admitted-chain supply observations, that coin’s weight is unavailable. The full configured scope retains the existing fallback policy.
- Fallback policy (preserves legacy behavior where per-chain data isn't available):
  1. Coin with no admitted tracked chains → unavailable weight; a legacy caller without an explicit publication scope retains the global-supply fallback.
  2. Canonicalized `chainCirculating` is empty → `getCirculatingRawOrNull({ circulating })` (keeps CG-fallback assets alive).
  3. No tracked chain has an entry in the canonicalized map → `getCirculatingRawOrNull({ circulating })`.
  4. Otherwise require an observed `current` for **every** admitted tracked chain and sum them (v6.40). A missing entry or `current = null` makes the entire weight unavailable; `current = 0` is real zero supply and does not trigger fallback. The global fallback cannot fill a partially observed breakdown.
- A fallback with no observed circulating bucket returns `null`: that coin's weight is unavailable, not `0`. The aggregate excludes it from the gauge inputs and from `gauge.trackedMcapUsd` and counts it in `gauge.mcapUnavailableCoins` (absent on payloads produced before the count existed). Its flow row is still published. Because a zero weight already contributed nothing, the gauge score formula is unchanged.

### Flight-to-Quality Detection

Detects simultaneous outflows from risky stablecoins and inflows to safe havens.

- **Activation:** `riskyNet24h < -$100M` AND `safeNet24h > +$100M`
- **Intensity:** `min(100, |riskyNet24h| / $1B * 100)`
- Safe/risky cohorts come from the report-card cache: `B-` or better is safe, `C+` through `C-` is neutral, and grades below `C-` are risky. If the complete identified report-card cache is unavailable, flight-to-quality classification is unavailable rather than falling back to hardcoded safe havens.
- Cohorts cover the classified roster within the published flow scope. A classified coin whose whole flow is pending mint/burn admission is outside that scope: it leaves the cohorts and its id is disclosed in `gauge.flightToQualityExcludedIds`, so it neither withholds the verdict nor counts as a measured zero. Any other unpublished classified coin (kill switch, missing row) contributes an unbounded unknown net, so an activation its flow could cause withholds the verdict instead of proving inactivity; a withheld verdict names its cause (`cohort-member-unpublished`, `flow-window-unavailable`, or `valuation-incomplete`) in `gauge.flightToQualityReason`.
- On aggregate API reads, a changed publication identity triggers FTQ recomputation from the validated cached per-coin `netFlow24hUsd` values and current cohorts. This updates only the response's FTQ fields, classification identity, and classification warning; the cached flow data, producer timestamps, freshness headers, and database row are preserved. Missing, held, stale, or malformed Safety Score sources and invalid cached coin inputs still fail closed.

## Classification Completeness

Since v6.38, classification is an independent completeness axis beside scan and USD valuation. `mint_unresolved_event_count` and `burn_unresolved_event_count` in `mint_burn_hourly` are nullable: NULL means the hour predates classification accounting; zero means materialization observed no unresolved standard-flow event on that side. Only counts are persisted; no classification bounds are constructed.

A standard burn is unresolved when `burn_type` is `review_required`, NULL or unrecognized. A standard `bridge_burn` is a proven exclusion. `bridge_transfer`, `atomic_roundtrip` and `protocol_internal` rows are proven exclusions rather than unresolved. The direction-neutral mint representation is `flow_type='standard', direction='mint', burn_type='review_required'`, with `burn_review_reason` naming the reason; such a mint does not count. No producer emits that mint state yet.

`shared/lib/mint-burn-classification.ts` owns each typed window verdict and the reasons `classification-unresolved` / `classification-unknown`. Any observed unresolved event makes the matching side partial and withholds exact net, direction, bounds, baseline, pressure, gauge contribution and unproved largest-event ranking. Gross valued counted subtotals stay visible with an incomplete-side qualifier, including observed zero. Legacy NULL hours become unknown when the coin's current configuration includes a reviewed supply-destruction proof gate or bridge review fallback; configurations without such a producer are structurally complete. The capability predicate is owned alongside the Worker config/conservation helpers.

All hourly writers share the unresolved counts, including debt drain, price heal, retained rebuilds and operator backfill. Every contribution-changing classification mutation records affected-hour debt in the same atomic batch; debt clears only with aggregate replacement. Replaying an ordinary standard mint can reverse an obsolete bridge/internal exclusion, while the deliberate atomic-group guard remains. Bounded retained-hour repair fills legacy NULLs only where the complete raw hour is still retained; pruned hours remain unknown. Retention preserves every sibling in an unresolved coin/chain/hour through hourly retention, with the existing deletion caps.

Public coin `classification` exposes full verdicts for `window24h`, `baseline`, `netFlow7d`, `netFlow30d` and `netFlow90d`; hourly, chain and per-coin window objects expose their matching verdict. Missing classification on older payloads retains the historical wire contract; new producers apply the current capability gate before publication. Gauge `partialValuationInputs` and `partialValuationMcapUsd` also disclose classification-withheld inputs and unknown baseline valuation, with the existing scored denominator and band-settlement rule. UI copy names incomplete flow inputs, rather than attributing every withheld input to price. Whole-coin long-window bounds require full coin scope. Baseline scoring and the exact Average Daily Net display require complete valuation and classification. `largestEvent24h.scope` identifies `valued-counted-admitted-scope`; ranking is withheld when scan or classification evidence is incomplete.

DEWS, DDR, OG, the activity watchdog, digest/FTQ and cached publication paths inherit this gate in addition to their own coverage and freshness rules. The counted event endpoint and Tape exclude unresolved mints as well as unresolved burns; unresolved observations remain in the raw review ledger. Unavailable evidence never proves quiet zero or no activity.

## Valuation Completeness

Since methodology v6.22 (CR-18 release A, migration `0251`), hourly buckets record per-side unpriced event counts. Only standard mints and standard effective burns count; events without `amount_usd` increment their side's unpriced count and add nothing to USD subtotals. Materializers share `mintBurnHourlyBucketAggregatesSql` so counts and subtotals agree. Recalc and heal rebuild use atomic per-hour delete+insert; retention evidence repair fills missing buckets with `INSERT OR IGNORE`.

**Scan evidence is independent of valuation.** Each 24h/7d/30d/90d signed window requires coverage for every configured source of that coin: current-fingerprint v2 proof after the immutable cutover, or the explicitly labelled bounded legacy assurance before it. The common end is the fresh fully scanned closed-hour watermark described above. A rounded scan tail that lands inside another source's gap steps backward to the latest common admitted hour within the same freshness budget. Missing or gapped evidence publishes null signed net, direction and pressure with a machine-readable coverage reason. `has24hActivity` stays null for incomplete scans; `observed24hActivity` independently preserves observed events. Gross volumes/counts remain `observed-subtotals`.

The pressure baseline uses only a continuous suffix of fully admitted complete UTC days before the watermark's day; admitted quiet days enter its denominator. DEWS reads hourly windows at the published watermark and preserves its own freshness and per-coin coverage gates. DDR's incident-anchored window and OG's independent windows retain strict v2 proof; the public transition does not silently weaken those readers.

Aggregate/per-coin readers, DDR and stablecoin OG cards read hourly data, current scan proof and overlapping `mint_burn_dirty_hours` in one D1 batch snapshot. Any debt for a required coin/chain/hour withholds exact-window admission until the atomic rebuild settles it, including corrections after v2 proof was recorded. DEWS batches its hourly reads with the same debt check before applying its published-window proof. A delayed or failed drainer therefore cannot certify stale hourly totals as complete.

The supply-destruction fingerprint remains `mint-burn-finalized-scan-v2`. Old segments are retained but never relabelled. Aggregate and per-coin cache namespaces move together to v7 so old all-roster/latest-hour materializations cannot mask the new contract. No sealed historical generation is rewritten; pre-cutover admission is disclosed as legacy and every later gap still needs real scan proof.

Maintenance rebuilds additionally settle durable per-hour debt atomically with the bucket write. A failure in aggregation, priced-repair finalization, or debt deletion rolls back the entire rebuild, preserving the last bucket and debt for recovery; source mutations already committed remain priced/classified. On non-error run completion, the independent drain seeds up to 100 retained legacy priced `pending_aggregate` hours not already dirty, then rebuilds up to 100 dirty hours oldest-first regardless of current price, flow classification or age. Seeding is idempotent and runtime-only; still-unpriced pending rows remain unresolved rather than claiming recovery. Historical repair uses the same atomic primitive and preserves the original price observation, operator run and Time Travel bookmark when finalizing an interrupted repair.

Mutating historical repair seeds up to 500 legacy hours before selecting its pending page, and selects only pending hours whose durable keys exist. Its stablecoin-first page therefore cannot rebuild unseeded hours from the seeder's hour-first page or resurrect a stale selected key after another drainer and retention. Dry-run remains read-only and previews pending source hours without requiring a debt key.

- **Valuation completeness:** `complete` means no observed counted event lacks USD valuation; an empty observed subtotal is valuation-complete, but only separate scan proof establishes genuine zero. `partial` means unpriced events exist; `unknown` means a bucket has NULL counts on a side with counted events. Precedence is partial > unknown > complete. Shared logic: `shared/lib/mint-burn-valuation.ts`; SQL tally: `worker/src/lib/mint-burn-hourly-valuation.ts`.
- **Legacy rebuild:** after each completed run, `rebuildRetainedLegacyValuationHours` re-aggregates up to 500 NULL-count buckets that start at least one hour inside the 8-day event-retention window (their raw events cannot have been pruned), newest first, through the partial index `idx_mbh_valuation_unrecorded`. Older legacy buckets stay `unknown` until hourly retention prunes them; nothing reconstructs pruned history.
- **Proven direction:** unpriced mints can only raise the true net and unpriced burns can only lower it. A direction survives only when that proven range excludes zero; `flat` requires complete valuation.
- **One-sided net bounds (v6.25):** the same range yields `mintBurnSignedNetBound()` (`shared/lib/mint-burn-valuation.ts`): with only the mint side partial the known net is a floor (`lower`), with only the burn side partial a ceiling (`upper`); both sides incomplete, or any `unknown` side, yields none. The API publishes `valuation.netFlow7dBound` / `netFlow30dBound` / `netFlow90dBound` (`{ kind, valueUsd }`, `null` when none, absent before v6.25) beside the still-null partial nets; the 24h bound derives from the published subtotals and `window24h` sides.
- **Internal consumers (active now):** DEWS flow is unavailable (`mint-burn-valuation-partial` / `-unknown`) unless the 24h window is complete, and when its burn baseline is partial or unknown (`mint-burn-baseline-valuation-partial` / `mint-burn-baseline-valuation-unknown`). DDR mint surge uses hourly evidence only when the proven range decides the 20% threshold, otherwise the supply-history proxy. The digest accepts withheld gauge weight only if every possible score preserves the published band, digest regime and risk-tape tone; pressure and chain nets require complete 24h windows, and FTQ is unavailable unless exact or provably inactive, naming `cohort-member-unpublished`, `flow-window-unavailable` or `valuation-incomplete`; a withheld 24h net degrades the digest run as `mint-burn-ftq:flow-window-unavailable` only when the coin's published `coverage.windows.window24h` is not complete, not when valuation alone withheld it.
- **Public API (v6.23 activation):** additive `valuation` fields on coins, chains, hourly buckets and per-coin totals/chains, plus `gauge.partialValuationInputs`, `gauge.partialValuationMcapUsd` and `gauge.scoredMcapUsd`. Signed nets are `null` for `partial` windows; gross volumes remain known subtotals. `netFlowDirection24h` uses `provenNetFlowDirection24h()` and is `null` when missing valuation could change it. Pressure requires a complete 24h window and a complete baseline; unknown baseline valuation is unavailable. Weighted coins with activity and at least seven baseline days whose pressure is withheld for valuation leave the gauge, which re-weights over scored coins and discloses their count and weight. `/flows` re-labels the beam and shows an `Incomplete flow inputs` chip. For withheld weight `w` and scored weight `W`, the full-cohort interval is `(W·S ± 100w)/(W+w)` (shift at most `w/(W+w)·(100+|S|)`). The digest requires `isGaugeBandRobustToWithheldWeight()` plus unchanged regime and risk-tape tone at both interval endpoints; a kept gauge carries `mint-burn-gauge-valuation-partial-band-stable`, while a positive count without published weights withholds it. FTQ uses `detectFlightToQualityFromValuedNets()`: exact, provably inactive, or `null` with its cause in `gauge.flightToQualityReason` and any pending-admission exclusion in `gauge.flightToQualityExcludedIds`; classification debt names `classification-unresolved` or `classification-unknown`; cached reclassification uses the same rule and absent coin valuation is unknown. Stablecoin OG cards show partial seven-day flow as `7D GROSS (MIN)` (`$X+`) and unknown flow as `7D NET (UNVERIFIED)`, never signed partial net.
- **Transition window:** existing legacy valuation may retain its labelled old-method known-valued net only after independent scan admission under the bounded transition or v2 rule. This does not waive missing event-time prices: partial valuation keeps signed nets and pressure unavailable. Sparse buckets alone cannot authorize quiet zero; raw-event rebuilds cannot reconstruct pruned history.
- **Event-time pricing (v6.23):** parse and the 48-hour heal value an event only through `resolveMintBurnEventPrice()` (`worker/src/lib/mint-burn-pipeline/context.ts`); see [Sync Algorithm](#sync-algorithm). More events can therefore stay unpriced (backfills, new configs, `price_cache` outages, NAV observations older than 24h, nominal-par assets, and events only a snapshot could value until the first post-`0253` daily snapshot records a clock); those hours are `partial` and their raw rows stay retention-protected debt for the historical repair path.
  The healer persists its last inspected key under `mint-burn-price-heal-cursor:v1` only after successful inspection and any source/debt transactions. It resumes strictly below that key even if the cursor row was deleted; exhausting a page shorter than the 500-row budget or aging the cursor outside the current 48-hour cutoff wraps the next pass to newest-first. This revisits new arrivals and previously ineligible rows when evidence becomes available without widening the inclusive ±24h policy. Evidence-less rows stay NULL. Healing still enqueues the existing durable materialization debt, and completion independently drains it; the scan adds no schema or index.
- **Historical repair admission:** daily supply snapshots use the same actual-clock projection and event-price resolver as parse/heal, including positive integral read-time-valid clocks, peg plausibility and inclusive ±24h event distance. The scanner considers nearby snapshot days rather than inventing a clock from the day label; an invalid or unclocked snapshot cannot suppress event-day provider fallback. Recovered rows persist the admitted observation timestamp, and already-valued rows are never overwritten.

## Retention

The critical `sync-mint-burn` producer owns bounded cleanup and aggregation-evidence repair after ingestion:

- Individual `mint_burn_events` rows are retained for at least **8 days**. An older row is eligible only after its USD valuation is settled (`amount_usd` is present or price repair is explicitly `recovered`/`irreducible`), its stablecoin/chain/hour aggregate exists, the Tape projector cursor has passed its timestamp, and any unsuppressed Tape claim for the row still matches its amount, flow and burn fields (a corrected source is kept until the claim is republished or retracted, so history older than the eight-day window is never reconciled). The shared whole-hour finality guard protects **all siblings**, including priced rows, whenever any sibling has unresolved valuation, pending aggregation, or a block beyond a matching config's committed scan frontier.
- A `mint_burn_dirty_hours` key protects **every raw sibling** in that stablecoin/chain/hour, even if all events are priced and an older aggregate exists. Dirty hours are also excluded from missing-bucket evidence repair; only the atomic maintenance rebuild can settle their debt. Independent completion draining releases that whole-hour protection only after the rebuilt bucket and applicable repair finalization commit together; interruptions leave debt for a later run.
- A missing hourly bucket for terminal, projected raw rows is rebuilt oldest-first before deletion. Unresolved or pending hours are neither rebuilt nor pruned. Missing sync state fails closed for active, enabled configs: every matching stablecoin/chain frontier, including secondary contracts across both lanes, must cover the hour's raw blocks. Disabled admitted configs (registry flag, runtime ID/key or symbol policy) and inactive assets do not hold frontier protection. Pending identities, including disabled ones, additionally require current-fingerprint finalized proof ending at the committed cursor and covering the candidate whole hour before ordinary retention applies. Their incomplete frontier/later hours, initial partial hour and hours without matching proof remain protected; proven completed hours retain ordinary eight-day, valuation, Tape and materialization fences. The 50,000-event candidate and 5,000-hour repair budgets remain in force; there is no age-based deletion escape. Historical price repair recalculates and verifies only its affected hours, preserving unrelated aggregate history.
- Proven events, including rows carrying `supply_proof_id`, follow the normal eight-day raw-retention rules; proof references alone do not extend retention. Existing unresolved-event protection preserves the complete coin/chain/hour. The same bounded cleanup job prunes proof records only after their range is older than raw retention and no retained event references them. Successful empty ranges carrying no event authority do not create proof rows. Durable configuration fingerprints and scan coverage preserve invalidation after raw/proof evidence expires, without retaining every proven hour for the public 90-day window.
- `mint_burn_hourly` buckets are retained for at least **95 days**, preserving the public 90-day aggregate window with a five-day operating margin. Cleanup never removes a bucket while any raw event still depends on it as aggregation evidence.
- Repairs are capped at 5,000 hourly buckets per critical run. Deletes run oldest-first in 10,000-row statements, capped at 50,000 event rows and 25,000 hourly rows per critical run. Event deletion, repair selection and their backlog probes materialize whole-hour eligibility in one grouped pass over the coin/chain/timestamp index, including all siblings in the cutoff-straddling hour. Eligible hours are ordered by their first Tape-eligible event and limited to the event candidate limit (one for backlog probes); applying protections before that limit prevents protected old hours from starving newer eligible rows. Protected history still requires a linear pass per statement; this is not a hard examined-hour bound. Independent families reuse the shared D1 idle pacing (three times elapsed family time, or a full resource-window cooldown after exhaustion). The extended lane does not run cleanup.
- Cron metadata reports aggregation repair and deletion cutoffs, changed counts, oldest backlog timestamps, cap states, durations, and errors. `retention.frontierProtection.configs` identifies each enabled config holding an expired hour: config/coin/chain identity, `lastBlock`, `highestProtectedBlock`, `lagBlocks`, `oldestProtectedHour`, and `oldestProtectedAgeSeconds`. Missing state has null frontier/lag, not fabricated progress; a failed diagnostic read publishes null configs and an error, not an empty healthy list. Cleanup or diagnostic failure degrades an otherwise successful critical run without discarding ingestion.

The daily `mint-burn-growth-watchdog` remains a fail-safe rather than the retention owner. At **2.3M event rows** (the existing proxy for the agreed ~5 GB investigation point), it returns `status=ok` with `metadata.quality.reason="row-count-threshold"`; it does not emit a degraded ingestion verdict. Each execution independently uses `COUNT(*)` on current `mint_burn_events`, and an unavailable or invalid count fails the job rather than reporting zero. The same daily run compares each enabled leg's trailing 7-day counted events with its 30-day baseline, using the same registry, runtime ID/key and durable symbol-disable scope as the producer (including retained keys for an ambiguous ticker): a leg with at least 30 baseline events and no event for a full week returns `status=ok` with `quality.reason="mint-burn-activity-collapse"` and `firedRuleIds: ["mint-burn-activity-collapse"]`; an unreadable baseline degrades the run with `mint-burn-activity-baseline-unavailable` instead of reporting healthy volume. An unreadable durable disable scope degrades it separately with `mint-burn-disabled-policy-unavailable` and `disabledPolicyUnavailable: true`; `activityBaselineUnavailable` stays tied to the activity query.

## Database Schema

Exact columns, constraints, and indexes live in `worker/migrations/0000_baseline.sql`, the follow-on migrations named below, and `worker/migrations/MANIFEST.md`. This section owns the table roles and flow semantics, not a second DDL copy.

### mint_burn_events (current excerpt; baseline plus later indexes)

`mint_burn_events` is the transaction-addressable recent event ledger with the protected 8-day retention policy above. It preserves token-native amount, optional event valuation and its source timestamp, chain/transaction provenance, counterparty, burn classification, and economic-flow classification. `standard`, `bridge_transfer`, `atomic_roundtrip`, and `protocol_internal` semantics decide whether a row contributes to aggregates; burn rows additionally distinguish effective burns, bridge burns, and review-required evidence.

Migration `0178_historical_data_debt_closure.sql` owns bounded historical price-repair state and its provenance columns; migration `0234_mint_burn_price_repair_backlog_index.sql` owns the repair backlog index (`idx_mbe_historical_price_repair_backlog`). Repair provenance distinguishes retryable unclassified debt, aggregate rebuild pending, recovered rows, and irreducible exact-day gaps; it also binds mutation attempts to their operator run and pre-run Time Travel bookmark. Migration `0097_mbe_flow_type_ts_index.sql` owns flow-classification query support. Exact index membership stays in the migrations.

### mint_burn_hourly (baseline `0000_baseline.sql`)

Pre-aggregated stablecoin/chain/hour buckets store counted mint and burn volume, event counts, signed net flow, nullable per-side unpriced counts and nullable per-side unresolved classification counts. The cron rebuilds affected buckets after ingestion; repair and reclassification paths recalculate the same canonical buckets before declaring completion.

### mint_burn_supply_proofs (`0301_mint_burn_supply_proofs.sql`)

Immutable proven, nonempty range evidence is keyed by `proof_id`, with config/range indexes and an independent pending/accepted/invalidated lifecycle. Nullable `mint_burn_events.supply_proof_id` retains exact proof membership without changing older named-column writers; migration 0300 owns `amount_raw`, and the partial `idx_mbe_supply_proof` index supports member acceptance/invalidation lookups. The immutable JSON payload owns source law, identity, pinned boundaries, integer arithmetic, event-set digest and evidence clocks; no foreign-key cascade can delete financial history. Evidence retention is bounded as described above. The small `mint_burn_supply_proof_configs` table retains the last config/law fingerprint per reviewed family key, including removed-key tombstones; its size is bounded by the reviewed identities ever seen, and invalidation does not depend on old proof records surviving.

### mint_burn_sync_state (baseline `0000_baseline.sql`)

This table owns the monotonic last-processed block for each chain/contract configuration. Cron and backfill ingestion share it, and partial backfills must never regress the stored frontier. `upsertMintBurnSyncState()` commits the cursor (with its scan-coverage merge) through `runWithOverloadRetry()`: the monotonic cursor and the coverage merge/compact converge on the same interval, so replaying a commit whose `Network connection lost` response hid a successful write is idempotent.

### mint_burn_config_deferral (baseline `0000_baseline.sql`; originally migration 0096)

Per-config deferral protects healthy work: more than five API errors plus less than 80% or unavailable coverage defers a configuration for one hour.

**Migration history:** The earlier per-step mint/burn migrations were squashed into the baseline; the `mint_burn_events`, `mint_burn_hourly`, and `mint_burn_sync_state` tables now live in `0000_baseline.sql`. `worker/migrations/MANIFEST.md` is the lineage authority.

## API Endpoints

These headings remain stable for feature-document navigation. The exhaustive HTTP contract is owned by the linked endpoint sections in `docs/api-reference.md`.

### GET /api/mint-burn-flows

All API totals and series use closed UTC hours: `end=commonWatermark`, `start=end-hours*3600`, with buckets in `[start,end)`. Responses publish `window: {start,end,semantics:"closed-utc-hours",watermark}`; the open current hour is excluded. Aggregate chart hours vary, but coin counts, volumes, pressure and largest events use 24 closed hours ending at that same boundary; 7d/30d/90d nets share it. Expired cached watermarks fail closed rather than being renewed by a newer cache-read or sync clock.

Parameters, response fields, cache/freshness behavior and errors are canonical in the [HTTP reference](https://github.com/TokenBrice/pharos-watch/blob/main/docs/api-reference.md#get-apimint-burn-flows).

Aggregate mode constrains configured `(stablecoin_id, chain_id)` pairs in SQL and selects the deterministic largest 24-hour event per coin there; the Worker does not materialize the full event day to compute that field.

Known quarantined coins retain per-coin history over their own admitted, enabled legs and frontier, without joining aggregate scope. A known configured coin with no admitted legs still returns `200` with a dense unavailable series and unavailable net/coverage, not stored pending or disabled totals. Initial admission/proof lookup failures use the same last-valid per-coin cache fallback as hourly query failures.

Each aggregate coin row publishes `pressureShiftScore` as the sole baseline-relative score field. The former `flowIntensity` alias duplicated the same value and is no longer part of the response contract.

`shared/types/mint-burn.ts` owns the producer and reader DTOs. The Worker derives `CoinFlowSummary` from `MintBurnCoinFlow`, requiring live `coverage` and `valuation` rather than maintaining mirrored interfaces; declared reasons survive shared-schema parsing. Per-coin totals, chains and hourly buckets carry their own `scanCoverage` block and withhold signed nets independently of their observed gross/count subtotals.

### GET /api/mint-burn-events

The event feed exposes recent classified, valuation-aware events above the native display threshold for one stablecoin; flagged accounting rows are omitted in every scope. Safely settled, aggregated, and Tape-projected rows remain available for at least 8 days; the separate hourly aggregate keeps 90 days of public flow history. The detail-page history deliberately uses the counted view so bridge transfers, review-required burns, and atomic roundtrips do not appear as ordinary economic flow.

Both `scope=all` and `scope=counted` constrain event selection and total counts to admitted, enabled config pairs before pagination. Pending or disabled legs remain stored but are absent from this public feed; a configured chain outside current admission returns an empty page rather than leaking its stored rows.

Filters, pagination, ordering, response fields, cache/freshness behavior and errors are canonical in the [HTTP reference](https://github.com/TokenBrice/pharos-watch/blob/main/docs/api-reference.md#get-apimint-burn-events).

### Operator CLI: backfill-mint-burn-prices

The recent cron path auto-heals bounded NULL-price debt; this operator path handles older history. Stored snapshots use actual observation clocks within inclusive ±24h of the event, including nearby UTC days; historical-provider fallback accepts only the exact UTC event day. Neither path invents a clock, current spot or peg-par price. Definitive no-source results become irreducible, transient failures remain retryable, and recovered rows stay `pending_aggregate` until affected hours are rebuilt and verified. Interrupted runs resume aggregate verification before new valuation work.

Operator auth, dry-run/confirmation/bookmark/idempotency and execution requirements have one owner in the [historical price-repair runbook](https://github.com/TokenBrice/pharos-watch/blob/main/docs/runbooks/one-shot-backfills.md#backfill-mint-burn-prices) and [integrity repair sequence](https://github.com/TokenBrice/pharos-watch/blob/main/docs/runbooks/mint-burn-integrity.md#historical-price-debt). Live aggregate replacement requires the [atomic-import availability gate](https://github.com/TokenBrice/pharos-watch/blob/main/docs/runbooks/one-shot-backfills.md#transport-safety).

### Operator CLI: backfill-mint-burn

Operator EVM ingestion shares finalized-head admission, bounded log fetching, parsing, classification and persistence with cron. Since v6.43 it scans all chunks before writing or rebuilding, including first/last block timestamps for quiet chunks. A touched hour must be closed and lie wholly within the retained-raw window (the same whole-hour floor as coverage repair), or lie strictly inside this invocation's complete scanned time range for every config in the coin/chain bucket. Because the job selects one config, expired shared buckets (including BUIDL's two share classes) cannot qualify. Range-edge fragments and open hours are refused. Any unsafe touched hour refuses the entire event-write/materialization/cursor phase, with `skippedHours[].reason`; this also prevents the persistence helper from queuing an unsafe deferred rebuild. `done=false` and `nextFromBlock` retain the invocation's start. No raw rows are inserted by a refused invocation.

Decode-incomplete ranges, including third-observation quarantine, refuse the write phase and never release the frontier; fetch, timestamp or context shortfalls abort before event writes. Complete accepted jobs rebuild once after scanning, then commit their finalized cursor. `scannedToBlock` is scan progress, not committed coverage; `hoursRebuilt`, `skippedHours` and `incompleteRange` disclose the outcome. This path writes no scan proof and has no staged historical replay store; a whole-hour/all-config historical repair system remains a separate operator campaign. Tron continues through scheduled catch-up, with explicit operator selection rejected as `mint-burn-operator-chain-unsupported: tron`.

Operator arguments, execution/atomic-import guards, selection/range parameters, progression, counters and errors are canonical in the [ingestion runbook](https://github.com/TokenBrice/pharos-watch/blob/main/docs/runbooks/one-shot-backfills.md#backfill-mint-burn).

### Operator CLI: reclassify-atomic-roundtrips

This bounded repair applies the shared exact raw-unit rule in both directions: eligible, exactly balanced groups become atomic roundtrips, while known-raw unequal or ineligible atomic groups return to standard flow. Legacy groups without raw amounts keep their existing tags. Every affected hourly bucket is recalculated before a batch reports completion.

Operator arguments, execution/atomic-import guards, scope, batch progression, counters and errors are canonical in the [roundtrip-reclassification runbook](https://github.com/TokenBrice/pharos-watch/blob/main/docs/runbooks/one-shot-backfills.md#reclassify-atomic-roundtrips).

## Cron Metadata Fields

`completeMintBurnRun()` owns bounded cron metadata: actual throughput, selected lane/job, source/config coverage, API/bridge shortfalls, decode/roundtrip diagnostics, recalc outcome, request/deadline stops, the extended-lane `coverageCycle` block and NULL-price debt. `attemptCoverage` keeps per-config attempt evidence (never a verdict); `coverageCycle.status`/`coverageCycleSec`/`expectedWindowSec` own the extended-lane verdict and are absent from critical-lane metadata. `coverageCycle.stuckConfigs` lists configs attempted twice without advancing, and a nonempty count degrades the run with `mint-burn-config-stuck`. Full per-config drilldown lives separately under its cache key, not in a second field catalog here.

The scheduled slot adds `providerOutcomes` from invocation-scoped RPC observations: provider/circuit identity, request success/failure/neutral counts, blocked requests, `terminalFailures` and machine-readable reason counts. Request counters are diagnostics; `terminalFailures` counts failed admitted config/head scopes after retries, not failed requests. The Access-protected cron detail endpoint retains this metadata. Publication membership and pending progress are separately exposed by the flow response's `publication` block.

Parsed rows are not inserted rows. NULL backlog counts with `nullPriceBacklogAvailable: false` mean a failed retried read, not no debt. `recalcFailed` means cursors did not commit even if event inserts succeeded. A saturated sweep can leave backlog beyond this run. These distinctions govern repair; metadata field definitions are source-owned.

### Page

The public [Flows page](https://pharos.watch/flows/) uses the instrument header (one-line deck, folded lead, methodology line, Share). Its order is answer, table, evidence, footer:

- **Hero** (`FlowGaugeHero`, `src/components/flow-gauge-hero.tsx`): the One Beam is `gauge.score` (`formatBankRunGaugeScore`) in neutral ink beside its published band chip (`GAUGE_BAND_LABELS` / `GAUGE_BAND_TONE_CLASSES`). A null score renders "—" with a `Not rated` chip (`gauge-score-null`). When `partialValuationInputs > 0` the beam label adds "partial: N weighted coins withheld" (the share card's stamp says the same) and an `Incomplete flow inputs` chip (`partial-valuation-inputs`) carries the scored and withheld weights. When that withheld weight could carry the full-cohort score across a band edge (`assessGaugeBandSettlement()` in `shared/lib/mint-burn-gauge-bands.ts`, the same `isGaugeBandRobustToWithheldWeight()` rule the daily digest applies), no band is printed: the beam shows the score alone, a `Band unsettled` chip (`band-not-robust-to-withheld-weight`) carries the score interval, the verdict drops its band sentence, and the share card omits the band and stamps "band unsettled". `mcapUnavailableCoins`, unavailable FTQ, `sync.warning` and a degraded or stale read are chips too (`mcap-unavailable-coins`, the published `flightToQualityReason` (falling back to `valuation-incomplete`) / `classification-unavailable`, `freshness-<status>`, `data-health-<state>` plus its reason), never body callouts or headlines; the shared freshness banner remains only when no data loaded. ### Valuation Completeness Rendering

Frontend consumers read the additive `valuation` fields through `resolveMintBurnValuation()` / `resolveMintBurnValuationCompleteness()` (`shared/lib/mint-burn-valuation.ts`), so a payload without `valuation` is `unknown`, never complete. Presentation helpers live in `shared/lib/mint-burn-valuation-display.ts` and `shared/lib/mint-burn-coin-helpers.ts`; the shared `FlowSignedNetValue` / `FlowVolumeValue` components (`src/components/flow-valuation-value.tsx`) render them.

- **Scan-window activity:** `has24hActivity: null` gates unproved windows for legacy readers, including observed-but-unscanned windows. Current readers retain observed activity through `observed24hActivity: true`; false does not override an unknown legacy gate. Unknown rows remain visible and contribute unavailable rather than idle/zero to totals. Observed activity never overrides incomplete scan proof: direction, pressure, literal dial and signed bounds stay unavailable. Gross values render as `≥` observed subtotals whenever scan coverage is incomplete, including fully priced nonzero observations and zero observations; valuation completeness is unchanged. The producer retains PR-B's null gate so normal Worker-before-Pages activation is safe.

- **Signed nets** (`netFlow*Usd`, hourly `netFlowUsd`): `null` or a `partial` window renders the component's unavailable placeholder (`—` or `NR`) with an accessible reason naming the unpriced mint/burn event counts, never `$0`. Since v6.25 a partial net with a proven one-sided bound renders as `≥ $X` / `≤ $X` (`FlowSignedNetValue`), coloured only when the bound proves the sign, with a reason naming the unpriced side; it is never shown as the net itself. `unknown` keeps the value with a `*` coverage-unknown marker.
- **24h direction**: producers and client overview sums use `provenNetFlowDirection24h()` with per-side completeness, including legacy `unknown` windows whose old-method net stays visible. The client aggregate adds a partial coin's known subtotals (mint − burn) to the proven range rather than discarding it (v6.25). A partial older payload with a numeric net is re-derived by the same helper; an unproven direction renders "Direction unavailable", never `flat` or `No activity`.
- **Pressure shift**: a partial 24h window or baseline renders `NR` with a partial-valuation reason and sorts last. The baseline average daily net is withheld when baseline valuation or classification is incomplete or the coin has partial scope.
- **Gross volumes**: a non-complete side renders as a `≥` lower bound (known-valuation subtotal).
- **Client-side sums** (overview/receipt totals, home mini card, chart re-bucketing): any null or partial component makes the summed signed net unavailable; an empty coin population (a failed or generationless summary read, passed as `coins: []`) is missing evidence, so the net, direction and scan proof are unavailable rather than a complete zero; leaders and sorts rank only displayable nets, never bounds; the "Largest valued event" sort puts an unavailable (dash) event last in both directions, after an observed zero, and the 7-day receipt prints `Unavailable` instead of `None` for an absent leader only when no coin has a displayable 7d net. ## Error Handling & Edge Cases

| Condition | Behavior |
|-----------|----------|
| No admissible price within ±24h of the event | `amount_usd` remains NULL; a counted event makes the hour partial (net unavailable, pressure NR). Cron heals recent rows (48h) with in-window evidence; the operator price-repair CLI handles older history |
| Fewer than 7 days of flow history | Pressure shift returns `null`; coin excluded from gauge weighting |
| No 24h mint/burn activity in a sparse window | Pressure shift returns `null` (NR) for that window; coin excluded from gauge weighting |
| All coins have null pressure shift | Gauge score returns `null`; the overview displays `NR` without a gauge marker |
| Alchemy API error for a config | `apiErrors` increments; a partially successful scan may stage the shared safe frontier, while a failed event definition with no covered prefix holds advancement |
| Incomplete timestamp resolution | `apiErrors`/`errors` incremented; sync state advances only to the safe coverage frontier (`earliestMissingTimestamp - 1`), or not at all when no safe frontier exists |
| Undecodable event amount | Hold at the safe frontier for two retries; on the third observation quarantine only that log as `amount-decode-retry-exhausted`; coverage remains unproved and retryable |
| Subrequest budget exhausted | Remaining configs skipped; picked up in next cron cycle |
| Finalized head unavailable or unsupported | Named `finality-head-unavailable` coverage, no tip scans or cursor advance; unaffected chains continue and cron status degrades immediately |
| Duplicate events | `INSERT OR IGNORE` on deterministic `id` key prevents duplicates |
| Unknown stablecoin ID in per-coin API | Returns 404 with descriptive error |
| Missing `stablecoin` param in events API | Returns 400 |
| Partial-coverage cron run | Hourly aggregation rebuilds from all DB events for affected hours; buckets may be temporarily incomplete for configs still catching up |

### Circuit Breaker Separation

Blacklist and mint/burn retain source-specific circuit breakers:

- **`CIRCUIT_SOURCE.ETHERSCAN`** — used by `sync-blacklist` (Etherscan REST API)
- **`CIRCUIT_SOURCE.ALCHEMY`** — run-level outcomes from both mint/burn lanes, with failures attributed to terminal Alchemy config/head work
- **`CIRCUIT_SOURCE.DWELLIR_EVM`** — owned by provider parity and runtime admission; mint/burn retains Dwellir observations but never writes this circuit

An Alchemy outage does not block blacklist sync, and vice versa. Each circuit breaker opens after consecutive failures and probes independently.

`mint-burn-slot.ts` retains Alchemy's run-level semantics: `ok` (including the implicit default) is a success only when an Alchemy request completed, `degraded` is neutral, and `error` is a failure only when required RPC evidence remains incomplete in an admitted config with observed Alchemy failures, or an Alchemy-failed head remains unavailable for an admitted chain. A completed config clears its recovered request failures; pending configs, thrown local work and another provider's failures do not establish Alchemy causality. Mixed runs retain protection for a terminal Alchemy config even when another Alchemy config succeeds. Only Alchemy receives a mint/burn circuit outcome; other providers retain diagnostic observations.

Required log definitions, event timestamps, transaction contexts and proof boundaries retain independent operation evidence. A successful fallback clears that operation, each retry discards earlier-attempt evidence, and another successful operation cannot erase a terminal failure. Maintenance and conservation-only reads remain diagnostic. Observed transport, HTTP, parse, invalid-envelope and explicit RPC server/rate-limit failures can establish provider evidence inside those scopes. Semantic reverts, unsupported methods, invalid parameters, range caps, unavailable objects, cancellation and requests blocked before admission remain neutral. Recognized semantic JSON-RPC rejections remain neutral on client-error HTTP responses such as 400; credential, timeout, throttling and server-error statuses retain failure precedence. Request splitting and retries cannot fail an otherwise healthy run.

An open Alchemy circuit blocks only Alchemy requests before network admission, leaving other admitted endpoints usable. A denied transaction-context read returns unavailable context, keeps affected rows/frontiers retryable with `tx-context-request-not-started`, and lets other configs continue; caller cancellation still aborts. Disable-policy persistence still runs. Critical degraded-streak escalation alone, local persistence errors and the aggregate publication sidecar cannot open Alchemy's circuit. The sidecar runs outside RPC observation, and its publication/freshness reasons remain separate. Circuit evidence does not replace per-config scan, conservation or publication admission.

`mint-burn-pipeline/rpc.ts::mintBurnRpcEndpoints()` consumes the scheduled runtime's already-admitted `chainRpcs` map. An enabled Dwellir endpoint with full log history is first for each configured EVM mint/burn chain, followed by the existing Alchemy URL; the former Ethereum/Arbitrum/Base-only fallback roster is removed. Missing admission, unsupported logs or `DWELLIR_ROUTING_DISABLED_CHAINS` keep Alchemy alone for EVM, with incumbent windows and budgets. Only Tron is exempt from the Alchemy-URL requirement: it uses the admitted native reader with TronGrid JSON-RPC fallback. Request/admin paths never acquire Dwellir. Heads, logs and hash-checked timestamps/receipts use their chain's provider order; conservation's historical supply/guard phase separately excludes recent-only Dwellir state and remains unsupported for Tron. Each endpoint's own budgeted head bounds its log frontier; a lagging fallback cannot prove the tail. Dwellir pages clamp to registry `maxLogBlockSpan` (usually 10,000), so successful scans can require more calls within the unchanged cap. Failed pages retain only the proven contiguous frontier. Registered auth and per-member metering cover every physical Dwellir request, including bounded unexecuted-batch retries. Existing subrequest caps/deadlines and receipt concurrency remain unchanged. Tron transport outcomes attribute to the contacted Tron provider path, never Alchemy; this source adds no historical-state capability.
