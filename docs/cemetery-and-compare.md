# Cemetery and Compare

## Overview

This document covers two frontend-only feature surfaces that are not backed by dedicated page-specific worker endpoints:

- `/cemetery` — static memorial dataset + interactive UI
- `/compare` — indexable multi-source live compare tool plus static pair-directory hub
- `/compare/[slug]` — static comparison landing pages generated from tracked metadata

## Stablecoin Cemetery (`/cemetery`)

The route title and description count from `buildCemeteryStats(CEMETERY_ENTRIES)` (total and per-cause tally with `CAUSE_META` labels; the description dates the failure window from the first death year), the same stats the hero and cause strip render.

`src/app/cemetery/page.tsx` owns the static shell. `shared/lib/cemetery-merged.ts` supplies data; `src/lib/cemetery-stats.ts`, `cemetery-register.ts` and `cemetery-selection.ts` own projections/navigation. `src/components/cemetery/` owns rendering and interaction.

### Data model

Cemetery data is static and versioned in-repo. The curated dead-coin dataset lives in `shared/data/dead-stablecoins.json` and is validated and exported as `DEAD_STABLECOINS` by `shared/lib/dead-stablecoins.ts` through `parseDeadStablecoinAssets`. The route, the public dataset export, the `/feed/cemetery.xml` RSS feed (`src/app/feed/cemetery.xml/route.ts`), the logo atlas and the worker cemetery tape projector (`worker/src/lib/tape-projectors/cemetery.ts`) consume `CEMETERY_ENTRIES` from `shared/lib/cemetery-merged.ts`, which combines those curated dead rows with frozen tracked stablecoins.

- `recordedAt`: <!-- GENERATED-START: cemetery-recorded-at-description -->UTC cemetery-entry/documentation date (YYYY-MM-DD); tracked rows default to frozenAt unless obituary.recordedAt explicitly overrides it. Distinct from deathDate; null when not recorded.<!-- GENERATED-END: cemetery-recorded-at-description --> Drives "Latest record added" and dataset `updatedAt`.

Frozen rows also carry `archivedDataAvailable: true` (the `CemeteryEntry` type); curated rows leave it absent.

`DeadStablecoinSchema` owns identity/narrative fields. Death dates use strict Gregorian `YYYY-MM` or `YYYY-MM-DD`; impossible days reject, never roll forward. Approximate peak is optional when not reliably sourced, never a zero placeholder. Mechanism is how the peg was designed, independently of cause of death.

Cause labels, approved definitions and theme colours derive from `shared/lib/classification.ts`; `shared/lib/cause-of-death.ts` adds `CAUSE_ORDER`. Consumers must not maintain independent vocabularies or imply a loss/risk ranking from categorical cause colours.

### Curating a record

The page prints its inclusion and primary-cause rules in the methodology section (`CEMETERY_INCLUSION_RULE` and `CEMETERY_PRIMARY_CAUSE_RULE` in `src/components/cemetery/cemetery-context.tsx`). That copy describes the whole archive as it stands: each record links one public source, most of which document the failure or discontinuation directly, while a coin that faded without an announcement links the best public context Pharos found. The page never calls the set "primary sources". New curated rows in `shared/data/dead-stablecoins.json` meet a stricter bar:

- **Inclusion.** A new record needs a public market and a primary public source documenting failure/discontinuation: issuer/protocol announcement, governance record, official docs/status, regulator/court/registry filing or on-chain evidence. Prefer that source in `sourceUrl`; reputable press qualifies only when it documents the same event. Listings, provider ended/deprecated markers, launch/fundraising articles and general wikis do not qualify. There is no size floor. Older contextual-source records do not weaken this new-row bar; never represent the whole archive as primary-source evidence.
- **Primary cause.** Each record carries one primary cause: the root reason the coin failed or its issuance and operation ended, whether or not it lost its peg. Triggers such as runs, exploits or orders are described in the obituary.

Every new curated row sets `recordedAt` to the UTC date it is added to Pharos. `parseDeadStablecoinAssets` rejects a curated row without a valid strict `YYYY-MM-DD` `recordedAt`. Set `mechanismArchetype` as well: the schema accepts its absence, but every curated row is classified today and `shared/lib/__tests__/cemetery-merged.test.ts` fails on an unclassified curated row. Classify how the coin was designed to hold its peg, independently of how it died.

A curated row may share provider identity with a still-tracked coin only through `ACTIVE_DEAD_LLAMA_ID_OVERLAP_ALLOWLIST` in `scripts/ci/check-stablecoin-data.ts` (Kava USDX, Hubble USDH). Such a row is a historical assessment, not a current exclusion: its obituary must not direct coverage to skip the tracked coin or state current-market facts the active profile contradicts.

New ids must not equal a section anchor or start with a reserved element-id prefix (`CEMETERY_SECTION_ANCHORS`, `CEMETERY_RESERVED_ID_PREFIXES`); `findCemeteryIdCollisions` must stay empty for the real set.

Every new death also has to fit the plot map. `src/lib/__tests__/cemetery-plot-map.test.ts` runs `validatePlotMapCapacity` on the real data in both presets, so a record that overfills a year block or shrinks plain stones below `PLOT_LAYOUT.faceFloorPx` fails the suite. Treat that failure as a design review: retune the lane depths in `PLOT_MAP_PRESETS` (or, as the archive approaches a few hundred records, add a deliberate overview and zoom policy), and never lower the face floor to make stones fit.

### Order authority

`sortCemeteryCoins` in `shared/lib/cemetery.ts` is the single cemetery order. The register's Died sort, the page's JSON-LD `ItemList`, the RSS feed, the dataset export and the case-study list all use it. Its keys, in order:

1. `deathDate` by year, month, then day, newest first (`oldest` reverses this key only). A month-precision date sorts as the start of its month, so newest-first lists a month's day-precision rows before its month-precision rows. A `deathDate` that does not parse follows every dated row in both modes.
2. Peak market cap descending; rows with no recorded peak follow known peaks.
3. Symbol ascending, then id ascending, compared by UTF-16 code unit so the order is identical in every runtime and locale.

Identical data always yields the same order regardless of input order. Source-file order is non-contractual. The dataset's `recordsOrderedBy` text describes these keys and must change with them.

### Public dataset export

`scripts/maintenance/generate-cemetery-dataset.ts` consumes `CEMETERY_ENTRIES` and writes one combined row set, in `sortCemeteryCoins` newest-first order, to static export files:

- `/datasets/stablecoin-cemetery.json`
- `/datasets/stablecoin-cemetery.csv`

The generator owns schema, field descriptions and CSV order. Metadata includes provenance/checksums, licensing, canonical URLs, ordering, counts and limitations. `updatedAt` is latest `recordedAt` (entry, not death/build time), null only when no record has one. JSON missing optionals are null, absent contracts an empty array; CSV missing cells are empty, never zero. `pharosUrl` points to archived detail when available, otherwise `/cemetery/#<id>`. Both formats contain the same merged ordered rows.

The `cemetery-dataset` artifact owns regeneration: run `npx --no-install tsx scripts/maintenance/generate-cemetery-dataset.ts` after source edits and commit outputs. Provenance pins curated JSON, frozen projection and consumed cause labels; label changes rotate checksum, unrelated active edits do not. Current Telegram snapshots use stable cemetery `id`; optional `llamaId` only aids legacy deduplication.

`buildCemeteryDatasetJsonLd` uses the checked-in header for Dataset schema at `/cemetery/#dataset`, alongside CollectionPage/ItemList. Link public JSON/CSV distributions, producer `updatedAt`, field descriptions/checksum/count, the death-date `temporalCoverage` interval read from the export rows and the public data catalog (`includedInDataCatalog`), never private site-data URLs or fabricated dead-coin profiles.

### RSS feed

`/feed/cemetery.xml` publishes the 50 newest records in `sortCemeteryCoins` order (`CEMETERY_FEED_MAX_ITEMS` mirrors the limit for page copy). Each item is titled `Name (SYMBOL): Cause label` with the `CAUSE_META` label, links to `/cemetery/#<id>`, uses `pharos:cemetery:<id>` as its GUID, and dates `pubDate` from `deathDate` (a month-precision date uses the first of the month).

### Frozen entries in the cemetery

`frozenToDeadShape()` in `shared/lib/cemetery-merged.ts` projects tracked obituaries, mechanism and contracts into archived entries linked to `/stablecoin/<id>/`; curated rows retain cemetery links. `recordedAt` defaults to `frozenAt`; a strict UTC `obituary.recordedAt` may override entry date without changing historical freeze date. Invalid dates throw. Frozen IDs are registry IDs, curated IDs remain stable cemetery identities; duplicates fail merge. Sort by deathDate, never frozenAt.

### Telegram channel notifications

`worker/src/telegram/digest/digest-appendices.ts` compares deployed dataset with D1 snapshot during daily digest delivery. Seed silently on first run; new rows become one consolidated next-digest appendix with available epitaphs. This is not a separate API feed. Digest delivery uses the Worker's `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID`.

### Selection and deep links

`CemeterySelectionProvider` alone owns hash, parsing mount/hashchange with echo suppression. Registered handlers own scrolling/motion. Record hashes request both pin and reveal; pre-registration requests queue latest-wins. `setRecordHash` replaces history, never adds entries. Pin/source state is separate from register reveal; responsive handoff must not replay scroll/focus, reopen dismissed pins or show a portrait sheet for a hash reveal.

Anchors:

- `#<id>` is the canonical public record anchor. RSS items, dataset `pharosUrl` values for curated rows, and the register's "Copy link" all use it. The register's main row carries `id="<id>"` and a scroll margin that clears the sticky chrome.
- `#obituary-<id>` is a legacy alias. `parseCemeteryHash` resolves it to the record, and the provider rewrites the hash to `#<id>`.
- Section anchors are `CEMETERY_SECTION_ANCHORS` (`cemetery`, `key-facts`, `causes`, `register`, `analysis`, `methodology`, `dataset`, `faq`) plus `#cause-<cause>` for each cause column. The autopsy row takes `autopsy-<id>`, a desktop grave `grave-<id>` and a phone grave `walk-<id>`; grave links point at `#<id>`.
- Unknown ids, unknown cause slugs and malformed encodings resolve to nothing.

`/cemetery/#<id>` resolves in CSS without JavaScript. The server renders the first 25 register rows (`REGISTER_FOLD_COUNT`) in full, each followed by a `hidden` autopsy row; a `@layer base` rule in `cemetery-register.module.css` shows the autopsy row after a `:target` row until the register hydrates (`data-enhanced`). Full rows replace the compact ones once the reader unfolds, filters, searches or sorts, or a reveal targets a folded record. From hydration on the client owns expansion, because `replaceState` never moves `:target`.

`revealRecord` in the register runs these steps in order: it clears any filters that exclude the row (keeping the sort) and announces that; unfolds the list; expands the row; scrolls it into view (instantly under reduced motion) and focuses its disclosure; highlights it (a static outline under reduced motion); and writes `#<id>`. The register registers its reveal handler only once the URL filters are readable, so a hash reveal queued during hydration judges the real filters. The peak chart's dots call `revealRecord` with the source `chart`, and the register's "Show on the field ↑" calls `pinGrave` with the source `register`.

Chart selection reveals with source chart. Hash pins do not scroll; register reveal owns that action and portrait hash pins only move the tab stop. Exactly one live responsive layer answers pin requests.

### Below the hero

`buildCemeteryStats(entries)` in `src/lib/cemetery-stats.ts` is the one view model for the key facts, cause band, charts, pattern headlines and FAQ. It is pure and SSR-deterministic, and its integrity rules bind every consumer:

- A missing, zero, negative or non-finite peak is "not recorded" (`null`), never zero. Sums and medians run over recorded peaks only, and every peak aggregate carries `knownCount`.
- `asOf` is the latest recorded `deathDate`, never the wall clock. `updatedAt` is the latest `recordedAt`.
- Headline counts use the full set. A trend claim ships only when it also holds on the curated records alone, because the tracked archive grew with Pharos's own coverage. A curated-only count is rising or falling only past both a 25% and a five-record change.
- Pattern headlines are guarded: a pattern whose guard fails is absent from `patterns`. "Counterparty failures are a larger share of recent deaths" compares curated records only, "Recorded deaths are becoming more frequent" appears only when the curated-only trend is rising, and "The largest coins did not all collapse" appears only when a discontinued cause (regulatory or abandoned) holds the largest recorded peak and a collapse cause has one.
- Copy says "peak market cap" and "failed or discontinued". Peak market cap measures size at the top, not holder losses; "destroyed", "wiped" or "lost" never label a peak sum, and "failure" never labels a regulatory or abandoned exit.
- `buildCemeteryFaq(stats)` templates every FAQ figure from the view model and quotes the inclusion rule.

Methodology distinguishes curated versus tracked-then-frozen admission, excludes active depegs/quarantined/delisted rows, and quotes the owning inclusion/primary-cause rules. Citation surfaces use `CEMETERY_DATASET_META`, never local counts/build times; dataset metadata facts stay unsplit (`whitespace-nowrap`) so wraps fall only between items.

Below-fold sections carry the hero's typography and stone vocabulary: section kickers (including the FAQ's "Questions" plate) echo the plot map's sans small-caps signpost plates, section and chart-card titles share the Cemetery's Newsreader serif (`digestDisplay.variable` mounted on the route shell), and cause markers in the causes band, register and charts draw the five gravestone shapes read-only from `graveGeometry` with colours from `shared/lib/classification.ts`. The causes band mounts the route's one `CemeteryCauseGlyphDefs` symbol sheet; every marker is an `aria-hidden` `CemeteryCauseGlyph` `<use>` of it beside visible text. The module is a client module, so a server component sends the RSC flight only a two-prop reference, and folded register rows carry no marker (route HTML budget). Key facts stay 2×2 below `lg` and 4-up from `lg`.

### Autopsy register

`buildCemeteryRegisterRows` projects data server-side; clients import types, never `CEMETERY_ENTRIES`. Missing peak/mechanism/epitaph is visibly/accessibly not recorded; duplicate tickers retain names/IDs. A tracked archive's name (full and folded rows) is a static link to its frozen profile, so the register links those profiles in the prerendered HTML; curated-only records stay plain text. The row's tap-to-expand handler ignores clicks on that link. Cause filters, cause cells, folded rows and expanded autopsies pair visible text with `aria-hidden` gravestone `<use>` references backed by one visually hidden `<symbol>` host inside `#register` (no per-row polygon duplication; works without JS).

`CEMETERY_REGISTER_PARAMS` owns filter keys, accepted values and canonical order. Invalid values drop; bounded trimmed search is case/accent-insensitive over name/ticker/id/epitaph, not obituary. URL writes replace history, preserve unrelated params and omit default sort/direction. Died uses canonical order; missing peaks sort last both directions with default order breaking ties. Result counts announce politely after a debounce; initial hydration stays quiet. A reveal announcement takes priority during its hold, including over count announcements already pending when the reveal occurs.

The server-rendered autopsy rows (first 25) carry the kicker, epitaph, obituary and source link (using a CSS-masked external-link icon matching the dataset links, never the emoji-prone `↗`), so a no-JS `#<id>` fragment shows them; the facts list (cause with a link to its definition, death date and precision, peak market cap, peg and record), mechanism (linked to its explainer), contracts, "Archived data →", the case study, "Copy link" and "Show on the field ↑" render once the row is expanded. Opening a row writes `#<id>`.

### Charts

Both charts are hand-rolled SVG driven by compact series props from `CemeteryStats`, with no Recharts on the route. Each has a `ChartDataTable` disclosure with a styled CSS chevron (no raw browser triangle), which is also the screen-reader surface. Cause legends, peak-chart lane labels and hover tooltips use the shared `aria-hidden` gravestone glyphs beside text.

- Deaths by year keeps a continuous axis, marks partial years and separates tracked/curated coverage. Empty years are catalog gaps, not evidence of no failures; absent peaks stay unrecorded. A year's median peak names its recorded denominator (`n of m recorded`) when only some of its records carry a peak. Count/share views and headlines use guarded stats.
- Peak-by-cause plots recorded peaks only, names omissions/denominators and uses deterministic jitter and roving tabindex. Jitter maps the same frozen `fnv1a32(id)` hash through `(hash / 0xffffffff) * 2 - 1`; labelled dots retain their below-lane placement. Selecting a dot reveals the register row; the data table is an equivalent screen-reader surface.

Peak market cap is never presented as a loss: the section copy states that it measures size at the top, and the only peak sums shown are over recorded peaks with their `knownCount`.

## Compare (`/compare` + `/compare/[slug]`)

`src/app/compare/` owns static shells; `src/components/compare/compare-client.tsx` composes live data. `src/lib/compare-pages.ts` owns pair descriptors, `compare-config.ts` limits/presets, and `use-compare-*` hooks selection/data/sharing.

### Route shell and SEO

`/compare/` is the indexable live tool plus complete server-rendered pair directory/FAQ. Registered `/compare/<left-id>-vs-<right-id>/` briefs generate static params/metadata from `STATIC_COMPARISON_PAGES` and reject unknown slugs. Pair actions do not promise saved watchlists. Profile actions and research links name the full recorded entity and ticker (`Open Tether (USDT) profile`, `Tether (USDT) profile`) so the destination reads as a profile, not a generic detail page.

Editorial briefs link issuer sources and keep visible short answers equal to FAQ answers. Sources-checked dates are source verification, not human review, independent audits or live reserve freshness. Enriched briefs lead without disturbing relative order within enriched/fallback groups.

Pair titles read `{A} vs {B}: Safety Scores, Reserves & Risk`, shortened to `{A} vs {B}: Safety Scores & Risk` past the title budget. When both coins have a rated grade in the `scores-latest` release mirror (`getSnapshotSafetyAssessment`, the source profile static HTML cites), the description, the Short answer, the safety FAQ answer and a first "Safety Score (as of DATE)" table row cite both dated grades; a missing grade falls back to the structural copy, never "N/A". Grades are dated facts, not a categorical safer verdict: the caveat stays.

Six reviewed pairs (`COMPARISON_EVIDENCE_PILOT_SLUGS` in `src/lib/presentation-pilots.mjs`: USDC/USDG, USDT/USDG, RLUSD/USDC, PAXG/XAUT, USDT/USDC and USDe/USDS) append at most five source-linked rows immediately after `Reserve signal`: `Latest reviewed report period`, `Assurance scope`, `Direct redemption eligibility`, `Redemption minimum` and `Redemption fee basis`. `buildComparisonEvidenceRows()` projects them from the merged `StablecoinMeta` and `getCurrentRedemptionConfig()` with no fetch, and the route passes that one row array to both the table and its ItemList so visible facts and structured data cannot drift. Other pairs keep their structural rows.

Report facts require a verified, structured `proofOfReserves.latestReport` with at least one HTTP(S) source. The period is `latestReport.periodEnd`; the scope names the reviewed method, scope and liability reconciliation, keeping `unknown` explicit as `Method not established`, `scope unknown` or `liability reconciliation unknown`. Reviewer notes and the free-text provider field are never rendered, and every recorded report source stays reachable as a numbered anchor, including both USDe reports. Citations name human-readable pages only: machine JSON endpoints (an `/api/` path, an `api.` host or a `.json` file) are never rendered, and a fact whose only citation is one of those is withheld. Redemption facts require a current reviewed config and field-scoped sources (`access` for eligibility and minimum, `fees` for the fee basis; explicit `v9RouteReviewTerms.docs` may supplement their own terms), so capacity-only sources cannot support an access or fee claim and USDS's capacity-only docs leave its cells `Not recorded`. Eligibility resolves `holderEligibility` or the route default after source admission, a suspended route reads `Route suspended`, and physical routes also expire at `physicalToUsd.reviewExpiresAt` (admitted through the expiry day). Minimums use a reviewed `v9RouteReviewTerms.minRedeemUsd`, otherwise an admitted physical route's token unit (`lot.minimumTokens`, with the commodity-delivery fallback); token units never become USD and a missing minimum stays absent. The fee cell prints the reviewed `costModel.feeDescription` with its qualifications, with four audited display overrides keeping USDT's fee minimum distinct from its redemption minimum, stating PAXG's standard tariff without an all-in ceiling, showing XAUT's issuer fee rather than a zero delivery model, and compressing USDe's reviewed fee prose. Each redemption value carries ` (reviewed YYYY-MM-DD)` from the terms it actually uses, before any final full stop.

A cell without admitted evidence reads `Not recorded`; a row with no evidenced side is omitted, so no empty heading or fabricated zero ships. The evidence-scoped table note replaces the `StablecoinMeta` provenance note only when a row exists; structural-only pairs keep the original note. Dates are the source dates, never build or publication substitutes.

Pair JSON-LD is WebPage/ItemList with coin Thing nodes and visible PropertyValue rows. Sitemap includes hub/pairs; pair lastModified is newest coin LAST_EDITED or substantive editorial updatedAt, never build/recheck time.

Each pair page ends with a "Related comparisons" section: "More {A} comparisons" and "More {B} comparisons" link lists built from `getStaticComparisonPagesForCoin()` (editorial briefs first), excluding the current pair, anchored with each pair's `{A} vs {B}` short title. A coin with no other pair contributes no list; the section is omitted when neither does.

`STATIC_COMPARE_PAIRS` (`src/lib/compare-links.ts`) admits only active, non-frozen coins with full static profiles on both sides; additions are demand-led (Search Console, or combined sibling-profile impressions where no pair query data exists). A pair without an editorial brief ships with the generated intro, summary and FAQ.

### Selection and URL contract

- Maximum selection: `MAX_COMPARE_COINS = 5`.
- Selectable coins are active plus frozen archive profiles (`src/lib/compare-config.ts`); the scope hero labels that count **Active + frozen**, never the active-only count.
- URL is the source of truth for selection state.
- Query param `coins` accepts canonical ticker-issuer IDs only (for example `usdt-tether`). Unknown IDs, legacy DefiLlama/historical IDs, and raw ticker symbols are dropped rather than guessed.
- Query param `range` stores the market-cap chart window. Accepted values are `7d`, `30d`, `90d`, `1y`, and `all`; `all` is the default and is cleared from the URL instead of persisted.
- Static comparison landing pages are generated from `STATIC_COMPARISON_PAGES` in `src/lib/compare-pages.ts` and live at `/compare/<left-id>-vs-<right-id>/`.
- Mobile selection renders selected-coin chips plus one add selector instead of all five selector slots up front. Each selected chip carries its coin's top exceptional state with specifics, because the phone matrix shows one column at a time. The underlying URL state and five-coin maximum are unchanged; desktop keeps the full slot grid.
- The shared coin selector publishes an active-option reference only for a rendered option; empty results have no active option. Every dismissal clears search and option focus, Escape restores trigger focus, and disabled options remain unselectable.

Static HTML never links a `/compare/?coins=` facet: `buildStaticCompareHref()` (`src/lib/compare-links.ts`) links the curated pair page when one exists (a coin's primary pair; for two coins, their pair) and otherwise `/compare/#coins=<ids>`, which crawlers read as `/compare/`. Once the query is readable, `useCompareSelection()` adopts that fragment into `?coins=` (an explicit `?coins=` selection wins on first load) and drops the fragment; later same-route `#coins=` navigations are re-adopted through the history-change signal. `buildLiveCompareUrl()` stays for client-side navigation and the pair pages' "Open live compare" tool links.

Initial load normalizes the `coins` URL param to the accepted canonical ID list. If invalid tokens were present, `useCompareSelection()` rewrites the URL to the surviving canonical IDs or removes `coins` entirely.

### Data dependencies

Compare composes stablecoins, peg summary, Bluechip, DEX, report cards, redemption, yield, stress and aggregate mint/burn queries plus per-coin supply/flow histories, and the coin exceptional-state ladder (`useCoinStates`, which shares the peg-summary and stress reads and adds published DDR verdicts; [design rule](./design-language.md#coin-exceptional-state)). `useCompareDataModel` owns query/window construction; successful aggregate evidence is required to claim tracking coverage.

Per-coin detail imports settle independently: a failed import keeps that coin's list metadata without inventing evidence or suppressing successful enrichment for other coins. A superseded selection's batch cannot publish late results.

An empty comparison admits only the stablecoin list used by its selector. Metric feeds enable as soon as at least one accepted comparison ID exists, including URL-initialized selections. Empty-state retries do not bypass those gates; pending evidence remains unavailable, not an empty or safe verdict.

Bluechip publication availability is separate from per-coin membership. A pending or failed whole-feed read without retained data leaves only Bluechip unavailable; a successful empty map is a usable publication. Refresh failures keep retained ratings and their original observation dates, with source error/freshness notices intact.

Compare uses the current stablecoins quote and resolves its display reference against the matching peg-summary observation.

In Normalized % mode, a displayed range that reaches a reviewed supply perimeter change (its adoption time or the ambiguous change-day label) resets that asset’s anchor to its first positive, unambiguous observation at or after adoption; earlier observations are unavailable (no tooltip value, a dash in the accessible table), while absolute mode and unaffected series retain their observations.

The safety radar baseline counts only rated cards with all three plotted pillars. Peg/mechanism cohorts below three usable members fall back to all usable rated cards; the displayed count and median use this same population. NR, pipeline-gap, and incomplete-pillar cards contribute neither counts nor scores. Fewer than three usable cards suppresses the median. A selected rated card missing one pillar is still drawn: its measured pillars plot as open segments, and the missing axis is a dashed "Unknown" spoke whose tooltip names the scoring assumption; the imputed value is never plotted.

The live-flow cards and comparison table both preserve an explicitly observed zero 24-hour net as `$0.00`, including inactive windows. Unavailable or partial valuation remains unavailable; the independent 30-day pressure rating may still be `NR`.

### Compare table context

The table and exported image share a price projection. Fixed-peg conversion uses the reference for the same observation and falls back to the observed USD mark when conversion evidence is unavailable. USD labels use adaptive precision.

The horizontally scrollable matrix is the comparable-field surface at every width; preserve accessible/narrow-screen access. Directional market-cap/issuance/yield fields are not universal winners.

The reserve cell names the scoped report as the denominator for measured selected-slice shares and uses the reviewed display label for own-liability claims. XO's share describes measured holdings in its observed Solana vault. Alto DUSD's cell names the reviewed nominal issuance paths as its denominator. Unweighted selected holdings show a scope label without ranking or percentages. A selected-slice review with entirely unknown allocation shows `Allocation unavailable`.

Overview opens with `Current state`: each coin's exceptional states, the top one with its specifics. `None` appears only once the live peg summary has loaded; before that a coin without a curated state shows a dash. Under a critical or paused state, a Peg Score whose current price is unavailable, unusable or inherited is muted with that reason, since the score reads recorded history, not today's peg. `How to read this set` names the members in an exceptional state, most decision-critical first, and a same-peg set is told to read those states before the substitution read.

The matrix uses the shared contextual methodology labels for Peg Score, Liquidity Score, and Safety. Missing source coverage renders as a dash rather than zero. External Bluechip says "Not rated" only when a usable publication omits that coin, including a successfully loaded empty map; no whole-feed publication means a dash, not an unrated verdict. A rated coin whose audit flag the source omits reads "audit not reported" beside its grade, and a source that positively reports no audit reads "no audit flag". Every rated cell carries the grade's neutral original observation date in its tooltip and accessible text; operator retained/stale labels are not shown. Time at peg · up to 90d renders `recent90d` occupancy; only a partial-coverage window adds an inline whole-day basis marker (`· 2d`, full basis in its tooltip), described by the section's record-derived caveat; missing stats stay a dash and a null occupancy never reads as 100% or 0%. Directional fields such as issuance flow, market-cap change, and yield are not styled as universal winners because their desirability depends on the comparison task.

Market cap uses the current USD circulation buckets. The `Market-cap change · 24h/7d/30d` rows use the requested window's dated `circulatingUsd`. A present map with a missing window leaves that change unavailable. Legacy USD-peg rows with no map can still use their historical buckets. An unchanged EUR or gold token balance can move in USD value. A change requires observed current supply and a positive prior value. Observed zero current supply renders `$0.00` and a `-100%` change when a comparable positive prior exists.

Price, confidence and source counts use the selected stablecoins row and its `currentPeg` publication. For a legacy fixed-peg block, a quote-matched admission verdict from peg summary governs the deviation and price conversion. NAV prices use their quote-matched currency reference. Historical scores and incident flags keep their own analytics generation.

The peg-track-record row `Open recorded incident` reports `activeDepeg` as Yes/No (or a dash when the peg-summary row is missing). No means only that no recorded incident is open, never that the asset is currently at peg. This remains true for NAV tokens, unusable prices/references, and assets below event-collection coverage; current deviation is a separate measurement.

## Operational notes

- Both pages are part of static export and rely on client-side fetches where applicable.
- Compare global error/freshness notices include aggregate mint/burn flows. Tracking coverage requires a successful aggregate read; failed or absent evidence is unavailable, not zero tracked. Per-coin flow-history failures get a retry notice; supply-history failures show inline "History unavailable". The supply-history read follows the chart range, requesting the unbounded `range=all` window for All and a covering bounded window otherwise. The shared retry includes both histories, preserving retained data and successful peers.
