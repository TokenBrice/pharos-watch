### Console errors

The decisive failure is **not** a Chromium CSP violation — it is Pixi's own self-check throwing before WebGL initialization:

> `Current environment does not allow unsafe-eval, please use pixi.js/unsafe-eval module to enable support.`

This is thrown by `AbstractRenderer._unsafeEvalCheck()` in `node_modules/pixi.js/lib/rendering/renderers/shared/system/AbstractRenderer.js:285`:

```js
_unsafeEvalCheck() {
  if (!unsafeEvalSupported.unsafeEvalSupported()) {
    throw new Error("Current environment does not allow unsafe-eval, please use pixi.js/unsafe-eval module to enable support.");
  }
}
```

In other words: Pixi v8.18.1 still requires `unsafe-eval` for shader compilation, the constraint that `@pixi/unsafe-eval` (last published at v7.4.3) was meant to address has not migrated into v8 mainline, and Pixi *detects* the strict-CSP environment ahead of time and aborts rather than risking an uncaught EvalError further down. The fact that no Chromium-level CSP violation is logged is exactly because Pixi short-circuits before attempting `Function(...)` / `eval(...)`.

The five `404` console errors are unrelated noise (favicon and similar) and do not change the verdict.

## Decision

NO-GO → escalate to controller for Plan-B (Canvas 2D fork) or per-route CSP scoping.

### Notes for follow-up

- Loosening the global CSP to add `'unsafe-eval'` is unacceptable for a production analytics surface; per-route scoping (a different `_headers` entry for `/lighthouse*` only) is technically possible on Cloudflare Pages but expands attack surface for a decorative feature. Plan-B (Canvas 2D port) is the lower-risk path.
- `@pixi/unsafe-eval@7.4.3` is **not** a usable workaround: it pins to Pixi v7 and would force the rest of the plan (which targets v8 APIs and `@pixi/react@8`) to be rewritten.
- The plan author flagged this exact uncertainty up-front. The probe confirms the worst case.
