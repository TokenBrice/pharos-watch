## HTTP Request Handling
### Method Routing

[`shared/lib/api-endpoints/definitions.ts`](../../shared/lib/api-endpoints/definitions.ts) owns registered paths, methods and metadata (`mutatingAdmin`, `cacheBypass`, probe groups and status actions); `shared/lib/api-endpoints/dynamic.ts` owns dynamic descriptors. Worker routing and frontend status tooling consume these registries. Use [API Endpoint Authoring: Source Of Truth](../api-endpoint-authoring.md#source-of-truth) for builders, validation and bindings rather than a method/path table here.

- `OPTIONS` returns `204` with CORS headers for admitted preflights; foreign origins are rejected as described under [CORS Headers](#cors-headers).
- Maintenance follows preflight handling, before auth and routing: `MAINTENANCE_MODE=true` returns `503` for non-`OPTIONS` requests.
- Read endpoints and admin debug routes use their registered methods. Mutating admin routes reject `GET` with `405` except registered dry-run previews and the read-only `GET /api/backfill-dews` backtest.
- Known endpoint families with disallowed methods return `405 { error: "Method not allowed" }`; `Allow` lists the endpoint's actual methods, including when rejecting `PUT`, `DELETE` or `PATCH`.
- Unregistered public `/api/*` paths can return auth errors first, then `404` after lane auth succeeds because no route dependencies can be hydrated.

### Public API Auth and Rate Limiting

The [public API auth contract](../api-reference.md#public-api-auth) owns token format, issuance/claim, tier quotas, retirement and error responses. `shared/lib/api-endpoints/` owns `publicApiAccess` exemptions, never a hand-maintained route list here. `worker/src/handlers/http/gates.ts` evaluates Access admin, shared-secret site, then public key/exemption lanes. Admin authorization bypasses the public per-key limiter; it does not make a public key administrative.

`api_keys` prefix lookup/HMAC verification and `api_key_rate_limit` own durable enforcement. Only recently verified **standard** keys on protected cacheable GET edge hits may use bounded fresh isolate auth/limiter state. Cold/expired keys, edge misses, bypass routes and non-GET stay D1-backed. Repeated limiter failure opens a bounded 60-second local circuit for cacheable reads only, capped at the self-serve default. Donor and self-serve keys always fail closed on D1/auth/limiter failure; local cache cannot weaken global donor quota or durable self-serve revocation.

Free safety grades/dependency routes spend their shared native `SAFETY_GRADES_RATE_LIMIT` allowance before cache/D1 work. Missing/failing binding is 503; exhausted allowance is 429 with retry evidence. Scenario reads remain uncached. Site/preview scenario reads also spend allowance using Worker-visible source (or shared unknown bucket), never attacker-provided forwarded IP. Per-location native allowances are not global durable quotas; broad WAF posture is separately owned by the account manifest. Verify binding activation and an affected deployed-version request before claiming remediation.

Donor claims spend their dedicated native allowance before bounded body/SIWE work and atomically issue claim plus key; [the API contract](../api-reference.md#public-api-auth) owns eligibility/reason codes. Mini App exemptions still validate signed `initData`, deny site-data and return no-store. [Site-Data Auth](#site-data-auth) owns credentialed GET/internal-build/adoption admission; browser-only reads use same-origin Pages rather than direct public access. `api_keys.traffic_class` separates site/external attribution; `FEEDBACK_IP_SALT` hashes feedback only.
- Telegram pre-auth ingress policy and body ceilings are owned by `worker/src/telegram/webhook/telegram-ingress-abuse.ts` (`TELEGRAM_INGRESS_POLICIES`) and the matching Rate Limiting bindings in `worker/wrangler.toml`. For webhook/Mini App 429/503, bounded-body, authenticated flood, and callback-ack triage, use [Telegram ingress, retries and setup incidents](../runbooks/telegram-webhook-retry-dedupe.md#preauth-ingress-abuse-controls).
- Supporter key claims use one table, `api_key_donor_claims` (`address` primary key, unique `key_prefix`, `claimed_at`), written in the issuance batch. It stores no signature, no token, and no request metadata; it exists so a wallet cannot claim twice and so an operator can find the key issued for one address. Removing a donation row later does not revoke anything on its own, so the operator must also deactivate the matching `donor` key.

### Request Attribution

- Worker-side request attribution writes selected minute-bucketed observations into `api_request_source_samples`, not the legacy source table.
- Valid protected `public-api` requests authenticated with API keys also write unsampled minute-bucketed per-key load into `api_key_request_stats`; `request_count` and `source_v2_request_count` advance together in one upsert.
- Pages `functions/_site-data/[[path]].ts` writes selected same-origin delivery observations into `site_data_request_samples`, not the legacy delivery table.
- Low-value route/source attribution writes can be paused with `REQUEST_SOURCE_ATTRIBUTION_DISABLED=true`
- Per-key public API load writes can be paused separately with `API_KEY_REQUEST_ATTRIBUTION_DISABLED=true`
- Worker route/source, per-key and Pages counters still use the existing 10ms/50-entry request-owned buffer and unchanged retry behavior; isolate eviction and failed persistence mean capture is best-effort, not an exact arrival ledger.
- Worker counters cover attributed non-admin API traffic, including registered mutations and authenticated unknown paths, and exclude `/api/telegram-webhook`; Pages counters cover the GET-only site-data proxy
- worker load is stored by:
  - `lane`: `public-api` or `site-api`
  - `consumer_class`: `site` or `external`
  - `authentication_class`: public-api uses `keyed` / `unkeyed` from the authenticated key identity; site-api uses `not-applicable`
  - `sample_inverse_rate`: the persisted inverse selection probability; `sample_count` stores selected observations, never expanded estimates
- keyed load is stored by:
  - `api_key_id`
  - `bucket_start`
- site demand on the public API host is recognized from:
  - `api_keys.traffic_class = 'site'` for authenticated requests
  - or browser evidence (`Origin` / `Referer` matching `https://pharos.watch`, or the frontend `Accept` marker with `Sec-Fetch-Site: same-site|same-origin`)
- Pages demand records delivery-path outcomes separately:
  - `pages-upstream-fetch`
  - `pages-upstream-timeout`
  - `pages-upstream-error`
- `GET /api/request-source-stats?measurementVersion=2` reports recorded/estimated demand separately from Worker lane pressure; it never double-counts site-api work as site demand.
- the same endpoint also exposes keyed public-API summaries plus the top per-key load rows used by the `/admin/` reliability table
- retention is bounded to the latest `35` days; daily `prune-cron-history` exclusively owns bounded deletion of sampled, legacy-source and per-key tables, including when attribution is disabled. Request-path flushes no longer issue prune SQL.
- operators must opt into measurement version 2 on `ops-api.pharos.watch`; older/unversioned calls fail visibly with `400`, not unlabeled estimates.

The kill switches are for observability degradation only. They do not disable API-key auth, D1-backed quota enforcement, feedback throttles, admin audit logs, or Telegram security checks. Per-key `api_key_request_stats` remain enabled when Worker route/source attribution is disabled so operators can still see keyed public API load driving limiter pressure. Setting `API_KEY_REQUEST_ATTRIBUTION_DISABLED=true` disables only those per-key stats rows and should be reserved for public API spikes where D1 pressure is already visible elsewhere.

Migration `0275_request_source_sampled_stats.sql` supplies additive `api_request_source_samples`, `site_data_request_samples` and default-zero `api_key_request_stats.source_v2_request_count`, without historical backfill or extra indexes. New tables have only time-leading composite primary keys. Apply the migration and deploy the measurement-aware reader/admin UI before activating sampled writers. Retain ledger, verified pre-window Time Travel bookmark, both Worker versions and immutable Pages marker; normal deployment applies D1 before Workers, then Pages. No new migration is needed for writer activation.

`shared/lib/request-attribution.ts` owns event selection and minute resolution, using the wire policy `request-source-bernoulli-64-v1`: independent per-event 1/64 for Worker source events and ordinary Pages upstream HTTP responses (including non-2xx), and inverse rate 1 only for Pages transport timeout/error observations. Selection precedes buffer allocation/merging; rejected events issue no source SQL or timer. No request identifier or personal data is stored. Source and per-key selection remain independent; auth, quotas, rate limits, last-used updates and audit/security writes do not use this sampling decision.

The reader composes old recorded counters and selected sample strata additively, even in one minute. It weights each sample by persisted inverse probability, publishes sample size/variance and labels low precision below 30 sampled events. Per-key load remains recorded and unsampled. The atomic regime marker supports direct unkeyed estimation without subtracting a sampled denominator or clamping inconsistent evidence. See the [wire semantics](../api-reference-admin.md#get-apirequest-source-stats) and [sample-aware recovery checks](../runbooks/db-connectivity.md#verification).

Both sampled tables use the existing small bounded daily retention ceilings; `apiRequestSourceSamplesDeleted` / `siteDataRequestSamplesDeleted` and their `requestTelemetryCappedAtLimit` / `retentionTruncated` entries expose progress and backlog. Legacy source and per-key retention keeps its existing daily budgets. Keep the 35-day legacy drain and old indexes intact; no immediate sub-95% utilization is guaranteed. Later destructive cleanup requires 35 days plus operational grace, empty old tables and fresh zero-use evidence. Once sampled history exists, the measurement-aware reader/UI is the rollback floor: roll back writers to that baseline, revert Pages independently, and leave additive schema/history intact. Code rollback does not require a D1 restore.

### Append-only D1 Retention Policy

`shared/lib/retention-policy.ts` is the declarative table-policy registry: table, retention clock, window and eligibility predicate, statement/run ceilings, owner and explicit permanence. The daily `prune-cron-history` job executes its operational entries through `runRetentionPolicies()` in independent groups of at most five statements per `db.batch()`. Empty/single-batch entries share binding calls, while entries sharing a run budget execute in separate groups to preserve declaration priority. A full batch repeats only that entry, clipped to its remaining budget; a short batch ends only that entry. Strict older-than cutoffs retain exact-boundary rows. High-growth defaults remain `RETENTION_DELETE_BATCH_LIMIT` / `RETENTION_DELETE_RUN_LIMIT` in `worker/src/lib/bounded-prune.ts`; repair, canary, recovery, Queue execution-ledger and sampled request telemetry use the smaller ceilings. Both retired self-serve limiter tables retain one shared 100,000-row budget and declaration priority. All entries, including quota, request telemetry and Safety evidence, publish an individual `retentionTruncated` flag; legacy deleted-count and grouped-cap fields remain available. The two-day selector quota sweep is capped too. Migration 0270 adds `idx_cron_slot_executions_slot_started_at_prune` on the logical `slot_started_at` clock; it is distinct from the older similarly named `(slot_key, started_at)` index. Product and specialized owner-managed retention remains with its existing owner rather than duplicating its predicates or clocks.

Producer-history retention distinguishes ordinary rows (30 days), budget-only rows (90 days) and UTC-calendar identities (550 days); rich cron drill-down remains separately short-lived. Retention never turns unconfirmed output into a publication.

Permanent product history is explicit, including `supply_history`, `tape_events` and `depeg_events`. The initial D15 dossier incorrectly listed `yield_source_decisions` and `dex_liquidity_history` as unpruned: their existing owner-managed window/predicate policies remain in force and are registered as windowed, not permanent. A schema-backed registry test requires every timestamp-bearing append/history family to have exactly one policy; mutable current-state/replaceable stores have explicit exclusions, not implicit omissions.

Finalized `mint_burn_scan_coverage` proof is permanent, including old source fingerprints; lossless segment compaction is not age pruning. `mint_burn_dirty_hours` is an explicitly excluded mutable debt queue: only the atomic materialization rebuild consumes each key, never a time cutoff.

### Edge Cache Strategy

The Worker uses `caches.default` (Cloudflare's per-colo edge cache) to cache GET responses:

1. **Cache bypass rules**:
   - All non-GET requests bypass edge cache.
   - GET paths marked `cacheBypass: true` in `shared/lib/api-endpoints/` bypass edge cache (status and recurring repair endpoints like `/api/backfill-dews`, including their dry-run preview variants, plus activation-gated public endpoints such as `/api/report-cards/v9`).

2. **Cache check:** `caches.default.match(cacheKey)` — returns cached response if available

For endpoint descriptors marked `cacheKeyIgnoresQuery: true`, the edge-cache key drops the URL query string because the route handler does not consume query parameters. Parameterized routes retain their full query-bearing identity. This changes only cache lookup identity: per-request auth gates, attribution, `Vary`, CORS, and response cache-control handling remain in force.

3. **Cache store:** `ctx.waitUntil(cache.put(cacheKey, response.clone()).catch(...))` — successful cacheable responses are cloned **without** CORS headers before caching. CORS headers are added per-request after cache lookup to avoid caching origin-specific headers. The Worker skips edge-cache writes for responses whose `Cache-Control` contains `no-store`, `no-cache`, or `private`; those responses are intentionally not persisted in `caches.default`.

**Conditional GET:** cache lookups use bare GET keys, stripping incoming conditionals and Range so Cloudflare cannot synthesize a 304/206 before lifetime admission. After authentication/rate limits, both cache-hit lanes and handler responses evaluate `If-None-Match` with weak comparison. A matching reusable representation returns a bodyless 304 with its original ETag, Cache-Control, Date/Age and freshness headers; CORS/security headers are applied afterward per caller. An expired bounded HTTP lifetime or explicit producer budget cannot be renewed by a 304. Held, non-fresh, private and no-store responses lose reusable validators.

Validators are scoped by canonical route plus meaningful query, so full/table/coin representations cannot collide. Safety materializations use producer version/generation/body digest plus the complete live publication-health overlay; accepted generation alone cannot hide held/reason changes. Response-ready cache envelopes store a body digest at producer serialization, reused without hashing the cohort on reads. These semantic validators are weak because assessment metadata and transfer compression can differ without changing the admitted evidence. Other cacheable responses receive a unique response-cache publication identity stored with those exact bytes; a new cache fill conservatively returns 200 instead of asserting equality from `updated_at`, which permits same-clock replacement. No multi-megabyte response is hashed for conditional transport.

Pages `/_site-data/*` already forwards both conditional request headers and allowlisted ETag/cache/freshness/CORS response headers. It passes upstream 304 status and a null body through both URL fetch and `SITE_API`, without a second cache or a restarted clock.

Freshness-aware cache profiles are ceilings: `api-freshness-headers.ts` bounds browser/shared TTL and the combined TTL + SWR window by the remaining fresh runway. At zero/subsecond runway it returns `no-store`. Generic 8x/12x, chains 1x/2x and yield publication bands remain distinct. Generic and route-specific `_meta` publish `assessedAt`, `freshBudgetSec`, and `degradedBudgetSec`.

Live OG route cards use `buildOgImageCacheControl` after rendering: browser/shared TTL is at most 900 seconds and no greater than the nonnegative whole seconds remaining before the source admission expiry, without a 60-second minimum. Expiry during rendering discards the live PNG and serves the existing figure-free timeless card with `stale-cache`; positive subsecond lifetime produces a zero-second live TTL. Account-wide browser-cache settings are an independent override, so origin tests require separate cached/uncached production-header acceptance ([operator cache-floor policy](../operator-origin-access.md#10-monitor-cloudflare-account-state-drift)).

Timestamp validity is separate from retention and age bands. The freshness oracle, policy cache and status snapshot/probe/state readers reject missing, invalid or excessively future generation clocks rather than call them fresh age zero. Their default allowance is explicit and overridable; DEWS hydration validates against read-time wall clock, not its earlier captured run clock, so an overlapping producer's legitimate publication remains admissible. A cache retention TTL of `null` still means no expiry, not exemption from timestamp validity.

`shared/lib/api-freshness.ts` names distinct endpoint freshness, Telegram six-hour flow tolerated-context, and four-hour PSI/DEWS canary incident policies. Operator env warning thresholds remain a separate policy. Centralization does not tighten Telegram primary-alert eligibility or force all consumers to use one number.

The top-level `fetch` and `scheduled` handlers load dispatchers lazily. HTTP keeps metadata/loader closures eager and initializes implementation only on invocation; scheduled slots load only their selected runner. `worker/src/routes/__tests__/lazy-route-loading.test.ts` guards unrelated graph retention. Retired Workflow shells/observer suites must not return through a compatibility import.

The reserve API and its snapshot display resolver use the existing Worker runtime registry projection. Configured feeds retain their complete display reserves, classification flags, and live-reserve configuration; the resolver guards that full-feed slice before applying fallback templates. Invoking this endpoint therefore does not hydrate the full evidence-rich catalog into an isolate shared with scheduled work. The endpoint tests compare every configured feed's fallback and configuration against the full registry. Internal resolver calls also preserve retained historical snapshots for unconfigured assets with ineligible provenance; only their no-snapshot fallback lazily loads full metadata, because the unconfigured projection does not promise complete display reserves.

Full-catalog consumers keep the shared registry's canonical semantics through a Worker-only byte transport; see [Packed catalog transport mechanics](#packed-catalog-transport-mechanics) for the codec, evaluation-build boundary and dated local probes.

Admin `GET` routes are forced to `Cache-Control: no-store` either by `addAdminGetNoStoreHeader()` in `worker/src/router.ts` for registry-dispatched routes or by the admin route wrapper for dynamic admin handlers.

### External API Monitoring Baseline

When public API usage grows, monitor these three Cloudflare dimensions first:

1. **Per-endpoint request volume**
   - Track top paths by requests and trend (`/api/stablecoin/:id`, `/api/stablecoin-summary/:id`, `/api/stablecoins`, `/api/report-cards/v9`).
   - Alert on sudden spikes (for example, >2x 24h baseline).
2. **Per-endpoint cache performance**
   - Track `CF-Cache-Status` mix (HIT vs MISS/BYPASS) and overall cache-hit ratio by path.
   - Investigate if heavy endpoints drift toward MISS-heavy traffic.
3. **Per-endpoint error rate**
   - Track 5xx rate by path (especially `502`/`503`), not just global error rate.
   - Alert when 5xx ratio breaches your SLO target (for example, >1% for 5 minutes).

This baseline is enough to catch most abuse, regression, or cache-efficiency problems early.

### Router-Dispatched Status Actions

Operator admin actions are dispatched through `worker/src/router.ts`; [`shared/lib/api-endpoints/definitions.ts`](../../shared/lib/api-endpoints/definitions.ts) owns their paths, methods and `statusPageAction` metadata, and `worker/src/api/admin-actions.ts` owns their handlers. `/admin/` derives its action inventory from that registry. Action effects remain handler-specific: digest triggering queues a leased background run with `force=true` and returns `202 Accepted` immediately; blacklist reset rolls EVM sync state back 50,000 blocks and Tron state back seven days; sync-state inspection returns all `blacklist_sync_state` rows. All use the [admin-auth lane](#admin-auth). Feedback is router-dispatched too, but is not part of the status action registry.

Every endpoint with `statusPageAction` metadata is audited at the shared router boundary after its handler returns, including read-only inspections and dry-run previews. The canonical row records only definition-owned action/path/scope metadata, the configured target query parameter (or `batch` / `invalid-target`), HTTP/result status, execution certainty, dry-run/live/inspect mode, and a SHA-256 idempotency identity. It never records request bodies, arbitrary query parameters, auth headers, raw responses, or plaintext tokens. A nullable unique `(action, intent_key)` index keeps one row per keyed intent: replay responses insert only when the first audit is missing, while the non-replay original response authoritatively replaces an earlier replay placeholder. A catalog handler that needs richer handler-specific details must set `statusPageAction.auditMode = "handler"` and write its single audit row itself; the canonical router then opts out.
Audit mode uses the handler's resolved `dryRun` response flag when available, never the catalog's UI preview default; body/query aliases and precedence therefore match execution without persisting their values.

### Idempotent Admin Actions

**File:** `worker/src/lib/idempotency.ts`

These router-dispatched admin routes honor an optional `Idempotency-Key` header. The complete action inventory and endpoint contracts live in the [API reference](../api-reference.md) and are derived from the shared endpoint registry.

Retired curl-only reset/kill/pending-clear/resend controls are unregistered. A direct exact-key D1 delete is equivalent only for simple lease/breaker rows after [shared recovery](../runbooks/lease-and-breaker-recovery.md) preconditions. Kill, pending cleanup and resend have no blanket D1 equivalent: deleting pending state bypasses dead-letter/projection/audit work and destroys evidence. Restore a control only through reviewed implementation, never route reversion alone.

API-key create/rotate use the sensitive-response replay mode: the first successful response returns the one-time plaintext token, while the idempotency row and every replay retain only allowlisted public key identity plus `tokenUnavailableOnReplay` recovery guidance. Redaction failure is fail-closed as `execution_unknown`; plaintext tokens are never persisted for replay.

The worker fingerprints method + path + sorted query + body for a given action key. Replays return the stored response with `X-Idempotent-Replay: true`; conflicting reuse returns `409` with `X-Idempotency-Conflict: request-mismatch` and cannot replace the original intent's audit. Reservations have an owner/generation and a separate durable execution-start transition. An unstarted reservation may be taken over after 20 minutes. A started reservation is at-most-once: once `execution_started_at` is set, the absence of a terminal response cannot prove the effect did not commit, so after 24 hours the row is compare-and-swap recorded as terminally `execution_unknown` with a structured warning and every replay answers `503`. The key is never automatically reopened, even if terminal marking fails or loses its compare-and-swap; operator reconciliation is required. A future reconciler needs an action-specific design, not a generic callback. Terminal writes remain owner/generation compare-and-swap operations. A thrown handler, an explicit unknown-certainty response, or any handler HTTP 5xx returns `503` with `error = "execution_unknown"` plus `X-Execution-Certainty: unknown`. Later requests with an explicitly stored `execution_unknown` key replay the same operator-reconciliation state without running the mutation again. Terminal rows age out of the table-wide seven-day prune; `PENDING` and `execution_unknown` rows are excluded, because an unknown row is a permanent reconciliation tombstone whose key must never reserve a fresh row and re-run after the TTL.

### Internal Detail Snapshot Inputs

`GET /api/stablecoin-detail-snapshot-inputs?ids=usdt-tether,usdc-circle` is a cache-only build transport, classified `publicApiAccess: "site-only"` in `shared/lib/api-endpoints/definitions.ts`. It requires the trusted site-proxy credential on the site API (or a credentialed preview) and explicitly denies the browser-facing Pages `/_site-data` mapping. The Worker admits this exact internal GET separately from browser-proxy eligibility after checking the existing site credential. Public-host requests return `404` even with an API key; missing site credentials return `401` and site-lane non-GET requests return `405`. It has no public/admin/manual probe and is intentionally excluded from integration OpenAPI, Postman, and the generated public endpoint catalogue. All responses bypass edge caching and use `Cache-Control: no-store`.

The request accepts 1–10 unique canonical IDs; malformed or oversized batches return `400` with the ordinary `{ error }` envelope. `worker/src/api/stablecoin-detail/snapshot-inputs.ts` reads one frozen canonical publication and completed supply marker per batch, then processes detail caches and exact 90-day D1 history sequentially. It never admits provider materialization, schedules refreshes, or writes caches. One full detail body at a time and a 128 KiB compact entry cap bound memory and response size.

The response is `{ version: 1, entries }`, with one entry per requested ID in request order. Available entries contain `liveSummary`, `supplyHistory`, independent millisecond lane `updatedAt` clocks, and per-lane `freshness: { status, maxAgeSec }`. `sources` carries second-resolution detail-cache, publication and completed-supply update clocks and supply snapshot date. Source absence stays `null`; projection is shared with the browser/per-coin generator in `shared/lib/stablecoin-live-summary.ts`, while wire schemas live in `shared/types/`.

Lane clocks prefer body provenance, then origin `X-Data-Updated-At` seconds from the real detail cache/publication or completed-supply marker. Pages forwards this header unchanged. A malformed present header leaves the clock unavailable without fallback. Legacy reconstruction is allowed only when the absolute header is absent and `Date`, nonnegative decimal `X-Data-Age`, and nonnegative decimal edge `Age` are all present and valid; Date or receipt time alone is not generation. Bulk uses these same response helpers, never synthetic HTTP dates, and available entries require both numeric lane clocks.

Unavailable entries explicitly carry `id`, `sources`, and `reason`: `unknown-id`, `detail-cache-missing`, `detail-cache-invalid-clock`, `detail-cache-too-old`, `publication-unavailable`, `supply-marker-missing`, `source-clock-unavailable`, `invalid-cache-input`, `entry-too-large`, or `cache-read-failed`. Unproven provenance in either lane produces `source-clock-unavailable` for that asset without freshness metadata; healthy assets remain available. Active details at least 24 hours old require normal per-coin acquisition; inactive cached records retain their existing no-refresh policy. Oversized or bad entries are quarantined, never truncated, silently omitted, or replaced with zero. The generator falls back to ordinary detail/history reads only for those coins. See [Build snapshot hydration](../stablecoin-detail-page.md#build-snapshot-hydration) for the source switch and byte-equivalence cutover proof.

### V9 public response materialization

`report-cards-v9-materialization.ts` serves the full V9 route from the derived D1 `safety_score_public_manifests` / `safety_score_public_fragments` tables (migration `0273`). The representation descriptor binds complete accepted policy/build/generation identity, result/candidate/fact-set identity, canonical payload checksum, accepted/source clocks, explicit projection version/encoding, full immutable suffix SHA-256/length and ordered fragment hashes/lengths. Projection-code changes must bump `V9_PUBLIC_REPRESENTATION_VERSION`; result digest alone is never a representation key.

The writer reuses only canonical-admitted card identities while retaining all public envelope, gap, graph, completeness and parent refinements, then resolves, validates and serializes one wire card at a time. It retains small dependency projections, not a second expanded cohort, and uses bounded canonical serializer chunks rather than one giant body string/UTF-8 copy. A fragment is at most 256 KiB; the independent expanded representation cap is 16 MiB and 128 fragments. These are not the canonical compressed publication's size ceilings.

The writer generates immutable representations serially and coalesces manifest/fragment rows across consecutive representations into serial D1 batches, inserting each manifest once. Each batch fits the existing four-max-fragment byte envelope (1 MiB), now accounting for fragment and manifest UTF-8 bytes, other string bindings, eight bytes per numeric binding, and SQL text; this is a buffered-content budget, not a measurement of the binding transport's serialized wire size. Small fragments may share a batch beyond four rows. Multi-row INSERTs use the existing D1 bound-parameter helper, and each batch respects the shared statement ceiling. Completed batch buffers are released before the next flush; only the current artifact plus the bounded pending rows are retained, never the full per-coin artifact cohort. Staged rows are generation/version/checksum keyed and invisible to readers until the canonical marker selects them. The publication/index/private projections/health/attempt fenced atomic batch verifies the complete staged census, activates its manifests and switches the canonical marker together. Staging or acceptance failure retains the previous accepted generation; held writes leave its fragments unchanged. Unselected staged rows carry retirement timestamps so interrupted attempts can be cleaned up by later accepted writes. Replaced accepted manifests are retired at replacement time, not original creation time, preserving a five-minute in-flight read grace even after a long hold. Later accepted writes delete retired, nonactive generations after that grace, cascading fragments. No R2/KV consistency gap, isolate-level parsed-object memo, final-response Cache API cache, or new binding is introduced.

Each request joins canonical metadata, manifest and live health. Missing/malformed/noncanonical/wrong-clock health fails closed; valid generation/time mismatches use the full route's held resolver, not the index's strict policy. Exact generation/version/checksum fragment reads pack serial ordinal ranges within 4 MiB of admitted manifest bytes (up to 128 fragments); staging writes are unchanged. Count, order, UTF-8 length, per-fragment/full-body SHA-256 and totals are verified **before** `200`; byte counting allocates no encoded copy. ### Cron Error Handling Policy

Shared cron behavior is narrower than a single worker-wide tier system:

- `runLeasedCron(...)` / `logCronRun(...)` record terminal outcomes per canonical schedule/job/path and persist Worker version plus invocation identity.
- A weighted slot semaphore allocates at most five declared connection units across child jobs, sidecars and budget-only work; provider-level limits still own physical fetch concurrency. Heartbeats and ledger writes are serialized per job.
- Thrown or explicit error outcomes are recorded after terminal accounting and before rethrow.
- Degraded returns, no-write fallbacks, and producer-specific retries remain job-owned.
- Exact V9 input preparation is a neutral not-started child when the preceding DEX consumer is locked or intentionally withholds publication. On a DEX error it may reuse a consistent last accepted generation inside `DEX_LIQUIDITY_EVIDENCE_MAX_AGE_SEC`; failed or out-of-budget recovery skips neutrally. An otherwise successful DEX result without an exact generation remains a fail-closed error.
- Sidecar publication returns a structured terminal outcome; failures cannot be swallowed behind a successful parent result.

### Lease Integration Status

Scheduled execution is now wired in two layers:

- `worker/src/handlers/scheduled.ts` normalizes `event.scheduledTime` into a durable slot timestamp and awaits the fenced slot inline via `runScheduledSlotWithFence(...)`, which keeps manual `/__scheduled` replays from being cancelled mid-slot by preview-only `waitUntil()` teardown semantics
- `worker/src/handlers/scheduled/context.ts` keeps per-job `runLeasedCron(...)` for job-level overlap protection, timeout logging, and progress

This means duplicate trigger deliveries for the same slot are skipped before shared-slot fan-out can reorder downstream jobs, while individual jobs inside the accepted slot still use their existing per-job leases. The slot fence also races controlled-deadline expiry against the runner promise: cooperative jobs still receive the abort signal, and a non-cooperative or stuck runner is finalized as an error before the platform has to reconcile it as an abandoned slot.

Same-slot takeover reconciles stale work before new admission; bounded global sweeping belongs to `digestTriggerPoll`, while minute reserve recovery retains only its targeted producer sweep. `scheduled-slot-policy.ts` owns silence/hard-dead bounds; the historical recovery key remains a long runner, not a 60-second deadline. Reconciliation CAS transitions the exact stale owner/generation/heartbeat from `running` to `reconciling`; a concurrent heartbeat changes zero rows and preserves all child state. A stale reconciliation claim can be reclaimed, but fresh claims remain protected. Takeovers increment generation; heartbeat/finalization require the current owner, generation and state. Lost heartbeat ownership aborts work, and late finalizers cannot overwrite takeover or synthetic error. Idempotent child `cron_runs` and abandonment markers retain interruption evidence.

Synthetic chronology uses the original evidence clock, not sweep wall time. A started child records its original `started_at` and ends at its last durable progress heartbeat; a child proven not started uses the slot invocation time and last slot heartbeat. The later reconciliation timestamp remains metadata only, so old abandonment evidence cannot outrank a newer real cron run or producer head. Conditional `digestTriggerPoll` slots are special: absence of daily-digest progress means the poll was idle and produces no synthetic child failure, while durable started progress is still reconciled as abandoned. Status history also excludes legacy false `daily-digest` not-started rows from idle polls before its per-job history limit, without hiding genuine forced runs or abandoned-progress evidence.

## RPC read admission details

Single EVM RPC outcomes preserve data, observed execution revert and unavailable evidence. Direct Multicall fallback tolerates only observed optional reverts, never exhausted provider or admission failures; numbered/hash selectors and the closing-header fence remain unchanged. Byte, uint and aggregate decoding reject malformed output before endpoint selection completes, allowing the next eligible provider within the existing admission, credit and deadline policy.

Timestamp-only reads reuse strict numbered-header admission, without adding a default freshness floor. Batched timestamp reads validate one complete `{number, hash, timestamp}` per requested block before projecting cache entries; duplicate IDs invalidate their member, out-of-range IDs are ignored, and malformed/missing members use the existing bounded retries. Expected log hashes still gate admission; a later timestamp cannot inherit an earlier response's hash.

DEX concentrated-liquidity source recovery shares `captureClSourcePools()` in `worker/src/cron/dex-liquidity/staged-pool-recovery.ts`: one numbered header supplies the EIP-1898 hash selector for every pool/token/factory chunk, followed by a closing numbered-header check. Header/state failure or hash change rejects the capture, never falls back to latest. Reads remain serial under caller-owned signals, request admission and deadlines; QuoterV2's existing request budget includes both header reads.

CCIP pages use the first eligible provider's span, independent of state history; Monad retention needs an observed head. Refusal never advances cursors. Serial `noBatch`, exact IDs, per-attempt admission/credits/deadlines and run-local network-failure demotion remain. Unstarted denial is uncharged/undemoted. [Parity](../api-reference-admin.md#get-apirpc-provider-trial) is independent, diagnostic and non-promoting; preference adds no fan-out or evidence of asset acceptance.

Parity token-state freshness requires a same-head hash match or adjacent-head parent-hash link; a larger head advance is indeterminate (`bracket-ancestry-gap`) without extra RPC requests. This cannot establish token freshness even beside a fresh sentinel. Retained runs stay time-ordered, and each chain's latest pointer accepts only equal/newer run timestamps, so late completion cannot rewind the reported observation; same-slot replacement and seven-day retention remain unchanged.

Capped inclusive Etherscan log ranges split sequentially; exhausted request budgets return incomplete `budget-exhausted` results and recursion beyond depth 8 returns `max-recursion-depth`. A capped singleton returns `etherscan-result-cap-unsplittable`, including when its parent spans two adjacent blocks.

## Event-entry recovery details

Synchronous decoding must itself terminate; an abort signal or wall timer cannot interrupt an infinite JavaScript loop. ICP query CBOR decoding bounds cursor access, declared lengths/counts and nesting, and rejects unterminated indefinite values before the existing boundary fallback. Regression coverage runs malformed bodies in a child process with a parent-owned kill deadline and proves the abort timer remains schedulable; network body caps and scheduled event deadlines are unchanged.

An ambiguous D1 acknowledgement is not a lost claim: after a zero-change retry, same-slot takeover reads the exact slot primary key and admits only `running` with the claimant's owner/invocation and scanned generation + 1. Heartbeat advancement of `updated_at` does not invalidate that identity. Reserve-checkpoint recovery likewise requires the scanned schedule/slot/job/attempt/generation, `recovering`, the new recovery invocation/owner and the exact claimed lease (still unexpired), never the old producer invocation. Readback does not grant a fresh deadline or bypass child leases, reconciliation or later ownership fences; a foreign or newer claim remains refused.

| Await boundary | Contract |
| --- | --- |
| Version first-seen stamp | Best-effort telemetry off the admission path, observed within the same deadline. Missing telemetry cannot prevent claim. |
| Slot insert/read, live-child admission, takeover/reconciliation | Mandatory fencing; expired results cannot start a runner or issue the next admission mutation. |
| Child protocol stamp, memory-lane wait, runner import | Mandatory admission; recheck before child work. Protocol stamping is required evidence, not optional version telemetry. |
| Child start/lease-owner marker, lease acquire/renew, terminal arbitration | Mandatory ownership/accounting inside the executing slot deadline. |
| Detailed progress and completion reports | Best-effort telemetry behind the inherited deadline; progress stalls cannot extend the work allowance. Dwellir credit flushes use the same bounded deadline rather than requiring a background execution-context hook. |
| Heartbeat drain, slot terminal write, failure cleanup | Work stops at the original deadline. Already-started settlement retains an observed continuation within the existing accounting reserve, never a new work budget; takeover wins over old writes. |

Public and heavy scheduled callbacks capture event entry before any lazy import and pass it to the dispatcher. Expiry returns a controlled failure even when D1 has not resolved. A late admission continuation rechecks expiry before starting anything; cleanup requires drained work and no unterminated children. Its actual in-flight promise is retained with `waitUntil` only within the existing accounting reserve, independently of the already-aborted work signal. If the isolate disappears, stale sweeping remains recovery authority. `scheduled-slot-delivery` events distinguish `delivered-not-admitted` (also duplicate/live-slot refusals) from `claimed-failed`, carrying executing slot, invocation and event-entry deadline. An absent D1 slot is not proof of missing delivery.

The existing public `digestTriggerPoll` lane starts with a DB-only sweep-only stage before outbox/demand/generation work, capped at 30 seconds and ten candidates and clipped to the inherited deadline. No trigger, fetch surface or connection reservation is added; connection peak and CPU placement stay unchanged. Global cleanup no longer shares reserve-recovery's lease/replay; reserve recovery retains targeted producer-slot preparation only. Every path imports `scheduled-slot-policy.ts`.

`scheduled-slot-sweep` events record counts, applied policies and `maxReconciliationLagSec` from policy eligibility to the sweep observation clock (null without reconciled observations). After deployment require lag within two poll intervals outside documented platform/D1 stalls; fixtures are not production acceptance. Reconciled child errors and abandonment events share `parentIncidentId`; event `childIncidentCounts` groups started and proven-not-started children without making required unstarted errors neutral.

## Database maintenance details

Scheduler enrichment preserves producer metadata while merging authoritative lease/slot identity. Row and validation measurements (`rowsRead`, `rowsWritten`, `rowsDropped`, `validationFailures`) remain `null` when absent or explicitly unknown; only producer-observed counts, including zero, are numeric. `itemCount` describes job output/work and never implies database writes. Write-time compaction preserves these nulls and measured values; historical terminal counters are not retroactively reclassified as measured.

`worker/src/cron/prune-detail-cache.ts` keyset-pages demand-refreshed detail rows with the existing page and per-run candidate budgets. Orphan keys are removed independently of age; week-stale active rows are deleted only when their current `updated_at` still matches the scanned clock and remains below the cutoff. Non-active readable rows remain exempt because the API cannot refresh them. `orphansDeleted`, `staleDeleted`, and `itemCount` count applied changes, not stale candidates; a skipped concurrent replacement still consumes the bounded candidate budget.

Benchmark recovery counters are publication evidence: the benchmark owner commits prepared streak markers and structured/legacy cache rows in one bounded D1 batch under the existing job lease. Canaries require a marker matching the accepted registry generation; monitor preparation or an optional recovery event alone cannot certify publication.

## Logging and privacy details

Cron observability has two paths. Terminal job outcomes continue through `logCronRun()` / `cron_runs`; swallowed exceptions that should remain non-fatal use `recordCronFailure()`. Degraded, skipped, fallback, or warning conditions that should survive log retention can call `logCronEvent(db, { job, eventType, severity, message, metadata })`, which writes a latest-event record to the existing cache table under a bounded `cron:event:<job>:<eventType>` key and also emits a structured console line. Use `logCronEvent` for non-terminal operational events rather than adding TODO-backed `console.*` call sites. Price observation collection runs after the existing status-check chain every 15 minutes. Narrow exact DEX refresh and the coverage refresh for rows the exact-address lane prices run first in each slot; broad price corroboration still runs only at `:09`, ahead of `:15` publication. It is budget-only serial work, retains the slot cancellation signal and requires a valid published stablecoins cache. Each collection attempt records its outcome in budget-surface telemetry; its 900-second interval uses the existing two-interval diagnostic stale threshold, independently of provider quote TTLs. No physical trigger is added and the primary publication does not wait for corroboration. It uses the exact `cron:event:sync-stablecoins:price-corroboration` key; the status collector explicitly joins this bounded record to the stablecoin job. Newest event time wins, with higher severity breaking equal-time ties, so a newer stale-slot recovery error is preserved. Its metadata contains slot/version and bounded provider identifiers, counts and failure classes, without provider URLs, credentials or response bodies.

HTTP, API, status, and admin route logs use `logWorkerEvent()` from `worker/src/lib/structured-log.ts`. It emits one JSON console line with stable top-level fields (`scope`, `level`, `event`, `route`, `job`, `provider`, `source`, `runId`) and bounded `metadata` / error fields so Cloudflare Workers Logs stay queryable without turning high-cardinality values into top-level keys. New route logs should use `logWorkerEvent()` instead of direct string console calls.

Telegram custom logs have a narrower privacy contract in `worker/src/telegram/common/log.ts`: no raw or pseudonymous chat/user/update/callback/pending/source-event identifier is emitted. The logger accepts only low-cardinality operation fields and bounded numeric/status metadata, drops unknown keys and non-primitives at runtime, normalizes error classes to a fixed vocabulary, and scrubs URLs, secret assignments, Telegram IDs, UUIDs, and opaque hashes/tokens from allowed strings. Chat-specific incident correlation belongs to Access-authenticated D1/admin diagnostics. A failed webhook terminal processed-update marker emits `action: processed-update-terminal-marker` with a bounded `reasonClass`: `sql_rejected` (D1 rejected the write), `zero_change` (the ownership/generation/effect/mutation fence matched no row), or `fence_rejected` (the intent fence refused before the write). The thrown error, HTTP status, retry and effect fences are unchanged; no SQL text, bound value, update/chat identifier or claim token is logged. Public Workers Logs use the checked-in 0.1 head sampling rate; heavy uses 1. The external retention/Logpush decision is owned by `tokenbrice`: structured logs remain local-only in Workers Logs, with no repository-configured Logpush archive or retention duration. Evaluate Logpush when log volume justifies retention beyond the documented D1 ledgers; until then, durable operational evidence must use those ledgers rather than console retention.

Provider URLs that may embed credentials must pass through `redactProviderUrls()` / `safeErrorMessage()` before logging. The central redactor strips path/query details for Alchemy, dRPC, Dwellir, Etherscan, Telegram, Twitter/X, and Anthropic hosts, and redacts generic secret query parameters on other URLs. Structured Worker and cron metadata applies the same redaction recursively to nested strings, arrays, objects, and `Error` message/stack fields before truncation or serialization. Telegram Bot API tokens still appear in outbound URLs, so Cloudflare invocation logs must be treated as secret; removing that legacy URL-token path is an operational follow-up.

## Initialization and RPC boundaries

The unqualified V9 guard and memory-evidence boundary are owned by the [memory appendix](#module-initialization-memory-evidence).

Worker scripts must be Latin-1-only: escape source code units above U+00FF as `\uXXXX`, including regex literals. One such raw character doubles V8's retained bundle source. `npm run check:worker-package` rejects these and warns on other non-ASCII; escape first-party Latin-1 too, since UTF-8 loading can retain two-byte source.

Derive Env per invocation and pass values as parameters, never at initialization: `worker/src/handlers/scheduled/context.ts`, `worker/src/handlers/http/context.ts`, and `worker/src/routes/dependency-hydrators.ts` normalize credentials, build RPC capability maps and resolve freshness settings.

API-key consumers import their owning `api-key-admin`, `api-key-auth`, `api-key-rate-limit`, or `api-key-core` leaf directly. HTTP gates keep administrative key mutation code outside their eager module graph; lazy-route tests observe the administrative leaf itself.

Module state: `buildChainRpcs()` registers/clears credentials in `RPC_AUTH_BY_ORIGIN` (`worker/src/lib/chain-registry.ts`); `shared/lib/cloudflare-access-jwt.ts` keeps a one-hour JWKS cache. The [isolate registry](#isolate-local-state-registry) owns mutable-state inventory.

Redemption `applyOutputDependencyResolution()` uses a run-local index and immutable completed snapshot/configuration map. No global clock-keyed join may cross-contaminate concurrent runs sharing a clock.

`shared/lib/chain-rpc-registry.ts` keeps RPC profiles separate. `hasRegistryRpc()`/`registryRpcUrls()` establish inventory membership; supplemental presence does not. [ADR-40](../architecture.md#adr-40) prefers eligible Dwellir without reordering incumbents or expanding inventory.

The shared Dwellir registries own capabilities. Scheduled EVM/native reads share credit-ledger/breaker admission; missing key, denial or `DWELLIR_ROUTING_DISABLED_CHAINS` excludes Dwellir. HTTP gets no native capability. Native operations retain exact pins, header credentials and ledger-floor checks, not TRON history or Sui object-history permission.

Native reads use `redirect: "manual"` (Workers rejects `"error"`); non-2xx is rejected, so keys never follow redirects.

The EVM resolver separates recent finalized state, arbitrary historical state, headers/receipts and inclusive log intervals. Recent pins bind chain/number/hash, original clocks, finalized head, age and retained floor; batch eligibility intersects actual members. BSC/Monad/zkSync remain recent-only. Unknown incumbent retention is not archive proof; HyperEVM Alchemy numeric mispins stay excluded. No hash-to-number/latest fallback.
RPC decoding, pinned CL recovery, timestamp batches, parity ancestry and capped-log splitting follow the [read admission details](#rpc-read-admission-details); failures never manufacture state, finality or completeness.
