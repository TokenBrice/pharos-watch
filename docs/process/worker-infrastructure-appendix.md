## HTTP Request Handling
### Method Routing

[`shared/lib/api-endpoints/definitions.ts`](../../shared/lib/api-endpoints/definitions.ts) owns registered paths, methods and metadata (`mutatingAdmin`, `cacheBypass`, probe groups and status actions); `shared/lib/api-endpoints/dynamic.ts` owns dynamic descriptors. Worker routing and frontend status tooling consume these registries. Use [API Endpoint Authoring: Source Of Truth](../api-endpoint-authoring.md#source-of-truth) for builders, validation and bindings rather than a method/path table here.

- `OPTIONS` returns `204` with CORS headers for admitted preflights; foreign origins are rejected as described under [CORS Headers](#cors-headers).
- Maintenance follows preflight handling, before auth and routing: `MAINTENANCE_MODE=true` returns `503` for non-`OPTIONS` requests.
- Read endpoints and admin debug routes use their registered methods. Mutating admin routes reject `GET` with `405` except registered dry-run previews and the read-only `GET /api/backfill-dews` backtest.
- Known endpoint families with disallowed methods return `405 { error: "Method not allowed" }`; `Allow` lists the endpoint's actual methods, including when rejecting `PUT`, `DELETE` or `PATCH`.
- Unregistered public `/api/*` paths can return auth errors first, then `404` after lane auth succeeds because no route dependencies can be hydrated.

### Public API Auth and Rate Limiting

The [public API auth contract](../api-reference.md#public-api-auth) owns token format, issuance/claim, tier quotas, retirement and error responses. `shared/lib/api-endpoints/` owns `publicApiAccess` exemptions, never a hand-maintained route list here. `worker/src/handlers/http/gates.ts` evaluates Access admin, shared-secret site, then public key/exemption lanes. Admin authorization bypasses the public per-key limiter; it does not make a public key administrative.

`api_keys` prefix lookup/HMAC verification and `api_key_rate_limit` own durable enforcement. Only recently verified **standard** keys on protected cacheable GET edge hits may use bounded fresh isolate auth/limiter state. Cold/expired keys, edge misses, bypass routes and non-GET stay D1-backed. Repeated limiter failure opens a bounded 60-second local circuit for cacheable reads only, capped at the self-serve default. Donor and self-serve keys always fail closed on D1/auth/limiter failure; local cache cannot weaken global donor quota or durable self-serve revocation.

Free safety grades/dependency routes spend their shared native `SAFETY_GRADES_RATE_LIMIT` allowance before cache/D1 work. Missing/failing binding is 503; exhausted allowance is 429 with retry evidence. Scenario reads remain uncached. Site/preview scenario reads also spend allowance using Worker-visible source (or shared unknown bucket), never attacker-provided forwarded IP. Per-location native allowances are not global durable quotas; broad WAF posture is separately owned by the account manifest. Verify binding activation and an affected deployed-version request before claiming remediation.

Donor claims spend their dedicated native allowance before bounded body/SIWE work and atomically issue claim plus key; [the API contract](../api-reference.md#public-api-auth) owns eligibility/reason codes. Mini App exemptions still validate signed `initData`, deny site-data and return no-store. [Site-Data Auth](#site-data-auth) owns credentialed GET/internal-build/adoption admission; browser-only reads use same-origin Pages rather than direct public access. `api_keys.traffic_class` separates site/external attribution; `FEEDBACK_IP_SALT` hashes feedback only.
- Telegram pre-auth ingress policy and body ceilings are owned by `worker/src/handlers/http/telegram-ingress-abuse.ts` (`TELEGRAM_INGRESS_POLICIES`) and the matching Rate Limiting bindings in `worker/wrangler.toml`. For webhook/Mini App 429/503, bounded-body, authenticated flood, and callback-ack triage, use [Telegram ingress, retries and setup incidents](../runbooks/telegram-webhook-retry-dedupe.md#preauth-ingress-abuse-controls).
- Supporter key claims use one table, `api_key_donor_claims` (`address` primary key, unique `key_prefix`, `claimed_at`), written in the issuance batch. It stores no signature, no token, and no request metadata; it exists so a wallet cannot claim twice and so an operator can find the key issued for one address. Removing a donation row later does not revoke anything on its own, so the operator must also deactivate the matching `donor` key.

### Request Attribution

- Worker-side request attribution now writes minute-bucketed worker load into `api_request_consumer_stats`
- Valid protected `public-api` requests authenticated with API keys also write minute-bucketed per-key load into `api_key_request_stats`
- Pages `functions/_site-data/[[path]].ts` writes same-origin site demand into `site_data_request_stats`
- Low-value route/source attribution writes can be paused with `REQUEST_SOURCE_ATTRIBUTION_DISABLED=true`
- Per-key public API load writes can be paused separately with `API_KEY_REQUEST_ATTRIBUTION_DISABLED=true`
- Worker route/source, Worker per-key, and Pages site-data counters are buffered briefly in isolate-local minute buckets and flushed through D1 batches, so bursts against the same route/source or key dimension collapse into one weighted counter upsert
- Worker counters cover attributed non-admin API traffic, including registered mutations and authenticated unknown paths, and exclude `/api/telegram-webhook`; Pages counters cover the GET-only site-data proxy
- worker load is stored by:
  - `lane`: `public-api` or `site-api`
  - `consumer_class`: `site` or `external`
- keyed load is stored by:
  - `api_key_id`
  - `bucket_start`
- site demand on the public API host is recognized from:
  - `api_keys.traffic_class = 'site'` for authenticated requests
  - or browser evidence (`Origin` / `Referer` matching `https://pharos.watch`, or the frontend `Accept` marker with `Sec-Fetch-Site: same-site|same-origin`)
- Pages demand records delivery-path outcomes separately:
  - `pages-upstream-fetch`
  - `pages-upstream-timeout`
  - `pages-upstream-error`
- this lets `/api/request-source-stats` report total site-vs-external demand while still surfacing actual worker pressure on `public-api` vs `site-api`
- the same endpoint also exposes keyed public-API summaries plus the top per-key load rows used by the `/admin/` reliability table
- retention is bounded to the latest `35` days; request-path flushes prune opportunistically, and the daily `prune-cron-history` pass provides the backstop
- operators read the aggregate split through `GET /api/request-source-stats` on `ops-api.pharos.watch`

The kill switches are for observability degradation only. They do not disable API-key auth, D1-backed quota enforcement, feedback throttles, admin audit logs, or Telegram security checks. Per-key `api_key_request_stats` remain enabled when Worker route/source attribution is disabled so operators can still see keyed public API load driving limiter pressure. Setting `API_KEY_REQUEST_ATTRIBUTION_DISABLED=true` disables only those per-key stats rows and should be reserved for public API spikes where D1 pressure is already visible elsewhere.

### Append-only D1 Retention Policy

`shared/lib/retention-policy.ts` is the declarative table-policy registry: table, retention clock, window and eligibility predicate, statement/run ceilings, owner and explicit permanence. The daily `prune-cron-history` job executes its operational entries through `runRetentionPolicies()` in independent groups of at most five statements per `db.batch()`. Its sixteen empty/single-batch entries therefore use four binding calls instead of sixteen sequential calls. A full batch repeats only that entry, clipped to its remaining budget; a short batch ends only that entry. Strict older-than cutoffs retain exact-boundary rows. High-growth defaults remain `RETENTION_DELETE_BATCH_LIMIT` / `RETENTION_DELETE_RUN_LIMIT` in `worker/src/lib/bounded-prune.ts`; repair, canary and recovery retain their smaller ceilings. Both retired self-serve limiter tables retain one shared 100,000-row budget and declaration priority. All entries, including quota, request telemetry and Safety evidence, publish an individual `retentionTruncated` flag; legacy deleted-count and grouped-cap fields remain available. The two-day selector quota sweep is now capped too. Migration 0270 adds `idx_cron_slot_executions_slot_started_at_prune` on the logical `slot_started_at` clock; it is distinct from the older similarly named `(slot_key, started_at)` index. Product and specialized owner-managed retention remains with its existing owner rather than duplicating its predicates or clocks.

Producer-history retention distinguishes ordinary rows (30 days), budget-only rows (90 days) and UTC-calendar identities (550 days); rich cron drill-down remains separately short-lived. Retention never turns unconfirmed output into a publication.

Permanent product history is explicit, including `supply_history`, `tape_events` and `depeg_events`. The initial D15 dossier incorrectly listed `yield_source_decisions` and `dex_liquidity_history` as unpruned: their existing owner-managed window/predicate policies remain in force and are registered as windowed, not permanent. A schema-backed registry test requires every timestamp-bearing append/history family to have exactly one policy; mutable current-state/replaceable stores have explicit exclusions, not implicit omissions.

The same daily `runPruneCronHistory()` owns the two [Safety publication journal](../report-cards.md#publication-journal-and-movement-attribution) tables added by migration 0262:

| Table | Retention clock | Evidence retained |
| --- | --- | --- |
| `safety_score_publication_journal` | `published_at`, 120 days | Change-only compact accepted per-coin cards, methodology/policy/build identity and input lineage |
| `safety_score_publication_attempts` | `attempted_at`, 120 days | Accepted/held attempt identity, candidate generation, hold codes, input lineage and accepted changed/unchanged counts |

`SAFETY_SCORE_PUBLICATION_JOURNAL_RETENTION_SEC` in `worker/src/lib/safety-score-v9/publication-journal.ts` is the shared cutoff authority. Each table drains oldest eligible rows in 10,000-row statements, capped at 100,000 deleted rows per table per invocation; rows exactly at the cutoff remain. Prune metadata reports `safetyScoreJournalDeleted`, `safetyScoreAttemptsDeleted`, their respective `safetyScoreJournalCappedAtLimit` / `safetyScoreAttemptsCappedAtLimit` flags, and `cutoffSafetyScoreJournalSec`. These bounded operational rows are distinct from permanent public `safety_score_history_v2` and the accepted replay cache; the [manifest retention inventory](../../worker/migrations/MANIFEST.md#append-only-retention-policy) owns the table-level policy. Export attribution reports before retention or missing journal writes erase needed baselines.

`safety_score_capture_archive` is a blob-free index of accepted replay objects. Daily `runPruneCronHistory()` alone deletes expired D1 index rows under `SAFETY_SCORE_CAPTURE_ARCHIVE_RETENTION_SEC`: strict older-than cutoff, oldest-first bounded batches with a per-run cap and explicit capped/deleted/cutoff metadata. Exact-cutoff rows remain. The bucket's `captures/` lifecycle alone expires R2 objects; Worker pruning never deletes them. Archiving attempts every accepted generation, but failed/skipped/timed-out and uploaded-but-unindexed writes leave permanent gaps. R2 precedes D1 indexing; bounded scheduled continuation handles cancellation without blocking publication. Held/failed publications archive nothing. [The archive owner](../report-cards.md#accepted-capture-archive-and-historical-replay) owns transports, continuation/outcome-unknown, lifecycle verification, retention/gap semantics and replay.

After a retention rollout, compare remote read-only table counts with `wrangler d1 info` database size; deleted rows do not prove reclaimed bytes. The per-database ceiling is `D1_PAID_MAX_DATABASE_SIZE_BYTES` in `shared/lib/d1-capacity.ts`. Historical September captures are git-only evidence, not a live baseline. Use [capacity signals](../runbooks/db-connectivity.md#capacity-signals) for current utilization, unknown-evidence handling and census verification.

The DDR publication family (`depeg_resolver_publication_snapshots`, `depeg_resolver_publication_snapshots_v2`, `depeg_resolver_publication_snapshot_refs`) is attributed in the daily table-growth snapshot: it is discovered through the `depeg_` family rule and carries an explicit `published_at` timestamp column in `worker/src/lib/status/d1-usage.ts`, so `/api/status.d1Usage.tableGrowth` reports its row counts, deltas, and oldest/newest publication for the archive decision. Since the reference rows landed, an unchanged quarter-hourly publication adds one narrow row to `depeg_resolver_publication_snapshot_refs` instead of a compressed payload row, so payload-table growth tracks content changes rather than the cron cadence.

The sibling daily `prune-detail-cache` job (`worker/src/cron/prune-detail-cache.ts`) keyset-paginates `detail:<id>` rows and deletes orphans absent from `WORKER_READABLE_IDS`, or active readable rows older than a week. Non-active readable coins (frozen, quarantined, delisted) remain exempt: their retained detail is not refreshable and deleting it would cause permanent 404s. The detail pass stops at the standard per-run row ceiling and reports `retentionTruncated.detail`. Separately, `CACHE_RETENTION_POLICIES` allowlists a 30-day telemetry-only sweep for `cron:event:`, `cron:budget-surface:` and the exact `ops:d1-capacity:v1` / `ops:d1-table-growth:v1` keys. It also retires only `mint-burn-flows:v1:`, `:v2:`, `:v3:` descendants and exact `blacklist:summary:producer:v1` / `:v2` keys; current mint/burn v4 and blacklist v4 readers are preserved. The no-reader audit covers the retired spellings in `worker/src`, backed by a regression test; it is not a blanket cache-version retirement rule. Each cache policy is capped at the standard statement limit per run and reports deleted count and truncation, even when nothing matched. No global cache expiry is inferred: product snapshots, frozen detail, provider credit ledgers, unreviewed namespaces and detail-write-failure markers are untouched.

Capped iteration is owned by `runBoundedPruneGroup()` in `worker/src/lib/bounded-prune.ts`: abort admission, remaining-budget clipping, overload retry and per-entry short-batch termination. `runBoundedPrune()` is its single-statement adapter; `deleteCapped()` adapts SQL/result names and `deleteCappedGroup()` sends independent groups through `db.batch()`. Telegram uses the same executor and shared limit authority, preserving complete child-before-parent drain boundaries for multi-batch workflow/replay families; ordered single-batch steps can share a transaction without changing eligibility. Every raw step now appears in `retentionTruncated`, including grouped steps whose older report intentionally omitted an individual cap. `runCappedPruneFamily()` retains ordered domain SQL, backlog probes, duration timing, shutdown-abort propagation and bounded failure text; its per-statement truncation map supplements the existing family flag. Specialized DEX, mint/burn, reserve and yield owners keep their existing lifecycle/protection predicates.

### Edge Cache Strategy

The Worker uses `caches.default` (Cloudflare's per-colo edge cache) to cache GET responses:

1. **Cache bypass rules**:
   - All non-GET requests bypass edge cache.
   - GET paths marked `cacheBypass: true` in `shared/lib/api-endpoints/` bypass edge cache (status and recurring repair endpoints like `/api/backfill-dews`, including their dry-run preview variants, plus activation-gated public endpoints such as `/api/report-cards/v9`).

2. **Cache check:** `caches.default.match(cacheKey)` — returns cached response if available

For endpoint descriptors marked `cacheKeyIgnoresQuery: true`, the edge-cache key drops the URL query string because the route handler does not consume query parameters. Parameterized routes retain their full query-bearing identity. This changes only cache lookup identity: per-request auth gates, attribution, `Vary`, CORS, and response cache-control handling remain in force.

3. **Cache store:** `ctx.waitUntil(cache.put(cacheKey, response.clone()).catch(...))` — successful cacheable responses are cloned **without** CORS headers before caching. CORS headers are added per-request after cache lookup to avoid caching origin-specific headers. The Worker skips edge-cache writes for responses whose `Cache-Control` contains `no-store`, `no-cache`, or `private`; those responses are intentionally not persisted in `caches.default`.

4. **Cache-Control profiles** (centralized in `shared/lib/api-cache-profiles.ts`; set by individual API handlers, with a small number of route-local special cases):

Freshness-aware cache profiles are ceilings: `api-freshness-headers.ts` bounds browser/shared TTL and the combined TTL + SWR window by the remaining fresh runway. At zero/subsecond runway it returns `no-store`. Generic 8x/12x, chains 1x/2x and yield publication bands remain distinct. Both HTTP dispatch cache-hit paths use `readEdgeCache`, which rejects an entry at its bounded TTL using preserved `Age`/`Date`; forwarding never restarts the original assessment clock. Generic and route-specific `_meta` publish `assessedAt`, `freshBudgetSec`, and `degradedBudgetSec`.

Timestamp validity is separate from retention and age bands. The freshness oracle, policy cache and status snapshot/probe/state readers reject missing, invalid or excessively future generation clocks rather than call them fresh age zero. Their default allowance is explicit and overridable; DEWS hydration validates against read-time wall clock, not its earlier captured run clock, so an overlapping producer's legitimate publication remains admissible. A cache retention TTL of `null` still means no expiry, not exemption from timestamp validity.

`shared/lib/api-freshness.ts` names distinct endpoint freshness, Telegram six-hour flow tolerated-context, and four-hour PSI/DEWS canary incident policies. Operator env warning thresholds remain a separate policy. Centralization does not tighten Telegram primary-alert eligibility or force all consumers to use one number.

The top-level `fetch` and `scheduled` handlers load dispatchers lazily. HTTP keeps metadata/loader closures eager and initializes implementation only on invocation; scheduled slots load only their selected runner. `worker/src/routes/__tests__/lazy-route-loading.test.ts` guards unrelated graph retention. Retired Workflow shells/observer suites must not return through a compatibility import.

The reserve API and its snapshot display resolver use the existing Worker runtime registry projection. Configured feeds retain their complete display reserves, classification flags, and live-reserve configuration; the resolver guards that full-feed slice before applying fallback templates. Invoking this endpoint therefore does not hydrate the full evidence-rich catalog into an isolate shared with scheduled work. The endpoint tests compare every configured feed's fallback and configuration against the full registry. Internal resolver calls also preserve retained historical snapshots for unconfigured assets with ineligible provenance; only their no-snapshot fallback lazily loads full metadata, because the unconfigured projection does not promise complete display reserves.

Full-catalog consumers keep the shared registry's canonical semantics through a Worker-only byte transport; see [Packed catalog transport mechanics](#packed-catalog-transport-mechanics) for the codec, evaluation-build boundary and dated local probes.

Admin `GET` routes are forced to `Cache-Control: no-store` either by `addAdminGetNoStoreHeader()` in `worker/src/router.ts` for registry-dispatched routes or by the admin route wrapper for dynamic admin handlers.

### D1 Read Snapshots And Pagination

- The retired unversioned `GET /api/report-cards` route is not registered. Runtime safety reads use only `GET /api/report-cards/v9`.
- `GET /api/report-cards/v9` is the canonical Safety Score contract backed by `cache["report-cards:v9"]` and `cache["report-cards:v9:publication-health"]`. The reader validates and projects the accepted evaluator publication into the owned public schema with complete model, policy, build, base-input, and publication identity. Missing, malformed, or incomplete accepted state returns `503`; when individually valid publication and health rows disagree, the route serves the authenticated publication as explicitly held instead of hiding the board. It never falls back to V8 or recomputes a score. While held it serves the last accepted snapshot with `X-Safety-Score-Status: held`, accepted-timestamp freshness headers, and `Cache-Control: no-store`.
- `GET /api/yield-rankings` hydrates Safety Score fields from a complete, identity-compatible canonical V9 publication. Unusable live hydration can retain coherent publish-time Safety when both the yield and Safety clocks fit `YIELD_SAFETY_STALE_COHERENT_MAX_AGE_SEC`; `safety-score-index-*` failures disable that fallback. Otherwise rankings remain available with Safety unavailable/NR and PYS null where applicable. The handler never recomputes a Safety Score. The post-V9 publisher stages a yield generation, rechecks active V9 identity, validates rankings and publishes the cache through CAS before replacing current `yield_data` rows. Identity changes, failed cache writes or CAS losses preserve prior published D1 rows; successful cache writes persist current/history rows and selected-source decisions as `published` for that generation.
- `GET /api/stablecoin/:id` serves D1 detail rows from the per-coin cache. Rows inside the 5-minute TTL use the per-coin cache profile. For active coins, older rows below the 24-hour max-stale ceiling serve immediately with `Warning: 110`, `X-Data-Age`, and `Cache-Control: no-store`, then refresh through an isolate-local per-coin single-flight background refresh. Active rows at least 24 hours old require synchronous refresh and cannot provide stale fallback on failure. Non-active readable coins serve their last cached row without provider refresh, regardless of age.
- Event feeds support bounded offset pagination plus opaque keyset cursors. `/api/depeg-events` caps `offset` at `50,000`; `/api/mint-burn-events` and `/api/blacklist` cap `offset` at `25,000`. Blacklist exact totals are opt-in; other feeds accept `includeTotal=false` to skip exact count queries. Inexact responses mark `totalExact: false`: a nonempty offset page establishes its offset plus observed rows/lookahead; an empty offset page establishes only a zero lower bound, not the requested offset. Cursor continuations expose only the observed page/lookahead bound.

### External API Monitoring Baseline

When public API usage grows, monitor these three Cloudflare dimensions first:

1. **Per-endpoint request volume**
   - Track top paths by requests and trend (`/api/stablecoin/:id`, `/api/stablecoin-summary/:id`, `/api/stablecoins`, `/api/report-cards/v9`).
   - Alert on sudden spikes (for example, >2x 24h baseline).
2. **Per-endpoint cache performance**
   - Track `CF-Cache-Status` mix (HIT vs MISS/BYPASS) and overall cache-hit ratio by path.
   - Investigate if heavy endpoints drift toward MISS-heavy traffic.
3. **Per-endpoint error rate**
   - Track 5xx rate by path (especially `502`/`503`), not just global error rate.
   - Alert when 5xx ratio breaches your SLO target (for example, >1% for 5 minutes).

This baseline is enough to catch most abuse, regression, or cache-efficiency problems early.

### Router-Dispatched Status Actions

Operator admin actions are dispatched through `worker/src/router.ts`; [`shared/lib/api-endpoints/definitions.ts`](../../shared/lib/api-endpoints/definitions.ts) owns their paths, methods and `statusPageAction` metadata, and `worker/src/api/admin-actions.ts` owns their handlers. `/admin/` derives its action inventory from that registry. The [admin API reference](../api-reference-admin.md#admin-endpoint-entry) owns individual endpoint contracts.

Action effects remain handler-specific: digest triggering queues a leased background run with `force=true` and returns `202 Accepted` immediately; blacklist reset rolls EVM sync state back 50,000 blocks and Tron state back seven days; sync-state inspection returns all `blacklist_sync_state` rows. All use the [admin-auth lane](#admin-auth). Feedback is router-dispatched too, but is not part of the status action registry.

Every endpoint with `statusPageAction` metadata is audited at the shared router boundary after its handler returns, including read-only inspections and dry-run previews. The canonical row records only definition-owned action/path/scope metadata, the configured target query parameter (or `batch` / `invalid-target`), HTTP/result status, execution certainty, dry-run/live/inspect mode, and a SHA-256 idempotency identity. It never records request bodies, arbitrary query parameters, auth headers, raw responses, or plaintext tokens. Browser actions use only the normalized email injected from the signature-verified Pages Access JWT; caller-supplied actor headers are not forwarded. A nullable unique `(action, intent_key)` index keeps one row per keyed intent: replay responses insert only when the first audit is missing, while the non-replay original response authoritatively replaces an earlier replay placeholder. If canonical persistence fails, the router returns `503 audit_persistence_failed` while preserving replay metadata; a same-key retry replays the stored action result and backfills the audit without rerunning the effect. A catalog handler that needs richer handler-specific details must set `statusPageAction.auditMode = "handler"` and write its single audit row itself; the canonical router then opts out.
Audit mode uses the handler's resolved `dryRun` response flag when available, never the catalog's UI preview default; body/query aliases and precedence therefore match execution without persisting their values.

### Idempotent Admin Actions

**File:** `worker/src/lib/idempotency.ts`

These router-dispatched admin routes honor an optional `Idempotency-Key` header. The complete action inventory and endpoint contracts live in the [API reference](../api-reference.md) and are derived from the shared endpoint registry.

Retired curl-only reset/kill/pending-clear/resend controls are unregistered. A direct exact-key D1 delete is equivalent only for simple lease/breaker rows after [shared recovery](../runbooks/lease-and-breaker-recovery.md) preconditions. Kill, pending cleanup and resend have no blanket D1 equivalent: deleting pending state bypasses dead-letter/projection/audit work and destroys evidence. Restore a control only through reviewed implementation, never route reversion alone.

API-key create/rotate use the sensitive-response replay mode: the first successful response returns the one-time plaintext token, while the idempotency row and every replay retain only allowlisted public key identity plus `tokenUnavailableOnReplay` recovery guidance. Redaction failure is fail-closed as `execution_unknown`; plaintext tokens are never persisted for replay.

The worker fingerprints method + path + sorted query + body for a given action key. Replays return the stored response with `X-Idempotent-Replay: true`; conflicting reuse returns `409` with `X-Idempotency-Conflict: request-mismatch` and cannot replace the original intent's audit. Reservations have an owner/generation and a separate durable execution-start transition. An unstarted reservation may be taken over after 20 minutes. A started reservation is at-most-once: once `execution_started_at` is set, the absence of a terminal response cannot prove the effect did not commit, so after 24 hours the row is compare-and-swap recorded as terminally `execution_unknown` with a structured warning and every replay answers `503`. Re-execution is possible only when the action supplies a `reconcileAbandonedExecution` callback that proves the original effect never landed; without that proof the key is never re-run and operator reconciliation is required. Terminal writes remain owner/generation compare-and-swap operations. A thrown handler, an explicit unknown-certainty response, or any handler HTTP 5xx returns `503` with `error = "execution_unknown"` plus `X-Execution-Certainty: unknown`. Later requests with an explicitly stored `execution_unknown` key replay the same operator-reconciliation state without running the mutation again. Terminal rows age out of the table-wide seven-day prune; `PENDING` and `execution_unknown` rows are excluded, because an unknown row is a permanent reconciliation tombstone whose key must never reserve a fresh row and re-run after the TTL.

### Internal Detail Snapshot Inputs

`GET /api/stablecoin-detail-snapshot-inputs?ids=usdt-tether,usdc-circle` is a cache-only build transport, classified `publicApiAccess: "site-only"` in `shared/lib/api-endpoints/definitions.ts`. It requires the trusted site-proxy credential on the site API (or a credentialed preview) and explicitly denies the browser-facing Pages `/_site-data` mapping. The Worker admits this exact internal GET separately from browser-proxy eligibility after checking the existing site credential. Public-host requests return `404` even with an API key; missing site credentials return `401` and site-lane non-GET requests return `405`. It has no public/admin/manual probe and is intentionally excluded from integration OpenAPI, Postman, and the generated public endpoint catalogue. All responses bypass edge caching and use `Cache-Control: no-store`.

The request accepts 1–10 unique canonical IDs; malformed or oversized batches return `400` with the ordinary `{ error }` envelope. `worker/src/api/stablecoin-detail/snapshot-inputs.ts` reads one frozen canonical publication and completed supply marker per batch, then processes detail caches and exact 90-day D1 history sequentially. It never admits provider materialization, schedules refreshes, or writes caches. One full detail body at a time and a 128 KiB compact entry cap bound memory and response size.

The response is `{ version: 1, entries }`, with one entry per requested ID in request order. Available entries contain `liveSummary`, `supplyHistory`, independent millisecond lane `updatedAt` clocks, and per-lane `freshness: { status, maxAgeSec }`. `sources` carries second-resolution detail-cache, publication and completed-supply update clocks and supply snapshot date. Source absence stays `null`; projection is shared with the browser/per-coin generator in `shared/lib/stablecoin-live-summary.ts`, while wire schemas live in `shared/types/`.

Lane clocks prefer body provenance, then origin `X-Data-Updated-At` seconds from the real detail cache/publication or completed-supply marker. Pages forwards this header unchanged. A malformed present header fails closed; legacy Date/data-age/edge-age reconstruction is used only when it is absent and can lose seconds at HTTP boundaries. Bulk uses these same response helpers, never synthetic HTTP dates.

Unavailable entries explicitly carry `id`, `sources`, and `reason`: `unknown-id`, `detail-cache-missing`, `detail-cache-invalid-clock`, `detail-cache-too-old`, `publication-unavailable`, `supply-marker-missing`, `invalid-cache-input`, `entry-too-large`, or `cache-read-failed`. Active details at least 24 hours old require normal per-coin acquisition; inactive cached records retain their existing no-refresh policy. Oversized or bad entries are quarantined, never truncated, silently omitted, or replaced with zero. The generator falls back to ordinary detail/history reads only for those coins. See [Build snapshot hydration](../stablecoin-detail-page.md#build-snapshot-hydration) for the default-off source switch and byte-equivalence cutover proof.

## Cron Scheduling

The [canonical cron cadence, physical aliases, Worker roles and slot identities](../worker-infrastructure.md#cron-scheduling) are generated from the shared registries and both Wrangler configs. This appendix retains dispatch ordering, CPU-class rationale and capacity contracts rather than a second schedule inventory.

Fetch-heavy lanes are split across the expressions in `worker/wrangler.toml` and `worker/wrangler.heavy.toml` so they do not compete with the quarter-hourly core pipeline for the trigger-wide fetch budget or share CPU budget with DB-only availability jobs. `shared/lib/cron-jobs.ts` owns logical cadences and physical hourly aliases; `shared/lib/scheduled-runner-registry.ts` owns public/heavy dispatch. The DEX source lane normally stages hourly at `:10`; the paired `:16` + `:46` consumer normally publishes at `:16` and reuses the accepted generation at `:46` for V9 preparation. If `:16` did not complete, `:46` may consume the hour's still-unconsumed stage. Bounded inline source recovery is separate from the normal staging cadence and requires its provider credentials. `[limits].cpu_ms = 300000` remains the repo cap, while Cloudflare's [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) give sub-hourly expressions a 30-second CPU class and hourly expressions a 15-minute class. Any further physical-trigger growth requires consolidation or an ADR-backed rebalance.

Scheduled child execution is accounted in the additive `scheduled_child_attempts` ledger (`worker/migrations/0260_scheduled_child_attempts.sql`). A deterministic attempt key includes producer schedule/slot/job/path/kind/invocation/attempt and the executing fence identity, so replay children retain their source identity without masquerading as the recovery slot's producer. A required start marker is durable before child work, including jobs that suppress detailed progress. One SQL-fenced terminal writer arbitrates real and reconciled terminals; its claim token also guards producer projections and head/publication updates in the same transactional D1 batch. The invocation-level producer-history aggregate remains separate from immutable attempt terminals. Apply the additive migration before either new Worker script; old Worker conflict targets remain valid.

Stale reconciliation keeps one terminal item per ledger `attempt_key`, even when multiple attempts share the same job, producer slot and second-resolution start timestamp. A shared progress row supplies evidence to each matching attempt; progress deletion and lease cleanup run once for that row, while `abandonedJobs` retains one entry per attempt (including repeated job names). Slot completion requires every started attempt to have a terminal token, and a sweep after completion is a no-op.

`resolveScheduledSlotPolicy()` in `worker/src/lib/scheduled-slot-policy.ts` owns unchanged heartbeat/abandonment thresholds for admission, takeover, targeted preparation and global sweeps. Candidates are policy-filtered before limits and policy is repeated in claim CAS. `status-self-check` stays first in its chain. The bounded global sweep-only stage starts `digestTriggerPoll`, independently of digest demand and reserve-recovery's lease; same-key presweeps no longer delay admission. [Event-entry lifecycle and admission](../worker-infrastructure.md#event-entry-lifecycle-and-admission) owns the await inventory, deadline and maintenance-stage contract.

`createSlotDeadline(eventEntryMs)` in `worker/src/lib/cron-timeouts.ts` creates one immutable `SlotDeadline` from the actual event-entry wall clock, not the logical producer slot. Its absolute deadline preserves the existing 15-minute ceiling minus the 60-second controlled-error reserve; `remainingMs()`, `childCeilingMs(budgetMs)` and `latestAdmissionMs(budgetMs, reservedWorkMs)` derive bounded child/admission windows without restarting time after waits or replay. DEX handlers pass that same object through source staging, inline recovery and consumer context to enrichment leaves, clipping their existing local caps. `sourceSlotStartedAt` remains source identity and `stageReadyDeadlineMs` remains readiness; neither reconstructs an execution deadline. Publication freshness remains a separate policy.

`worker/src/lib/scheduled-child-terminal.ts` owns `markScheduledChildStarted(db, identity, startedAt, leaseOwner)` and `writeScheduledChildTerminal(db, input)`. The marker returns the deterministic attempt key; terminal arbitration returns `{ accepted, attemptKey, token }`. `ScheduledChildIdentity` carries the producer identity plus required source `slotStartedAt`, `attemptNo` and `executionFence`. The persisted attempt remains after settlement, even when its detailed progress row or short-lived cron history is pruned; slot deletion cascades the ledger under the existing retention policy.

[ADR-38](../architecture.md#adr-38) defines the public/heavy split shown in the [generated cron table](../worker-infrastructure.md#cron-scheduling). Dispatch requires an explicit caller role and logs the neutral `scheduled-worker-not-owner` skip before runner imports, fences or D1 writes. It creates no counterfeit `cron_runs` row; unknown expressions still throw. Public bypasses heavy memory-lane waits while heavy retains admission/producer priority. Owner-aware stale-slot reconciliation resolves the dead slot's registry owner and reads the verified `worker-active-version:<owner>` marker, never a caller-supplied UUID or role; a public deployment cannot manufacture heavy deploy-neutral evidence. First-seen and activation UUID keys remain immutable.

Reconciled child rows preserve bounded `progressSnapshot` evidence before cleanup, and slot events expose shallow `abandonedProgress` entries with validated counts, reserve coin/adapter identifiers and aggregate I/O/timing counters. `metadataStatus` names missing/malformed/oversized input. Last-known progress is diagnostic context, not interruption attribution. Compact slot metadata retains child-job counts/outcomes (`jobsRun`, `jobsSkipped`, `jobsNeutralSkipped`, `jobsDegraded`, `jobsErrored`, `budgetOnlyJobs`), and degraded/error children escalate the slot even when best-effort work continues.

A stale child is deploy-neutral only when its executing UUID differs from the **registry owner's** current verified UUID, the stale slot heartbeat is no more than 15 seconds newer than child progress, progress leads the heartbeat by at most `resolveScheduledSlotPolicy(slot.slot_key).heartbeatSec`, and latest life evidence `max(slot.updated_at, progress.updated_at)` falls from 15 seconds before to 120 seconds after the owner's immutable `worker-version-activated:<uuid>` timestamp, with activation no later than the sweep. A missing slot UUID can use the dying invocation's `cron_run_progress.metadata.workerVersion`; another script's reconciler UUID cannot substitute for owner deployment evidence. This directional alignment admits eviction between slot ticks without admitting a slot that continued heartbeating after its child stopped. Zero progress past child start is not required. Activation clocks come from Cloudflare `created_on`, never CI wall time; first-seen evidence stays diagnostic, and absent/out-of-window activation stays error/abandoned. Idle neutral no-op children never synthesize missing daily-digest failures, but durable started digest progress is reconciled when abandoned.

`cron-sentinel` is the shared control-plane identity for status, daily, turnover and reserve-post-sync invocations. Its rule table records source severity, cooldown and sustained window. Status evaluates freshness and digest publication; daily evaluates growth, duration and repair debt. DEX turnover and reserve checks remain producer-adjacent. Health readers consume the nested daily growth/repair evidence from the sentinel result; retained standalone job rows are a legacy read fallback, not newly emitted compatibility jobs.

Successful sentinel leaves publish `ok` with observed findings under `metadata.quality`; operational failures remain non-ok and quality aggregates by source. Repair execution exceptions publish `degraded` with `repair-execution-failed`, preserving per-task isolation and fenced backoff; safe-class deferrals remain successful evidence. Configured `ruleIds` and triggered `firedRuleIds` are separate. Failed reads, required persistence and attempted operator-alert delivery remain non-ok; cooldown/unconfigured transport leaves transitions pending.

Reserve recovery persists phase progress before targeted config recovery (including lazy initialization), producer-slot checkpoint preparation and replay; it does not own global sweeping. Redemption consumers persist a stage before module initialization and before input reads, resolution and publication. Reconciled `progressStage` identifies the last entered phase, not proof that it completed or caused the interruption.
The reserve chain keeps producer → redemption → sentinel ordering. Redemption reads producer-only sealed acceptance after any settled head outcome; only the sentinel requires successful current-cohort exhaustion. Recovery completion reruns redemption even when an earlier fallback child completed, while consumer-only replay stays idempotent. No trigger, lease reset or recovery admission bypass is introduced.

Post-claim producer/heavy-slot priority deferral awaits exact-owner `recovering → ready` release before returning. Untouched replay suffix/progress/children and historical domain attempt remain intact and immediately reclaimable; started, terminal, lost or mutated claims refuse without clearing ownership. `recoveryClaimRelease` records the actual disposition, and the hourly guard requires its invocation to own the claim. This changes neither family TTL nor admission/concurrency.


Scheduled consumers that need only lifecycle, identity, contract, price-sanity, or bounded DDR structural metadata use `shared/lib/stablecoins/worker-runtime-registry.ts`, never the evidence-rich full registry. This includes daily housekeeping, blacklist, DEX discovery, detail-cache prune, supply snapshot, Telegram, extended mint/burn, and DDR (including its review path). Daily housekeeping uses its own daily-only cron-sentinel entrypoint, so it does not initialize reserve-post-sync code. `npm run check:runtime-reachability` bundles the memory-constrained entrypoints, including DDR, and rejects paths back to the full registry. The quarter-hourly sync still legitimately consumes evidence-rich metadata elsewhere in its graph, so its entrypoint is not falsely classified as registry-free.

Physical dispatch preserves logical slot identity while using reviewed hourly CPU-class aliases and staggered starts. This is placement protection, not proof of CPU exhaustion, isolate separation or new memory headroom.

Unchanged-config polls do not initialize adapter fetchers or execution machinery, and checkpoint replays with an exhausted reserve queue load only unfinished consumers. Reserve request-cache telemetry recognizes immediate LRU delete/reinsert pairs with one key and a weak promise-identity marker. The hourly yield slot (`hourlyYieldSync`) also runs two chains: the publication chain `sync-yield-supplemental → fetch-tbill-rate → sync-yield-data`, and beside it the Dwellir trial's observation lane `observe-rpc-provider-parity`. Per chain, the probe compares Dwellir with the reviewed comparator described below (normally the first registry operator or reviewed public pin): head lag, totalSupply read at a common block, a short address-filtered log window, and a pruned-log probe for chains whose Dwellir `logsHistory` is `none`. The parity lane covers the 37 reviewed EVM chains without promoting Dwellir. It separates first-touch latency from warm per-call method metrics and records per-method availability. Latest-state freshness keeps two separate proofs per chain, and either one failing marks the run stale. The served-block sentinel uses Multicall3 getBlockNumber on thirty-four chains and ArbSys arbBlockNumber on Arbitrum and Robinhood, so Nitro's L1-height domain cannot be mistaken for the execution-chain block height; XDC has no deployed sentinel. The token proof compares the chain's state-target `eth_call` at `latest` against Dwellir numeric-block reads that must fully cover `[max(0, H1 − T), max(H2, R)]` (H1/H2 the bracketing heads, R the sentinel's served block, T the shared tolerance below), capped at ten numeric calls; uncovered, regressed, errored, or moving no-match windows are inconclusive, because a stable H2 does not establish continuity with H1 across a reorganization. A frozen value matched across an unchanging window is non-discriminating. Freshness sufficiency requires 24 discriminating fresh or stale sentinel observations; only targets without a deployed sentinel use token-proof sufficiency, while any stale token proof still fails freshness. Token-proof coverage is opportunistic: quiet tokens yield inconclusive proofs, which the report counts but never treats as passes. The full-run envelope is 648–802 total calls and 536–690 Dwellir responses per run, or 12,864–16,560 Dwellir credits per day at hourly cadence; calls remain serial within the same one-connection/four-minute limit, hourly target-start rotation spreads deadline skips with bounded partial coverage, and the report retains per-chain skips. A separate Alchemy head read before logs establishes genuine first-touch/warm phases; `logsComparator` and `comparatorsByStep` retain the actual references, and failure/mismatch diagnostics name the reference actually read. Ordinary targets retain their originally captured headers; split-reference headers are captured before the first await. ### Cron Error Handling Policy

Shared cron behavior is narrower than a single worker-wide tier system:

- `runLeasedCron(...)` / `logCronRun(...)` record terminal outcomes per canonical schedule/job/path and persist Worker version plus invocation identity.
- A weighted slot semaphore allocates at most five declared connection units across child jobs, sidecars and budget-only work; provider-level limits still own physical fetch concurrency. Heartbeats and ledger writes are serialized per job.
- Thrown or explicit error outcomes are recorded after terminal accounting and before rethrow.
- Degraded returns, no-write fallbacks, and producer-specific retries remain job-owned.
- Exact V9 input preparation is a neutral not-started child when the preceding DEX consumer is locked or intentionally withholds publication. On a DEX error it may reuse a consistent last accepted generation inside `DEX_LIQUIDITY_EVIDENCE_MAX_AGE_SEC`; failed or out-of-budget recovery skips neutrally. An otherwise successful DEX result without an exact generation remains a fail-closed error.
- Sidecar publication returns a structured terminal outcome; failures cannot be swallowed behind a successful parent result.

Best-effort handling retains that result separately from persistence error; void completion stays absent.

Calendar work retains UTC-month identity. History stores compact scalars; rich detail belongs in short-lived `cron_runs`, current heads and generation ledgers.
  `loadProducerHeads()` joins `worker_producer_retained_counts` by identity: O(number of heads), never an invocation-history aggregate per request. - Error descriptors compose runtime-neutral `describeError` with Worker `stripSensitive`: sanitization precedes bounds, root stack only, cycle-safe property reads and bounded causes/aggregates. Original error/timeout/abandonment identity survives failed accounting separately from the persistence cause. `shared/lib/cron-quality-reasons.ts` is the import-free shared quality parser; operator tooling must not import Worker D1 types through the logger.

The baseline schema and migration manifest own column inventories; [retention](#append-only-d1-retention-policy) owns pruning. Attempt terminals remain independent of detailed progress; slot deletion cascades their ledger.

### In-flight Cron Progress

`cron_run_progress` is diagnostic live state, not execution authority. Status exposes it only with an active matching lease; expired/orphan rows become stale artifacts. Slot heartbeats use `resolveScheduledSlotPolicy()`; child lease renewal is separate from slot heartbeats. `runCronWithLease` defaults to `heartbeatSec = max(15, floor(ttlSec / 3))` with `maxRenewFailures = 2`; the named long-running jobs in `PER_JOB_LEASE_OPTIONS` (`worker/src/handlers/scheduled/context.ts`) override that to 30 seconds and 3 consecutive failures. Terminal cleanup is invocation-fenced.

Heartbeat writes retry D1 overloads; a queued write lasting a heartbeat period cannot suppress later ticks. Replacement CAS attempts require owner/generation/state and apply `MAX(updated_at, attempt timestamp)`, so delayed writes cannot move life evidence backwards. Stale/hard-dead thresholds remain those of the [slot policy](#cron-scheduling).

Stage transitions always persist; same-stage updates within 10 seconds coalesce. `shouldSkipCronProgress()` and `PROGRESS_TELEMETRY_SKIP_JOBS` in `worker/src/lib/cron-timeouts.ts` own suppression (including `prune-*`/`*-watchdog`), not inferred timeout size. Wrapper milestones start only after lease acquisition. Producer-specific phase names live beside producers; reserve recovery reports fence reconciliation. A last-entered phase proves neither completion nor interruption cause.

### Per-Job Cron Timeouts

`logCronRun()` supplies the abort signal; exceeded ceilings log error and propagate cancellation through `fetchWithRetry()`. Jobs may stop admission earlier to preserve persistence/cleanup time; the wrapper remains authoritative if a bounded call runs late. An unstarted tail must retain its producer's deferred/degraded semantics, never silently vanish.

[Worker and API Limits](../worker-and-api-limits.md#per-job-cron-timeouts) owns the timeout source index and cancellation semantics. `worker/src/lib/cron-timeouts.ts` derives ceilings from `CRON_JOB_DEFINITIONS` and `CRON_TIMEOUT_OVERRIDES_MS` and falls back to `DEFAULT_CRON_TIMEOUT_MS` for any job without an override; the runner contract test asserts only that every registry job has a finite positive budget, so a new job is auto-defaulted rather than rejected. Read source-owned producer budgets rather than a second timeout roster.

### Circuit Breakers

`worker/src/lib/circuit-breaker.ts` owns per-source `circuit:<source>` state; `shared/lib/circuit-sources.ts` owns keys/scopes and active/retired classification. Individual rows are execution authority. Admin summaries enumerate active sources with bounded reads, never rebuild the retired aggregate index. Malformed records fail closed; diagnostics label them invalid/unavailable rather than inventing closed evidence. Absent initial rows are legitimate closed state; admitted records preserve additive fields.

Three consecutive failures open; recovery probing begins after 30 minutes. Half-open admission is best-effort, not a cross-isolate lock, and may admit concurrent probes; unresolved probes reopen after two intervals. State transitions emit structured events, not webhook fan-out. Cron degraded/locked/neutral outcomes are neutral by default, explicit `ok` heals and thrown/error fails unless the source opts into stricter behavior.

Public health degrades with three open public-impact circuits. `isPublicImpactCircuitKey()` admits source-wide/unknown scopes, excluding asset-scoped, optional, retired and dynamic reserve scopes; scoped reserve/price health remains independently enforced. The shared protocol-redeem family stays source-wide even for single-asset members. Health inventories active plus configured reserve keys, filtering retired/stale rows. Scoped reserve resets still target exactly one `circuit:<source>` row under the shared recovery runbook.

Pricing emitted provenance is not necessarily circuit identity: `shared/lib/pricing-source-registry.ts` owns producer/scoped/local/cached enforcement; retired sources can remain historical provenance without rejoining outage counts. Retired vaults.fyi evidence remains protected pending separate archive/rollback-floor cleanup. Provider source handlers own exceptions: guarded no-quote can stay neutral, malformed pool members are schema degradation (valid siblings stage; all-invalid is not verified absence) while breaker transport accounting remains separate, and DexScreener partial success can heal before a later rate-limit stop; zero-success refusal fails. REDSTONE requires usable symbols, not merely transport success. Provider-specific request batches/retries and endpoint inventories belong to their sources.

### Cache Table

### Multi-key generations

A shared `updated_at` is not generation identity: independent conditional upserts may accept different runs at the same clock. Related keys require atomic publication and one-snapshot reads. `persistFxRateState()` in `worker/src/lib/fx-rate-state.ts` fences both `fx-rates` and `fx-rates-meta` statements on neither key being newer; either newer row blocks both and second-statement failure rolls back the first. ### FX and metals references

`worker/src/cron/sync-fx-rates.ts` owns FX/metals collection; `worker/src/lib/fx-config.ts` owns currency/provider membership. Quarter-hour triggers claim generation-fenced 30-minute cadence buckets; completion requires canonical publication, and failed buckets remain retryable. Frankfurter is the ECB/business-daily primary; dated currency-API mirrors cover the secondary/calendar-daily set and full-set recovery, followed by ExchangeRate-API before eligible cache carry. Full-set fallbacks require every `EXPECTED_FX_PEG_KEYS` fiat peg. Partial live fallback preserves canonical state and degrades with `partial-live-fallback-coverage`; partial primary responses may recover omissions only from cadence-valid original observations, otherwise `incomplete-expected-fx-coverage` remains visible.

`fx-rates`/`fx-rates-meta` are one atomically published generation; [Multi-key generations](#multi-key-generations) owns pair fences/digests. `usableSyncAt`, per-peg observation time/cadence/date and per-source successful-fetch time are distinct. Daily carry uses expected publish cadence; intraday carry uses elapsed seconds. Overlays preserve existing daily cadence/date and every explicit cadence override; only legacy cadence-less metadata may infer natural cadence and its date together. No carry refreshes an observation clock. Cached fallback is reserved for unavailable live sources plus no cadence-valid carry; fresh full-set recovery through OXR/Chainlink exits fallback immediately.

Chainlink overlays use reviewed EUR/GBP/JPY/XAU/XAG feeds, source freshness and 5% divergence bounds, trying dedicated dRPC before shared RPC and Etherscan proxy. `worker/src/lib/chainlink-round-data.ts` separates undecodable transport failures from decodable invalid answers (`invalidReason`, counted as `invalidAnswers`, not `fetchErrors`); reserve consumers still fail closed through `requireChainlinkLatestRoundData()`. OXR observations retain provider `timestamp`; missing, >2-hour-old or >5-minute-future observations emit `openexchange-rates-observation-rejected`, fail the breaker and leave incumbent provenance unchanged. Chainlink replacement compares actual source clocks, not fetch time.

`assessFxPegAdmission()` serves pricing and health. Missing/malformed/mismatched generation, missing source mode, missing intraday source time or >5-minute-future source time never becomes healthy through cache recency. Pricing returns its established `stale`/`none` verdict; health degrades with `fx-metadata-<identity>` or `fx-source-provenance-unknown:<peg>=<reason>,…` and names every affected peg. Timestamp-less values retain null provenance.

Metals use keyless `https://api.gold-api.com/price/XAU` and `/XAG` when due, with bounded retries. Preserve ISO `updatedAt`; missing/malformed/nonpositive/>60-second-future timestamps are null, never fetch time. `isValidFxRate()` applies metal bounds and 20% prior-value delta limits, plus 5% agreement with any fresh commodity-peer median. Failed/divergent spots may recover from freshness-admitted tracked gold-token medians (silver's tracked token), dated by the oldest contributing quote, then eligible cached metals. Chainlink metal quotes remain freshness/divergence cross-checks; older rounds cannot replace fresher spot provenance. Failed-bucket retries mean one gold/silver pair per successful bucket is not a physical-request ceiling.

Supported native-fiat CoinGecko history precedes USD history plus historical FX; Frankfurter ranges cover ECB currencies and date-addressed currency-API snapshots cover the rest. Sparse historical references fall back to the current peg reference. Extraction validates against each timestamp's direct reference in `historical_backfill` mode. ### Batch Execution

`batchExecute()` in `worker/src/lib/d1-primitives.ts` serially executes bounded chunks (default `D1_BATCH_SIZE`) and sums `meta.changes`. This conservative statement cap is distinct from D1's per-query bound-parameter limit, not a claimed platform `batch()` statement ceiling.

Each chunk is its own transaction: later failure leaves earlier chunks committed. `setCachesAt()` inherits this boundary. All-or-nothing publications must fit an explicit `executeAtomicBatch()` (`worker/src/lib/db.ts`) or their guarded publication protocol. Chunking never authorizes partial audience/generation publication; Telegram membership pages remain pending until every chunk succeeds.
### Cron Lease Primitives (Phase C)

`worker/src/lib/cron-lease-primitives.ts` owns acquire/renew/release; `worker/migrations/0000_baseline.sql` owns schema. Acquiring an unexpired foreign lease fails; renewal/release require the exact current owner. `runCronWithLease()` releases only after settlement; uncooperative aborted work leaves ownership to expire, never clears it early. Contention and priority deferral remain distinct locked/neutral outcomes.

Defaults are timeout + 60s TTL, `max(15s, ttl/3)` heartbeat and random owner. Successful renewal resets the consecutive-failure counter; isolated misses do not accumulate forever. The outer timeout aborts the lease wrapper, not merely its inner job. Slot fencing precedes all child work and is separate from per-job overlap protection.

### Lease Integration Status

Scheduled execution is now wired in two layers:

- `worker/src/handlers/scheduled.ts` normalizes `event.scheduledTime` into a durable slot timestamp and awaits the fenced slot inline via `runScheduledSlotWithFence(...)`, which keeps manual `/__scheduled` replays from being cancelled mid-slot by preview-only `waitUntil()` teardown semantics
- `worker/src/handlers/scheduled/context.ts` keeps per-job `runLeasedCron(...)` for job-level overlap protection, timeout logging, and progress

This means duplicate trigger deliveries for the same slot are skipped before shared-slot fan-out can reorder downstream jobs, while individual jobs inside the accepted slot still use their existing per-job leases. The slot fence also races controlled-deadline expiry against the runner promise: cooperative jobs still receive the abort signal, and a non-cooperative or stuck runner is finalized as an error before the platform has to reconcile it as an abandoned slot.

Fence admission pre-sweeps stale prior `cron_slot_executions` rows for the same schedule key, and a same-slot takeover performs the same reconciliation before new work starts. The five-minute reserve-recovery lane additionally retains a global sweep. A `running` row older than the 15-minute scheduled-event wall clock plus a minute of skew is treated as provably dead regardless of its heartbeat column, and a child lease whose heartbeat has been silent for five minutes no longer shields its slot even while the lease TTL is unexpired. Before touching child artifacts, reconciliation atomically transitions the exact stale owner/generation/heartbeat row from `running` to `reconciling`; a concurrent heartbeat makes that claim change zero rows and leaves all child state untouched. If the claiming process dies, a later admission can reclaim the stale `reconciling` row with the same owner/generation/heartbeat compare-and-swap and a new generation, while a fresh reconciliation claim remains protected for the full stale window. Takeovers increment `execution_generation`, and heartbeat/finalization updates require the current owner, generation, and state. A zero-change heartbeat aborts controlled work, while a late original finalizer cannot overwrite the takeover or synthetic error. Reconciliation writes idempotent synthetic child `cron_runs` evidence and the compact abandonment event marker. This keeps platform-killed scheduled events from remaining operationally `running` or `reconciling` without letting a stale observer corrupt live artifacts.

Synthetic chronology uses the original evidence clock, not sweep wall time. A started child records its original `started_at` and ends at its last durable progress heartbeat; a child proven not started uses the slot invocation time and last slot heartbeat. The later reconciliation timestamp remains metadata only, so old abandonment evidence cannot outrank a newer real cron run or producer head. Conditional `digestTriggerPoll` slots are special: absence of daily-digest progress means the poll was idle and produces no synthetic child failure, while durable started progress is still reconciled as abandoned. Status history also excludes legacy false `daily-digest` not-started rows from idle polls before its per-job history limit, without hiding genuine forced runs or abandoned-progress evidence.
