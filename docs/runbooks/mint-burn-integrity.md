# Runbook: Mint/Burn Integrity

Triggered by `StatusCause.code`:
- `onchain_integrity_degraded`
- `onchain_integrity_stale`
- `onchain_monitor_unavailable`

## Symptom

On-chain supply divergence/staleness causes remain a separate supply-monitor surface. The Mint/Burn Integrity card instead diagnoses exact native-token conservation over reviewed matched-block ranges; a verified mismatch is critical, while missing, stale, malformed or unsupported proof remains unverified. USD circulation differences are retired and cannot diagnose ingestion integrity.

Public mint/burn availability causes (`mint_burn_public_degraded`, `mint_burn_public_stale`) are emitted from the critical-lane freshness/health path and currently do not attach a dedicated runbook link. Use this runbook for on-chain integrity causes and the `/flows` / cron diagnostics when the public mint/burn lane is implicated.

## First checks

1. For the trigger codes above, inspect `onchain_supply` monitor freshness/divergence first. **Pipeline → Mint/Burn Integrity** is a separate native-conservation surface: inspect the affected contract, config fingerprint, reviewed law, block range/hashes and raw residual. A one-base-unit mismatch matters.
2. **Critical/extended crons:** inspect each contract's lane, observed head and stored cursor. A passing record requires a completed fresh scan covering its audited blocks; an unrelated new run cannot renew it.
3. **`mintBurnReconciliation`:** inspect `conservationIssue`, per-record reason, both audit/checkpoint ages and `coverageStatus`. Missing supply-cache data must not hide native records. Unsupported identities require reviewed admission, not a fabricated pass.
4. **Publication versus ingestion:** inspect the flow response's `publication.legs` before attributing a stale watermark to a new config. `pending-admission` does not enter published totals or weights. In Access-protected cron detail, `providerOutcomes` identifies actual RPC successes/failures, neutral reads and blocked requests; the cron's overall `error` status is not proof of an Alchemy outage.

## Remediation

- **Native mismatch:** investigate exact identity, reviewed conservation law, fetched/parsed/stored native event completeness and checkpoint hashes before choosing any repair. A mismatch stays unresolved until a verified pass replaces it; do not clear audit caches to make it green.
- **Coverage/backfill:** use the existing bounded mint/burn backfill only after identifying missing events/cursor coverage. Price backfill repairs valuation debt, never the native residual.
- **On-chain monitor unavailable:** usually indicates the recent `onchain_supply` monitor rows are missing or unreadable globally. Check the relevant supply-monitoring cron/status sections before treating it as a mint/burn config issue.

### Publication admission and operator disable

The admission, isolation, quarantine/reactivation and grandfathering contract is owned by [Mint/Burn Flows: Publication admission](../mint-burn-flows.md#publication-admission). Operationally: inspect public `publication.legs` diagnostics (`legsScope` marked non-admitted, membership counts, `admittedPairs`, evaluation clock and budgets) and cron `legsShown`/`legsOmitted`/`legsTruncated`; missing proof is unavailable, not zero progress. For `valuation-incomplete`, use the historical-price debt workflow below — scan proof alone cannot repair missing USD values. Do not move a cursor or extend the grandfathered roster to make admission pass; the roster kill switch remains the operator rollback.

For a misbehaving config, use the supported configuration rollback:

1. Set `MINT_BURN_DISABLED_IDS` to the leg's exact `configKey` from the checked-in `MINT_BURN_CONFIGS` registry (`mintBurnConfigKey(config)`), or its stablecoin ID to disable all that coin's configs. Non-admitted publication diagnostics also expose the key; the exact Tron key is listed below. Values are comma-separated and matched case-insensitively. `MINT_BURN_DISABLED_SYMBOLS` remains supported, but a symbol shared by more than one coin (`GUSD`, `MUSD`, `OUSD`, `REUSD`, `USDP`, `YUSD`) disables nothing: use the exact ID or config key for those tickers. The run emits `mint_burn_disabled_symbol_ignored` naming the ignored symbol, its `shared-symbol`/`unknown-symbol` reason and any previously durable disabled keys it retained, so a deployment that already used the symbol keeps its quarantine instead of silently re-enabling those legs. `enabled=false` is the checked-in configuration equivalent. Changing the runtime switch requires configuration activation, not a code revert.
2. Observe the first scheduled mint/burn run using that configuration. Before scanning it persists the effective disabled-key policy and atomically purges affected flow caches. A stored `disabled_keys` value that cannot be decoded does not abort the lane: the run logs `mint_burn_disabled_policy_unreadable`, retains no disabled keys from that row, and the same sync rewrites it from the configured switch. A `paused_keys` value that cannot be decoded fails the run and publication readers closed (it gates reactivation, so it is never read as empty); repair that row before the next run. A failed read of the policy row itself still fails the run closed before any rewrite. Publication readers and later cache writes obey that durable policy, including the aggregate gauge and downstream published-flow readers. A configuration update alone is not evidence that the policy has been applied; verify the affected legs report `disabled` and that the next aggregate's watermark/totals/weights use the remaining admitted scope.
3. Preserve raw events, scan proofs and admission rows for diagnosis. Explicitly disabled keys, keys that left the active roster (admitted or grandfathered) and stalled active admitted keys are retained in `mint_burn_publication_policy.paused_keys`; that pause gates re-admission but never withholds an inactive quarantined coin's retained per-coin detail, which only an explicit disable does. A stall quarantine withholds that active leg's flows until catch-up. Removing the switch retains membership, but a stale leg remains `pending-admission` / `reactivation-pending` until its current-fingerprint frontier is fresh and it proves the incumbent publication's closed hour. It does not repeat 90-day admission. Verify a fresh publication rather than treating the first attempted scan as recovery.

Existing same-coin/same-chain contracts share an hourly bucket. Disabling one therefore removes that shared chain leg (`shared-bucket-disabled`); automatic isolation tests independent survivors only after expanding candidate scope to all existing siblings, and the existing BUIDL siblings wait together during reactivation. A newly added sibling cannot be safely isolated in that bucket yet: it remains `pending-admission` / `unsupported-shared-bucket` and is excluded before scanning. Add per-contract event/hourly attribution before supporting such siblings; independent new-chain configs follow ordinary catch-up.

Apply the revised, unreleased `0288_mint_burn_admission.sql`, including `paused_keys`, before activating this Worker. The earlier draft is insufficient for these readers; a database that already applied it needs a separately numbered additive migration because `CREATE TABLE IF NOT EXISTS` cannot amend that table. During rollout, DEWS can consume a retained gauge without `publication` metadata by using only its published coins in the pinned legacy roster and reapplying current policy; it does not invent an empty scope while waiting for the next gauge. Existing freshness and coverage checks still apply.

Pending hourly-materialization failures are isolated after admitted work commits. `pending-hourly-recalc-failed` or `pending-cursor-commit-failed` holds the affected pending cursors/proofs for retry; it does not roll back admitted progress. Inspect the bounded `pendingMaterialization` failure metadata and retained dirty-hour evidence before repair.

Provider recovery is separate: an open Alchemy circuit blocks only Alchemy requests; another admitted endpoint can continue, and the disable policy still persists. Denied transaction-context reads keep the affected config retryable with `tx-context-request-not-started` instead of aborting every config. Inspect `providerOutcomes.terminalFailures` alongside request diagnostics: `ok` resets Alchemy only with an observed request, `degraded` is neutral, and `error` fails Alchemy only with required RPC evidence still incomplete in an admitted config/head scope. Recovered or certified-prefix retries, decode-only errors, conservation failures, exhausted budgets, denied requests, pending work, local exceptions and the publication sidecar cannot establish that failure. Mint/burn does not write Dwellir's parity circuit. Do not clear another provider's breaker to cure a local write, conservation or coverage failure.

### USDT Tron admission and rollback

USDT Tron uses exact config key `tron-TR7NHqjeKQxGTCi8q8ZY4pL8otSzgjLj6t`. It starts as `pending-admission`; scheduled critical catch-up establishes its history after activation, with no pre-activation bootstrap requirement. The reviewed floor is block **84,842,059**, timestamp **2026-07-28 00:00:00 UTC**; its predecessor **84,842,058** is **2026-07-27 23:59:57 UTC**. The source label is `dwellir-tron-header-2026-07-28-reviewed-2026-10-28`. This is a coverage floor, not deployment evidence. Keep the block, source and event definitions stable because they participate in the scan-proof fingerprint used for initial admission and published coverage.

Admitted work runs first. Each pending Tron opportunity spends at most the 60-request critical config cap and reserves capacity for a half-range retry, so eventful headers cannot force the same oversized prefix to fail every run. With two topics and 10,000-block pages, a 170,000-block prefix plus its 85,000-block retry fits after shared head reads. No historical-conservation requests are made.

Pending work stops six minutes after run start, including head preparation, scan/retry reads and coverage repairs; a new pending config requires more than 60 seconds before that stop. This reserves roughly four minutes of the ten-minute task timeout for materialization, retention and cache publication; it is not a completion guarantee for those stages. Event timestamps, reduced retry prefixes, fallback, latency, sparse usable evidence, the earlier stop and missing historical valuations can delay admission; this is not an admission guarantee.

First-production acceptance:

1. Confirm the revised migration `0288_mint_burn_admission.sql`, including `paused_keys`, is applied before the Worker/config activates.
2. Observe Tron as `pending-admission` with the expected fingerprint and advancing durable coverage/frontier metadata. The existing admitted roster, USDT published scope and common watermark must remain unchanged by pending Tron.
3. Inspect request diagnostics, `providerOutcomes.terminalFailures`, request limits and `tronRpc` diagnostics. `tronRpc.circuitState` names the TronGrid circuit state read by this run and `tronRpc.circuitInvalid` flags a corrupt row that was replaced with a fail-closed open record (TronGrid requests are then denied, not the whole run). Tron failures must not establish terminal Alchemy evidence, and mint/burn must not write Dwellir's parity circuit. A stale solidified head carries `tron-rpc-stale-solid-head`; a failed head carries its failure reason. Neither is a successful up-to-date scan. Conservation remains `unsupported` / `tron-historical-state-unavailable` rather than a pass.
4. After full current-fingerprint 90-day coverage, complete baseline valuation and a fresh frontier, confirm durable `admitted` membership and a new publication containing Tron. Check `netFlow90dUsd` remains available where the incumbent value was available; then verify the expanded USDT nets, gauge weight, digest gauge inputs and DDR mint-surge scope. An eventful control must count Issue/Redeem once despite the paired Transfer.

To remove only Tron from ingestion and publication, append **`tron-TR7NHqjeKQxGTCi8q8ZY4pL8otSzgjLj6t`** to `MINT_BURN_DISABLED_IDS`, retaining other configured values, and activate that configuration. Do not use `usdt-tether` or `USDT` when Ethereum should remain enabled. Follow the policy-persistence/cache checks above: wait for the scheduled run to report this leg `disabled`, verify the remaining scope and account for ordinary edge-cache expiry. This is not an instantaneous CDN purge. Removing the switch retains config-key membership; a stale previously admitted Tron leg remains `pending-admission` / `reactivation-pending` until current-fingerprint frontier and incumbent-hour proof pass, without repeating 90-day admission. The scheduled path is the supported Tron catch-up mechanism; operator Tron backfill is not included in this release. Automatic operator selection stays EVM-only; explicit Tron selection returns HTTP 400 with `mint-burn-operator-chain-unsupported: tron` before credential checks, provider reads or D1 selection writes.

Before rolling back to a pre-admission-gate Worker, pause Tron ingestion and either purge retained `usdt-tether` / `tron` rows from `mint_burn_events` and `mint_burn_hourly`, with reviewed backup and derived-publication/cache handling, or explicitly accept that those rows can become public. The old Tape projector has no admitted-chain filter, and the old DDR query filters by coin only; both can expose pending Tron history. The new disable policy cannot protect readers that do not implement it. A purge is a separate reviewed database-maintenance operation; Worker rollback alone leaves these rows and the additive admission tables intact.

### Bridge classification and historical repair

Use [Bridge Classifier](../mint-burn-flows.md#bridge-classifier) for exact deployment/version/token proofs. A known-pool burn with resolved context but no recognized signal remains `review_required / known-bridge-pool-without-bridge-signal`; do not clear it by counting all pool burns or excluding an entire transaction. Missing/malformed receipt context is a deferred read, not a non-bridge verdict. Unresolved mints are stored the same way (`review_required` with the bridge reason) and count as unresolved mint events in the hourly bucket.

After activation, retain the deployed Worker version and one new affected execution with actual row-level CCTP v1/v2, CCIP or OFT proof. Validate a mixed transaction preserves its economic row through the later roundtrip stage. No additional context reads should appear. Historical rows need a separately reviewed whole-hour replay and classification/materialization proof; a successful forward run cannot repair a 90-day net. Changed decoder fingerprints keep earlier hours outside certified windows until fresh complete replay or age-out. Worker rollback does not undo already stored classifications.

### Historical price debt

The command contract is canonical in [Operator runbook: historical mint/burn prices](./one-shot-backfills.md#backfill-mint-burn-prices). Operationally:

1. Preview a bounded batch and review every disposition, especially `irreducible` and provider-retry outcomes.
2. Before mutation, take a fresh D1 Time Travel bookmark and coordinate a maintenance window for the [atomic import availability impact](./one-shot-backfills.md#transport-safety). Execute the same scope with `--execute --allow-atomic-import`, the required confirmation, bookmark, and a unique `--idempotency-key`.
3. Repeat until both `backlog.unclassified` and `backlog.pendingAggregate` are zero. A pending aggregate rebuild must finish before more price rows are attempted.
4. Reopen `irreducible` rows only after adding or repairing a named event-day historical source. Current spot, peg-par, and adjacent-day prices are not substitutes.
5. No lane substitutes ingestion time for event-time price evidence. Since mint-burn-flow v6.23, live ingestion and the 48-hour auto-heal admit only evidence whose actual observation time is within ±24 hours of the event (a `supply_history` snapshot price through its recorded `price_observed_at`, or an in-window replay-safe `price_cache` observation); anything else stays NULL and enters this backlog. Expect this for NAV tokens over weekends/holidays (observation older than 24h) and for nominal-par assets. Heal skips coins with no admissible evidence in its 48-hour window, so their rows age into this historical backlog instead of blocking the auto-heal budget. The operator path is stricter still: exact UTC event-day evidence only.
6. Rows written before v6.23 with `price_source = 'price-cache-current'` were valued at ingestion and stamped with run time. Audit only retained raw rows (compare `timestamp` with `price_timestamp`) through a separately approved bounded repair plus hourly rebuild. Eight days is the pruning age floor, not a guaranteed deletion time: unsettled valuation, incomplete hours and tape/frontier debt can retain older rows. Pruned rows and their hourly buckets cannot reconstruct that provenance.

### Valuation-completeness debt

Unpriced events are retention-protected until price repair classifies them, so a burst of out-of-window events (backfills, new configs, `price_cache` outages) grows `nullPriceBacklogHistorical` and keeps their hours `partial`: the public API publishes null nets and NR pressure for those windows. Watch `nullPriceBacklog` in `sync-mint-burn` metadata and drain it through the historical price debt sequence above rather than loosening the ±24h admission.

### Classification-completeness debt

Inspect the flow response's independent `classification` verdict for the affected window. `classification-unresolved` means standard events still require review; `classification-unknown` means legacy hourly counts are NULL on a coin whose current config can produce unresolved events. Both withhold exact net, direction, bounds and score inputs. Valuation repair and a complete scan do not resolve classification evidence.

The hourly `mint_unresolved_event_count` / `burn_unresolved_event_count` columns distinguish an observed zero from historical NULL. The bounded retained-hour rebuild may replace NULL only while every raw sibling is still retained; older hours require a complete audited replay, never a rebuild from survivors. Unresolved raw events and their whole coin/chain/hour remain protected through hourly retention. Every source classification change and its dirty-hour debt commit together; debt settles with the rebuilt aggregate. Do not clear debt or set counts to zero manually.

DAI and USDD use v6.42 range proof and retained repair. Recent repaired windows recover independently, while windows containing unresolved or historically unknown hours keep null signed nets and withheld derived signals until complete replay or age-out. The bridge decoder's changed scan fingerprints independently exclude hours classified under earlier evidence. After deployment, correlate the active Worker version and methodology with a new affected execution and its publication before claiming acceptance; a green deploy or a completed maintenance attempt alone is insufficient. The [owning methodology](../mint-burn-flows.md#valuation-completeness-rendering) defines value-level disclosures; no reader-facing banner is needed.

### Conditional range supply proof

Apply additive migration `0301_mint_burn_supply_proofs.sql` before the v6.42 Worker. Retain the pre-window Time Travel bookmark, migration ledger and both Worker identities. Schema success is separate from proof acceptance: verify a new DAI and USDD range, exact pinned boundary hashes, integer `M/Z/Δ/R`, event-set digest and matching event proof references, then its complete-hour rebuild and publication. A non-bridge proven range must not require per-burn supply receipts. Existing bridge classification remains independent.

Inspect `mint_burn_supply_proofs` by config/range and lifecycle. Only proven nonempty witnesses are persisted; unavailable or residual outcomes leave real event rows unresolved, and proven empty ranges create no proof row. `pending` evidence cannot authorize public totals while its members or dirty-hour rebuild are incomplete; `accepted` evidence still needs current config/law identity and canonical boundaries. Retained invalidated members become unresolved, and only complete raw-retained hours are dirtied for rebuild. Never promote events by block range alone, change raw arithmetic, delete proof records to clear a finding or turn missing reads into zeros. Receipt-only replay must preserve a valid proof reference while its evidence is retained.

Config/law changes withdraw scan coverage directly from durable configuration fingerprints in `mint_burn_supply_proof_configs` and scan-ledger evidence, independently of surviving proof rows or event references. Retain removed-key fingerprint tombstones. Detected canonical conflicts also retire overlapping scan fingerprints while preserving ledger rows as replay anchors; merged spans may remain unavailable more broadly until fresh complete replay. Do not enqueue pruned hours for a rebuild from partial survivors.

Proven events follow normal eight-day raw retention even when they carry `supply_proof_id`; unresolved hours retain their existing complete-hour protection. The bounded retention job prunes proof records once their range is older than raw retention and no retained event references them. The partial event proof-reference index in migration 0301 supports member lookups. Monitor actual D1 size and the existing growth watchdog's event counts; fingerprint-based withdrawal keeps older public windows fail-closed without retaining 95 days of proven raw events.

For a reviewed `source-only` law, negative residual means false zero transfers exist: ingestion can advance, candidates remain unresolved, and existing receipt proof may resolve independent burns within the budget. Do not tolerate or distribute the residual. Positive residuals, positive 0→0, reorgs or inconsistent raw evidence are hard fences requiring investigation. Missing archive, log, implementation guard, request budget or deadline evidence is a named unavailable outcome, never a latest-state proof. USYC requires a mint-free complete range; a fake mint/burn cycle does not qualify. Guarded proxy/delegate identities cannot be enabled from matching boundary implementations alone: the complete range must exclude upgrade/delegation changes, including change-and-back.

Retained range repair re-fetches complete logs and pinned state with a progress cursor separate from live `last_block`, and rebuilds whole coin/chain hours through the shared writer. Start only at the first complete raw-retained hour. An old surviving row does not establish that its siblings remain available; pruned-hour reconstruction belongs to separately audited historical replay. On failure retain debt and unresolved rows; do not move the live cursor to simulate repair. Worker rollback retains the additive table, event columns and proof history; restore D1 only for unexpected mutation using the verified bookmark.

## Prevention

- Token identity comes from shared stablecoin metadata, but tracker-specific config lives in `worker/src/lib/mint-burn-contracts.ts` and lane state in `worker/src/cron/mint-burn/run-state.ts`. Adding a new coin without mint/burn contract config keeps it outside mint/burn reconciliation and backfill scope; it does not emit a per-coin `onchain_monitor_unavailable`.
- Supply-monitor divergence thresholds live in `shared/lib/status-thresholds.ts`. Native conservation instead requires an exact zero residual; audit, closing-checkpoint and scan clocks must each fit the owning lane's three-interval producer grace band (90 minutes critical, three hours extended), published as `conservation[].maxAgeSec` by `worker/src/lib/status/derived-data.ts`. Check both original proof clocks: a recent audit of an old catch-up range is still unverified. Do not loosen either policy to conceal missing proof.
