# Worker & API Limits

Reference for limits we can verify from repo code and checked-in config.

This document intentionally focuses on:

- limits enforced in code
- budgets encoded in config
- runtime assumptions the scheduler is explicitly designed around

It intentionally does **not** treat vendor pricing-plan quotas as source of truth. Cloudflare, CoinGecko, Alchemy, Dwellir, Etherscan, Anthropic, X, and similar providers can change those independently of this repo. Re-check official vendor docs or your live account dashboard before making spend-sensitive or capacity-sensitive changes. Where the repo controls admission instead of trusting the vendor, the named repo constant — not the plan's published quota — is the authority (the Dwellir admission threshold below is the worked example).

### Connection-budget operating assumption

Cloudflare currently limits each invocation to six simultaneous outbound requests still waiting for response headers; a request frees that header-wait slot once headers arrive. Pharos deliberately uses a stricter trigger-wide six-connection model in its static scheduler budget so nested and chained fetch phases cannot overlap at the platform ceiling. See the [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) and the [April 2026 connection-limit change](https://developers.cloudflare.com/changelog/post/2026-04-09-relaxed-connection-limiting/).

Conservative scheduler rules:

- heavy lanes get isolated trigger slots (`sync-blacklist`, `sync-mint-burn`, `sync-mint-burn-extended`, `sync-dex-discovery`, `sync-dex-liquidity-stage`)
- shared slots bundle only related work
- the quarter-hourly handler sequences jobs instead of fanning them out blindly, with D1-only DDR work on the independent `depegResolverOffset` lane
- `npm run check:cron-connections` fails any trigger at or above `6/6` and reports `5/6` triggers as **headroom full**
- the connection check includes budget-only scheduled surfaces that do not create separate `cron_runs` rows: `telegram-registration-reconciliation`, `telegram-digest-outbox-drain`, `safety-map-producer-kick`, and `digest-trigger-poll`

New fetch-heavy work added to an existing trigger slot competes for the same trigger-wide outbound connection budget. A `5/6` trigger is full for new fetch-heavy work unless the change also reduces existing peak usage or moves work to another slot.

The one-lane `project-tape` geography canary reserves **one** in-flight service-binding request on its public driver (`dewsPsiOffset`: `1/6`); the heavy projector has no outbound HTTP, and DEWS and PSI stay serial/in-process. The reservation stays at one with the rollback flag off, covering either configuration. The reviewed deduplicated fetch-capable ceiling admits this binding call; physical-trigger and headroom-full ceilings are unchanged. Consume/cancel the returned body before later work; no transport retry or in-slot local fallback is permitted. [Placed-fetch lifecycle, auth, placement-hint limits and qualification](./worker-infrastructure.md#project-tape-placed-fetch-canary) own the contract.


`status-self-check.maxConnections` is **2**: its optional Cloudflare D1 REST database-info and GraphQL trailing-24h usage requests run concurrently. Capacity monitoring and endpoint/monitor probes remain serial. The existing later budget-only price-corroboration reservation still owns the status trigger's **4/6** peak; `:09/:24/:39/:54` aliases and runtime concurrency are unchanged. Rollback must not restore an underdeclared one-connection child while retaining that concurrent pair. The permanent D1 census runs serial aggregate reads of reviewed table families once per UTC day via same-day cache reuse, not a separate claim or a full-database/storage-size census.

Current state: `halfHourlyOffset` and `halfHourlyChartsOffset` remain the two modeled `5/6` slots, full for new fetch-heavy work. Charts-offset's reviewed recovery peak is `5/6`, ordinary serial work `3/6`; heavy has Graph credentials for inline missing/terminal-stage recapture under Graph-key preflight, source-stage lease and inherited deadline. A live producer is never overwritten. Absent credentials still fail preflight as `missing-graph-api-key`; a configured key is capability, not evidence recovery succeeded. The hourly :10 source stage remains at most `5/6`. Active measured execution uses three EVM lanes (`3/6`); shadow EVM remains daily. DEX consumption, turnover, V9 preparation and charts remain serial. Both :16/:46 use one exact source-slot consume/reuse decision; an actual accepted publication drives turnover. Payload v4 (D1 schema v1) supplies the frozen registry-read clock; older payloads fail closed without reducing the target catalog. See [DEX stage/recovery contract](./dex-liquidity.md#dex-liquidity-score).

Supplemental families run serially; Beefy, Royco and Aave each cap outbound concurrency at three. Due Aave work follows safe stablecoins publication at unchanged `4/6` peak. Siblings retain their `3/6` slot and hourly catch-up plus parity at `4/6`. Aave's six targets run in two batches of three within its unchanged 28-second deadline; nested fan-out must stay inside that cap.

For `sync-stablecoins`, failed upstream responses must still be consumed or canceled before later passes start. This bounds unread bytes, completes transport cleanup and keeps fetch phases deterministic; it does not claim an unread body still occupies Cloudflare's header-wait slot. The late fallback phase remains `CoinMarketCap` -> `Jupiter` -> `DexScreener`.

Mint/burn conservation audits pool boundary-header, hash-pinned supply and boundary-recheck reads in a serialized pre-pass before contract scans. The three phases consume chunks of at most 100 calls per POST from the lane global request budget, not per-config budgets, with a 45-second pre-pass allowance capped by the lane deadline and a 15-second per-POST timeout capped by the remaining allowance. They introduce no new trigger or parallel connection peak. Each config still reuses fetched logs and independently fences/persists/advances its cursor. Exhausted audit capacity remains unverified rather than causing an unlimited retry loop or expanding the lane budget. See [Raw Token Conservation](./mint-burn-flows.md#raw-token-conservation).

The same cleanup rule applies to Worker-side integration clients: Telegram delivery, X posting and GitHub feedback submission consume or cancel response bodies before returning, so transports retain no unread streams or unbounded response bytes.

Shared JSON-RPC transport does not parallelize requests: no-batch members and log-context recovery stay serial, and every physical generic RPC attempt rechecks admission before metering and network intake under the original deadline/body ceiling.

Worker response readers use one bounded byte-stream transport for bytes, UTF-8 text and JSON; diagnostic snippets truncate at their byte cap. Strict reads validate the cap and declared length before intake, then enforce the cap on actual bytes even when headers lie. Native null bodies yield empty bytes/text and a JSON `SyntaxError`, retain unknown (`null`) intake evidence, and still honor pre-aborted signals and strict preflight. Null-body JSON keeps rejected observation semantics; streamed JSON parse failure does not turn an accepted transport read into rejected intake. Method-only response doubles are unsupported.

The response-body suite also exercises null bodies, streamed bytes and parent cancellation in local workerd with production compatibility settings; its temporary Wrangler config resolves the Worker tsconfig relative to that config's directory, not the repository working directory.

## Cron Budgeting


### Per-job resource evidence

`ResourcePressureSchema` in `shared/types/status/cron.ts` is the single contract for progress and terminal `resourcePressure`. `logCronRun()` keeps the latest validated snapshot before progress suppression/coalescing; result evidence wins observation-time ties. Error paths retain the last observation time instead of stamping old intake as freshly measured. Metadata compaction preserves the complete validated block. Uninstrumented jobs expose null policy/measurements and `not-measured`, not zero or a green heap claim.

Reserve request retention is estimated, not measured heap: JSON counts **8 × actual intake bytes**, strings count `max(intake bytes, 2 × characters)` (plus 512 bytes for response wrappers), binary counts its byte length, and branch-price Maps declare `sum(128 + 2 × key.length)`. `REQUEST_CACHE_MAX_TOTAL_BYTES` is 16 MiB; `REQUEST_CACHE_MAX_ENTRY_BYTES` is 4 MiB. Pending deduplication is separate from retained entries. Valid entries evict the LRU **before insertion**; unknown/oversized estimates bypass retention without failing work. The existing two-operation adapter I/O limiter also bounds fetch/body/decode work; no new trigger or separate heap boundary is implied.

Intake counts streamed bytes across retries, separately from declared `Content-Length`; declared preflight rejection consumes zero bytes. Missing body evidence is null. The snapshot's body cap is the maximum source cap admitted this run, not a claimed heap ceiling. Cache and input/catalog admission fields do not include in-flight buffers, parse expansion, source-result groups, warmed module graphs, concurrent HTTP work, or native/Wasm storage.

`heapUsedBytes` is always null with `workers-runtime-no-heap-api`. The installed unenv `node/internal/process/process.mjs` memory-usage implementation is a zero stub; [Workers process documentation](https://developers.cloudflare.com/workers/runtime-apis/nodejs/process/) and the [workerd native process declaration](https://github.com/cloudflare/workerd/blob/main/src/workerd/api/node/process.h) do not establish a usable production heap API. Never sample `process.memoryUsage()` as production heap evidence. `platformOutcome` is populated only by the existing slot reconciler's proven abandonment/interruption classification and names `slot-reconciliation`; it is **not** inferred OOM/CPU evidence.

The Node-only [`ops:worker-memory`](./scripts.md#operator-cli-contract) collector and hourly **Worker Memory Monitor** Action independently query Adaptive `status:"exceededMemory"` for `stablecoin-heavy` and `stablecoin-api`, separately from broad sampled memory and direct role/day P50/P90/P99/P999. Every byte value is **sampled V8 isolate memory shared across concurrent invocations**, not a phase high-water mark, invocation-population estimate or headroom. Unknown metrics/sampling are null; observed numeric zero stays zero. Lane/day distributions use nearest rank over underlying uniquely matched row `memoryUsageBytesP50` samples, with N/outcome/version/colo and physical/logical lane strata, so a colo change splits the lane/day row instead of pooling its memory samples; direct Cloudflare role/day quantiles stay date-level and colo-free, separate from lane stats, never percentiles-of-percentiles.

Correlation requires same-script exact invocation second and CPU difference strictly under 2 µs, unique in both directions, **requests = 1 and sampleInterval = 1**. Scheduled labels may differ from Adaptive; the normalized slot uses the Scheduled clock and canonical registry/helper. Registry candidate chains/budget-only jobs are not historical execution/culprit proof. Six-hour queries bisect at 10,000 returned rows; unsplittable one-second caps, 240-request/360-second ceilings, auth/schema/transport failures remain named incomplete evidence, with positive kill subtotals retained. Requests are sequential, spaced at least one second, with 30-second per-request limits and no retries.

Schema-v1 reports retain source windows (labelled `default` or `explicit`), per-query sampling/coverage, source SHA, generation and policy. Lane descriptors appear once in `report.json.laneDescriptors`, keyed by `lane.scheduleKey`; sample and kill rows retain lane identity/candidate chains without repeating descriptors. The default covers the previous complete UTC day plus today (≤48 hours), ending 900 seconds behind collection time. Coverage lag above 8,100 seconds is labelled `coverage-stale`: it fails the **Collection incomplete** workflow step for default windows, but is report-only for explicit forensic `--from/--to` windows. `collectionIncomplete` describes missing/failed required sources only; freshness failure is separate (`freshnessFailed`). No report-age budget is enforced; inspect `generatedAt` when reusing retained evidence, and do not treat a historical report as fresh coverage. The ingestion allowance is not a provider completeness guarantee. Heavy kills in `[to−86400,to)` alert through the separate **Heavy kill observed** step, with physical/logical lane labels or explicit unattributed status in the annotation and summary. Public kills and incomplete public broad sampling are report-only initially; review after one week. Five evidence files are retained 30 days, with no Worker API/D1 changes. See [OOM triage](./runbooks/cron-slot-abandonment.md#first-checks).

### D1 overload retry posture

Cron persistence helpers retry transient D1 queue pressure through `runWithOverloadRetry()` in `worker/src/lib/d1-overload-retry.ts`. Retried errors include `D1 DB is overloaded`, `Requests queued for too long`, D1 storage-operation reset timeouts (`D1 DB storage operation exceeded timeout ...`), Cloudflare D1 internal-reference errors (`D1_ERROR: internal error; reference = ...`), and transient D1 transport loss (`Network connection lost`). Retry backoff is abort-aware, and `batchExecute()` can accept an `AbortSignal` so chunked persistence can stop before the next D1 batch after cron timeout or lease loss. Every status-tracked job resolves a `CRON_TIMEOUT_MS` ceiling, with the five-minute default permitted; the scheduled-runner contract test checks roster coverage and finite positive values. If a leased job ignores timeout or lease-loss aborts, `runCronWithLease()` records an abandoned failure and leaves the lease row to expire by TTL instead of releasing it while late writes may still be running. Long-job lease heartbeats renew every 30 seconds and abort controlled work after three consecutive renewal failures. The duration watchdog excludes stale-slot reconciled synthetic child rows from runtime averages, keeps 7-day runtime totals for diagnostics, but requires repeated cap hits or unrecovered `runBudgetTruncated` rows (those without a persisted deferral cursor, `cursorTailState <> 'complete'`) to reach the alert threshold inside the 24-hour recency window — cursor-complete truncations are the designed graceful-deferral path and no longer alert; `cron_slot_executions` remains the separate scheduled-slot abandonment signal. DEX source-stage chunks use deterministic one-row direct conflict upserts with progress writes every 24 chunks plus the final interval, and an ambiguous final manifest update is accepted only after an exact readback proves the ready/consumed schema, slot, chunk, record, and byte totals. DEX-liquidity publication streams 15 candidate rows at a time into five three-row statements, staying below D1's 100-bind ceiling while reducing statement and batch-call overhead; it still validates the complete per-run generation before updating the public current table. Live reserve, redemption-backstop, cache-sentinel, and DEWS persistence paths should route bursty run-manifest writes, cleanup, prune, and chunked batch work through this helper or `batchExecute()` so one transient D1 queue spike does not fail a whole scheduled run.

Endpoints with live transforms should not use this shortcut unless the companion body already includes those transforms.

Overflow semantics (R1-R8: unavailable is not zero, a failed read never becomes a positive claim):

- The reader rejects a declared over-cap `Content-Length` before reading and otherwise streams and aborts at the cap, so an over-cap body is never parsed and never becomes partial data; the connection returns to the pool immediately.
- The DEX stage turns the overflow into that source's own failure: `fetchSubgraphEntities()` reports `failed: true` with the machine-readable `failureReason: "body-over-cap"` (also `"http"` / `"graphql"`), `readDexApiJson()` returns `"<context> response body exceeded <n> bytes"`, and `fetchFluidPools()` records `fluid <chain> response body exceeded <n> bytes`. Consumers keep the existing degraded/failed-source accounting (`failedSources`, `criticalSourceFailures`, circuit outcomes) instead of publishing a short pool list.
- `worker/src/lib/response-body.ts` keeps `ResponseBodyTooLargeError` module-local and exports `isResponseBodyTooLargeError()` so callers can classify the overflow without string matching; `fetchJsonWithRetry()` remains the owner of the cap check, retries, and body cancellation.
- Callers that must classify the final failure pass `throwOnFinalNetworkError: true` (DEX subgraph pages, Fluid tickers, PancakeSwap subgraph pages); the retry loop still retries the earlier attempts, and the last attempt's typed error reaches the caller's failure path.

Long synchronous work in these phases yields between pages (`yieldToEventLoop()` in the subgraph page loop and the direct-API pagination loop) so slot heartbeats and abort timers keep firing during a multi-page fan-out instead of waiting for the whole provider family to drain.

Bounding each catalog/page intake limits one source's contribution, not the accumulated graph or whole-isolate heap. ### What this means operationally

- Source staging and scoring are separate resource phases. The source stage reduces external bodies into a generation-fenced graph; the consumer is D1-only unless same-hour recovery passes Graph-key preflight, source lease and inherited deadline admission. Heavy has the Graph key and can recover missing/terminal output inline, never overwrite a live producer. Missing credentials still refuse recapture before source/target writes. Invalid/older formats fail closed; unavailable recovery preserves prior accepted publication rather than shrinking the catalog.
- The source and recovery-capable consumer declarations are headroom-full. Sequential Curve rate/model enrichment after graph/direct-provider work cannot add to that peak. Source/RPC/header/identity/fee failures retain capability gates, never a fabricated model. [DEX Liquidity Score](./dex-liquidity.md#dex-liquidity-score) and the [DEX appendix](./process/dex-liquidity-appendix.md) own producer algorithms and stage/quote joins.
- Active measured opportunities share one whole-asset cursor and job lease, not multiplied per-run budgets. Reads remain clock-bounded; shadow generations never score. Expiry-priority packet reservation stays inside admission limits without advancing the cursor; other targets retain whole-coin rotation. New adapters, including hook-free V4, reuse the existing request/subcall/body limits and bounded transport-fragmentation reserve. See [capacity design](./process/worker-infrastructure-appendix.md#measured-execution-capacity-expansion).
- Exact legacy 3pool directions remain atomic, including retained route-only packets. Until both directions meet maturity/success requirements the reserve simulation remains score-facing. Last-known-good evidence retains its original block/time and expires under the common measured-adapter ceiling. Absent bytecode is semantic drift and cannot retain that evidence; unavailable RPC is operational failure, not proof of drift.
- Discovery is best-effort with hard shared/source/coin stops, deterministic lower-priority sharding and a bounded stale-pool refresh slice. Provider/open-circuit failure ends only refresh; registry failure also degrades the run. Cohort crawling continues. New providers need both throttling and a hard stop.
- Missing-price fallback must fit its slot. Replay-safe continuity has a **six-hour maximum** and any shorter source `maxTrustedAgeSec`; low/fallback or non-replay-safe sources are ineligible. The separate verified-CMC bridge (`CMC_VERIFIED_QUOTE_BRIDGE_SEC`) keeps its upstream timestamp/fallback confidence and revalidates identity/peg bounds.
- `activePriceCoverage` is independent of execution/publication: a missing active price degrades public health while a valid remainder stays served and successful publication can remain `ok`. Exact adapters fail closed on stale/RPC/identity/parent/bridge/depth/impact failure; never compensate by widening replay age or substituting nominal parity.

## Design Guidance

Before adding a worker feature that touches external services:

1. Pick the trigger slot first. Shared slots are a capacity decision, not just a schedule decision.
2. Add explicit throttle constants and an overall time budget before writing the fetch loop.
3. Prefer chunked / batched writes and bounded SQL fan-out.
4. Add or reuse a circuit breaker when the feature depends on a flaky upstream.
5. Run `npm run check:cron-connections` and document the trigger-slot impact for any new outbound I/O.
6. Update this doc only with limits the repo actually enforces or depends on architecturally.

If you need current provider-plan quotas, verify them outside the repo before relying on them.
