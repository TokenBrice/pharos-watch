## Overview

Operational and CI helper scripts live in `scripts/`, while worker-bound operational tooling that imports `worker/src/**` lives in `worker/scripts/`. Together they support build integrity, smoke checks, data sync, and targeted maintenance tasks.

## Operator CLI Contract

State-changing and release-control scripts use `scripts/lib/cli-args.mjs`, a strict wrapper around Node's `util.parseArgs`. These entrypoints reject unknown options, missing values, accidental duplicate options, unexpected positionals, and declared option conflicts before network or filesystem effects. Intentional repeats are explicit: for example, `wait-pages-release-marker.mjs` alone permits repeated `--url` values. Every migrated command supports `-h` / `--help`; usage errors exit `2`, runtime failures exit `1`, and help exits `0`.

Every committed source file that reads `process.argv` is enrolled by exact path in `scripts/lib/cli-argv-policy.mjs`. Operator and production-mutating entrypoints must reach a parser that imports and calls the shared strict wrapper; read-only, build/local-artifact, and test/dev entrypoints require an explicit categorized exemption and audit reason. `npm run check:cli-args-policy` rejects unclassified additions, stale or duplicate declarations, strict/exempt overlaps, and strict-parser claims that are not reachable from the entrypoint. Add or remove entries in the source-owned policy with the corresponding script change; there is no count baseline to update.

For these scripts, `--dry-run` means no mutation: a command may read local state or fetch remote data to validate the planned operation, but it does not write files or call a mutating API. `register-telegram.ts --check` remains a compatibility alias for its no-network dry run. `sync-digests.ts --check` remains the narrower no-network wiring check; it conflicts with `--dry-run` so the selected behavior is unambiguous. Existing no-flag workflow invocations retain their prior live behavior.

## D1 Insights Capture

Use `npm run ops:d1-insights -- --dry-run` to preview the default read-only Wrangler calls. Without `--dry-run`, the helper captures `7d` reads, `30d` reads, and `30d` time for `stablecoin-db`, then writes `agents/d1-insights-<timestamp>.json`.

Report shape:

```json
{
  "generatedAt": "2026-06-04T00:00:00.000Z",
  "database": "stablecoin-db",
  "captures": [
    {
      "period": "30d",
      "sortBy": "reads",
      "rows": [
        {
          "query": "SELECT /* pharos:example */ ...",
          "_pharos": {
            "sqlFingerprint": "0123456789abcdef",
            "sqlComment": "pharos:example",
            "sourcePaths": ["worker/src/api/example.ts"]
          }
        }
      ]
    }
  ]
}
```

Compare captures before and after an infrastructure change by `period`, `sortBy`, `_pharos.sqlFingerprint`, and `_pharos.sourcePaths`. Keep generated reports under `agents/` unless a durable methodology or source change requires documentation.

`pharos-change-contract.mjs` is the shared local agent hook engine for CI PR comments and explicit local agent hook opt-ins. `SessionStart` records fingerprints for pre-existing dirty files. Repository-tracked Codex hook configs are intentionally not installed because they would execute mutable working-tree code automatically in every checkout; Codex users who want local hooks should keep their `.codex/config.toml` or `.codex/hooks.json` untracked in their own environment. The checked-in Claude config installs `SessionStart` and `PreToolUse`; the script still supports Codex/Claude `PostToolUse`, `PostToolBatch`, and `Stop` modes for manual or future user-local hook wiring, but they are not installed by the checked-in configs today. `PreToolUse` and `PermissionRequest` are intentionally narrow: they block destructive git cleanup, raw production deploys, remote D1 mutations, direct writes to env/git/build-output paths, and obvious destructive migration SQL without running heavy validation automatically. Deploy and remote-D1 guards inspect executable shell command positions, so searches and patches can still mention blocked release commands.

`worker/package.json` keeps `npm run deploy` as a guarded command via `scripts/ci/guard-worker-deploy.mjs` that exits with release-flow guidance and rejects all undeclared arguments. Production Worker releases prefer the CI-documented sequence: upload a Worker Version, run validation and migration checks, preview-smoke the candidate, promote it through `.github/scripts/deploy-worker-version.mjs` using the Cloudflare Workers Deployments API, and then sync triggers. The promotion helper strictly accepts `--version-id`, `--name`, `--message`, and `--dry-run`; its dry run prints the target and payload without requiring an API token. When Cloudflare rejects Workers Versions with `entitlements.not_available [code: 10007]`, CI keeps the same validation and migration gates but falls back to `wrangler deploy` before trigger sync and production smoke.

`.github/scripts/wait-for-workflow-job.mjs` polls the GitHub Actions REST API for same-run job completion. Jobs that call it must grant `actions: read` and pass `GITHUB_TOKEN`; transient API/JSON failures are retried by the polling loop. Its `--job` option is required, numeric options are strict bounded integers, and duplicate/unknown options fail before polling. `scripts/maintenance/wait-pages-release-marker.mjs` applies the same contract while allowing repeated `--url` values intentionally.

## Safe Usage Guidelines

- Treat `backfill-*` scripts as admin operations: run against staging/dev first when possible.
- Run smoke scripts against explicit URLs during incident debugging (avoid relying on default env fallback).
- Keep script-owned generated artifacts (`data/digests.json`, `data/logos.json`, `public/og-*.png`) under version control policy used by this repo.
