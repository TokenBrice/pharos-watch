# Q-012 — Bare catch in loadPriceValidationReferences silently swallows DB errors and masks degradation
**Medium** · effort **S** · _error-handling_ · pillar **quality** · ✔︎ verifier-adjusted
**Location:** `worker/src/lib/price-validation.ts:L191-L197`
**Found by slice:** `wl-core-6`

**Verifier note:** The bare `catch` at worker/src/lib/price-validation.ts:191-197 is confirmed: it catches all errors from the `loadFxRateState` call (including any D1 `getCache` throws) and returns the fallback with no `console.warn`, no `console.error`, and no metric increment. `loadFxRateState` itself also has no logging — it returns `null` silently on JSON parse failures. Any transient D1 error will cause all non-USD FX-pegged stablecoins to fall into unbounded validation mode (`type:"none"`) with zero observability. The finding is real. However, severity "High" overstates the impact: the fallback is an intentional design choice (not a data-corruption or security path), nothing crashes, and price acceptance just widens temporarily. The gap is purely operational visibility — there is no way in Cloudflare log tail to detect when or how often this degradation fires. Correct severity is Medium: a real observability/debuggability defect, not a correctness or safety failure. The proposed fix (add `console.warn(err)` before the return) is minimal and appropriate.
## Problem
The outer try/catch on loadFxRateState (line 141–197) catches all errors and returns type:'none' without any logging. A transient D1 error, an unexpected exception, or a programming bug in the FX-rate loading path will silently degrade every price that relies on FX references (all non-USD fixed pegs) to unbounded mode. There is no observability into when or how often this fallback fires.
## Proposed remediation
Log a console.warn/error with the caught error before returning the fallback, so degradation is visible in Cloudflare's log tail. Optionally increment a metric counter. Do not change the fallback behavior itself — it is intentional.
