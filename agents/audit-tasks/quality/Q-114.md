# Q-114 — UptimeBar.buildDaySegments is O(days × transitions) — inner loop does not advance a cursor
**Medium** · effort **S** · _complexity_ · pillar **quality**
**Location:** `src/components/status/uptime-bar.tsx:L33-L80`
**Found by slice:** `sc-status`
## Problem
The outer loop iterates over each day segment (default 30 days) and the inner loop at L71-L74 scans every transition for every day: for (const t of sorted) { if (t.at < dayEnd) runningStatus = t.to }. Because there is no early break or cursor advancement, a data set with N transitions and D days costs O(D×N) comparisons. With 30 days and 100 transitions this is 3,000 comparisons — harmless today. But the logic also has a subtle correctness bug: a transition that falls before the day being examined will set runningStatus even on later days where the cursor has already advanced, meaning all days after the last transition in the window are correctly coloured, but a transition on day 20 still iterates all 30 days. The more serious issue is the missing `break` — transitions are sorted but the loop never exits early, so the last transition before dayEnd always wins regardless of whether it falls inside this day's window. This is only correct by coincidence because the outer loop progresses forward.
## Proposed remediation
Replace with a single-pass O(D + N) approach: walk the sorted transition list while advancing a day pointer. Alternatively, add a cursor index that starts from 0 each outer iteration but breaks once t.at >= dayEnd, making the intent explicit.
