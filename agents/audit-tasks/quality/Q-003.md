# Q-003 — Slipstream pools hardcode volume24hUsd=0, triggering silent large-pool filter exclusion
**High** · effort **S** · _dead-code_ · pillar **quality** · ✔︎ verifier-confirmed
**Location:** `worker/src/cron/dex-liquidity/fetch-slipstream.ts:L278; worker/src/cron/dex-liquidity/scoring-helpers.ts:L158; worker/src/lib/dex-api-pool-shaping.ts:L48`
**Found by slice:** `wc-dex-2`

**Verifier note:** All three cited locations are confirmed by the code:

1. `/worker/src/cron/dex-liquidity/fetch-slipstream.ts:L278` — `volume24hUsd: 0` is hardcoded for every Slipstream pool, and there is no `tokenVolumes24h` field set either.

2. `/worker/src/lib/dex-api-pool-shaping.ts:L48` — `isPreferredDirectApiPool` requires `pool.volume24hUsd > 0`, which Slipstream pools can never satisfy. This is used in `orchestrator.ts:L57` to build the known-pool index that suppresses duplicate DL rows (`filterPrimaryPoolsPreferDirectApi`). Slipstream pools are excluded from that index and cannot suppress DL duplicates.

3. `/worker/src/cron/dex-liquidity/scoring-helpers.ts:L158` — `filterRetainedPools` drops any pool where `tvlUsd > 100_000_000 && vol < 50_000`. With `volumeUsd1d = 0` (mapped from `volume24hUsd` in `pool-contribution.ts:L90`), every Slipstream pool above $100M TVL is silently removed. There is no guard on `pool.extra?.measurement?.volumeMeasured`.

The `measurement.volumeMeasured` flag is correctly set to `false` in `convertToGtNewPools` (`dex-api-pool-shaping.ts:L345`): `volumeMeasured: pool.tokenVolumes24h != null || (Number.isFinite(pool.volume24hUsd) && pool.volume24hUsd > 0)` — but `filterRetainedPools` never reads this flag, so the guard exists in metadata but is ignored at the filter decision point.

`derivePoolVolume24hUsd` (`dex-api-token-pricing.ts:L99-143`) offers no rescue: it falls back to `pool.volume24hUsd` when `tokenVolumes24h` is absent, returning 0 for all Slipstream pools.

Aerodrome and Velodrome regularly host stablecoin pools above $100M TVL, making silent removal from the retained set a real, recurring TVL under-reporting issue. Severity High is warranted.
## Problem
`fetchSlipstreamPools` sets `volume24hUsd: 0` for all pools because the Aerodrome/Velodrome Sugar v2 contract exposes no volume data. This has two downstream consequences: (1) `isPreferredDirectApiPool` (dex-api-pool-shaping.ts:L48) requires `volume24hUsd > 0`, so Slipstream pools are never treated as preferred and cannot suppress duplicate DL rows. (2) `filterRetainedPools` (scoring-helpers.ts:L158) drops any pool with `tvlUsd > 100M && vol24h < 50K`. A large Slipstream pool that is not also covered by DL yields (e.g., newly launched or low-yield pool) will be silently removed from the retained pool set, causing the stablecoin's TVL to be under-reported.
## Proposed remediation
Add a `volumeMeasured` guard to `filterRetainedPools`: skip the large-pool volume filter when `pool.extra?.measurement?.volumeMeasured === false`. Also consider setting `isPreferredDirectApiPool` to accept zero-volume pools from trusted direct sources by checking `pool.source` in addition to volume. Document the Sugar v2 API limitation with a code comment at the zero-volume assignment.
