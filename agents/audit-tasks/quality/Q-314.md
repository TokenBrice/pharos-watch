# Q-314 — Pages site-data origin gate accepts any *.pages.dev preview subdomain via isPagesAppHostname
**Low** · effort **S** · _security_ · pillar **quality**
**Location:** `functions/lib/site-data-origin.ts:6-22; shared/lib/site-data-lane.ts:94-99; shared/lib/runtime-origins.ts:67-69`
**Found by slice:** `spec-security`
## Problem
rejectIfNotSiteDataUiOrigin() allows the request when the Origin/Referer hostname satisfies isSiteDataAllowedUiHostname(), which returns true for any hostname ending in '.<PAGES_APP_HOSTNAME>' (e.g. any *.pages.dev preview deployment under the project). The site-data lane is read-only GET, allow-listed to public API paths, and the upstream shared secret is held server-side, so the blast radius is limited to letting an arbitrary preview-subdomain page read already-public data through the cache layer. Opinion: acceptable for the threat model, but the suffix match is broader than the canonical site/ops origins and is worth a conscious note since it is the one place an externally-influenceable hostname suffix gates access.
## Proposed remediation
Confirm the *.pages.dev wildcard is intended for preview deployments; if only first-party previews matter, consider tightening to the specific project's preview pattern or documenting the accepted breadth inline next to isPagesAppHostname.
