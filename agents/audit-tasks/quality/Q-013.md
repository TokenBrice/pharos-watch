# Q-013 — resupply-pairs serialises all pair I/O in a sequential loop, multiplying latency with pair count
**Medium** · effort **S** · _complexity_ · pillar **quality** · ✔︎ verifier-adjusted
**Location:** `worker/src/cron/reserve-adapters/resupply-pairs.ts:L324-L366`
**Found by slice:** `wc-reserve-adapters-1`

**Verifier note:** The sequential loop at L324-L366 is confirmed: each pair runs 3 parallelized calls (L327-L337), then 2 sequentially-chained calls (L340 fetches collateralAddress; L342 depends on it). The latency-multiplication claim is real — N pairs × ~3 RTTs minimum runs strictly sequentially. However, severity should be Medium, not High, for two reasons: (1) The CLAUDE.md hard rule states "Worker cron jobs share Cloudflare's per-trigger 6-connection pool; consume response bodies before opening more fetches." Fanning out all pairs with a naive `Promise.all` as the finding proposes would saturate this pool with 5N concurrent connections, potentially causing timeouts worse than the sequential approach. The remediation as stated is therefore incorrect without batching (e.g., p-limit or chunked Promise.all). (2) Within each pair there is a genuine data dependency (L340→L341→L342) that cannot be parallelized regardless of pair-level fan-out, so the wall-time reduction from parallelization is partial. The issue is real and worth fixing with a batched fan-out (e.g., process pairs in groups of 1-2 to respect the 6-connection budget), but the naive fix proposed could introduce new failures, and the actual impact depends on how many pairs are configured — not a High-severity production hazard.
## Problem
The `for (const pair of params.pairs)` loop at L324 awaits three or four RPC calls per pair before starting the next pair. With N pairs and a 12-second timeout per call, the worst-case wall time grows as O(N). Pairs are independent; the redemption handler guard (L302-L320) is already fetched before the loop, so per-pair calls can be fanned out in parallel with `Promise.all`.
## Proposed remediation
Replace the sequential loop with `await Promise.all(params.pairs.map(async (pair) => { ... }))`. The `throwIfAborted(signal)` call inside the loop should be preserved by calling it at the start of each async closure instead.
