# Q-313 — Site-data cache existence check via cached!==null doesn't distinguish negative cache or error responses
**Low** · effort **S** · _error-handling_ · pillar **quality**
**Location:** `functions/_site-data/[[path]].ts:159-166`
**Found by slice:** `fn-proxy-auth`
## Problem
beforeFetch serves any cached entry whose presence is truthy. canCacheResponse (lines 65-74) only stores response.ok bodies and skips Set-Cookie/no-store/110-warning, which is reasonable, but the cache-hit path records 'pages-cache-hit' telemetry and returns the stored Response without re-validating it is still semantically fresh against its own Cache-Control max-age. Because Cloudflare's caches.default honors stored Cache-Control for expiry this is usually fine, but the handler also strips no-store via canCacheResponse only at WRITE time — a response that became cacheable then later should have been treated as no-store cannot be invalidated except by TTL. Minor: the conditional-request bypass (hasConditionalRequestHeaders) is correct, but there is no max-stale guard for the served hit.
## Proposed remediation
If staleness matters for site-data, add an explicit freshness check on the cached entry's Date/Cache-Control before serving, or rely documented-explicitly on caches.default expiry semantics. Low priority; likely acceptable by design — confirm intent.
