# R-001 — Two divergent functions named classifyLiquidityEvidence classify the same public field differently
**High** · effort **M** · _naming_ · pillar **redundancy** · ✔︎ verifier-confirmed
**Location:** `worker/src/api/dex-liquidity-history.ts:15-51 + worker/src/api/dex-liquidity-response.ts:205-234`
**Found by slice:** `wa-core-2`

**Verifier note:** Both functions exist exactly as claimed. `dex-liquidity-history.ts` lines 15–51 defines a private `classifyLiquidityEvidence(totalTvlUsd, coverageClass, coverageConfidence)` that emits `"measured"` when `coverageClass === "primary" && coverageConfidence >= 0.75`. `dex-liquidity-response.ts` lines 205–234 exports a different `classifyLiquidityEvidence(totalTvlUsd, balanceMeasuredTvlUsd)` that emits `"measured"` when `balanceMeasuredTvlUsd >= totalTvlUsd * 0.8`. The exported version is imported and called by `dex-liquidity.ts` (line 14, 110). No shared canonical classifier exists in `shared/` or elsewhere. The two functions use completely disjoint inputs and thresholds to produce the same public `liquidityEvidenceClass` union field, so a coin can legitimately return `"measured"` from `/dex-liquidity` and `"observed_unmeasured"` from `/dex-liquidity-history` for the identical underlying snapshot. The identical name across two separate files actively conceals this divergence from readers. Severity High is warranted: this is a silent public API contract inconsistency that affects any client (frontend, grader, external consumer) that treats `liquidityEvidenceClass` as a stable signal across endpoints.
## Problem
The history endpoint (/dex-liquidity-history) and the live endpoint (/dex-liquidity, via dex-liquidity-response) each define a function called classifyLiquidityEvidence that emits the SAME public union field liquidityEvidenceClass ('unobserved'|'measured'|'partial_measured'|'observed_unmeasured'), but with different inputs and different rules. The history version derives 'measured' from coverageClass==='primary' AND coverageConfidence>=0.75; the live version derives 'measured' from balanceMeasuredTvlUsd >= totalTvlUsd*0.8 (and 'partial_measured' otherwise). A coin can therefore be classified 'measured' on the live card but 'partial_measured'/'observed_unmeasured' on its own trend history (and vice versa) for the same snapshot, with no shared source of truth. The identical name actively hides the divergence from readers/graders and makes the two impossible to keep in sync.
## Proposed remediation
Extract a single canonical liquidity-evidence classifier into a shared helper (e.g. shared/lib or a worker lib module) keyed off one agreed input set, and have both endpoints call it; or, if the two truly must differ, rename them to encode the basis (classifyLiquidityEvidenceByCoverage vs classifyLiquidityEvidenceByBalance) and document why the same public field is computed two ways.
