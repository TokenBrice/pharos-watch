# PharosVille Implementation Plan

Created: 2026-04-28

## Decision

Replace the current `/lighthouse/` experience with PharosVille.

The public URL remains `/lighthouse/` for now, because that route already exists in metadata, sitemap generation, docs, smoke UI, and public LLM exports. The product name inside the page can be "PharosVille" while the route remains the existing Lighthouse slot.

Mobile, narrow, and short layouts are out of scope for MVP. Screens narrower than `1280px` or shorter than `760px` should render a polished desktop-only notice with links to existing analytical pages and no canvas runtime, no world data queries, no asset manifest fetch, and no sprite decode.

This document supersedes earlier research-pack assumptions that proposed a new `/pharosville/` route or mobile/tablet canvas. Supporting notes should be read through this replacement plan.

## V0.1 Definition

V0.1 is the first beta-quality `/lighthouse/` PharosVille release:

- desktop gate
- pure world model
- semantic visual cue registry
- Canvas 2D renderer with code fallbacks for unloaded sprites
- basic camera navigation and hit-target collection
- clustering
- DOM ledger, map key, keyboard entity browser, and detail panel
- route-mocked visual tests
- reduced-motion deterministic render
- performance budget assertions

Full 45-60 PNG asset coverage, richer minimap polish, semantic motion, mint/burn cargo flows, DEX channel effects, and yield gardens are v0.1.x/v0.2 unless the v0.1 baseline is already stable. The first committed sprite batch may be smaller than the 28-34 core target if it proves the manifest, validator, critical/deferred loading, and in-world scaling contract.

## Success Criteria

- `/lighthouse/` renders PharosVille on screens `>= 1280px` wide and `>= 760px` tall.
- Screens `< 1280px` wide or `< 760px` tall render a desktop-only fallback and do not initialize heavy canvas/sprite systems.
- Screens below the desktop gate do not mount the query-backed world component.
- The world is an old-school RPG island city with at least `68%` and at most `74%` water by map-tile count.
- Ships are built from active stablecoins only.
- Frozen/dead stablecoins appear only in the cemetery model.
- Chain docks are sized from chain stablecoin supply.
- PSI controls the central lighthouse.
- Peg/depeg/DEWS state controls ship risk placement.
- Recent changes are represented through wakes/cargo markers from existing supply and chain deltas.
- Every selectable canvas entity has an equivalent DOM detail path.
- The map key explains every visual metaphor inside the page.
- Production never renders fixture/default market data as if it were live.
- Visual tests use mocked data and cover the full map, not an empty unauthenticated static-export scene.
- No Worker endpoint is required for MVP.
- No Pixellab key or generated temporary URL is exposed client-side.

## Non-Goals

- No mobile/tablet world renderer in MVP.
- No new `/pharosville/` route in MVP.
- No WebGL/Pixi/Phaser.
- No per-coin history fetches for the world.
- No fully generated map image as runtime.
- No first-pass per-chain or per-stablecoin bespoke art.
- No market exchange, mint house, DEX channel, cargo-flow, or yield-garden data effects unless the matching optional dataset is loaded.
- No primary nav promotion until the beta gate passes.

Inputs:

```ts
interface PharosVilleInputs {
  stablecoins: StablecoinListResponse | null | undefined;
  chains: ChainsResponse | null | undefined;
  stability: StabilityIndexResponse | null | undefined;
  pegSummary: PegSummaryResponse | null | undefined;
  stress: StressSignalsAllResponse | null | undefined;
  reportCards: ReportCardsResponse | null | undefined;
  cemeteryEntries?: readonly CemeteryEntry[];
  freshness: PharosVilleFreshness; // per source, not one global freshness flag
}
```

Output:

```ts
interface PharosVilleWorld {
  generatedAt: number;
  routeMode: "world" | "desktop-only" | "loading" | "error";
  freshness: PharosVilleFreshness;
  map: PharosVilleMap;
  lighthouse: LighthouseNode;
  docks: DockNode[];
  ships: ShipNode[];
  shipClusters: ShipClusterNode[];
  graves: GraveNode[];
  effects: WorldEffect[];
  detailIndex: Record<string, DetailModel>;
  legends: LegendItem[];
}
```

Required data rules:

- Active ships:
  - `ACTIVE_IDS.has(asset.id)`
  - `ACTIVE_META_BY_ID.get(asset.id)` exists
  - `asset.frozen !== true`
- Graveyard:
  - use `CEMETERY_ENTRIES` from `@shared/lib/cemetery-merged`
  - do not duplicate frozen assets as ships
- Market cap:
  - use `getCirculatingRaw(asset)`
  - never multiply list endpoint supply by price
- Chain supply:
  - use `canonicalizeChainCirculating()` or `findCanonicalChainData()`
  - never use raw chain keys directly
- Lookups:
  - use `buildPegSummaryCoinMap()`
  - build report-card map once
  - build stress map from `stress.signals`
- Top chain docks:
  - use `/api/chains` for dock size, health, and summaries
  - use `/api/stablecoins.chainCirculating` for full ship berth assignment
  - use `chains.topStablecoins` only for summary decoration/default labels
- Chain dominance:
  - dock footprint uses `chain.totalUsd`
  - crowded berth / dominant-ship cues use `dominantStablecoin.share` or `healthFactors.concentration`
  - do not treat `ChainSummary.dominanceShare` as within-chain concentration
- PSI:
  - null/unavailable PSI renders the lighthouse as unlit/fogged, never default-safe
  - lighthouse detail includes score, band, methodology version, computed timestamp, input degradation, and missing contributors
- Semantic ownership:
  - lighthouse = PSI composite
  - ship distance/risk zone = peg/depeg first, with DEWS escalation
  - weather/sea state = aggregate DEWS breadth
  - detail panels explain overlap instead of implying independent signals when the same evidence contributes to multiple cues

Visual cue registry:

- Implement `buildVisualCueRegistry(world): VisualCue[]`.
- Each cue must define:
  - `id`
  - `visual`
  - `sourceField`
  - `questionAnswered`
  - `failureState`
  - `domEquivalent`
- No generated asset or map prop should carry analytical meaning unless it appears in this registry.

Ship visual resolver:

- Implement `resolveShipVisual(asset, meta, reportCard): ShipVisual`.
- Use non-overlapping channels:
  - hull silhouette = backing/collateral model
  - rigging/material = governance/issuer model
  - pennant tint = peg currency
  - overlay/ring = yield/NAV/report-card state
  - scale = market cap bucket
- Add tests for overlapping stablecoin attributes so one trait does not override another accidentally.

Risk placement:

- Implement `resolveShipRiskPlacement(input): ShipRiskPlacement`.
- Precedence:
  1. inactive/frozen: excluded from ships
  2. `pegCoin.activeDepeg`: `storm-shelf`
  3. NAV token with missing peg summary: `ledger-mooring`
  4. fresh absolute deviation bps:
     - `>= 500`: `storm-shelf`
     - `>= 200`: `outer-rough-water`
     - `>= 50`: `harbor-mouth-watch`
  5. fresh DEWS:
     - `DANGER`: `storm-shelf`
     - `WARNING`: `outer-rough-water`
     - `ALERT`: `harbor-mouth-watch`
     - `WATCH`: `breakwater-edge`
  6. missing peg/price/low confidence: `data-fog`
  7. stale evidence with no fresh peg/DEWS signal: `data-fog`
  8. default: `safe-harbor`

Freshness policy:

- Do not use one stale endpoint flag to fog every ship.
- Evaluate freshness per evidence source: peg summary, price confidence, DEWS/stress, report cards, chain data, PSI.
- Fresh active depeg, deviation, or DEWS danger may still place a ship in a risk zone when another endpoint is stale.
- Stale secondary evidence appears as badges/fog overlays and detail-panel explanations.

Recent change:

- Use `getPrevDayRawOrNull`, `getPrevWeekRawOrNull`, and `getPrevMonthRawOrNull`.
- Derive `change24hUsd`, `change7dUsd`, `change30dUsd`, and percentage where previous value exists.
- Cap visible recent-change effects to:
  - selected ship
  - top 8 absolute 24h movers above a minimum-dollar threshold
  - top 8 percentage 24h movers above a minimum-dollar threshold
  - top 8 chain dock movers
- Encode direction with stable static cues as well as wakes/glints so reduced-motion remains informative.
- Keep 7d/30d values in details; do not overload the map with three simultaneous change windows.

Map layout:

- Fixed authored map, recommended `64 x 64` tiles.
- Required water ratio: `0.68 <= waterTiles / totalTiles <= 0.74`.
- Required regions:
  - central lighthouse island
  - main island/city
  - dock ring
  - breakwater
  - outer storm shelf
  - cemetery district/islet
  - market exchange as a navigation-only civic landmark in v0.1
  - mint house as a navigation-only civic landmark in v0.1
  - archive/ledger hall

MVP districts that are not backed by loaded route data must be dimmed or purely navigational. Do not show cranes, cargo flow, channel depth, yield gardens, or DEX liquidity signals without loading the matching optional dataset.

Renderer requirements:

- Canvas 2D only.
- `imageSmoothingEnabled = false`.
- Effective DPR budget, not plain DPR cap.
- Main canvas and offscreen caches share a total backing-store budget.
- Static terrain renders into a cache canvas.
- Dynamic layers draw only visible entities.
- Minimal camera support lives in this phase: viewport bounds, resize handling, projection, pan/zoom state, deterministic `fitToMap` mode for visual tests.
- Draw order:
  1. background wash
  2. water/deep water
  3. terrain/shore/roads
  4. docks/buildings
  5. cemetery
  6. ships/clusters
  7. lighthouse/beam
  8. weather/effects
  9. selection/highlight overlay
- Pause RAF on:
  - component unmount
  - page hidden
  - route/client gate below 1280px
  - reduced-motion static mode when nothing is animating
- Release offscreen cache backing stores on teardown.
- Use `ResizeObserver` to recompute CSS size and effective DPR.
- Handle `visibilitychange`, `matchMedia('(min-width: 1280px)')`, `contextlost`, and `contextrestored`.
- On teardown, cancel RAF, detach listeners, clear decoded callbacks, and zero offscreen canvas widths/heights to release backing stores.

- Default zoom: max 80 individual ships, 40 graves, 24 labels, 120 hit-test candidates.
- Medium zoom: max 140 viewport-local ships, 70 graves, 36 labels, 200 hit-test candidates.

- Culling uses viewport tile bounds plus sprite bounding boxes and anchor margins.

Render scheduling:

- Implement `requestRender(reason)` and `needsContinuousFrame(world, motionPolicy)`.

- Hover hit testing is RAF-throttled and only notifies React when hovered id changes.

- Do not spend implementation time on mobile canvas layout.

## Phase 4 — Data Fetching And Live Data Binding

Goal: connect route queries to the world model without weakening the desktop gate or rendering fake production analytics.

`client.tsx` should first render the viewport gate. Only the desktop branch should mount a query-backed component that fetches required MVP data:

- `useStablecoins()`
- `useChains()`
- `useStabilityIndexDetail()`
- `usePegSummary()`
- `useStressSignals()`
- `useReportCards()`

Do not fetch at route load:

- `useDexLiquidity()`
- `useMintBurnFlows()`
- `useYieldRankings()`
- `useInfiniteDepegEvents()`

These are optional later layers or selected-entity detail fetches.

Components:

- `query-status-banner.tsx`
  - shows stale/degraded/error state
  - never substitutes fixture/default market data in production
  - can keep the authored map visible only when live market entities are clearly loading, absent, or errored
- `accessibility-ledger.tsx`
  - visible or collapsible DOM ledger, not sr-only only
  - includes PSI, dock summary, ship cluster counts, cemetery summary, freshness
- `detail-panel.tsx`
  - exact values for selected lighthouse/dock/ship/cluster/grave
  - includes "why this appears here" placement explanation, source fields, timestamps, confidence, and methodology version where available
  - links to `/stablecoin/<id>/`, `/chains/<chain>/`, `/cemetery/`, `/stability-index/`, `/depeg/`
- `keyboard-entity-browser.tsx`
  - searchable/filterable list of selectable entities
  - supports lighthouse, docks, visible clusters, selectable ships, graves, and long-tail search
- `map-key.tsx`
  - persistent or collapsible legend sourced from `world.legends` and the visual cue registry
- `world-toolbar.tsx`
  - filters: risk placement, chain/dock, type, top assets/clusters
  - controls: zoom in/out/reset, follow selected, clear selection

Accessibility:

- Canvas can be `aria-hidden="true"` only because all entities are reachable in DOM.
- Entity list must allow keyboard selection.
- Pointer selection keeps focus on the pointer/toolbar context and announces the selected entity with `aria-live`.
- Keyboard entity selection moves focus to the detail panel heading.
- Escape clears selection and returns focus to the originating control/entity row.
- If a data refresh or filter removes the selected entity, clear selection, announce the reason, and return focus to the nearest stable control.
- Toolbar and detail controls have at least 44px targets, even though narrow screens are gated.
- Canvas entity hit targets use at least 24px pointer hit slop where the visual sprite is smaller.
- Toolbar controls use visible labels or accessible tooltips, grouped labels, `aria-pressed` where applicable, and disabled states for unavailable actions.
- Camera has keyboard equivalents: arrow-key or button panning, zoom buttons, reset, follow selected, and clear selection.

Anchor semantics:

- `anchor` is the source-pixel contact point before `displayScale`.
- Renderer draws at `screen - anchor * displayScale`.
- Hit testing and sort bounds use the same scaled anchor.
- Add an anchor/debug contact sheet gate before updating visual baselines.

Tile contract:

- Use isometric slots compatible with `TILE_WIDTH = 64` and `TILE_HEIGHT = 32`.
- Prefer `128 x 128` 4x4 Wang sheets with `32px` cells for water, shore, road/cobble, and transition terrain.
- Do not generate many one-off `48 x 48` terrain tiles for v0.1.
