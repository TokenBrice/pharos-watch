# Legacy Stablecoin ID Cleanup Implementation Plan

Date: 2026-04-22
Status: Reviewed v3
Owner: Codex

## Objective

Retire the remaining app-facing legacy stablecoin ID system while preserving `llamaId` as the active DefiLlama provider key.

This plan intentionally removes:

- legacy stablecoin detail-route redirects
- legacy route/token decoding in frontend compare, stress, and portfolio flows
- legacy portfolio/localStorage/share-link ID migration
- defunct-only numeric-ID emissions that still behave like Pharos IDs
- the remaining historical repair-script aliases for old stablecoin IDs

This plan intentionally keeps:

- `llamaId` in tracked/shadow metadata
- `REGISTRY_BY_LLAMA_ID`
- DefiLlama intake remapping
- DefiLlama detail/history fetches by `llamaId`
- discovery/admin telemetry that stores provider-side `llamaId`
- cemetery dataset `llamaId` field as external provider metadata

## Assumptions

- Breaking old detail URLs, old compare/stress query params, and old portfolio/localStorage payloads is acceptable.
- No compatibility grace period is required for portfolio data.
- We do not want a partial rollback path or fallback alias layer in the app after this cleanup.
- Introducing a stable shared cemetery ID for dead assets is acceptable if that is the cleanest way to remove numeric legacy IDs from defunct outputs.

## Success Criteria

1. No runtime path in the app accepts numeric, `cg-*`, commodity-prefix, or legacy-symbol stablecoin IDs as Pharos IDs.
2. Stablecoin detail pages are reachable only by canonical `ticker-issuer` URLs.
3. Compare, stress, and portfolio flows accept canonical IDs only, and compare/stress/portfolio scrub stale non-canonical params instead of leaving them in the address bar.
4. Portfolio storage/share parsing drops non-canonical IDs instead of migrating them.
5. Defunct report-card IDs, telegram cemetery snapshot keys, and cemetery dataset IDs all use the same stable dead-coin identifier rather than numeric DefiLlama IDs.
6. The legacy repair aliases (`cg-idrt` and `300`) are removed from the repair script after zero-row confirmation or one-time cleanup.
7. Docs and build/deploy pipeline references are updated so no verified doc describes removed compatibility behavior.
8. Validation passes, and a final grep shows no app-facing legacy ID acceptance/emission paths remain.

## Non-Goals

- Do not remove `llamaId` from stablecoin metadata.
- Do not redesign DefiLlama-backed cache admission or detail fetches.
- Do not change the stablecoin cemetery dataset's `llamaId` export.
- Do not touch canonical worker/API ID resolution beyond doc updates.
- Do not refactor unrelated URL helpers, routing, or dead-stablecoin infrastructure.

## Implementation Order

The plan is sequenced to remove public compatibility first, then consumer-side decoding, then portfolio migration, then defunct/historical holdouts, then docs/validation.

### 5A. Introduce shared stable cemetery IDs

Current behavior:

- dead stablecoins have no explicit stable source `id`
- `scripts/generate-cemetery-dataset.ts` derives a public cemetery ID from `symbol`, `name`, and `deathDate`
- defunct report cards use `dead.llamaId` when present, else `dead-${symbol.toLowerCase()}`

Problem:

- numeric IDs still leak into `/api/report-cards` output for cemetery coins
- report cards and cemetery dataset currently use different dead-coin ID namespaces
- telegram cemetery fallback keys are mutable editorial strings rather than stable IDs

Planned change:

- add a required `id` field to the dead-stablecoin source model:
  - `shared/types/market.ts`
  - `shared/lib/stablecoins/schema.ts` `DeadStablecoinAssetSchema`
  - every row in `shared/data/dead-stablecoins.json`
- populate `dead.id` once with the existing cemetery dataset namespace so we reuse one public dead-coin ID:
  - `${slug(symbol)}-${slug(name)}-${deathDate}`
- after the one-time population pass, treat `dead.id` as curated source-of-truth rather than as a field re-derived from mutable editorial metadata
- update `scripts/generate-cemetery-dataset.ts` to trust `coin.id` instead of re-deriving the field inline
- update `worker/src/lib/report-cards-snapshot-finalize.ts` so defunct `ReportCard.id` uses `dead.id`
- add dead-ID uniqueness/shape validation in the source-data path:
  - schema validates `id` presence/shape
  - dataset export path fails on duplicate `dead.id` values
- update cemetery UI identity consumers to use `coin.id` instead of `coin.symbol` wherever uniqueness matters:
  - React keys
  - expansion/highlight state
  - DOM anchor ids
  - any client-side counters/maps keyed by dead-coin identity
- update `src/components/report-card-mini.tsx` so defunct cards do not blindly build `/stablecoin/${card.id}` links
  - preferred behavior: render non-link cards for `card.isDefunct`
- add explicit frontend regression coverage:
  - `src/components/__tests__/cemetery-client.test.tsx` proves duplicate-symbol dead rows do not collide in expansion/highlight behavior once UI state keys switch to `coin.id`
  - `src/components/__tests__/report-card-mini.test.tsx` proves defunct cards no longer render stablecoin-detail links while live cards still do

Reasoning:

- stable
- human-inspectable
- collision-resistant across duplicate symbols and repeated names
- shared across `/api/report-cards` and the public cemetery dataset
- no dependence on numeric legacy IDs

Required doc and contract follow-up:

- update `docs/api-reference.md` so the `ReportCard.id` contract distinguishes:
  - live cards: canonical Pharos stablecoin ID
  - defunct cards: stable cemetery ID from `shared/data/dead-stablecoins.json`
- perform a focused consumer audit for downstream code that assumes `ReportCard.id` is always a live routable coin ID
  - include at minimum `worker/src/lib/report-card-cache.ts`, `worker/src/api/cache-handlers.ts`, `src/app/safety-scores/view-model.ts`, `src/lib/contagion-layout.ts`, and `src/components/report-card-mini.tsx`
- add an explicit contract test in `worker/src/api/__tests__/report-cards.test.ts` that verifies defunct IDs are non-numeric and unique
- update `docs/cemetery-and-compare.md` so cemetery identity now includes stable `id` rather than optional `llamaId` preference

### 5B. Telegram cemetery snapshot keys

Current behavior:

- `buildDeadStablecoinKey()` prefers `llama:${coin.llamaId}`

Planned change:

- switch the steady-state cemetery snapshot key to the new shared `dead.id`
- add a one-release compatibility migration in `worker/src/lib/telegram-digest-appendices.ts`:
  - when checking whether a cemetery row is already known, treat these as equivalent:
    - new `dead.id`
    - old `llama:${coin.llamaId}` when present
    - old fallback `SYMBOL|deathDate|name`
  - after a successful digest post, rewrite the stored `telegram:cemetery-snapshot` payload to `dead.id` values only

Reasoning:

- avoids false “new cemetery entry” announcements on the first post-cutover digest
- gives cemetery diffs one stable identity source that is shared with the public dataset and report-card output
- removes numeric-ID dependence without making long-term diff identity depend on mutable editorial fields

Test impact:

- expand `worker/src/lib/__tests__/telegram-digest-appendices.test.ts` with a case that:
  - seeds `telegram:cemetery-snapshot` with an old `llama:*` key
  - seeds `telegram:cemetery-snapshot` with the old fallback `SYMBOL|deathDate|name` key for a no-`llamaId` row
  - confirms no false cemetery diff is emitted after the code switches to `dead.id`
  - confirms the committed snapshot rewrites to the new `dead.id` values

Required doc update:

- update `docs/telegram-alerts.md` so cemetery snapshot identity no longer claims `llamaId` preference

## Recommended Commit Slices

To keep reviewable changes surgical:

1. `cleanup: retire stablecoin legacy redirects and prebuild generator`
2. `cleanup: make stablecoin URL decoding canonical-only`
3. `cleanup: drop portfolio legacy ID migration`
4. `cleanup: remove defunct legacy ID emissions and historical repair aliases`
5. `docs: remove legacy stablecoin ID compatibility references`

If conflicts are low and the user prefers one patch, these can still land together; the slice list is for reviewability, not a hard requirement.

## Review Plan

The plan itself should be reviewed before implementation by three parallel `gpt-5.4` xhigh reviewer subagents:

1. Routing/compatibility reviewer
   - focus: redirect removal, frontend canonical-only decode semantics, compare/stress fallout
2. Validation/docs reviewer
   - focus: tests, docs, build pipeline, deleted-file fallout, verification completeness
3. Historical/output reviewer
   - focus: defunct report-card IDs, telegram cemetery keys, repair-script alias retirement

Review acceptance target:

- zero blocker or major plan issues
- fewer than `2` unresolved minor issues in the final plan revision

## Exit Conditions

This plan is ready to execute when:

- the review loop has finished
- blocker/major issues are resolved
- unresolved minor issues are fewer than `2`
